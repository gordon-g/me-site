3. ilodezis/vitals: 103 MCP tools across 15 health domains — Garmin, Hevy, GLP-1, lab reports and VCF genetic files land in one self-hosted health data lake, with a "doctor report" you can freeze

URL: https://github.com/ilodezis/vitals ｜ ★12 ｜ PolyForm Noncommercial 1.0.0 (README badge; GitHub API field reports NOASSERTION) ｜ Python 3.14 / FastAPI / PostgreSQL 18 / Redis 7 / React 19 PWA ｜ A single-user, self-hosted personal health data lake and dashboard exposing read and write access to Claude.ai over MCP

What happened

Only 2 commits fall inside today's window (17:45 and 19:29 Beijing time on 11-01), but the architectural density here is worth walking through item by item: this is the most complete open-source implementation of the "personal health data → MCP → AI" chain I have seen.

  • 103 MCP tools (46 read + 55 write) spanning 15 domains: weight and body composition, InBody BIA, HRT/TRT, GLP-1, Garmin activity/sleep/recovery, Hevy strength training, nutrition and calories, supplements, skincare, labs, genetics, custom charts, timeline, goals and milestones, and Signals/Telegram proactive notifications. Tools are filtered dynamically by enabled module — switch a domain off and its tools disappear from tools/list.
  • Lab reports go through LLM OCR: upload a PDF or a photo of a lab report, parse biomarkers with gemini-2.5-flash, recognize reference ranges and Low/High/Critical status, and keep the original input in raw_payloads — so when the parser is upgraded, historical data can be re-parsed.
  • Genetics supports VCF import (50k rows per import), parsing SNPs and linking them to a susceptibility catalogue — HFE, MTHFR, G6PD, CYP1A2, COMT and others are listed; genetic information feeds the Conflict Engine (116 rules with evidence tiers and sources), where for example haemochromatosis-related rules will block or warn against iron supplementation.
  • The GLP-1 module detects plateaus: it raises a warning when the dose has run past 14 days while the weight trend stays below 100 g per week. The supplement catalogue holds roughly 90 entries with Chinese and English aliases, doses, timing and evidence tiers.
  • The "doctor report" is the most worth-copying design here: after selecting a time range the system freezes the data at that moment and produces an immutable snapshot, returns a password-protected share link, supports configurable expiry, one-click revocation and access counting; snapshots are excluded from database backups; and the report can be downloaded as a self-contained HTML file with no scripts, no external network requests, openable offline and printable. Crucially: "when data changes a new report must be created — the old report the doctor already received cannot be replaced."
  • Irreversible writes uniformly require confirm=True: delete_record, resolve_all_alerts and create_shared_report return a dry-run preview instead of executing when unconfirmed.
  • Today's two commits: migration to PostgreSQL 18; and a dependency security update (glob to v14, minimatch overridden to 11, tagged [security]).

Why it matters

  • Its domain split is almost exactly the domain split of my GLP-1 Nutrition Companion V2. My V2 already covers the morning/evening double-cup design, lab-indicator trend tracking (blood glucose / HbA1c, lipids, liver function, vitamin D, iron / ferritin, uric acid, weight / waist), and the main loop of "improved / unchanged / worsened triggers re-optimization." vitals has a working implementation over the same domains — and its GLP-1 plateau detection (dose duration plus a weight-trend threshold) is the same class of problem as my medication-cycle and drug-stop cascade design.
  • "Keep the raw payload, re-run the parser later" is the single rule I most need to copy for my lab-report-photo OCR → AI → App import path. In my current design, once an OCR result lands in the database it is treated as fact; but as long as the original photo and raw payload are retained, a future parser upgrade can re-process the entire history — which matters enormously for closing the "zero AI hallucination" evidence chain: I can demonstrate that a conclusion was recomputed from the original report rather than improvised by a model at the time.
  • The Conflict Engine's 116 rules with evidence tiers, with genetic data participating in the decisions, are the same problem as my supplement contraindication logic solved differently. My "forbidden supplements" document is currently a hand-maintained list; here it is a rule engine, and haemochromatosis → block iron supplementation uses genetic information directly. Upgrading a contraindication list into a rule set with evidence tiers that can decide automatically is the single most valuable thing for the 4P platform next.
  • "Doctor report = frozen snapshot, immutable, revocable, excluded from backups, self-contained offline HTML" is a capability I simply do not have today. Intervention reports on the 4P supplement platform are still "generated and sent"; there is no freezing and no revocation. Once a user takes a report to a specialist, the report must be traceable, tamper-evident, and able to prove "this was the state as of November 2" — this design is one order of magnitude more rigorous than what I have.
  • ⚠️ Licensing must be resolved first: PolyForm Noncommercial 1.0.0 permits personal use, modification and distribution, but not commercial use. My one-person company intends to sell exactly this kind of capability, so this repository can be read, its architecture studied and its ideas copied, but its code cannot enter a commercial product. Either negotiate a commercial license or treat it strictly as a reference implementation. That call has to be made before any work starts, not discovered at launch.

5. claimseed/claimseed: entirely synthetic U.S. medical-billing PDFs, each shipped with an answer key saying exactly which error was planted — built for OCR extraction agents that cannot explain their own accuracy

URL: https://github.com/claimseed/claimseed ｜ ★0 ｜ Apache-2.0 ｜ Node.js 22.13+ / Chrome-Chromium rendering / MCP server ｜ Fully synthetic U.S. medical-billing specimens (Medicare Summary Notices, hospital itemized bills, Medicare Advantage EOBs), each shipped with ground-truth JSON naming the billing errors embedded in it

What happened

There was 1 commit inside today's window (12:51 Beijing time on 11-01, the merge of the release-0.4.0 branch), alongside two published releases: 0.3.0 (10-29) and 0.1.0 (10-28).

  • Three hard rules for the synthetic data: all names, identifiers, addresses, phone numbers and amounts are seed-generated, and nothing in the repository is or is derived from a real document; every rendered page states that it is a specimen — a band of text in the foot margin, a diagonal watermark drawn as shapes (so it never leaks letters into the text-extraction layer), and PDF metadata, all stamped in by the renderer itself, with no CLI flag, library call or data object able to switch them off.
  • Same seed means reproducible output: two renders on the same Chrome build (Linux, as in CI) are byte-identical; other platforms produce the same content with bytes that may differ by Chrome version.
  • The verify command scores extractors: it compares an extractor's report against the answer key and reports field accuracy (including paths read wrongly or missed), error recall and precision, and false alarms; amounts, dates and text are compared the way the documents actually print them, not as parsed values.
  • The batch command renders a whole test set: PDFs, answer keys, plus a manifest.jsonl carrying the SHA-256 of every file, with verify --manifest scoring the entire set in one go.
  • It is also offered as an MCP server (@claimseed/mcp, stdio): rendered documents come back as page images inside the chat client, so the injected errors can be viewed side by side with the pages in a conversation or in an MCP Apps view; a container image with Chromium included is available, and docker run --network none runs it with networking disabled.

Why it matters

  • It hits precisely the step I currently want but have no method for: building a reproducible evaluation set for my "lab report OCR → AI → App import" pipeline. What I have been missing is not a parser — it is "how do I prove this extraction is more accurate than last time". claimseed hands me the ready-made answer: generate specimens with known answers, provide a command that compares extraction output against the answer key field by field, and keep a manifest with the SHA-256 of every file. Add those three and I can run regression tests on the 4P platform's extraction pipeline: after changing the OCR model or the prompt, one run tells me whether it got better or worse.
  • "False alarm count" is a metric I had never thought to track separately. I care about missing abnormal indicators, but if an extractor flags normal indicators as abnormal, a doctor faced with a wall of false alarms stops trusting the system altogether. Missed positives damage credibility; false positives damage trust — both need to be counted on their own. This lines up with how I already think about "24 risk dimensions and 6 risk levels" in 4P intervention reports, but now with a more precise way to measure it.
  • "Compare the way the document actually prints it, not the parsed value" is an easily missed but critical evaluation convention. Date formats, units, range symbols and reference-range wording on lab reports vary enormously, and comparing normalized values hides real extraction errors. This is a directly usable principle for writing my own evaluation cases.
  • "Draw the watermark as shapes so it does not pollute the text layer" is an elegant fix for the risk that the evaluation set itself teaches the wrong behaviour. The biggest danger of synthetic data is that it does not look like real data, so the model underperforms on the real thing. Using a graphical watermark rather than a textual one keeps the extracted text layer as clean as a real document's while still marking the page for real. Balancing "must look real" against "must be identifiable" with this much care is far more refined than simply stamping the word SYNTHETIC.
  • Apache-2.0: commercially usable. At ★0, with four document types and seventeen scenarios, the project is small — but what it demonstrates is a method, not a product, and I can port that entire method onto my own lab-report evaluation set.

3. Trends today

The most important signal today is that the skill ecosystem is hardening from "writing a pile of prompts" toward "verifiable, governable, deployable" — and that shift is happening simultaneously in three completely unrelated codebases.

First, skills are acquiring their own lint and packaging conventions. Forge's forge skills validate exists to catch "silent tool-registration failures that surface only at runtime," and it ships default-deny tool governance guidance; the dsh plugin installs 27 skills into its sidebar with a six-step initialization flow; claimseed validates extractor output against a ground-truth answer key. All three point to the same conclusion: the quality of a skill is increasingly determined by how much of it a machine has checked, rather than how many times a human has read it. For my expert-package QA checklist this means two columns — semantic criteria for humans, and validation items for machines.

Second, "missing" and "zero" must be treated as different things. The dsh plugin's bugs today (a missing comment total treated as known, insufficient snapshot-ownership checking when list truncation is backfilled, a taken-row count passed off as the total) are all one error wearing different clothes: the system gave a confident answer when the data was incomplete. This is the other end of the same thread I noted on 10-31 with OpenAdapt, where an agent "declared success on all 30 bad saves" — one lies about success at the write end, the other treats absence as zero at the read end. For a system that writes "24 risk dimensions across 6 risk levels" into an intervention report, "we could not fetch this one data point" has to propagate as-is, rather than becoming a 0 or a plausible-looking value.

Third, health-oriented AI is shifting from "recording data" toward "managing conflicts and issuing freezable conclusions." vitals' 116 evidence-tiered conflict rules (with genetic data participating in the decision), its GLP-1 plateau detection, and a doctor report that is "frozen snapshot + revocable + excluded from backups + self-contained offline HTML" all point the same way: the value of a single-user health AI is not the charts, it is whether the system dares to issue a conclusion with a timestamp that cannot be tampered with and that a physician can review. For 4P intervention reports, that is the same engineering requirement.

Fourth, compliance boundaries are being written into code, not just into documentation. The datalife-ehealth clinical-agents research scaffold includes a section listing "explicit non-goals": no autonomous diagnosis, no risk disposition, no prescribing, no ingesting names or tax identifiers, no unrestricted web browsing or shell access, no silent actions in clinical systems. claimseed stamps every page as synthetic with no switch able to turn it off; haola-checkup-mcp binds credentials to the official origin and follows only same-origin redirects. Explicitly enumerating non-goals is becoming basic literacy for AI projects — and for anyone producing health content this matters, because compliance burden is not waived by declaration; it is removed by architectural constraint.

Fifth, licenses must be sorted out at selection time, and this issue's spread is unusually stark. Among the new repositories, MIT (dsh plugin, forge, claimseed, haola) and Apache-2.0 (forge, claimseed, praxovela, gateway) are suitable as foundations; AGPL-3.0 (orbi, papez, marotte, flotta, cupful) can be read but not copied; and PolyForm Noncommercial (vitals) even plants a wall between "personal use" and "commercially sellable." For a one-person company with only eight hours a week, the most expensive mistake is not reading that line before starting work and only discovering at launch that the foundation cannot be used commercially.
