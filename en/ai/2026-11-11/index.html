1. Today's picks (5)

1. Prabh54/groundedmed: A biomedical RAG agent that has to prove it did not make anything up

URL: https://github.com/Prabh54/groundedmed ｜ ★0 ｜ Unstated ｜ Research demo: agentic RAG that gives citation-checked answers to biomedical yes/no/maybe questions, refuses when evidence is weak, and publishes its results from a frozen 200-question PubMedQA test. Not medical advice.

What happened

  • v1.1.0 shipped at 2026-11-11 02:24, barely more than a day after the public v1.0.0, adding a critic-guided rewrite plus a second hash-locked test set; production smoke-test results were published on the README and the /eval page in the same run.
  • The pipeline is a four-stage agentic RAG: planner, retriever, answer writer and critic. Answers come back as yes / no / maybe, and every finding must point at the abstract it came from.
  • Citation checking is done by code, not by the model's own word: the program verifies each citation, and the critic re-checks every finding against the abstract it cites. When the critic flags an answer that should have been refused, the writer gets one guided rewrite and the critic checks it once more.
  • Evaluation runs on hash-locked PubMedQA splits: the decision rules for the second 400-question set were written down before the run, and both the baseline and agent scores are published side by side.

Why it matters

  • This is the ruler my public-account content is missing. On 11-09 I wrote down a to-do for myself: every extraction must carry the source location, and if it cannot, it must not enter the report. GroundedMed is stricter than my sketch — not just "cite the source" but machine verification first, then a critic model that does not know the answer checks each finding against the original text. It is the mirror image of the bpf-benchmark pattern I noted on 11-10: replace "I say I am right" with "an uninvolved third party decides."
  • "Not enough evidence" as product behaviour is copyable. I have always worried that my GRPM intervention reports will let the model fabricate a conclusion when the evidence is thin. GroundedMed writes not enough evidence into product behaviour — that is product design, not prompt tricks.
  • The hash-locked test set is worth copying wholesale. Freezing the decision rules for the second 400-question set before the run is the cure for the classic failure mode of my A/B tests: setting the standard after seeing the results. My next step is to freeze one version of the GRPM SNP-extraction rules the same way.

2. Muratovnik/assay: A gate that forces coding agents to list every file they actually read

URL: https://github.com/Muratovnik/assay ｜ ★1 ｜ MIT ｜ Evidence-grounded methods for coding agents: skills and agent profiles for Claude Code, Codex, Cursor and Gemini CLI

What happened

  • v0.44.0 and v0.44.1 shipped within a single day on 2026-11-10, with v0.44.1 targeting the visibility of skill file checkouts.
  • The core is a set of hooks that binds a read claim to the file it names. The commit messages are explicit: keep a read claim's file list going past a name with no Read; tie a read claim to every file its sentence lists; compare a full-read claim with the file its own clause names.
  • The other half is conditional skill loading: the existing-solutions section is requested from a plan only when the planning skill is loaded, and the skill-evaluation sign applies only to skills in a repository that is not a plugin.
  • Self-described as evidence-grounded methods for coding agents — skills and agent profiles, not a prompt library: executable evidence discipline bolted onto the agent.

Why it matters

  • This hits the biggest hole in my expert-package QC. My current approach is asking the model to grade itself — it claims it read a file and I believe it. Assay instead makes "I read this" carry a complete file list, with every listed name backed by an actual Read, and it goes red if one is missing. This is precisely the executable form of my 11-09 second to-do (every extraction must carry its source location): my version asks the model to write it down; this one makes the machine check it.
  • I am almost certain my own expert packages commit the failure mode "a read claim hanging off a name with no Read." A report says "based on this file's methodology" while the model only ever saw the filename — to a human reviewer the two look identical, but under an assay-style gate the difference surfaces instantly. This belongs on line one of my expert-package checklist.
  • "Only ask the question when the skill is loaded" holds for on-demand retrieval too. In my GRPM pipeline, SNP extraction rules should load only when a nutrition-relevant variant shows up; feeding them unconditionally doubles both token cost and hallucination surface.

3. vxxqv/openomicsbench: A locally runnable answer to "how do you validate omics software?"

URL: https://github.com/vxxqv/openomicsbench ｜ ★2 ｜ Apache-2.0 ｜ Offline RNA, DNA, protein, single-cell and genomic interval benchmarks with a five-assay demo and traceable reports.

What happened

  • v13.0.0 shipped at 2026-11-10 17:30, just two days after v12.0.0 — a tight release cadence.
  • The headline addition in v13 is RNA-seq input packs: packable per study or across all 12 biological objects, and each pack keeps the count matrix, the sample sheet and the declared contrast together, with checksums and a design preflight.
  • Result tables plug natively into DESeq2, edgeR and limma conventions and can be scored or converted directly; the repository also ships reference results, so it explicitly states that this is not a blinded challenge.
  • Offline operation is a hard promise: once installed it needs no network, sequence files stay on the local machine, and the bundled tools cover inspection and light preprocessing only — they do not claim to replace aligners, variant callers or taxonomic classifiers.

Why it matters

  • Checksums, a design preflight, and stating plainly how this differs from a blinded test — together these are exactly what my GRPM report lacks most. The 11-10 path I wrote down (archive data → fix decision rules → reproducible artifacts) is what openomicsbench has already packaged into something pip-installable, and the line "this is not a blinded challenge" is more candid than most papers.
  • It moves "is the method reproducible" from "I say so" down to "here is my published decision surface." Twelve biological objects, seven deterministic sequence and classification fixtures, a 10x-style single-cell benchmark and a peak-calling benchmark are reference materials you can read directly, not a leaderboard where everyone scores against different yardsticks.
  • The most practical use for me is as a counter-example library. In my GRPM pipeline the extraction and interpretation logic differs across each of the 40 nutrition-related SNPs; if the definition of "evidence strength for this recommendation" is redefined whenever the SNP batch changes, then cross-report comparison is theatre. openomicsbench is a standing reminder that decision rules should be version-frozen, not written afresh per report.

4. shubhampawar05/nutrikit: A self-hostable nutrition API with an MCP server — and it fixed a real-world food-matching gap

URL: https://github.com/shubhampawar05/nutrikit ｜ ★0 ｜ Unstated ｜ Self-hostable nutrition API: food search, portion-aware nutrients, meal logging from text, voice, photos, barcodes and labels, meal plans and an AI nutrition advisor. JS SDK on npm (@nutrikit/sdk).

What happened

  • Three commits in the window, the newest being #21 "fix/regional-food-matching", which also adds spelling correction — misspelled food names now produce respelling suggestions.
  • The concrete fix: matching dal makhani to CoFID's black gram and kidney bean curry — a genuine cross-database naming gap rather than a staged demo.
  • The shape is a complete self-hostable stack: nutrition API, website, developer portal, JavaScript SDK and an MCP server, with @nutrikit/sdk on npm and a free-API-key instance on Render.
  • The data surface covers 13,000+ foods with up to 33 nutrients each and understands portion expressions like "2 medium" or "1.5 cups"; there are text, voice and photo logging paths plus barcode scanning.

Why it matters

  • This is the only repository in this issue's health line about database semantics rather than photo-based calorie counting — and the latter accounts for the bulk of GitHub's health line. Photo food-recognition projects are everywhere; aligning a food name to a nutrient-database identifier is a problem only someone actually using the thing in production would hit, and the dal makhani case shows the author has hit that wall.
  • It ships an MCP server, which lines up directly with my GLP-1 nutrition companion and the 4P platform's integration needs. My nutrition data sources are currently scattered; consolidating onto one self-hostable, programmatically callable, versioned source is the direction I want — and self-hosting means a patient's diet data never has to leave the machine.
  • The respelling feature looks minor but is the first line of defence at the data entry point. When a user types a food name with a typo and the system silently fails to match and returns nothing, the user stops logging; offering a corrected candidate is what keeps logging rates intact. My nutrition companion's input layer should copy this interaction instead of returning an empty result.

5. chainloop-dev/chainloop: Turning "what the AI wrote" into an auditable trace

URL: https://github.com/chainloop-dev/chainloop ｜ ★611 ｜ Apache-2.0 ｜ Agentic SDLC infrastructure. Define guardrails. Collect signals. Enforce continuously. Signed records of what your AI coding agents and CI/CD pipelines did, checked against policies as code, with the loop closed in CI/CD. AI sessions, SBOMs

What happened

  • Six commits in the window, with the main line being GitHub Copilot integration: #3801 "feat(trace): GitHub Copilot support (spec, plan, and M1)", #3804 "Copilot skills, spec pointers, and pasted images (M2)", and #3805 enabling Chainloop Trace hooks for Copilot.
  • Pi skill loads were folded into the record in the same period (#3759) — meaning which skill was loaded becomes an auditable event in its own right.
  • Self-described as agentic SDLC infrastructure: define guardrails, collect signals, enforce contracts.
  • Apache-2.0, with v1.134.0 released 2026-11-09 and v1.133.0 on 11-06, plus a fix making the lab compose stack work end to end (#3797).

Why it matters

  • "Which skill was loaded" becoming an auditable event matters more than the trace itself. My third to-do from 11-09 was to add "last verified time" and "does the target still exist" to every rule — but if I never recorded which rule set produced a conclusion, I cannot even begin to judge whether that conclusion has gone stale. chainloop records that step.
  • Running several hosts at once — Copilot, Claude Code, Pi, Codex — is now the norm, so logs from a single host are not enough. I run dsh, WorkBuddy and Ollama side by side locally, and any cross-host compliance requirement needs a host-agnostic recording layer — which is exactly where chainloop sits.
  • The most directly transferable idea for the 4P platform is the notion of a contract. If the input data snapshot, the decision-rule version and the citation list each carry a hash and are strung into one trace, report auditability stops being a wish and becomes one stage of a pipeline. That is the same road as the hash-bound evidence I noted under bpf-benchmark on 11-10, implemented differently.

3. Trends today

  • ⭐⭐⭐ "Did you actually read it" is becoming a question a machine can fail. On 11-10 I noted astryx reporting named scenarios rather than line numbers, and on 11-09 I noted squad aligning spec, docs and matrix with the code plus regression guards. Today assay takes that idea all the way onto the agent itself: tie a read claim to every file its sentence lists — when the model says "I read this file", it must produce a complete list, and every name in that list must have a matching Read. My expert-package QC is still "ask the model to grade itself"; this whole mechanism is copyable.
  • ⭐⭐⭐ "Pinning a conclusion to its source material" now has three different implementations. groundedmed has a critic model check each finding against the original abstract; openomicsbench freezes decision rules together with checksums into an installable package; chainloop makes "which skill was loaded" an auditable event in its own right. Three stacks with nothing in common, all answering the same question — three months from now, how do I know how that report was actually produced? My GRPM to-do from 11-09 only solves half of it: the fields are there, but which rule set and which raw data produced a given conclusion is still untraced.
  • ⭐⭐ The dividing line in the health line: database semantics versus photo calorie counting. Most of this issue's 28 health entries are still "photograph the meal, count the calories", while nutrikit works on aligning food names to nutrient-database identifiers — the dal makhani to black gram fix is a wall only someone running this in production would hit. The point is that the hard part of nutrition AI is not recognition, it is alignment. What stalls me in supplement formulation and functional-medicine assessment is exactly this layer. The self-hostable + MCP combination also lines up directly with my GLP-1 nutrition companion's integration needs.
  • ⭐⭐ The dsh ecosystem keeps showing up. AdamPlatin123/dsh-plugin-radar (★1,500, 238 commits in the window) is an open-source ecosystem radar that continuously snapshots and renders changes across the dsh plugin ecosystem — I run dsh locally, so this line deserves persistent priority. Last issue had four dsh extensions from four different teams on the board at once (dsh-Go, dsh-blender-plugin, dsh-mnemon, dsh-memory), which says this is no longer one person's project but an ecosystem that has formed.
  • ⭐⭐ Licensing this round produced a fresh three-tier sample. Genuinely open source (MIT and Apache-2.0 together, 128 entries, 66%; 146 entries once BSD / ISC / MPL and other permissive terms are included, 75%), source-visible but not open source (orionbelt-semantic-layer on BUSL-1.1, phoenix on ELv2, TrenTorch on PolyForm NC), and not open at all (forma-ai and meliusme proprietary, rakaia all-rights-reserved, CRISPResso2 academic non-commercial — 4 entries). For a one-person company these are still three different things: the third tier cannot even be read, the second can be read and studied but must never become a product dependency, and only the first tier is a selection candidate. The sharpest detail this round: two pick repositories (groundedmed and nutrikit) have no LICENSE file at all — their methodology is worth copying, but their code cannot be depended on directly.
