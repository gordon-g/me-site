1. Turning "sessions that went wrong" straight into reproducible eval cases: coding.sh logs 72 commits today, all circling the agent observability and evaluation loop

URL: https://github.com/jackulau/coding.sh ｜ ★117 ｜ MIT ｜ Local-first observability and evaluation tooling for AI agents, recording every prompt, model call, tool call, file change and dollar cost of Claude Code, Codex, Cursor and other agents

What happened

  • 72 commits on the default branch today (the endpoint truncates at 100, so the real number is higher), and v0.1.7 was published at 16:17 last night. The repository was created on 2026-11-07 and has shipped seven versions in ten days.
  • The quality signal in today's commits is unusually strong: fix(eval): eval validate fails a task whose reference patch rewrites the tests the verifier runs, fix(eval): --hidden-test takes a matching test file out of the agent's start tree too, fix(harness): a Claude Code snapshot carries the files CLAUDE.md imports with @path and leaves out skills/.trash, fix(harness): Ctrl-C stops harness audit while it lists files on disk. The first of these targets the classic way an evaluation gets compromised: if the reference patch rewrites the very test file the verifier runs, the evaluation silently evaporates.
  • The toolchain has four stages: coding.sh sessions / show to read sessions, eval new to turn a failed session into a replayable evaluation, eval validate to check whether that evaluation's judge is fair, exp compare / compare for A/B tests with paired statistics, and bench to draw new cases every day from scripts, failed sessions, GitHub issues or a sitemap, with every contender running the same frozen set.
  • The data boundary is stated hard: every session lands in a local SQLite index, and "No session data leaves your machine unless you add a remote sink." Unless a remote sink is explicitly configured, not a single byte leaves the local machine. No runtime dependencies, Node 22.16+.
  • One README sentence deserves to be quoted on its own: "You read each run in a local viewer and turn the ones that went wrong into evals." — eval cases are not written up front; they grow out of real failures.

Why it matters

  • This is the most directly executable template for the "30–50 question two-by-two comparison evaluation" of my 4P expert package — the task I have been deferring for several issues. What I recorded in earlier issues was always a principle (NVIDIA/SkillEvaluator distinguishing "the evaluation arm that failed" from "the evaluation arm that never ran", cqframework giving every skill its own evals, ASB anchoring to verbatim evidence). Today, for the first time, someone has packaged the whole flow into one command chain: read the failure → convert it into an evaluation → verify the evaluation is fair → derive a conclusion with paired statistics. The first step of my 30–50 question assignment is not "write the questions" but "go collect the sessions that broke inside my expert package over the past few months."
  • "An evaluation whose reference patch rewrites the test file the verifier runs is void" is precisely the most dangerous loophole in my scheme of "generating intervention reports with AI and then scoring them with AI." If my evaluation questions are LLM-generated and the reference answers are LLM-written, the score may be nothing but the system grading its own homework. coding.sh turned this loophole into an automated check. I can lift it straight into the 4P evaluation spec: any automatically generated evaluation must first pass the check "the reference answer must not rewrite the verifier's test file."
  • Local-first plus SQLite plus no egress lines up naturally with the "customer health data never leaves my machine" baseline of the 4P platform. My Ollama, the Flask ports 8889/8899 and the Obsidian knowledge base all run locally on this machine. If I attach evaluations to the expert package, there is no reason to ship session data to any remote endpoint.
  • Paired statistics are far stricter than "run three times and take the average." My evaluation targets are prompts, models and report templates — strongly correlated variants — so an independent-samples t-test is simply the wrong test here; the paired test is the right one. I am writing this into the evaluation methodology directly.

2. Clinical agent evaluation resolved a question I have been circling: is the model judging wrongly, or is the interface painful? Health-CUA isolates the interface and tests it separately

URL: https://github.com/ybkim95/health-cua ｜ ★1 ｜ Apache-2.0 ｜ A benchmark for clinical computer-use agents in electronic health records, giving the same agents the same clinical task through two interfaces — API and graphical UI

What happened

  • A single commit at 23:52 today completed a major version: Revised grader v4 as the leaderboard grader, Gemini 4 Carbon on the leaderboard (17 models), release 1.1.0. The repository was created on 2026-11-08, ten days ago.
  • The evaluation design is the hardest part of the whole write-up: the task, the record and the grader are all fixed, and the only variable is the interface. Through the API the agent calls a FHIR server with the tools released with PhysicianBench; through the GUI it operates a web EHR with mouse and keyboard. Both interfaces read and write one HAPI FHIR R4 record, which is restored to a verified snapshot before every episode, and one deterministic grader checks the orders and notes left in the final record.
  • The leaderboard covers 17 models over 39 consultation tasks, pass@1 with three attempts per task, scored with the revised grader v4: Claude Fable 5.2 API 75.2 / GUI 79.5, Claude Opus 5.5 API 64.1 / GUI 77.8, Claude Sonnet 5.5 API 69.2 / GUI 76.9, Gemini 4 Carbon API 55.6 / GUI 76.1, GPT-6 Astra API 47.0 / GUI 74.4, MedGemma 27B API 0.9 / GUI 0.0.
  • There is a separate track of 150 held-out synthetic tasks: Claude Opus 5.5 API 78.0 / GUI 88.0, with synthetic task grader synth_reasoning_v9.
  • Grader version discipline is spelled out in full: the original grader is the paper's preregistered primary outcome (the predecessor of S2, called P1), while the revised version accepts clinically equivalent orders and dose ranges and fails forbidden or excess orders, so no ordering script can pass it. --grader v3 and --grader original remain selectable, and the fact that the paper's table and the leaderboard table carry different numbers is stated outright, with a recompute command supplied.
  • The limitations are reported just as plainly: on its own controls the revised grader still wrongly rejects 3 of 43 clinically equivalent orders and wrongly accepts 2 of 12 tenfold doses; the synthetic task set carries Synthea artefacts such as implausible histories; and the physician-review field on the task set is still marked pending.

Why it matters

  • "Fix the task, the record and the grader; change only the interface" is a ready-made methodology for attributing quality in my 4P precision nutrition platform's intervention reports. When a client says "the report isn't useful", my current troubleshooting is intuition: is the intervention plan itself wrong? Is the lab-value interpretation wrong? Or is the report simply too long, with the key points buried and the format unsuited to a physician? If those three causes are entangled, my iteration is blind. Health-CUA supplies the standard method: fix the variables one at a time, move one, then measure. I can split 4P report quality evaluation into three parallel tracks — judgement layer (plan correctness), data layer (indicator interpretation accuracy) and presentation layer (format and readability) — each scored independently.
  • The counterintuitive finding that API scores run below GUI scores is directly useful to me. For most leading models the GUI arm beats the API arm (Opus 5.5 by 13.7 points, Sonnet 5.5 by 7.7, Gemini 4 Carbon by 20.5). The README explains part of why: the GUI message form can only address patients, while the API message tool can address anyone — and messaging anyone other than the task's patient counts as harm, so that harm can only occur through the API. Put differently: the API is harder not because it carries less information but because it can do more dangerous things. That insight transfers directly to my AI assistant — greater capability does not mean a better experience; greater capability means the tool boundary must be stricter.
  • "No ordering script can pass it" is a hard criterion my report-quality grader currently lacks. I should set myself one: if there exists a shortcut in my evaluation where simply emitting a fixed format earns a high score, then it is measuring formatting rather than capability. Health-CUA's approach is to design that shortcut directly into what the grader must reject.
  • Publishing the grader's own error rate (3 of 43 wrongly rejected, 2 of 12 wrongly accepted) is the scorer-layer counterpart of the "model evidence gaps as a first-class state" thread I recorded in earlier issues. Not "my grader is accurate", but "here is where my grader is inaccurate and by exactly how much". If my 4P report hands a client a risk rating, it has to state the error boundary of that rating instrument too.
  • Reality check: ★1, created ten days ago, zero issues — this is research code, not a product — and the model names on its leaderboard (Claude Fable 5.2, GPT-6.1 Sol, Gemini 4 Carbon) show it evaluates models far beyond the capability ceiling of my local Ollama qwen2.5:7b. I can borrow its experimental design and its failure-attribution method; I cannot draw any inference from its scores.

3. The nutrition track produced a template for "report the number if you ran it, write 'not run' if you didn't": nutrition-rag states outright that the harness is built but the paid evaluation has not been published

URL: https://github.com/jordanT667/nutrition-rag ｜ ★0 ｜ No licence declared ｜ A question-answering assistant over the official French adult dietary guidelines (Santé publique France 2019), with BM25 retrieval, Claude generation, page-level citations and a three-mode evaluation harness

What happened

  • The repository was created today (2026-11-18) with two commits: Question-answering assistant on French dietary guidelines, with page citations (00:26) and Run the tests on GitHub Actions and show the badge (01:33). This is a brand-new project that stood up its evaluation harness on day one.
  • The corpus is Santé publique France's 2019 official PDF, Recommandations relatives à l'alimentation, à l'activité physique et à la sédentarité pour adultes, 62 pages. It is chunked into 151 passages of roughly 1,200 characters, and no passage crosses a page boundary, so every citation points at one exact page of the official PDF.
  • Retrieval is BM25 (accent folding plus light plural stemming) running locally with no model download; generation uses Claude Opus 5.5 with retrieved passages passed in as search_result blocks with citations enabled, so "citations come from the API, not from the model's free text."
  • The evaluation set is 50 French questions, each with a reference answer and reference pages: 32 factual, 6 paraphrased, 2 requiring two pages, and 10 not covered by the document. The last ten specifically test whether the assistant admits the limits of its sources instead of filling the gap from general knowledge.
  • Measured retrieval numbers: BM25 Top-1 0.700 / Top-3 0.900 / Top-5 0.950 / MRR 0.811; character TF-IDF MRR 0.739; rank fusion of the two MRR 0.792 — the conclusion is that BM25 alone is best and fusion brings no gain on this corpus.
  • The answer-quality section says it plainly: "Status: the harness is built and tested, the paid run has not been published yet. No answer-quality figure is reported here until it has run." The three-mode script (RAG with 5 passages / the whole document at 151 passages, about 40,000 tokens / a no-document baseline) is written and tested, but the paid run has not happened, so not a single answer-quality figure is reported.

Why it matters

  • "The paid run has not happened, so not one number is reported" is the self-discipline template I most need for evidence-based content. The standing temptation in my public-account writing on functional medicine and precision nutrition is to give a "probably effective" percentage when no measurement exists. This project turns that principle into engineering language: an evaluation that did not run produces no number, rather than producing a reference value. My GLP-1 nutrition companion is on version 61 and still lacks exactly this — I have been tuning prompts without ever making "did the evaluation run?" a mandatory field. This goes into my content and product spec.
  • "No passage crosses a page boundary, so every citation lands on one page" is a physical guarantee of citation verifiability. What I recorded in earlier issues as "every number carries a source and a confidence level" has stayed a slogan. Today there is an executable version: chunking granularity must align with citation granularity, otherwise "labelled with a source" still cannot be checked. I am writing this into the 4P supplement platform's knowledge-base spec: every nutrition figure either resolves to a specific page or clause, or does not get written.
  • Ten "not covered by the document" questions are the smallest testable form of "zero AI hallucination." I keep saying my content must be "evidence-based + referenced + zero hallucination", yet never turned it into something that can be run. "Will the assistant admit it on the ten questions the guidelines do not cover" is a far stronger guard against hallucination than any prompt constraint. I can do the same thing inside the 4P knowledge base next week: take a batch of "users ask this often but the evidence does not support it" questions and see whether my assistant admits or fabricates.
  • BM25 alone beating hybrid retrieval, with Top-5 already at 0.950 on a 62-page document, is directly relevant to my decisions. My 4P supplement knowledge base is far larger than 62 pages, so if a naive retriever like BM25 already reaches 0.95, then the "should we adopt a vector database" decision becomes a data-driven one rather than a matter of technical taste. This directly determines whether the 4P platform should use SQLite FTS5 or stand up a vector infrastructure — the engineering time saved matters under my eight-hours-a-week constraint.
  • Reality check: ★0, created today, and no licence declared (there is no LICENSE file in the repo either) — the design can be learned from, but the code should not be copied into a commercial project. At the level of methodology, however, it is the most on-target thing on the internet today.

4. The memory layer starts confessing its failures: nautilus-compass quantifies "recall noise at 76.2% of top30" today and admits a second identical livelock in ten days

URL: https://github.com/chunxiaoxx/nautilus-compass ｜ ★1,258 ｜ No standard SPDX licence (README labels it a Modified MIT variant) ｜ An open-source memory and reliability layer for AI agents, with independent judging and verification (NACRE judge, caliber-bench meta-benchmark, preregistered criteria)

What happened

  • Four commits today, all written as "on-watch" log entries (the repository numbers them consecutively R559–R562 as duty shifts), and this is not a feature release — it is the project writing its own runtime outages into a public repository.
  • The hardest line today is R560: "distill contamination's recall-side harm quantified for the first time (noise at 76.2% of top30)" — memory distillation contamination is no longer "feels a bit dirty" but now has a concrete ratio.
  • R562 records the recall entry point going fully down, caused by daemon overload producing a livelock, explicitly labelled "recurrence of the same type as 10-12" — the second identical livelock in ten days. The response was to restore the transport layer and upgrade the watchdog liveness-check criterion.
  • R561 gives the exact benefit table for distillation approach A from an offline rehearsal: hooks 494 → 188, daemon 1417 → 189, noise 0%; it also corrects the in-library noise measure from 84.0% → 86.7% (40 sessions had been missed).
  • R559 records that "distill freeze is disproven": freezing was assumed to stop the contamination, but legacy session backfill keeps pouring into the formal memory store — all 270 published sheets were legacy sessions older than seven days.
  • The capability claims are themselves hard: LongMemEval-S full 500 P@5 97.8% (against mem0's 91.6%), EverMemBench 44.4% → 47.3%, drift-detection AUC 0.83 on a held-out set; the NACRE judge compresses judging knowledge into a 1.7B LoRA with 88.5% three-state agreement and ECE 0.072; and it ships caliber-bench, a meta-benchmark that scores benchmarks themselves.
  • The deployment-precision discipline is worth listing on its own: under 291 preregistered cases, fp16 matches the bf16 anchor with 100% label agreement (safe), int8 comes in at 98.28% (judged a failure) and int4 at 94.16% (judged forbidden), with the full verdict table kept in the repository.

Why it matters

  • "Recall noise at 76.2% of top30" is the most jarring number I read today. It means that even when a memory layer recalls 30 items, roughly 23 of them are contaminated — and the entire value of a memory layer rests on recall quality. The core selling point of my GLP-1 nutrition companion version 61 is that every interaction is persisted to support self-evolving learning. If my historical interaction data is heavily polluted with low-quality or stale records, my "self-evolution" is really just pouring noise into the system. Today's line gives me a concrete action item: before doing any memory augmentation, quantify my own recall-noise rate.
  • "distill freeze is disproven" — assuming you can block the entry point does not stop the contamination, because legacy backfill routes around it. The same lesson applies to the 4P platform: if I merely add a freeze switch or a time filter to the knowledge base, historical dirty data will still reach the context through another path. Defence has to be structural (validated at write time, traceable source) rather than a runtime toggle.
  • "Second identical recurrence in ten days" is a far more honest way to write it than "we fixed the issue." My spec-document template has been missing one rule: log outages by recurrence count, not by "fixed" status. A problem that has been fixed twice and a problem that has never occurred are not the same maturity level. This goes into the 4P platform's operations log spec.
  • The deployment-precision discipline (int8 judged a failure, int4 forbidden) is a hard constraint I had not even considered. Its logic: when quantisation to int8 drops label agreement to 98.28%, that means 1.72% of cases will be judged wrongly, which is unacceptable in risk-grading scenarios — so rather than degrade, refuse to deploy. If my 4P risk ratings ever run on a quantised model, this criterion applies directly: it is not "the accuracy loss is within an acceptable range" but "past a threshold, disable it."
  • The "same model, two harnesses" comparison (v5-harness 26.7% vs mini-swe-agent 16.7%, +10.0 points) shows that an agent's ceiling is largely determined by its harness, not by its model. I have consistently attributed "my AI assistant isn't good enough" to "the local model isn't strong enough" — this result says check the harness first, then the model.
  • Reality check: ★1,258 but the licence is a Modified MIT variant rather than standard SPDX, and all four of today's commits are duty-shift logs rather than features. The LICENSE text must be read clause by clause before any commercial use. As always, that goes into the open-source dependency inventory.

5. "Filter by permission first, retrieve by relevance second" has become a product: schemagate keeps tables the caller may not read out of the prompt entirely

URL: https://github.com/ashishsinha1602/schemagate ｜ ★137 ｜ Apache-2.0 ｜ An access-control layer for Text-to-SQL that trims the schema by the caller's grants before handing the model only the tables they may read

What happened

  • Six commits today, with v1.18.2 published at 02:06 (v1.18.1 on 11-11, v1.18.0 on 11-09 — three versions this week). The commits include release: 1.18.2 - case-sensitive Oracle names reach the model in quotes, fix(oracle): show case-sensitive names in the quotes SQL needs, and a Docker base image bump from 3.14-slim to 3.15-slim.
  • The core mechanism in one sentence: it filters tables by the caller's grants first and then selects by relevance, so restricted tables are "absent from the prompt rather than ranked low". The README's own words: "restricted tables are absent from the prompt rather than ranked low".
  • The effect is quantified: 91.1% fewer schema tokens (median) on databases with 50+ tables (measured across 24 databases). The README gives a reproducible extreme case: a 1,201-object schema is 146,695 prompt tokens in full, while schemagate sends 12 tables — including all 3 the query actually needs — totalling 1,348 tokens — and notes that this is rebuilt by a script from a seeded fixture and counted with tiktoken's cl100k_base, not drawn.
  • Accuracy does not pay for it: first place on BIRD's Mini-Dev leaderboard in all three dialects (SQLite 81.0, PostgreSQL 72.6, MySQL 72.4 execution accuracy, with Claude Opus 5.5 and one model call per question); UniQL Oracle 63.7% on the first attempt.
  • Retrieval quality against alternatives: on the data warehouses, the table set schemagate selects contains every table the gold query reads for 86.7% of questions. At the same table count and with zero model calls, schemagate selected every needed table for 85.3% of warehouse questions where BM25 managed 78.7% and embedding search 78.2%, and for 98.7% of BIRD questions against 81.0% and 89.4%.
  • It states the consequence of a row-level-security failure very concretely: "the model writes valid SQL against a table the caller cannot read, RLS strips every row, and the user is told 'no records found' — indistinguishable from 'this data does not exist'."
  • It supports LangChain, LlamaIndex, MCP and any SQL agent, across Postgres, Oracle, MySQL, SQL Server and SQLite; it carries an OpenSSF Best Practices badge and patent application US 64/183,987.

Why it matters

  • "Tables the caller may not read are absent from the prompt" and "rows the caller may not read come back as 'no records'" are two failure modes of the same hole, and the second is far more serious. My 4P precision nutrition platform is Flask + SQLite with an admin backend, and customer data shares one database. Today's entry amounts to a security audit I should run on myself this week: if my AI assistant opens natural-language database access, could client A's lab data be hit by client B's query and then masked by a single "no data" reply? This is not a hypothetical risk; it is a point I should self-check immediately.
  • "Authorise first, then retrieve" is the same class of principle as the "AI only selects, never calculates" thread I recorded in earlier issues — just another face: not compute first and check permissions afterwards, but draw the boundary before doing any computation at all. If the 4P assistant is to answer "show this client's HbA1c trend over the last three months", the correct order is: first bound the row range the client ID permits, then retrieve indicators within that range — not retrieve across the whole database and filter the results afterwards. The former carries zero leak risk; the latter always carries a race window. This goes into my assistant prompt template.
  • 91.1% token savings with no accuracy cost is a direct cash saving under my eight-hours-a-week constraint. Every call in the 4P platform pushes a large amount of client material into the prompt context; if nine-tenths of that is irrelevant tables, I am both burning money and diluting attention. Optimisations that save money without costing quality should be prioritised over any model upgrade.
  • The way it presents evidence is worth copying wholesale: "Measured, not drawn", with the rebuild script supplied. This is the same spirit as the "do not pad the numbers" thread I keep recording — a number is either measured or it is not written. Every technical decision document in the 4P platform should carry a line saying how to reproduce its own numbers.
  • Reality check: ★137, repository created 2026-09-06 (two and a half months old), patent pending and not yet granted — the licensing status needs attention. The core idea is something I can build myself; I would not make a component with a pending patent a direct dependency.

3. Trends today

  • ⭐⭐⭐ "The evaluation itself must be challengeable" landed simultaneously in three ecosystems that do not know each other. coding.sh ships eval validate to check whether an evaluation's judge is fair (today it fixed the loophole where "the reference patch rewrites the tests the verifier runs"); nautilus-compass ships caliber-bench to score benchmarks themselves, measuring criteria drift, contamination and judge stability; Health-CUA designs "no ordering script can pass it" into the grader and publishes its own error rate (3 of 43 clinically equivalent orders wrongly rejected, 2 of 12 tenfold doses wrongly accepted). Together these three cover a complete set: the evaluation must be fair, the benchmark must be trustworthy, the grader must disclose its own error. My 4P expert package's "30–50 question two-by-two comparison evaluation" has implemented none of these three dimensions.
  • ⭐⭐⭐ "Did not run, so no number" is now a hard rule rather than a personal style. nutrition-rag states plainly that the harness is built but the paid run has not been published, so not one answer-quality figure is reported; schemagate states "Measured, not drawn" and supplies the rebuild script; cal-dining-macros states that if a nutrient is blank in the published file it shows - and leaves it out of the totals instead of inventing a number. Three projects in three unrelated domains did the same thing: do not pass an estimate off as a measurement. This is exactly the discipline my public-account content and product documentation need — the 4P platform still has no "was this number actually run?" field.
  • ⭐⭐⭐ "Attribute the failure to the right layer" produced one directly transferable experimental design today. Health-CUA fixes the task, the record and the grader and varies only the API and GUI interfaces, separating "the clinical judgement was wrong" from "the interface was hard to use". Attribution of 4P intervention report quality is exactly my problem. And it yields a counterintuitive finding: API scores run below GUI scores not because the API carries less information but because the API can do more dangerous things (the GUI can only address patients, the API can address anyone). Greater capability does not mean a better experience; greater capability means the tool boundary must be stricter — I am lifting this straight into my AI assistant prompt template.
  • ⭐⭐ The memory layer has started publicly confessing failures and quantifying them into ratios. nautilus-compass delivered three lines today: recall noise quantified for the first time (76.2% of top30), the freeze-distillation approach disproved (legacy session backfill routes around the freeze and pours into the formal store), and a second identical livelock recurrence in ten days. "Fixed twice" and "never happened" are two entirely different levels of maturity. I am adding one rule to my spec-document template: log outages by recurrence count, not by "fixed" status.
  • ⭐⭐ Permission boundaries must be embedded in the data path, not bolted on at the exit. schemagate's mechanism is to trim the schema by grants first so tables the caller may not read never appear in the prompt; medical-privacy-guard is a local fail-closed guard with four verdict states (release / rewrite / await human / block) and a hash-chained audit log; compactbench collapses submission, contact and MCP limits into one database step. All three say the same thing: boundaries must be enforced along the path data flows, not left to a single judgement at the exit. The customer-data isolation in my 4P platform should be rebuilt along these lines.
  • ⭐ The DSH ecosystem moved for the fourth consecutive issue, and today landed on the packaging-and-distribution layer. runzhliu/deepseek-harness-docker published image-v0.2.2-rc.4-r1 (hardened image + Compose + Helm + Web UI + headless CLI), and adsorgcn/DeepSeekHarness published v1.1.32 (persistent local memory + one-click install + skill library + Gitee mirror). Earlier issues covered the application, protocol and methodology layers; today adds the layer of "making it easy for others to install" — which is exactly the capability I lack as a one-person company: not building things, but making things installable.
  • ⭐ Tooling is turning "context compaction" into an independent, benchmarked engineering object. compactbench states that it "measures the compaction layer, not the model", and defines eight families of compaction failure (buried constraint, decision override, entity confusion, reference resolution, numeric precision, conditional scope, task continuity, provenance authority), backed by oracle / null / truncate-last-n controls and a hidden ranked set resampled every run. Context compaction used to be each agent framework's private implementation; today it has a public benchmark — the next step on the same curve as "the evaluator itself must be evaluated."
