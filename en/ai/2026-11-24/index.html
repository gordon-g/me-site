1. Medical agents hand every number to a deterministic engine: LesionAgent forbids the LLM from computing a single figure

URL: https://github.com/MIC-DKFZ/LesionAgent ｜ ★13 ｜ Apache-2.0 ｜ The German Cancer Research Center's (MIC-DKFZ) training-free tumor tracking agent: frozen 3D foundation models are used as tools, the LLM only judges, and every measurement plus RECIST 1.1 category is computed by a deterministic guideline engine

What happened

  • One commit today (link to paper), but the action itself is substantive: the paper "LesionAgent: Training-Free Agentic Tumor Tracking and Response Assessment in Longitudinal CT" was posted to arXiv on 2026-11-20 (number 2611.27876), and the repository added the link the same day. The authors are Maximilian Rokuss, Jeya Maria Jose Valanarasu, Alejandro Lozano, Benjamin Hamm, Yannick Kirchhoff, Fabian Isensee and Klaus Maier-Hein.
  • The architecture is split by decision type: 3D foundation models handle perception (VoxTell detects, nnInteractive segments, uniGradICON registers, LongiTrack tracks, TotalSegmentator assigns organs), the LLM handles what the models cannot judge (is this finding a lesion, is it the same lesion at the next visit, is a new spot real progression, which should be followed), and a deterministic guideline engine measures the lesions on their masks and applies RECIST 1.1. The README's words are the LLM never computes a number or a response category.
  • The agent acts only through 18 typed tools, in four groups: perception (detect/segment/track_all/refine_lesion/edit_mask/totalsegmentator), inspection (study_info/view/view_pair/inspect), registry (review_candidates/update_lesion/set_visit_judgement), decision (score_lesions/propose_targets/set_targets/recist_report), plus a human channel ask_clinician.
  • The abstract gives the key numbers: with the same 3D models chained by fixed rules, progression was falsely called at 33 of 56 follow-ups, while LesionAgent does so only twice; on clinical follow-up CTs it agrees with the radiologists' response assessment at 20 of 23 follow-ups, including every change in response; and without training on DeepLesion it retrieves 89.0% of its lesions, above every tracker trained on it (87.4%).
  • The sharpest line in the paper is that the harness, not the model, makes the difference: given the same LLM and the same 3D models, Claude Code reaches a detection F1 of only 41% while LesionAgent reaches 78%, and an open-weight LLM that can run inside the hospital rises from 6% to 73%.
  • The README states plainly that the current status is "Coming soon"; the roadmap lists four steps — the paper, the code, a CLI / Python API and a napari reading app. The napari app works with any LLM: a clinician can watch the read live, answer the agent's questions (for instance, which target set to use when two valid sets give different responses), correct any decision, and the RECIST report is regenerated from the registry afterwards.

Why it matters

  • This is an architecture pattern that can be copied directly, not a tool recommendation. The question I have been stuck on — who should compute the numbers in an intervention report — has an explicit answer here: the LLM does not compute a single number, the numbers come from a deterministic engine working off the raw masks, and the LLM only judges what it is good at judging. My GLP-1 nutrition companion currently runs "model reads the metric → model gives advice → model writes the conclusion", with no deterministic step anywhere in the chain. If an unreadable metric reading still yields a number out of it, then "zero AI hallucination" on my side is just a slogan, whereas LesionAgent offers a way to take the number-producing step away from the model entirely.
  • "The harness, not the LLM, makes the difference" is a warning bell for a one-person company. 41% vs 78% for Claude Code, and 6% → 73% for an open-weight model, means the same models inside a different harness can differ by an order of magnitude. In other words, my local Ollama qwen2.5:7b performing poorly may not be the model's fault — it may be that I never gave it the right harness (typed tools, an engine split, registry state). That is far cheaper and far faster than swapping in a stronger model.
  • The lesion registry (a lesions × visits matrix that keeps the mask at every visit) is the piece I should copy most closely for a family health archive. My companion has multi-member records, a timeline and metric trends, but every metric reading today is an isolated row — there is no structure for "the same thing at different points in time, with its original evidence attached". The registry guarantees that any conclusion can be traced back to a specific visit and a specific mask. That is how the three evidence-strength columns I noted last issue would be implemented at the storage layer.
  • The order of magnitude of "18 typed tools" is worth remembering. It is neither "give the agent a universal shell" nor "wire in dozens of APIs", but exactly the set of judgement surfaces this reading workflow needs. Typed tools plus an engine split plus a human channel is an interface design I can reuse directly when I build "algorithm modules + LLM orchestration" for the 4P platform.
  • Honestly stated: this entry has 1 commit, 13 stars, and unreleased code; the paper numbers come from arXiv rather than from repository measurements. But it is the only project I have seen this week that turns "evidence-based" from a promise into a code structure — every number traces to a mask, every category traces to a rule table. Its value to me is not that I can use it tomorrow, but that it points at the direction I should be changing.

2. Agents that generate no text: SystemOneAgents makes "the model judges, the code assembles" a 97.0% reproducible process

URL: https://github.com/eltzanis/SystemOneAgents ｜ ★15 ｜ Apache-2.0 ｜ The official implementation of "System 1 agents: a method for local, reliable and fast agentic AI": a deterministic compiler turns tool schemas and requests into multiple-choice questions, and a one-pass decision model only picks an option while code assembles the call

What happened

  • One commit today (Update README); the repository itself is the open-source companion to the paper posted on arXiv on 2026-11-16 (number 2611.21053, 18 pages, 5 figures, 9 tables), authored by Eleftherios Tzanis and Michail E. Klontzas.
  • The core mechanism: a deterministic compiler turns each tool's JSON schema plus the user request into typed multiple-choice questions, where the options come only from the request and the schema; a decision model returns a probability for every option and answers in a single forward pass; code owns the control flow and assembles the call. The README's words are the model judges; code assembles — every tool name, argument name and argument value comes from the catalogue, the schema or the request itself.
  • The abstract gives the numbers: across 1,952 requests to 157 biomedical tools, the best System 1 agent chose the right tool, or correctly declined, on 97.0% of requests, well ahead of the best of all 18 local LLM-agent settings (95.2%); it filled 97.0% of 6,056 stated argument values; and no System 1 call contained invented content, against 5.5–19.7% of LLM calls.
  • Three cases are explicitly separated: an enum argument asks over its values, a boolean asks over "on", "off" and "not mentioned", and paths, numbers, names and free text are asked over candidates extracted from the request, the schema or earlier steps, plus a "not specified" option. An optional argument is only filled at probability 0.7 or above; if a required argument has no supported value, it is reported as missing and the agent asks the user rather than inventing one.
  • The agent explicitly declines: when no tool can do what was asked, it says so instead of forcing a tool call. Every question and answer can be stored, so a run can be audited and replayed decision by decision.
  • Engineering-wise it runs locally: the decision models run through llama.cpp with no fine-tuning; the code lives under code/ and installs with pip install -e ..

Why it matters

  • Those eight words, "the model judges, the code assembles", map onto a specific defect in my own platform. My 4P precision nutrition platform has three algorithm families (P4 local, DINGXIANG, JINGYAN), and today all of them are chosen by a model inside free text with free-form parameters. Two consequences follow: parameter values can be "polished" into something that looks reasonable but has no basis behind it (that is exactly the 5.5–19.7% fabrication rate), and the whole decision process cannot be replayed and audited step by step. Switch to "schema-constrained options plus code assembly" and every recommendation I make can be replayed as a series of multiple-choice questions with known answers — that is how "zero AI hallucination" stops being an attitude and becomes an interface contract.
  • "If a required value is missing, ask — do not invent" is the rule I should copy most directly. My companion consumes glucose, CGM, dietary records, lab reports and medication logs at the same time. When one metric reading is missing, does my system currently produce an estimate, or does it stop and ask? By today's criterion the correct answer is "report the missing required value and follow up". My "improved / unchanged / worsened" trigger logic is in essence a classification problem, and its inputs (readings, adherence, activity) are almost all enumerable or extractable — the methodology fits my scenario almost exactly.
  • The 97.0% vs 95.2% comparison makes a point that is easy to misread. Switching to System 1 buys only about two points of tool-selection accuracy, which looks like "not worth it". The real gain is in the other column — fabrication falls from 5.5–19.7% to zero. This is the same point as the verifylens criterion I noted in the 11-22 issue, stated differently: a wrong parameter that looks plausible is more expensive than choosing the wrong tool, because it propagates through every later step.
  • "Runs locally, no fine-tuning, llama.cpp" is decisive given my real constraints. With 8 hours a week and roughly one month of cash runway, any plan requiring GPU fine-tuning, a cloud account or a paid API must stay off my roadmap. This plan costs nothing, needs no training, runs locally, and the domain in its paper (biomedical tools, local sensitive data) is precisely my business domain — this is the repository from this issue whose README I should read most carefully.
  • It also warns me against introducing free-text generation for its own sake. I have been thinking about adding a "natural-language consultation" entry point to the 4P platform, letting users describe their diet in colloquial terms and receive a suggestion. By today's criterion the first step of that path must be constrained: fix the structured parameters first and leave free text to the last layer as a presentation concern, rather than letting it carry the decision.

4. Agents start putting memory in git: Letta Code makes context diffable, rollbackable and self-rewritable

URL: https://github.com/letta-ai/letta-code ｜ ★3,902 ｜ Apache-2.0 ｜ A stateful agent framework from the creators of MemGPT and sleep-time compute: agents have memory, identity and long-horizon experience, and will proactively rewrite their own memory, skills, prompts and even the harness itself

What happened

  • Twelve commits today and release v0.34.70 (2026-11-23). The README positions it in one line as a stateful agent harness for creating agents that are more like people than tools — agents have memory, identity and experience that accumulates over time, learning and evolving across long horizons by rewriting their own memory, skills, prompts and mods (the harness itself).
  • The single most important design decision is MemFS: all context, including memory blocks, is tracked by git, and it can be synced to a custom GitHub repository with /memory-repository set git@github.com:.... The README's words: All context (including memory blocks) is tracked via git.
  • The three commands for self-improvement are spelled out: /sleeptime configures periodic "dreaming" (i.e. sleep-time compute), /doctor [symptom] investigates agent behaviour, /palace views memory. Skills load from three layers — global ~/.letta, project-level .agents/skills, and agent-scoped (stored in MemFS) — and can be created with /skill-creator.
  • Three of today's commits handle the risk surface of self-improvement: feat(agent): scope subagents to a task description — subagents are scoped to a task description; fix(subagents): record task descriptions in traces and conversations — task descriptions get recorded into traces and conversations; fix(agent): validate cloud options against the resolved computer — cloud options are validated against the computer actually resolved to. There is also fix(skills): choose image models by task and preserve full edits and chore: delete all code comments.
  • Deployment forms: a local CLI, the browser (including mobile at chat.letta.com), and messaging integrations such as Telegram, Slack and Discord. It supports hooks, permission modes, scheduled tasks and heartbeats, working across machines (letta server --computer-name "..."), and secrets usable across machines but obfuscated from context.

Why it matters

  • MemFS tracking all context with git is the most "engineering" decision I read this issue. It means an agent's memory is not a blob in a database but a set of files that can be diffed, committed, rolled back and reviewed. In the GLP-1 nutrition companion V2, my "persist every interaction to support self-evolving learning" currently means writing rows into SQLite — it can store, but it cannot be inspected, version-compared or rolled back. Move it to git and "what did the agent actually learn" becomes a diff a human can read. For me this matters more than any new feature: a one-person company's self-evolution system must be inspectable by its owner, or it is silently drifting.
  • "Memory as files" also solves explainability by the side. My intervention reports need to answer "why this recommendation". If memory and skills are files, the answer can quote a specific line of a specific memory block. That is far more reliable than "ask the model to explain itself" — a model's explanation is also generated, while a git diff is not.
  • Today's three commits happen to be three guardrails on self-improvement. Scoping subagents to a task description, recording task descriptions into traces, and validating cloud options against the resolved computer — all three are the same problem in three shapes: when the agent modifies itself, where did it modify, in relation to what, and on which machine, must all be recorded. I noted in the previous issue that "a self-evaluation loop needs an external nail"; today's entry supplies the other half: a self-improvement loop needs an external trace.
  • For the reality of 8 hours a week and one month of runway, this project is attractive because it is not yet another framework I have to evaluate for days: 3,902 stars, a real release cadence, three install methods (npm / uv / pipx), and it is free. It is installable today, with two commands — /palace and /doctor — to try immediately. Compared with swapping local models, turning memory into a reviewable file is the more worthwhile step this month.
  • Its sleep-time compute route echoes the "reflection / warm-up" idea I noted before. But one caution: this is also a commercial product with Letta Cloud as the default backend. A local mode exists (--backend local), but cloud-by-default means memory leaves the machine by default — for someone working with health data, the first thing to do on installation is force the local backend. I hit the same choice in the 11-23 issue with OpenScientist's air-gapped mode; this is the second time.

What happened

Why it matters

  • "Bias-rated" is the three words I most want to copy. Every recommendation in my intervention report ought to carry an evidence grade, but "has a citation" and "the citation is trustworthy" are two different things — a 2019 small-sample RCT and a 2026 phase III randomised controlled trial currently look identical in my reports. The three evidence-strength columns I noted in the previous issue have a ready-made implementation vocabulary here: the evidence itself carries a bias rating. I can add that column next week.
  • Marking placeholder data as "not real evidence" is worth more than the feature. My GL-1 companion has 153 ingredient templates and 15 functional targets — these are templates I wrote, not clinically validated ones, and I have never said so in the product. This project settles it in one line of README: the boundary between "template" and "evidence" has to be written into the artifact, not just kept in my head.
  • The server-side fail-closed disclaimer gate is a reusable pattern for health content. My site (54hrm.com) carries the line "nothing here is medical diagnosis; plans are for research reference only" in the footer — but that is a sentence anyone can ignore. This project turns it into the entire site being unavailable if the key is not set. Enforcement beats declaration, and the same holds for how the GLP-1 companion is delivered: if it does not give medical advice, that should be structurally impossible for it to give, rather than merely promised in copy.
  • It also demonstrates the "claim matrix as the contract between pipeline and front end" structure. My intervention report has a 9-chapter structure, 24 risk dimensions and 6 risk levels — which is in effect a claim matrix, where what the front end shows and what the back end computes are aligned through one JSON contract. My current setup has the back end emit HTML directly, with no intermediate contract layer, so every new risk dimension means changing both sides. That layer is worth extracting on its own.

3. Trends today

  • ⭐⭐⭐ "The model should not compute the numbers" landed simultaneously in two teams who have never heard of each other, completing a thread I can copy directly. LesionAgent hands measurement and RECIST classification to a deterministic guideline engine, and the README states plainly that the LLM never computes a number or a response category; SystemOneAgents compiles the whole tool call into finite-option questions, and the README states plainly that the model judges; code assembles. Two teams, one shared conclusion: judging is the model's job, computing is code's job. The two observations I recorded over the past days turn out to be two sides of the same thing — last issue's "refusing beats guessing" is upgraded today into "draw the line first between what the model may touch and what it may not".
  • ⭐⭐⭐ "The evidence itself carries a bias rating" is the landing point I most want to copy this issue. Concordance uses brand-blind comparison, user-defined weights and bias-rated cited evidence to rank GLP-1 options, and writes placeholder data down as not real evidence; my intervention report has a "has a citation" column but no "how trustworthy is that citation" column. A 2019 small-sample RCT and a 2026 phase III RCT currently look identical in my reports — which is the same class of problem as having no citation at all. Adding this "evidence strength" column is doable this week.
  • ⭐⭐ "Memory has to be inspectable by its owner" got a concrete implementation today. Letta Code tracks all context including memory blocks in git and can sync it to a custom GitHub repository; smolvm offers checkpoints, branches and rewind for microVMs; Concordance uses a claim matrix JSON as the contract between pipeline and front end. All three do the same thing: turn a smart agent's internal state from an invisible black box into a diffable artifact. My 4P platform's intervention report currently has the back end emit HTML directly with no contract layer in between — that layer should be extracted.
  • ⭐⭐ "Failures must say which step broke" became the through-line in the highest-commit-count projects. Nearly all of AutoClip's 12 commits fall into this class: a Gemini network failure still belongs to the model, one-pass LLM failures get classified, and the reason a closed-set trial run failed must surface in the interface across 8 locales; cli-agent-orchestrator separates "delivery failed" from "reply sent" and requires flaky-window oracles to be as strict as the properties they guard; sglang_ling_v3 fixes the release timing of PP prefill transfers. These failures do not error out, which makes them the expensive kind — my OCR→AI→App chain's error messages are still stuck at the level of "this metric was not recognised".
  • ⭐ "The same models can differ by an order of magnitude depending on the harness" belongs in my technology-selection logic. LesionAgent's controlled comparison: with the same LLM and the same 3D models, Claude Code reaches a detection F1 of 41% against LesionAgent's 78%, and an open-weight model that can run inside a hospital goes from 6% to 73%. This means my local qwen2.5:7b performing poorly may not be the model's fault — it may be that I gave it the wrong harness. For a one-person company with 8 hours a week, that is far cheaper than swapping in a stronger model.
  • ⭐ ③ The health / nutrition line finally has one project with a clear stance, but it is still low-star. Only TandoorRecipes/recipes (★8,745) is in the four-digit range among the 16; everything else sits at 0–6 stars — consistent with the six consecutive issues from 11-18 through 11-23.
