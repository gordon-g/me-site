My skill sources are scattered — functional medicine frameworks, peer-reviewed literature, my own decision rules — so the moment someone plugs an external formulation into the 4P platform, there must be a "is this source trusted?" gate rather than default trust.

Atomic's answer is more engineering-driven: rather than running a heavy process every time, make the heavy process an explicitly selectable tier in the runtime — fast path by default, escalate to the heavy path only when evidence is needed. 2. Skills now ship with their own "verification ladder": modulestf writes Terraform review as graduated evidence from L1 to L4

URL: https://github.com/modulestf/modulestf ｜ ★374 ｜ Apache-2.0 ｜ Agent skills for Claude Code and Codex that review and modify reusable Terraform modules against a written profile of the module family's rules

What happened

  • 22 commits today, with four releases inside four hours: v0.11.0 (23:53), v0.11.1 (00:57), v0.11.2 (01:28), v0.11.3 (02:52) — the rhythm being "change one rule → calibrate once → cut a version".
  • Two of today's key commits make the basis of judgement explicit: fix(reviewer): Judge new-input defaults by effect and calibrate doc and gating rules (#155), feat(pr-fix): Surface a round finding late only for a local text rule on an unchanged span and count a closed item as pro..., and feat(pr-review): let known blockers outrank unknowns in the verdict ladder (#148).
  • The most copy-worthy part of the README is the verification ladder table: L1 evaluates the base and head expressions offline with typed samples and unknowns (requiring only terraform, mtf-facts, perl, jq, plus macOS's sandbox-exec or Linux's bwrap), L2 runs a plan-only terraform test of the instances a count or for_each creates, and heavier levels follow. One hard constraint is stated in the original: "Reading the code supports a claim and never verifies one."
  • The repo contains six named skills (pr-review / pr-fix / pr-merge / reviewer / maintainer / change-scope), and the rules themselves live not in code but in profile files (the shipped profile being terraform-aws-modules' PROFILE.md). PR review calls the reviewer, and both call change-scope; merging additionally verifies the full head SHA.
  • The review skill is read-only and returns findings without a verdict; the verdict and comment are only posted after human confirmation.

Why it matters

  • "Reading the code cannot verify a claim" is the single rule I most want to copy into my 4P expert package. The most dangerous error pattern in my nutrition intervention reports is precisely "I read the literature, so this dose is correct" — literature can only support, never verify dose ceilings, contraindications and interactions. Today this repo writes that sentence as an engineering principle rather than a reminder.
  • "Known blockers outrank unknowns in the verdict ladder" is the same idea as the "explicitly model missing evidence" note from previous issues, one step further along. Not only do you need to know that evidence is missing — you also need to know where "missing evidence" ranks in the verdict. My 4P reports have risk gradings (six levels); now there is a basis for the ordering.
  • Keeping rules in a profile file rather than in code is a separation worth copying. My 4P package currently mixes decision logic with output format; splitting it into a knowledge-and-rules layer (versionable, auditable) plus an output layer (fast to iterate) would stop evidence updates and product iteration from blocking each other.
  • Four releases between 23:53 and 02:52 shows that skill maintenance is itself a high-frequency engineering object, not a document refreshed once a quarter. That directly changes my assumption about how often my own expert package should be updated.

4. The most solid slot on the nutrition line today: foodswap judges an allergen named only in the product name as unverifiable

URL: https://github.com/sahil-gidwani/foodswap ｜ ★0 ｜ GPL-3.0 ｜ A constraint-aware packaged food substitution engine using hybrid lexical-semantic search, nutrition-aware ranking and Open Food Facts

What happened

  • 16 commits today, with four functional blocks each paired with an explanation document and an "explainer": search (Add keyword and meaning-based search), allergen checking (Add the allergen check), data cleaning (Build the cleaned US product table), and request/constraint verdicts (Add shared types for requests and constraint verdicts).
  • The most consequential line is Treat an allergen named only in the product name as unverifiable — an allergen appearing only in the product name is judged "unverifiable" rather than "absent". This distinction is the bedrock of the whole pipeline.
  • The data pipeline is written out completely: first download pulls roughly 8 GB and performs a completeness check, then build cleans it into a US products table (about one minute, including the allergen verdicts), and finally foodswap.search build builds the search indexes (about 18 minutes in full, about one minute in sample mode).
  • The documentation directory is itself a methodology skeleton: 01 scope and features, 02 data sources, 03 data pipeline, 04 architecture, 05 query understanding, 06 retrieval and ranking, 07 constraints and safety, 08 explanations and UI, 09 evaluation, 10 plan, 11 deliverables, 12 methods survey, 13 related work, plus a decisions.md and an explainers/ directory.
  • License and data provenance are both stated: code under GPL-3.0, data from Open Food Facts under the Open Database License.

Why it matters

  • "An allergen named only in the product name = unverifiable" is a criterion I want to carry over verbatim into the label-validation rules of the 4P supplement system. My case is stricter than food: a "contains ingredient X" claim on a supplement label often comes from a supplier's marketing page rather than a test report. If an ingredient appears only in the product name, the correct handling is to judge the source untraceable and trigger human review — not to silently pass it. This rule prevents my AI assistant from hallucinating "this product contains no ingredient X" far better than any prompt could.
  • "Unverifiable" and "absent" being explicitly separated is the third independent implementation of "model missing evidence as a first-class state." The first two were ontology-atlas (missing evidence shows as unknown, never as safe) and cqframework (each skill records the version of the specification it relies on). Three teams that don't know each other, with different tech stacks and different domains, converge on the same criterion — this has stopped being a "best practice" and become a de facto standard. I can finalize this line in my 4P expert package's specification document.
  • Its documentation structure (12 chapters plus decisions.md and explainers/) is practically a methodology paper on nutrition retrieval, and chapter 12 is a methods survey while chapter 9 is evaluation. This is exactly the skeleton I need for the content architecture of my 4P supplement platform: every retrieval capability needs its own explainer and evaluation chapter, rather than scattered across code comments.
  • Reality check: ★0 is a brand-new repository whose single author pushed 16 times in one day. High engineering quality but zero community validation. Projects like this are good as design references, not as dependencies.

5. Temporal context is being built as infrastructure: TemporalStore breaks "memory" into cells / anchors / quotas / decay in Rust

URL: https://github.com/matrixarkai/TemporalStore ｜ ★212 ｜ Apache-2.0 ｜ An open-source Rust temporal store for LLM context management, providing temporal features, member sets, anchors and quota decay primitives

What happened

  • 17 commits today, with the main line decomposing "context" into a set of composable temporal primitives: The cell protocol maps member sets, anchors, quotas, decay, merged reads and batches (#3122), A ranked read command carries a member set, an anchor, a quota and a decay score (#3115), Roll old cell snapshots up in tiers, by age, with a truncation and cap controls, through the command (#3121).
  • The storage-layer reliability details are notably hard-edged: Price the WAL placement map apart from the key-entry guard (#3119), Guards for every way a failed compaction round must keep its slabs (#3117), The periodic loop declines a shard that is still replaying its log (#3116), Write the WAL records of concurrent writers as one batch per shard (#3106).
  • One commit about handling large objects deserves separate mention: An oversized SequenceAdd is split by a running total, not by serializing every candidate (#3108) — oversized sequence writes are split by a running total rather than serializing every candidate.
  • The repo self-describes as "LLM context management, temporal features, and risk control", and its topics explicitly list context-engineering, context-runtime, llm-context, memory, temporal-features and risk-control.
  • The "cell" concept can be read as the smallest unit of memory: a single read must carry a member set, an anchor, a quota and a decay score — these four parameters together determine "what you can recall right now".

Why it matters

  • "A single read must state a member set, an anchor, a quota and a decay score" is precisely the complete semantics of lab-indicator trend tracking in my GLP-1 nutrition companion. My current implementation is "look up the last N records by indicator name" — with no anchor (when was this baseline?), no quota (how many records for one indicator at most?) and no decay score (should a weight from three months ago count the same as yesterday's?). Today's repo turns "what to recall" into four parameters that must be declared explicitly, and I can copy that parameter set directly.
  • "Memory decays" being written as an infrastructure primitive rather than an application-level heuristic. My 4P platform has a business rule that a customer's weight from three months ago should not weigh the same as today's. That rule currently lives scattered across business code; moving it into the storage layer as a decay score is the correct home.
  • The WAL and compaction commits (crash recovery, concurrent-write batching, which slabs a failed compaction must preserve) touch a layer I have not engaged with at all. My Flask+SQLite 4P platform runs locally on port 8899 with customer data in the database, with no WAL-level guarantees whatsoever. This is a reminder that "it runs on my machine" and "the data survives a restart" are two different things, and I have only achieved the first half.
  • Rust plus Apache-2.0 is also worth noting: for infrastructure components meant to evolve over the long term, a memory-safe language saves trouble.
