1. open-mtor-atlas/atlas: an mTOR research database graded by what the evidence can carry — 400+ primary studies where every claim names its source, its measurement conditions, and the point where it stops holding

URL: https://github.com/open-mtor-atlas/atlas ｜ ★0 ｜ CC BY-4.0 (data) / MIT (code, dual-licensed) ｜ HTML

What happened

5 commits inside the window (11-08 10:43Z to 11-08 19:33Z), all data updates, running steadily at several increments a day. The README states the whole project's position in one line: "a curated, evidence-graded database of mTOR pathway research in which every claim carries its source, the conditions it was measured under, and the point where it stops holding." — every claim carries its provenance, its measurement conditions, and the point at which it stops holding.

  • ⭐ Evidence is graded by study design, not by quality, and the README insists on this repeatedly: S = synthesis of human data (systematic review / meta-analysis), H = human study (clinical trial or observational), A = animal model, M = molecular / in-vitro (mechanistic), R = review. It says plainly that studies are "labelled by study design, not by quality, importance, or citation count" — "The code says what kind of claim a study can support, not how good it is."
  • ⭐⭐ The grading scheme itself was changed once, and the reason is worth copying: the letter ladder was originally A–D, and was replaced in September 2026 by the current five tiers. The README gives the reason directly: "a lettered ladder reads as a quality grade, which it never was", and "the old bottom tier merged primary mechanistic work with narrative reviews — two different kinds of claim". The change was prompted by an external critique from a researcher in the field, and the README is explicit that the underlying data was not re-graded — only the labels shown to readers were.
  • ⭐ The project states one counter-intuitive sentence out loud: "A mechanistic paper is not 'worse' than a trial."
  • ⭐ Beyond the study corpus there are two more layers: a knowledge-graph view connecting genes, diseases and interventions, and an "open questions" layer — evidence gaps identified across the corpus, each paired with a proposed testable experiment.
  • ⭐ AI-friendly access is complete: a read-only JSON API (no key required), an OpenAPI 3.1 specification, and an MCP server for AI assistants (source and install instructions under mcp/); the dataset itself carries a Zenodo DOI (10.5281/zenodo.22059963) for formal citation, plus one page gathering every identifier — bio.tools, FAIRsharing, GitHub, ORCID — with a ready-to-use citation.
  • ⭐ The licensing is a clean dual licence: curated content and data (study records, evidence grades, curated prose, gap hypotheses, everything under atlas_data/ and the generated pages) are CC BY 4.0; source code (the Python generators, validation and verification scripts, site JavaScript) is MIT.

Why it matters

  • ⭐⭐ This is very nearly the ruler my "4P Precision Nutrition Watch" public account is missing, and it has already been calibrated. When I write about mTOR, rapamycin or autophagy, the easiest mistake is to present "a mechanism at the cellular level" as "an effect in the human body" — and this project blocks that at the data layer with five letters: a reader seeing M knows it only holds in vitro, and only H tells them human data is behind it. Applied to my platform: every SNP judgement in GRPM and every mechanistic statement in an intervention report should carry an "evidence design type" label rather than an evidence-strength score.
  • ⭐⭐ "The grading was changed because a lettered ladder reads like a quality grade" is a hard constraint on my own content system. I had previously designed an "evidence strength A/B/C" label scheme for my articles — which is exactly the design this project criticises. Grading by evidence type (cell experiment / animal / observational human / randomised trial / systematic review) is more honest than grading by strength, because the former only declares what kind of claim a study can support, while the latter implies a comparison across study types that does not hold. What I need to change is not the label but the axis it is graded on.
  • ⭐⭐ The "evidence gap layer with testable experiment proposals" is the structure I should copy most urgently. My GRPM project has been stuck on one thing: a report can only say what is known, not what is still missing — because gaps have never been treated as first-class records. Listing the questions this report could not answer, and for each one naming the kind of study that would answer it, makes a report far more credible than ten more paragraphs of what is known. And it structurally defuses the hallucination problem: a gap is a schema field, so the model cannot invent one — it can only invent an answer, and an answer must attach to an existing piece of evidence.
  • ⭐ "Every claim carries its measurement conditions" is precisely the link missing from my intervention-report storage checklist. The same sentence — "magnesium improves sleep" — means one thing in magnesium-deficient adults and something else entirely in people with normal serum magnesium. The conditions under which evidence holds must live in the same field as the data, not in a paragraph of prose.
  • ⭐ Data under CC BY 4.0 plus code under MIT is a licensing structure I can build on directly — I do not even need to modify the code; pulling its study records into my content library as cross-references is legal as long as I attribute. It also ships both a JSON API and an MCP server, which means my article-topic tooling can plug it in as a controlled corpus source rather than scraping web pages.
  • ⭐ Maintained independently by a high-school student and his father, with a Zenodo DOI, an OpenAPI spec and an MCP server — the signal value here is that a teenager can deliver "evidence grading + machine-readable interface + formal citation + dual licensing". By that standard, requiring the same of my own expert packages is not excessive.
  • ⭐ Licensing note: of this issue's 121 entries, MIT and Apache-2.0 account for 93 and are safe to build on, while AGPL-3.0 (9) and GPL-3.0 (5) can be read but not copied, PolyForm Strict forbids commercial use entirely, and 4 are undeclared. mTOR Atlas's "data CC BY 4.0 / code MIT" is the cleanest licensing structure in this issue — this is what the right answer looks like when a one-person company picks a foundation.

2. hherb/bmlib: turning "can this paper be trusted" into programmable infrastructure — a four-state retraction verdict, Cochrane nine-domain risk of bias, and a PICO where every part is backed by the paper's own quoted passages

URL: https://github.com/hherb/bmlib ｜ ★2 ｜ AGPL-3.0 ｜ Python + Rust

What happened

26 commits inside the window (11-08 11:33Z to 11-08 20:30Z), whose thread is plugging holes in secret handling and cross-language consistency. The two newest commits make one concrete thing very clear: fix(secrets): #686's review — refuse another account's Windows credential, and require the interop t... and fix(secrets): one keychain item from both languages on every platform (#686) — the same secret must be one keychain entry from both the Python and Rust implementations, on every platform, and another account's Windows credential must be refused rather than used. On the same day there is also fix(agents): #717's review — pin the system prompts across languages, and say when a retry carries t... — the system prompts are pinned across the two languages, and a retry says what it is carrying.

  • ⭐ It turns "the plumbing every biomedical literature tool would otherwise rewrite" into a shared library, covering ingestion and lookup (PubMed, bioRxiv/medRxiv and OpenAlex synced with dedup by DOI/PMID; one paper reachable by PMID, DOI, PMC ID or preprint accession), retractions (Retraction Watch lookup and one four-state verdict: retracted / concern / clear / unchecked), full text (tiered retrieval via Europe PMC, Unpaywall and DOI, JATS XML parsing, PDF and HTML conversion, and one canonical text per paper with retrieval chunks), and embedding (snowflake-arctic-embed-l-v2.0 in process, with a per-paper vector store).
  • ⭐⭐ The assessment layer is the hardest part of this line: tiered study-quality assessment up to a Cochrane nine-domain risk of bias; PICO extraction whose every part is backed by the paper's own quoted passages; and transparency and bias analysis over five public APIs.
  • ⭐ The LLM layer is more thorough than most: a unified client for Anthropic, OpenAI, Ollama, DeepSeek, Mistral, Gemini and OpenAI-compatible servers, with streaming, tool calling, reasoning traces, context-window handling, JSON repair and chunking.
  • ⭐ Two languages that are a real port rather than a rewrite: the Python package bmlib and the Rust crate bmlib ship in the same release (0.12.0 / 0.3.0), and the Rust side adds UniFFI bindings for Swift and Kotlin mobile apps.
  • ⭐ Infrastructure is handled too: citation formatting, a database layer over SQLite and PostgreSQL, prompt templates, and API keys in the OS keychain rather than in config files.

Why it matters

  • ⭐⭐ "Every part of the PICO must be backed by the paper's own quoted passages" is precisely the hard constraint my evidence-based public-account content has been missing. When I write that a nutrient affects a marker, the AI hands me a neatly structured PICO — but the passage it quotes is often one my source never contained, and I put it in precisely because it looked well-formed. bmlib makes "every quote must be text from the paper" a code-level constraint: if the original passage cannot be located, the PICO does not exist. Applied to my pipeline: every AI extraction must carry the character span and sentence where it was located in the source, and without that it must not enter the report — the same line as assay's "a tool returning success is the provider's assertion, never proof" from the 11-08 issue, but with a more concrete implementation shape.
  • ⭐⭐ The four-state retraction verdict (retracted / concern / clear / unchecked) is the layer of evidence work that most deserves to exist in my workflow and least does. I never check whether a paper I cite has been retracted — and a retracted paper cited by my public account shows no anomaly to the reader. bmlib makes this step an automatic field at ingestion, not an ad-hoc check before publishing. The "unchecked" tier is especially honest: it admits "I looked and found nothing", rather than defaulting to "fine".
  • ⭐⭐ Making Cochrane nine-domain risk of bias a first-class library means something beyond medicine. The value of a nine-domain assessment is not that it yields a score; it is that it splits "how might this study be fooling me" into nine separately answerable questions. Applied to my GRPM reports and intervention plans: an SNP-to-phenotype association should have its own nine-item checklist (sample size, reproducibility, effect size, confounding control, publication bias, cross-ancestry consistency and so on), with each item marked assessed / not assessed / not applicable rather than collapsed into one overall verdict. This is the same thread as Calibrate's 2×2 dependency matrix and assay's refusal to output a single score from the 11-02 issue — but the nine domains are a list the medical community has already validated, and I should adopt it rather than invent my own matrix.
  • ⭐ "Pinning the system prompts across the two languages" is a direct warning for my multi-model content pipeline. My public-account content runs on several models (WorkBuddy on this machine already has a single OpenRouter key covering the whole family), and the same prompt set drifts across models and versions. bmlib's answer is to pin the prompt text in code, and to say what a retry carries. That is the exact inverse of what I recorded on 11-07 — "an answer that is wrong and you do not react to looks like a clean run": a retry must leave a trace.
  • ⭐ "Secrets live in the OS keychain, and the Python and Rust sides must resolve to the same entry" is a rule I can adopt directly. My 4P platform is Flask + SQLite and the GRPM report pipeline calls several model providers — API keys are currently scattered across environment variables and config files. "A credential accessed from several modules or languages must be one keychain entry, and another account's credential must be refused rather than overwritten" is a rule worth copying verbatim.
  • ⭐ "Reasoning traces as a first-class output" is a capability I simply do not have today. Every model call I make keeps only the final answer and discards the intermediate reasoning — so when a conclusion goes wrong, I cannot tell whether retrieval, reasoning or citation was at fault. bmlib makes reasoning traces a retrievable artefact, which is enormously valuable for the review and compliance side of content production.
  • ⚠️ The licensing is a hard wall: AGPL-3.0. I can read its design and copy its thinking, but I cannot make it a dependency of my own product unless that product is also AGPL. What should be carried over is the "structured evidence" specification, not the code — "every PICO part needs a source passage", "four retraction states" and "the nine-domain checklist" are specifications I can implement myself; bmlib's code is best read as a reference implementation.

  • ⚠️ Licensing is FSL-1.1-ALv2, not MIT. Why it matters

  • ⭐⭐ "SWE-bench Verified from 54% to 66%" is the most convincing evidence about a context layer I have seen in two years. The comparable projects I recorded — skill-diet's token cuts, sprag's 72.6% bill reduction — all optimise cost, and only this one gives cost (tool calls −46%, tokens −42%, time −60%) and outcome (+12 points of pass rate) together. Cases where cost and quality improve together are rare — they show that giving an agent better context is not trading quality for money but winning on both.
  • ⭐⭐ "A learning that points at code which no longer exists gets flagged" can become a fixed health check on my expert packages and prompts. My prompt library already contains entries that reference specific code paths or specific fields — and when the code changes, those entries silently stop working, with no one telling me. The corresponding action: before an expert package or prompt template is used, run a reference-validity check that flags entries pointing at things that no longer exist. The cost is near zero (a grep, or a schema validation), and it blocks an entire class of failures that "look like they are working but have been running off the rails for a long time".
  • ⭐⭐ "Quoting who decided it and why" is exactly the thing my platform does not have. When my intervention report is written to the database it records "conclusion + basis", but not "who set this basis and what the reasoning was at the time" — so whoever changes the rule later cannot know why the old rule existed and can only override it or route around it. Git blame is the code world's answer, and my platform needs the same thing.
  • ⭐⭐ "Telling me that another branch changed the same place right after it edited the code" applies to me even though I work alone. My "no teammates" status does not mean I have no concurrency: the 4P platform, the GLP-1 nutrition companion, the GRPM reports and the public-account content library all share some underlying conventions (ingredient dictionaries, marker definitions, report templates). A warning, delivered before a change lands, that another project is touching the same area should become a fixed check across my four projects.
  • ⭐⭐ "Letting one person use Trail just for themselves" fits my situation exactly. I have previously recorded risks like "any npm package may carry a suspicious postinstall script" and "installing something means executing third-party code". Trail offers the right posture: use it for yourself first, and do not push it onto a team that does not exist yet.
  • ⭐ MIT licensed, readable, modifiable and commercially usable — in contrast to vostride/agent-qa's FSL-1.1-ALv2 and ccch1mneyyy/dsh-Go's AGPL-3.0, Trail-Code has the cleanest licence of this issue's three agent-infrastructure picks. The shape "self-learning context layer" is one I can safely start building on under MIT.

3. Trends today

The clearest thread in this issue is that AI-generated artefacts are now systematically required to substantiate themselves — and this time the requirement reached three different layers: the conditions under which evidence holds, the replayability of execution, and the traceability of change. mTOR Atlas requires every claim to carry its measurement conditions and its failure boundary, and grades research by the type of conclusion the evidence can support rather than by quality; bmlib requires every PICO part to be backed by the paper's own quoted passages and turns retraction status into a four-state field; agent-qa stores knowledge as diffable files in the repository and keeps evidence for every run; Trail-Code flags learnings that point at code which no longer exists. Four teams from four different technology stacks, on the same day, independently did the same thing: make "what the AI said" and "what the AI did" both reviewable by a third party. This is the third stage of the same thread I recorded with assay (evidence packages recomputable offline) and lights-out (eight gates) on 11-08: the first two issues pushed the requirement down into the runtime; this issue pushes it down into the structure of the evidence itself.

The second thread, and the one that stings most for me, is that two projects this issue treat knowledge as something that rots — and both ship a concrete decay detector. agent-qa explicitly says it validates lessons from runs and retires stale knowledge; Trail-Code explicitly has a commit that flags learnings naming code that has gone. Two independent paths to the same judgement: knowledge without an expiry marker will eventually lie. And my current situation is precisely "knowledge only grows": my public-account article archive, GRPM's SNP judgement rules, the 4P platform's intervention-plan templates and the prompts inside my expert packages all keep expanding, and not one has ever been marked as expired. The single thing to do first is this: give every rule entering my content and report pipeline two fields — a last-verified time and whether what it points at still exists — and let a weekly task pick out the failures.

The third thread: this issue produced a licensing sample worth watching closely — using licence terms to express a business model. mTOR Atlas licences data CC BY 4.0 and code MIT, on the reasoning that the data should be citable and re-workable while the code only needs to be auditable; novu licences everything outside enterprise/packages as MIT and the rest under its own proprietary terms, using a directory boundary to draw the line between the open-source and commercial editions. Neither is "picked a licence at random" — both write "who I want to be able to use this, and how" into the licence structure. For a one-person company this suggests something very practical: my public-account content library can go CC BY 4.0 (attribution is enough for it to spread), while the 4P platform's code should stay closed-source and commercial — the same content, two sets of terms, declared separately. Of this issue's 121 entries, MIT and Apache-2.0 account for 93 (77%), but there are still AGPL-3.0 (9), GPL-3.0 (5), one PolyForm Strict (research and non-commercial only), one FSL-1.1-ALv2 (commercial use needs a separate agreement) and 4 undeclared — this list belongs on the first line of any foundation-selection document, and it should be read before the work starts, not after.

The fourth thread, a note to myself: the most valuable thing in this issue is not any single project but three assertions I can act on tonight. First, mTOR Atlas's "grade evidence by study design, not by quality" and its self-criticism that "a lettered ladder reads like a quality grade" — this directly shows that the "evidence strength A/B/C" label scheme I designed for my articles is graded on the wrong axis, and it should be re-cut as a type axis (cell / animal / observational human / randomised trial / systematic review) rather than a strength axis. Second, bmlib's three rules — "every PICO part needs a source passage", "four retraction states", "Cochrane nine domains" — are the ruler my GRPM reports and evidence-based articles are missing, and the medical community has already standardised it, so I should not invent my own. Third, agent-qa's "knowledge as reviewable files in the repository" and Trail-Code's "flag learnings that point at code which is gone" — together these are what my expert-package review process should look like: not asking the model to grade itself, but making every lesson a diffable, blameable record in the repo that can be marked expired. Concretely, four things to do: ① replace strength labels with evidence-type labels; ② attach the source span to every extraction; ③ give every rule a "last-verified time + does its target still exist" pair of fields; ④ run a weekly expiry scan. None of the four needs a new framework — four fields and a scheduled task.
