1. NVIDIA completes the other half of the skills ecosystem: SkillSpector scans "before you install", SkillEvaluator handles "whether it works after you install"

URL: https://github.com/NVIDIA/SkillSpector ｜ ★27,568 ｜ Apache-2.0 ｜ NVIDIA's official security scanner for agent skills: 71 vulnerability patterns spanning 17 risk categories (prompt injection, data exfiltration, privilege escalation, supply chain, MCP tool poisoning, memory poisoning and more), a two-stage analysis of static analysis plus optional LLM semantic judgement, and the scan never executes the target skill

What happened

  • 12 commits today plus the v2.13.7 release (2026-11-24 05:58). This is the formal version published that day, and the release notes state verbatim that it comes from main at 2d0c6ddcb, and that "the previous release used the 2.13 maintenance branch. The changes below include earlier work on main and fixes merged after 2.13.6 shipped."
  • The centre of gravity of this issue's changes is making the command and source boundary determinations solid: fix(cli): report recursive root scope exclusions (recursive root scope exclusions must be reported explicitly rather than silently skipped), fix: report RP3 at the manifest version field (RP3 must be reported at the manifest's version field), fix(ingestion): keep host Git templates out of URL scans (scanning a Git URL must exclude the host's own Git templates, otherwise it produces false positives), and test: count AST parses only for the scanned fixture (AST parse counts apply only to the fixture actually being scanned).
  • The distribution pipeline was connected at the same time: ci: publish SkillSpector releases with PyPI Trusted Publishing and ci: publish existing GitHub release distributions to PyPI — from today, GitHub Releases and PyPI are aligned automatically through trusted publishing, and installing the package no longer requires a manual sync.
  • First-hand figures from the README: in the 31,132-skill subset of its research dataset, 26.1% contain vulnerabilities and 5.2% show likely malicious intent; the scanner covers 71 vulnerability patterns across 17 categories (prompt injection, data exfiltration, privilege escalation, supply chain, excessive agency, output handling, system prompt leakage, memory poisoning, tool misuse, rogue agent, anti-refusal, trigger abuse, dangerous code AST, taint tracking, YARA signatures, MCP least privilege, MCP tool poisoning).
  • The scan does not execute the target skill: static analysis plus optional LLM semantic judgement (--no-llm keeps it fully static), with output as terminal, JSON, Markdown or SARIF reports and a 0–100 risk score; SC4 queries OSV.dev live for real-time CVE data and falls back to offline automatically; a baseline mechanism suppresses known findings by glob rule or fingerprint so re-scans surface only new problems.
  • Officially it is positioned as the first gate of the NVIDIA Verified Skills pipeline: scan → evaluate → sign, with only skills that pass entering the NVIDIA skills catalog.

Why it matters

  • This one cashes out a judgement I recorded last issue. Last issue I wrote that "if my 4P expert packages stay at the level of a Markdown checklist, I will fall a tier behind" — today NVIDIA wrote the concrete standard for "that tier" as code. My expert-manager skill packages currently rely on human judgement for quality; this repository offers an executable threshold: scan 71 risk categories before installation, and be able to evaluate afterwards. That means every expert package I publish should go through SkillSpector first, rather than shipping and waiting for users to report problems.
  • The figures "26.1% contain vulnerabilities, 5.2% look malicious" are a direct warning for someone in my position, doing content and doing skills. When I republish, recommend or wrap other people's skills in my WeChat article and skill packs, I am effectively vouching for a third party. If a quarter of the skills I cite carry vulnerabilities, then my "knowledge sharing" brand is amplifying risk without knowing it. The fact that the scanner does not execute skill code and does not upload content is what makes me willing to put it into a production workflow.
  • The "does not execute" boundary deserves to be remembered on its own, because it decides whether this tool can enter CI. A common flaw in security scanners is "to analyse more accurately, run the thing being scanned once" — which is exactly putting untrusted code onto my machine. SkillSpector is explicitly static analysis only, and even the LLM judgement merely reads file contents. That is the same kind of restraint I have held to with "zero AI hallucination, no unauthorised actions".
  • It and my second pick are the two halves of one ecosystem, and that pairing is itself the signal. The last two issues of this daily talked about the skills ecosystem purely in terms of "how to write more skills"; from today it is about "how to insure skills". Skills are turning from prompt fragments into engineering assets that need a CI gate — I wrote that sentence only last issue, and this issue it has a concrete implementation.

2. Skills need a health check-up too: SkillEvaluator v1.2.0 turns "does this skill actually work" into an automatable gate

URL: https://github.com/NVIDIA/SkillEvaluator ｜ ★4,504 ｜ Apache-2.0 ｜ NVIDIA's multi-tier evaluation framework for agent skills: 500+ static rules that run without an LLM key, a reusable CI template that wires quality and security gates straight into the repository, plus weighting and de-duplication to spot skills with overlapping functionality

What happened

  • 8 commits today plus the v1.2.0 release (2026-11-24 07:15). The theme of the release notes is "bring clearer evaluation results and stronger security checks into your skills workflow", with three headline items: an exemption mechanism for reviewed command hooks (--hook-waivers, which waives only an exact matched reviewed package while preserving all other findings and coverage gaps), GitHub Actions annotations, and more reliable agent evaluation.
  • The most telling commit in this issue is fix(nemo-gym): score multi-step episodes and keep step evidence — multi-step episodes are now scored correctly and the evidence for each step is retained. That solves a very practical problem: previously, when a skill finished a multi-step flow, evaluation only looked at the final outcome and there was no way to locate which step went wrong when something failed.
  • Another commit, fix(security): accept unrequested SkillSpector dependency metadata, shows that it and the SkillSpector from my first pick are two links of the same pipeline: SkillEvaluator v1.2.0's security checks depend directly on SkillSpector 2.13.6 (release notes verbatim: "SkillSpector 2.13.6, bounded YAML/JSON parsing and tighter scanner configuration improve validation of untrusted s...").
  • The three-tier structure: Tier 1 is pure static analysis — 500+ rules and detection patterns with no LLM key required (skillevaluator validate ./my-skill --tiers 1); a full run adds de-duplication (identifying skills with overlapping functionality) and live agent evaluation (measuring skill lift by comparing a run with the skill against a run without it).
  • It also provides a compatibility checkup: since v1.0.1 there is a built-in HarnessCheck that verifies whether a skill will be correctly discovered across six hosts — Claude Code, Codex, Copilot CLI, Hermes, OpenClaw and OpenCode — checking discovery paths, frontmatter, description and content length limits, invocation settings and plugin components, so a skill is not silently ignored, rejected or truncated by the host.
  • The official paper is on arXiv (number 2608.20614), and a copy-paste CI template is provided, with the integration path documented as "without building or maintaining evaluation code".

Why it matters

  • "Compare a run with the skill against a run without it" is where it is more sophisticated than its peers, and it is exactly what I can use. The hard part of skill evaluation has never been "did the skill run through", it is "did installing it actually make things better". That A/B definition maps precisely onto the central question of my GLP-1 nutrition companion: after adding the "morning and evening dual-cup plan" skill, did the accuracy of the nutrition advice and the adherence of the user actually change? What I do now is "I feel the plan got better", which methodologically is no evaluation at all.
  • HarnessCheck covering six hosts hits my "delivery across many fronts" constraint head on. My skill packages have to work in WorkBuddy, in WeChat article form, and potentially in third-party CLIs. "A skill silently ignored or truncated by the host" is a failure mode I have never systematically ruled out — when a user says "nothing happens", my first thought is that the content is bad, when the more likely cause is that the description exceeded the length limit or that a frontmatter field name is wrong. This is the cheapest kind of debugging there is.
  • Retaining step evidence for multi-step episodes is the same line as the "a failure must be able to say which link broke" I recorded last issue. I see the same class of fix once more today, in conductor-oss/conductor (a SQLite queue pop statement matched on the wrong condition, so a message with the same id on a different queue could be wrongly marked as popped). Two repositories fixing the same class of bug on the same day says that "localising a failure to a specific step" is becoming the industry default. My platform still cannot say whether a failed recommendation came from missing data, an inapplicable algorithm, or an out-of-bounds statement.
  • It has 500+ static rules that need no LLM key, and for a one-person company limited to eight hours a week that is decisive. Any evaluation step that costs extra API keys or extra billing is one I probably will not actually keep running long-term. Only gates that run offline survive in practice — that is the most useful product lesson I have taken from the "exam hook plus a lightweight nutrition AI core" niche I picked: every time a workflow gains a step that costs money or needs a secret, the actual execution rate halves.

3. Evidence grading pushed into the retrieval layer: med-research-mcp makes an agent know the weight of the card in its hand before it answers

URL: https://github.com/emilkrebs/med-research-mcp ｜ ★1 ｜ MIT ｜ An evidence-graded medical literature search MCP server for AI assistants: one search merges four databases — PubMed, Europe PMC, ChinaXiv and RussiaRxiv — and labels every result with its study design and retraction status straight from NLM metadata, with no LLM calls, no account, no telemetry

What happened

  • 1 commit today plus the v0.8.1 release (2026-11-24 10:36). The release notes state two things plainly: it is now listed in the official MCP registry (under io.github.emilkrebs/med-research-mcp, which MCP clients and directory sites read), and the library exports Article under the name its guide uses. Tool behaviour is unchanged from 0.8.0, with inputs and output the same.
  • Its core mechanism is that study-design labels come directly from NLM metadata rather than being guessed by a model: every result states what kind of study it is, where that design ranks in the evidence hierarchy, and whether it has been retracted or corrected. When metadata is missing it is labelled unknown rather than glossed over — the README's words are "No guessing: a record without metadata says unknown".
  • The design grading criterion the README gives is the Oxford CEBM levels of evidence: from 5 (systematic reviews and randomised controlled trials) down to 0 (animal and lab studies, retracted papers). It ranks the design, not the quality — a level-5 systematic review is not thereby a high-quality study.
  • Four databases in one search, merged and de-duplicated: tirzepatide[tiab] AND "sleep apnea"[tiab] returns 143 records on PubMed and 142 on Europe PMC (both figures come from the v0.8.0 release notes, demonstrating that field tags now work across the two databases).
  • Full text is fetched three ways: open access, institutional proxy, or DOI resolution; ChinaXiv and RussiaRxiv go through ChinaRxiv's machine translation, and the README warns explicitly that "its English text is machine-translated, and it wrote most RussiaRxiv abstracts itself; check the original record before relying on a dose, population or outcome."
  • Three agent skills ship alongside: med-research (the workflow itself — writing precise PubMed queries, reading the labels, classifying unlabelled papers, and reporting findings along with how certain they are), med-research-ebm (critical appraisal, loaded only when a conclusion will rest on a single paper: risk of bias, effect sizes, heterogeneity, causation, applicability), and med-research-setup (installation and troubleshooting).
  • No LLM calls, no accounts, no telemetry; the server runs on your machine, and queries go only to the databases you searched (NCBI, EMBL-EBI, ChinaRxiv) — though a full-text request may send an article's id or DOI to services you did not search (NCBI, Europe PMC, ChinaRxiv, Unpaywall, doi.org, publisher sites, institutional proxies). The README states plainly: "Don't put anything that identifies a patient into a query."
  • The repository carries full compliance documentation: docs/compliance.md records intended use and data flows, and there is a benchmark that grades how well models answer biomedical questions with the server present.

Why it matters

  • "Label it unknown when unsure rather than guessing" is the discipline I most need to copy for evidence-based content. The easiest mistake I make when writing nutrition intervention articles is smoothing away the qualifier "this study had a small sample" — and what the reader receives is a clean conclusion. This tool turns "how strong is this evidence" into a field on each record rather than an adjective in the author's tone. My "evidence first, references attached, zero AI hallucination" can only become a verifiable mechanism rather than a self-imposed intention if there is an evidence-grade field at the data layer.
  • "It ranks the design, not the quality" is the sentence that shuts down the kind of over-reading I am most prone to. I used to treat "systematic review" as high-grade evidence outright, but CEBM's level 5 covers systematic reviews and randomised controlled trials, level 2 covers cohort or case-control studies, and level 0 covers animal and lab studies and retracted papers — so if an article cites level-0 evidence, my old habit would easily turn it into "research shows" in the WeChat article. This grading is a direct reminder: when citing, the design level has to be written out alongside it.
  • It connects to ChinaXiv and RussiaRxiv, two databases I had no idea existed. That was the most surprising piece of information today — Chinese preprints have an independent ChinaRxiv platform outside the Chinese Academy of Sciences system, and RussiaRxiv is a separate project. This directly affects the coverage of my searching: a meaningful share of evidence in Chinese nutrition and TCM directions lives in preprints, and conventional searches systematically miss them. I checked today, and found AndyZHENG0715/TCM-Sage (listed in this issue, a Chinese project) — a Chinese tool doing evidence synthesis that could connect to ChinaXiv would be a good complement.
  • "No LLM calls" is an architectural hint for my 4P platform. The division of labour between my three algorithm families (P4 local / DINGXIANG / JINGYAN) is essentially "deterministic code computes, the model phrases". This MCP makes "retrieval plus grading" a purely deterministic service, with the model only reading labels and assembling conclusions. That is exactly the pattern LesionAgent and SystemOneAgents kept pointing to last issue: numbers and verdicts should not be generated by the model. I can move this design directly onto my contraindicated-supplement and lab-indicator modules.
  • Honestly, it has 1 star and 1 commit today — it is a new project that has just entered the official registry. I am putting it in the picks not because it is mature, but because it turns "evidence-based" from a promise into a data structure — and that may matter more to how I produce content than its current maturity does.

What happened

  • 96 commits today plus the v2.37.0 release (2026-11-25 02:22) — the highest commit count of all 119 repositories in this issue. This is the 63rd version shipped by the repository (the README badge reads "Releases 63 shipped").
  • The architecture rule fits in one line: read one raw signal → grade every number → fuse across signals. Each analyser takes exactly one kind of signal (OxyDex takes SpO₂ and motion, ECGDex takes raw ECG, PulseDex takes RR intervals, PpgDex takes raw PPG, HRVDex takes HRV summaries, GlucoDex takes CGM, CPAPDex takes CPAP therapy data, EEGDex takes a Muse headband), and they then read each other through the shared bus and the fusion layer.
  • Every number carries an "evidence grade" — the dividing line between it and an ordinary sleep app. The README's words are "Every number carries an evidence grade". Why it matters

  • "Every number carries an evidence grade" is the layer I have been missing for two years of 4P precision nutrition. When I write a staged intervention plan, every value in it actually rests on evidence of uneven strength — but in my document I only wrote "value plus recommendation", and I never kept "how reliable is this number" as an independent field. Tepna puts it into the data model: any number computed from a raw signal has to travel with its evidence grade attached. That maps directly onto the "three evidence-strength columns" I noted last issue — I wrote it down, but it never reached the storage layer.
  • "One raw signal, one analyser" is a crucial decomposition for my health data. My GLP-1 nutrition companion currently mixes blood glucose, CGM, sleep, weight, waist circumference and diet records into a single evaluation logic. Tepna's approach is to separate them completely by signal type, let each compute its own metrics, and only join them at the fusion layer. That way a sensor dropping out or a poor-quality reading only affects its own path and cannot pollute the overall conclusion. That structure is far more robust than "one large model reads all the data" — which is exactly what I do now.
  • "Publishing its failures too" has the biggest leverage for my content business. When I write nutrition science popularisation, the most valuable pieces are often not "this works" but "this does not work, and here is why the evidence does not hold". Tepna maintains a dedicated "map of dead ends", publishing the paths that do not work in citable form. My "4P Precision Nutrition Watch" WeChat account and the "Cuncai Shang'an" Xiaohongshu account would gain a far sharper professional position if each issue could hand over a list of "which popular claims actually lack evidence" like this.
  • "No network enforced by CI" is the engineering constraint I most want to copy. I have always stressed "local first, do not upload user data", but in my 4P platform that is still only a spoken principle — nothing in it prevents some change from quietly introducing a telemetry SDK. Tepna turns the promise into a build that fails. The cost is low (one headless gate) and what it protects is my most sensitive asset: user health data.
  • Its 96 commits and one release a day is a reminder that my platform iterates far too slowly. The reason is obvious: I am one person with eight hours a week, split across the WeChat account, Xiaohongshu, the practical training cohort and the platform. What Tepna teaches is that it automated a great deal of the work (gates, the export census, rebuilding build outputs). With the same eight hours, a different level of automation means a different order of magnitude of output.

5. Agent workflow engines start fixing low-level bugs like "the queue hands the message to the wrong place": Conductor ships two versions in a day

URL: https://github.com/conductor-oss/conductor ｜ ★32,502 ｜ Apache-2.0 ｜ An event-driven agentic workflow engine providing a durable and highly resilient execution engine for applications and AI agents; in this window it released v3.34.1 and v3.34.2 and added an MCP server for workflows and agents

What happened

  • 8 commits today, shipping v3.34.1 (2026-11-24 10:59) and v3.34.2 (2026-11-25 00:31) back to back. The repository has been a fixture on the GitHub weekly star-gain charts (★32,502).
  • v3.34.2 fixes a correctness bug at the queue layer: the SQLite pop query previously matched on message_id alone, so a message sharing that id on a different queue could be marked as popped — or returned — by the wrong queue; the UPDATE is now scoped to its own queue_name. The release notes call it "a SQLite queue-pop correctness fix".
  • The same version also moves two HTTP status codes from 500 to 409/400: resuming a workflow that is not paused, or skipping a task that cannot be skipped, now returns a 409/400 with a clear message instead of a blanket 500. That is the act of separating "the caller got it wrong" from "the server broke".
  • v3.34.2 also carries a security action: the server image now pins the nginx version floor above the CVE-flagged 1.30.6-r0, so a rebuild cannot slide back to a vulnerable build (fix(docker): pin nginx floor above CVE-vulnerable 1.30.6-r0).
  • v3.34.1 fixes "the queue going quiet": Bump orkes-conductor-queues to 2.0.0.rc4 fixes a race that could leave a queue stuck and never polling again until the server was restarted; fix(agentspan): stop PLAN_EXECUTE silently dropping or misrouting valid plans fixes the agent planner silently dropping or misrouting valid plans — a plan with no validation used to short-circuit before on_success, and a pure gate plan (empty steps, validation → on_success) was rejected as "No JSON plan found." A plan is now valid if it has any of steps, validation or on_success; on_success runs even with no validation, and a dangling on_failure surfaces as a compile warning instead of vanishing.
  • The most notable new feature is feat(ai): MCP server for workflows and agents (#1827) — the workflow engine itself is now exposed as an MCP server. That means external agents can call Conductor's durable workflows directly as tools.
  • There are also operational commits such as fix(ci): make es8 e2e runner scripts executable and [CLOUD-1401] Restore the GA4 tag on conductor-oss.org (lost in the September site migration).

Why it matters

  • The conclusion I draw from "a message with the same id on a different queue can be taken by the wrong queue" is: the moment I implement my own task queue, I will make this mistake. In my 4P platform's Flask + SQLite back end, the calls into recommend.py and the DINGXIANG and JINGYAN integrations are all queued by my own code. "Match on the message id" is the most natural line to write, and it happens to be insufficient. Conductor, a project of 32,502 stars, only hit and fixed this at that layer — so I should write it as "queue name plus message id, doubly qualified" today rather than wait for it to become a bug nobody can trace.
  • "Change 500 to 409/400" — separating "the caller got it wrong" from "the server broke" — has concrete value for a one-person company. My 4P platform exposes APIs and will eventually connect to 4pwellness over MCP. If a caller passes an invalid parameter and receives a 500, the investigation starts in the server logs; the correct behaviour is to let the caller know immediately where it went wrong. That distinction saves a whole night of debugging in a small team.
  • "Silently dropping valid plans" is the one I most want to remember from this issue. Conductor's agent planner hit both "a plan short-circuits because it has no validation" and "a pure gate plan is rejected as no JSON plan found" — both cases amount to "something was there, and it was thrown away". Last issue I noted "a failure must be able to say which link broke", and today I see the same class of fix in two different repositories (the other being SkillEvaluator retaining evidence per step for multi-step episodes). Turning "dropped" into a compile warning rather than silence is, I think, the single most important change in agent infrastructure in the second half of 2026.
  • The new MCP server is the first clear signal that "workflow engines are turning into agent tools". Workflow engines used to be for back-end services; now the engine exposes itself as an MCP server, which means my 4P platform's algorithm orchestration layer may not need me to write an MCP adapter at all. I already connected the 4pwellness MCP connector last issue — if the orchestration layer standardises, the delivery cost of something like the "4P precision nutrition thousand-pioneer project" batch intervention plan drops by an order of magnitude.
  • Its fixing a "quietly stalled" queue and pinning a nginx version floor to stop a CVE regression, both shipped the same day — that is the everyday of mature infrastructure. I tend to treat "added a new feature" as progress on my platform, but in Conductor's two releases the thing worth celebrating is one bug and one version pin. The contrast reminds me: what my platform lacks is not features, it is this kind of "quietly getting it right" maintenance rhythm.

3. Trends today

  • The skills ecosystem is turning from "prompt fragments" into "engineering assets that need a CI gate" — and today that tier was filled in on both halves at once. The last two issues I recorded were all about "how to write more skills"; today NVIDIA offers both the pre-installation scanner (SkillSpector, 26.1% of skills contain vulnerabilities, 5.2% look malicious) and the post-installation evaluator (SkillEvaluator, 500+ static rules, a CI template and compatibility checks across six hosts). That pairing means a "skill pack" now carries the supply-chain status of a software dependency: scanned, evaluated, signed, versioned. For my own expert packages, it means I can no longer treat a skill checklist as a Markdown deliverable — it needs a gate.
  • "Localising a failure to a specific step" is becoming the default for agent infrastructure, and today two repositories fixed the same class of bug. SkillEvaluator retains the evidence for each step of a multi-step episode (fix(nemo-gym): score multi-step episodes and keep step evidence); Conductor turns a dropped valid plan into a compile warning instead of making it vanish (stop PLAN_EXECUTE silently dropping or misrouting valid plans). The common enemy is silence — silent dropping, silent truncation, silent rerouting. This picks up exactly where I left off last issue with "a failure must be able to say which link broke": a system that cannot say where it broke has not failed yet, it simply has not been noticed.
  • "Taking the generation of numbers away from the model" showed up today in three unrelated domains. SkillSpector's analysis is entirely static (it does not execute the target code), med-research-mcp's evidence grading comes entirely from NLM metadata (no LLM calls), Conductor's queue correctness comes from SQL condition scoping (not from model judgement). Three unrelated projects all doing the same thing: let the rules that can be reproduced produce the verdict, and let the model only phrase it. I now lean more strongly toward blaming the framework rather than the model for my local Ollama qwen2.5:7b's mediocre results — but only if I first draw the line between computing and judging.
  • The centre of gravity in the health and nutrition line is visibly converging on three things: local-first, evidence grading and auditability. Tepna gives every number an evidence grade and turns "no network" into a CI gate; biomarker-tracker gives each of its 81 markers a source (Europe PMC, EFSA, the original paper) and does all computation in code; med-research-mcp encodes CEBM levels directly into the retrieval layer. None of these three argues for a smarter model — all three argue for a harder evidence chain. For my GLP-1 nutrition companion, the reference value of this line may exceed any single model upgrade.
  • A gap in my knowledge that I had no idea existed until today: Chinese preprints have their own independent ChinaRxiv platform. med-research-mcp's README states plainly that ChinaXiv comes from ChinaRxiv, an independent project outside the Chinese Academy of Sciences system, and that its English text is machine-translated, with most RussiaRxiv abstracts written by it itself. This means that in Chinese nutrition and TCM directions, conventional PubMed searching systematically misses a whole block of evidence. My plan for the next issue is to find out how much nutrition content this database actually holds — if the volume is meaningful, it is a new seam of topic ideas for my WeChat account.
  • One quiet but important observation: local-first has moved from "a selling point" to "a verifiable engineering constraint". Tepna enforces no-network with a build that can fail; biomarker-tracker is explicit that there is "no account, no cloud, no telemetry, telemetry none", with each person's data in a folder on their own computer and the page only able to talk to itself and two research databases; med-research-mcp runs on your own machine and calls no LLM. All three share one property: they do not promise they will not go online — they make the promise fail. I have always stressed "local first, no uploading of user data" for the 4P platform, but that is still only a sentence — that sentence now has three implementable forms.
