1. ovumcy/ovumcy-web: turning "can this prediction be trusted" into a gate in code — it does not merely compute the fertile window, it withholds the whole thing until there is enough data

URL: https://github.com/ovumcy/ovumcy-web ｜ ★133 ｜ AGPL-3.0 ｜ Go ｜ a self-hosted menstrual cycle tracker: one Go binary or container, SQLite or PostgreSQL, no accounts, no analytics, no telemetry

What happened

54 commits inside the window (11-03 08:20Z ~ 11-04 02:00Z), with the main thread being the refactor of the forecast-display gate (forecast notice) and reliability fixes to the calendar feed.

  • The core action this issue is the clean separation of "display" from "computation": the document docs/cycle-prediction.md states plainly that "whether a given estimate is shown is a separate gate", and describes "the one that withholds the whole fertility half until the account completes three cycles" — until the user has logged three cycles, the entire fertility half (ovulation date and fertile window alike) is simply not shown. The gate itself was then pulled into a single flag (refactor(dashboard): drop the forecast notice in its flag, not per site) rather than being judged separately at each surface.
  • "One rule decides it, and every surface reads the same answer": completed-cycle count, individual cycle lengths, last period start, the dashboard's cycle day, the calendar's "recorded" marker, statistics insights and luteal-phase inference — six readings must agree; two screens cannot disagree about the same history. The rule itself is spelled out in unusual detail: period days fewer than five clear days apart form one bleeding episode; an episode opens a cycle when it has any of: two or more consecutive non-spotting period days; a non-spotting day the owner marked as a cycle start (and did not mark as uncertain); or a lone non-spotting period day dated today or yesterday (the period may still be running).
  • "Spotting never opens a cycle, even when marked": a day whose flow is spotting, or whose only bleeding signal is the Spotting symptom with no flow chosen, does not start a cycle even if marked. A start marked as uncertain ("Mark anyway" after the short-gap warning) counts as no mark. A start dated in the future is ignored.
  • Document and implementation are hard-bound together: every worked example in the document is mirrored 1:1 by automated reference tests (internal/services/cycles_reference_test.go), so the documentation and the implementation cannot silently drift apart. This is what "evidence-bound claims" looks like when it is written in code.
  • The boundary is stated in the very first line: a > [!IMPORTANT] callout reads "This is a calendar-based estimate, not medical advice and not a method of contraception", and enumerates what it cannot do — it cannot detect ovulation, does not account for illness, stress, medication or hormonal conditions, and is unreliable for irregular cycles. The document is 38 KB, the security-invariants file 109 KB, and there is a dedicated 23 KB GDPR chapter.

Why it matters

  • "Computing it" and "showing it to you" as two separate gates is precisely the layer my GRPM report and 4P intervention report are missing. My algorithms can work out "this person is low in vitamin D, has poor magnesium absorption and is borderline on B12" — but I have no ruler for deciding when those statements may be spoken and when they must be withheld. Ovumcy's answer is: if the data is not sufficient, do not display that section at all — rather than display a low-confidence number. Applied to my case: when GRPM's 40 SNPs only cover part of the relevant loci, the report should not deliver a half-formed conclusion like "your folate metabolism is impaired"; it should state explicitly that the evidence base for that section is insufficient. This is the same family of thinking as aureproof's "the gate can return inconclusive" from the previous issue, but ovumcy goes further: inconclusive is implemented as displaying nothing, not as displaying "inconclusive".
  • "No fertile window until three cycles are logged" can be copied straight into a product rule. My supplement plans have exactly the same problem: the moment a user finishes the intake questionnaire, the algorithm's intervention advice is really just a guess. Using "N cycles completed / N data fields filled" as the display gate is far more effective than writing "for reference only" in the report — nobody reads the latter.
  • ⭐ Mirroring documentation in reference tests, 1:1, lands directly on the pain point of my evidence-bound content. My WeChat articles (4P Precision Nutrition Watch, Health 100 Observation) must carry references and must contain zero AI hallucination — but I have no mechanism that keeps "the mechanism described in the article" and "the algorithm actually running in the platform" in sync. Ovumcy turns every worked example in the document into a test case, so if the document changes and the code does not, CI goes red. This one can be ported directly to GRPM: every SNP interpretation rule goes into the documentation, and every rule gets its own test.
  • "Six readings must agree; two screens cannot disagree about the same history" is textbook data consistency. For my 4P platform: the same person's lab markers must be identical across the dashboard, the AI advice, the Excel export and the intervention report — and today those four are written by four separate code paths. Ovumcy puts "one rule decides it, and every surface reads the same answer" on the first screen of its documentation. That convention is worth copying.
  • "Spotting never opens a cycle, even when marked" — expressing an exception as an absolute prohibition rather than a priority ordering. The grotyx note from the previous issue — "when the evidence only supports association, the wording must not be upgraded to causation" — is the same species of rule: give the prompt and the algorithm hard veto conditions; they are far more reliable than adding "priorities".
  • AGPL-3.0: readable, not copyable. For a one-person company this does not stop me learning the design, but if I ever wanted to lift its cycle-prediction algorithm into the female-cycle module of my GLP-1 nutrition companion, that licence is a hard wall. If I do, I need to look for a separate "personal health use only" path from ovumcy.

2. vercel-labs/agent-desktop: letting an agent operate the desktop without "guessing coordinates from a screenshot" — it reads the OS accessibility tree and hands every actionable element a stable reference, and today it added MCP

URL: https://github.com/vercel-labs/agent-desktop ｜ ★12,940 ｜ Apache-2.0 ｜ Rust ｜ computer use for AI agents across macOS, Windows and Linux via the OS accessibility tree, shipping as both a CLI and a C library

What happened

6 commits inside the window (around 11-03 23:13Z) — but this is the first release after it took the top of the GitHub trending chart, and the release itself carries a signature move.

  • ⭐ The most important commit this issue is feat: agent-desktop mcp (#519) — it brings desktop operation into MCP. Any MCP client (Claude Code / Codex / Claude Desktop) can now drive real desktop applications directly, with no need for each vendor's private extension protocol. For a product you intend to sell, that step matters more than ten thousand stars.
  • The core mechanism is "read the accessibility tree → issue stable references → act → read again to verify": agent-desktop snapshot --app Finder -i lists the app's interactive elements and gives each one a ref (of the form @s8f3k2p9:e8, with the reference carrying its snapshot id); the agent clicks or types against a ref and then reads the UI once more to confirm the result. "The loop lives in your agent; agent-desktop has no model inside."
  • Failure modes are explicit, not guessed: a stale reference returns STALE_REF, an ambiguous target returns AMBIGUOUS_TARGET, and a bare @e8 without a snapshot id returns INVALID_ARGS outright. Actions are headless by default — no pointer movement, no focus change — and physical input requires passing --headed explicitly.
  • The output is a JSON envelope carrying a complete boolean: {"version":"2.6","ok":true,"command":"snapshot","data":{"app":"Finder","snapshot_id":"s8f3k2p9","ref_count":59,"complete":true,"tree":{...}}}. That complete field is a self-attestation of completeness for the caller — the same family of design as the shown N of M line I recorded from aft on 11-03.
  • The architecture deliberately isolates platform differences: both the CLI and the C library run through agent-desktop-core and a PlatformAdapter trait, with exactly one platform crate chosen at compile time, reaching the target app through the macOS AX API, Windows UI Automation, or Linux AT-SPI. It can be called in-process from C, Python, Go or Node.
  • Two macOS edge-case fixes also landed: the cursor overlay now draws above menus and system panels (fix(macos): draw the cursor overlay above menus and system panels), and list rows that only their container can select are now selected correctly (feat(macos): select list rows that only their container can select). Both are the kind of corner that makes real desktop automation maddening.

Why it matters

  • "Not guessing coordinates from a screenshot" is the watershed for this whole generation of tooling. Most agents operating a GUI today work like this: take a screenshot, let the model guess pixel coordinates, click, screenshot again to check. That chain breaks silently whenever a button shifts, the window scrolls or the theme changes. Ovumcy deserves its own note below, but agent-desktop's point is more direct: the OS accessibility tree gives you "this button is named this, its role is button, its available action is Click" — semantics, not coordinates.
  • ⭐ The most transferable artefact for me is that complete field together with the explicit STALE_REF / AMBIGUOUS_TARGET failures. My 4P platform's lab-report OCR pipeline currently treats a failed extraction as "skip this field and continue" — which is exactly how you end up with a report claiming 24 risk dimensions when only 18 were actually recognised, without the report itself knowing. agent-desktop's rule: either return the complete result with complete: true, or tell the caller explicitly that a target was ambiguous and a reference had gone stale. This is the same rule as aft's "no shown N of M means the list is complete", read from the other side.
  • "Headless by default: no mouse movement, no focus stealing" is decisive for any agent that runs on a user's machine. Nobody accepts a background agent that grabs their mouse while they work. The same principle applies to my 4P platform: anything that runs locally on a user's device must be reversible, visible and non-intrusive by default. That belongs in the requirements document.
  • ⭐ Three platforms each going through their native OS interface, with one thin adapter trait behind a single core — this is exactly the structure I should copy when wiring up the 4pwellness.org.cn MCP connector. Today my MCP tools are hand-written one by one, each handling its own parameters and its own errors. agent-desktop's approach: every tool shares one core, and platform differences live behind a single trait.
  • Apache-2.0, from Vercel Labs: readable, modifiable and commercially usable. It also ships both a CLI and a C library and explicitly supports in-process calls — which suits my SaaS shape (running on the server) better than desktop-only options.
  • Note how bluntly it states the privacy caveat: "Snapshots, clipboard reads, screenshots, command output, and debug artifacts can contain private desktop content. Keep them out of public logs and uploads." A snapshot is literally what is on the user's screen, clipboard included. That is a direct reminder for the log-redaction work on my 4P platform.

3. zarnautovic/tdeemon: writing the hard floors of a calorie or supplement plan into code — the AI may propose but never execute, and there is a floor nobody can lower

URL: https://github.com/zarnautovic/tdeemon ｜ ★0 ｜ AGPL-3.0 ｜ Go ｜ self-hosted, AI-first nutrition tracking with an adaptive TDEE, where an AI coach may adjust goals within limits enforced in code

What happened

22 commits inside the window (11-03 ~ 11-04 02:24Z), with the main thread being the second interface redesign (redesign 2) — proceeding screen by screen from the app shell (day / foods and recipes / settings / progress, PRs #252–#256). Note this is an early-stage project: the README states plainly that only the server skeleton, the database layer, the API contract and the web app's frame exist so far.

  • ⭐ The most valuable material sits in docs/limits.md, which defines three levels of limits, the lowest of which "nobody can lower":
    1. A floor in the code that nobody may lower, the administrator included: never 800 kcal a day or less; never less than 0.8 g of protein per kg of reference mass; never a rate faster than a loss of 1.5% or a gain of 1% of trend weight per week (a convention, so that no configuration allows a plan far beyond the literature's ranges); no plan at all for someone under 18; and no change that starts or deepens a loss of weight below a BMI of 18.5 by the current trend weight — this covers a cut, a recomp below 0, a calorie target implying a loss, or one that lowers the weekly average before calibration trusts the TDEE — nor any goal or milestone weight below it. A loss already under way when the trend crosses 18.5 is not changed without the user: the autopilot applies no further steps, proposes maintenance instead, and flags it in the summary.
    2. The instance's limits, set by the administrator in configuration, forming the outer bound for everyone on that instance.
    3. The user's limits, within the instance's, starting at the "Default" column; the user may tighten them freely, but loosening one — up to the instance limit and no further — takes an explicit confirmation in a web session.
  • A single function, Validate, checks every change of a plan against all three, and says which rule a change breaks, together with the limit and the proposed value. "An AI client can propose a change of the user's limits, but only the user applies it, from a web session, with the confirmation a loosening takes" — the rest of a proposal is still held to the limits as it leaves them, so a faster cut arrives together with the limit that permits it. Only the user sets the profile.
  • Logging is never limited and never judged: a 4,000 kcal day is simply logged. "Limits apply to plans only." That distinction matters: limits constrain advice, not record-keeping.
  • Adaptive calibration carries confidence intervals (learning real energy expenditure from intake and weight trend), and the AI can only change a plan through a proposal the user accepts. The documentation is explicit that this is "not medical advice", and it lists the cases that belong with a clinician.
  • The technical base matches Gordon's own shape almost exactly: one container, one SQLite file, multi-user (one household shares a kitchen and its foods and recipes, while each member's meals, weight and plan stay their own); an MCP server any MCP client can drive with any model (Claude Code, Codex, Hermes, a local model), with coaching sessions that read the numbers exactly as tdeemon computes them.

Why it matters

  • ⭐ "The AI may propose; only the user may apply, and loosening takes a second confirmation" is almost exactly the rule my 4P supplement platform and the GLP-1 nutrition companion should adopt — and today mine does the opposite. In the current implementation, when the AI sees a signal that a lab marker has deteriorated, it recomputes and writes a whole new morning/evening cup plan into the database; the user then sees a result that is already in effect. tdeemon's three-tier limits plus a Validate function plus propose/execute separation is the layer I am most missing.
  • ⭐ "800 kcal floor / 0.8 g protein per kg / no more than 1.5% weekly loss / no deepening a loss below BMI 18.5 / no plan under 18" — these five are the hard floors I should cite directly when building the supplement-plan engine. In my current engine these constraints are scattered natural-language constraints inside a prompt, which an LLM can be talked out of. tdeemon's approach is to write them as floors in code that even the administrator cannot lower. These five also happen to match the evidence-based line my public accounts have consistently held.
  • The split "limits apply to plans, never to logging" is the cleanest handling of this problem I have seen. A user occasionally eats 4,000 kcal and should not be scolded by the system — but the system must never derive a 1,200 kcal plan from that meal. My platform currently mixes these two things together.
  • "Validate says which rule was broken, what the limit is and what the proposed value is" — that is an error message written for an AI, not for a human. This matters enormously: when an AI's plan violates a bound, the error message has to let it correct itself rather than merely saying "invalid". My 4P platform's validator currently only returns "failed", leaving the LLM to guess how to fix it.
  • "At a BMI below 18.5 the autopilot stops stepping and proposes maintenance instead" — the boundary where automation stops short of a dangerous action. Applied to my case: when a user's signals indicate a supplement should be stopped or the case referred, the system should propose and warn rather than execute.
  • "One container + one SQLite file + multi-user + MCP" is a package whose architecture is nearly identical to my GLP-1 nutrition companion. It can be compared against my own design directly. AGPL-3.0 means the code can be read but not copied — the design ideas are fair game.
  • ★0 stars, and there is no reason to skip it on that basis. This is the eighth zero-star entry among the 119 this issue, and the information density in docs/limits.md exceeds that of half the high-star projects here. The previous issue (11-02) already confirmed the pattern: low-star projects remain the best seam to mine.

4. cyanheads/clinicaltrialsgov-mcp-server: turning 600,000 clinical-trial registry records into an MCP service — and stating in the tool description that "patient matching" does not check inclusion criteria

URL: https://github.com/cyanheads/clinicaltrialsgov-mcp-server ｜ ★100 ｜ Apache-2.0 ｜ TypeScript ｜ an MCP server for ClinicalTrials.gov, the NIH trial registry: 7 tools / 1 resource / 1 prompt / 1 skill, over STDIO or Streamable HTTP, no API key required

What happened

11 commits inside the window, and this issue shipped version 2.11.0 (chore(release): 2.11.0 — published skill, nctIds fitting, site-bound locations).

  • Seven tools cover the full path from "find a trial" to "read the results": clinicaltrials_search_studies (full-text and field-specific queries, status/phase/geographic filters, pagination, sorting, field selection), clinicaltrials_get_study_record (the full protocol record by NCT ID, with optional location/outcome/reference caps), clinicaltrials_get_study_count (count only, without fetching data), clinicaltrials_get_field_values (discover the legal values of an API field, with the number of studies per value), clinicaltrials_get_field_definitions (resolve legal field names), clinicaltrials_get_study_results (posted results: outcomes, adverse events, participant flow, baseline), and clinicaltrials_find_eligible (matching patient demographics and conditions to candidate recruiting trials).
  • ⭐ That last tool's own description carries a self-limitation: clinicaltrials_find_eligible is described as "match patient demographics and conditions to candidate recruiting trials, without checking inclusion/exclusion criteria". "Matching" and "qualifying" are explicitly separated — it matches "the kind of trial this person might fall into", and does not claim this person meets the entry criteria. This is precisely the line an AI medical tool most easily oversteps, and it is written into the tool description rather than buried in documentation.
  • Lists in the resource layer are capped: the clinicaltrials://{nctId} resource returns the study JSON with "capped lists and results replaced by counts" — when a list is truncated, it is not silently truncated; the results portion is replaced by a count.
  • Version 2.11.0 itself brought three things: a "published skill" (a skill shipped with the package for the first time), "nctIds fitting" (packing long NCT ID lists into the output), and "site-bound locations" (trial site information). This comes with an explicit technical handling: an over-long parameter returns a request_too_long error rather than being silently truncated.
  • One very specific correctness fix landed this issue: fix(tools): name the AREA[] names the advancedFilter case correction skips — certain case variants of the advanced filter are skipped by that correction, and the tool now names those fields explicitly. The accompanying test is test(get-study-results): fold every line break in the linear-growth oracle — every line break in the linear-growth assertion is folded away, which shows the assertion would otherwise misfire on formatting differences alone.

Why it matters

  • ⭐ "Without checking inclusion/exclusion criteria" is the technical form of the disclaimer I need most for evidence-bound content. When I write about supplement interventions in my articles, I regularly cite the conclusion of a clinical trial. If a tool can tell a user "your profile resembles the entry criteria of this trial", someone will inevitably read that as "this trial proves this plan works for you." cyanheads writes that sentence into the tool description rather than into a documentation footnote, which is far more effective than any disclaimer.
  • "Lists are capped, and over-long output becomes a count" is a design I can port straight into my lab-report extraction pipeline. My GRPM and 4P platforms currently truncate long lists. Once a complete list is replaced by a count, the downstream LLM no longer believes it received everything.
  • "The field_values tool discovers legal values and reports the study count per value" — this is letting the LLM perform schema discovery itself. More resilient to API change than hard-coded enums. For my own work: if the 4P platform's lab-indicator dictionary could auto-discover legal values and the sample size behind each, the out-of-range judgement could rest on a real distribution instead of a guess.
  • The explicit request_too_long error class is worth copying. Over-long payloads are routine when I feed lab data to an LLM. Turning "it does not fit" into a named error category, so the caller can decide whether to paginate or to select, beats silent truncation.
  • Apache-2.0, with a public hosted instance (https://clinicaltrials.caseyjhand.com/mcp), no API key, installable with npx. For a one-person company this is a zero-cost, evidence-grade data source.
  • And it is an MCP, not yet another SaaS. I am driving the 4pwellness.org.cn MCP connector forward, and this class of project — an authoritative public database wrapped in MCP — is exactly what that connector should reach for first, ahead of building an API of my own.

5. eltmon/overdeck: trading the era of prompts for the era of loops — and giving the agent a review pipeline built from four independent lenses

URL: https://github.com/eltmon/overdeck ｜ ★34 ｜ MIT ｜ TypeScript ｜ an IDE for the agent era: "loops, not prompts", with three nested loops and a built-in specialist review pipeline, runnable straight from npx

What happened

505 commits inside the window — among the highest commit counts this issue — and heavily automated (most titles are chore(workspace): backlog sequence), which tells you a continuously running agent pipeline is feeding itself work.

  • ⭐ The core claim is one sentence, and it is heavy: **"IDEs were built for humans who type code. Overdeck is built for humans who direct it — not with prompts, with loops." It redefines the unit of AI-assisted work as the loop** — act, verify, correct, go again.
  • Three loops are explicitly layered:
    • Inner — the agent (seconds to minutes): the harness loop: write code, run it, read the result, try again.
    • Middle — the pipeline (minutes to hours): "the verifier wrapped around every agent", comprising a four-lens review convoy, quality gates, tests, browser UAT, per-bead inspection, and a merge train that keeps main green.
    • Outer — the Flywheel (continuous): "the loop that prompts the loops" — pull the next issue from the backlog, drive it end to end, file what it finds along the way, and go again.
  • The README defines what is now scarce: "Models write better prompts than we do now; the scarce skill is designing the loop that keeps agents pointed at the goal, and the verifier that decides whether the work is actually done." — models write better prompts than we do; what is scarce is designing the loop and the verifier.
  • The barrier to entry is low: npx @overdeck/core starts Command Deck and opens the browser dashboard; Node.js 22.16+ is required, and if your shell's default Node is older, Overdeck automatically relaunches under an installed compatible Node (Homebrew node@22, nvm, fnm, volta or asdf), printing the exact install command if none is found; the dashboard runs on https://overdeck.localhost.
  • MIT licensed, directly usable commercially.

Why it matters

  • ⭐ "The middle pipeline is the verifier wrapped around every agent" maps straight onto how my 4P platform generates intervention reports. Today the shape is "one LLM call produces the report", with no independent verifier. overdeck's structure: the agent produces, the middle pipeline verifies (four-lens review, quality gates, tests, merge train). What I recorded last issue as the "intervention-report write-back checklist" (exact-value comparison / None matching a stored null / rejecting literal placeholders) is precisely a minimal version of such a verifier.
  • ⭐ "Four-lens review convoy" is a shape worth studying closely. It is the same idea as the athril project I noted in the previous issue (six independent lenses — genetics / biology / safety / clinical / business / regulatory — each scoring a target 0–100 and producing a sourced dossier): a set of mutually independent perspectives rather than one more refined score. My intervention report scores a single dimension today (six risk levels); switching to "multiple lenses each reach their own conclusion" would eliminate the class of problem where a single score hides an extreme value on one axis.
  • "A merge train that keeps main green" maps onto my content production. My articles and intervention reports follow "generate in batch → human review → publish", but the human review is serial, one piece at a time. If there were a merge train, so that every piece first passes automatic gates (number checks, reference existence, length and format, banned terms) before entering the human queue, my content throughput would look materially different.
  • "The outer Flywheel: pull the next issue from the backlog and drive it end to end" — this is unattended self-propulsion. It corresponds to my 4pwellness MCP plus AI assistant: it should be able to pull the next task from a queue by itself. Today I have to say "continue" every time.
  • "Models write better prompts than we do now" is itself a verdict on prompt engineering as a craft. This continues the trend line I noted last issue — "AutoGen has stopped being maintained, LangChain shipped core 1.7.3 the same day" — value is migrating from "writing good prompts" to "designing verification loops". That is good news for a one-person company: prompts are not a moat, loop design is.
  • ★34 stars, MIT, runnable from npx. Among this issue's low-star, high-density candidates, this is the one most worth actually running.

3. Trends today

The judgement most worth carrying out of this issue: the competitive focus in AI tooling is shifting from "who can generate" to "who can prove". Three entirely unrelated projects arrived at the same answer in the same week. agent-desktop's snapshot JSON carries a complete field, a stale reference returns STALE_REF, and an ambiguous target returns AMBIGUOUS_TARGET; ovumcy splits "is there enough data to show this" out of the computation logic into a separate gate, with the documentation mirrored 1:1 by reference tests; tdeemon writes the 800 kcal floor, 0.8 g of protein per kg, 1.5% weekly loss and the rest as code-level floors the administrator cannot change, with the AI limited to proposing and only the user able to apply. What they share is that none of them lets "generation succeeded" equal "the content is trustworthy". This matters most to anyone building health products: once health advice is acted on it becomes behaviour, and the cost of an error is far higher than a mis-written paragraph.

Second observation: separating "computation" from "presentation" is becoming standard practice in health products. ovumcy keeps the fertility half locked until three cycles are logged; tdeemon never limits logging but always limits plans; clinicaltrialsgov's find_eligible states plainly that it does not check inclusion/exclusion criteria. All three put a gate in the same place: when data or conditions are insufficient, give nothing rather than a complete-looking wrong answer. My GLP-1 nutrition companion and 4P intervention reports are both currently "give it if you can" — that gap is now explicit.

Third observation: the agent's interface is moving from "chat box" to "loop console". overdeck redefines the unit of work from prompt to loop, layering an inner agent, a middle verifier pipeline and an outer Flywheel; vespin has every coding agent post questions into one inbox; ai4kanban is a draft-first workspace; commonly has agents sit on the task board like members with owners. What they share: people no longer sit in a chat box waiting for an agent to speak — the board is a stack of cards awaiting a decision. overdeck puts it most directly: "models write better prompts than we do now; the scarce skill is designing the loop and the verifier".

Fourth observation, and the sharpest one this issue: licence fields cannot be trusted. Twenty-four repositories reported NOASSERTION this round, and reading the LICENSE text showed MIT and Apache-2.0 (commercially usable) sitting alongside Elastic-2.0, SSPL-1.0, BSL-1.1, FSL-1.1, CC BY-NC-SA, a PENN academic licence and three all-rights-reserved entries (not commercially usable). If you read only the API field, your misjudgement rate is 100%. For a one-person company this is fatal: Elastic-2.0 carries explicit server-side SaaS restrictions, SSPL-1.0 forbids nearly any commercial distribution, CC BY-NC-SA forbids commercial use outright, and the three all-rights-reserved projects warrant caution even for personal use. This should be fixed as a selection procedure: for any repository you intend to use as a foundation, the first step is not reading the README — it is opening the LICENSE file and reading the first paragraph.

Fifth observation: the two top spots on today's GitHub trending charts (vercel-labs/agent-desktop at +1,179 stars, thedotmack/claude-mem at +1,803 for the day) are not new architectural paradigms but "give agents the capabilities humans already have" — sight, memory, desktop operation. The projects genuinely introducing something new at the architectural level this issue are all at or below 120 stars (ovumcy ★133, clinicaltrialsgov-mcp-server ★100, overdeck ★34, tdeemon ★0). This is not new projects winning — it is that the "fill the gap" category saturated during 2026, and from here the differentiator is who gets the details right.
