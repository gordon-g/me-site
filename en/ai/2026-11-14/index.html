1. Browser vendors start giving "web platform knowledge" an evaluation dashboard: Google Chrome turns 203 guides into an asset that needs continuous regression testing

URL: https://github.com/GoogleChrome/modern-web-guidance-src ｜ ★5154 ｜ Apache-2.0 ｜ A source repository jointly maintained by the Chrome, Edge, Firefox and MDN teams that turns modern web-platform knowledge into a searchable, installable and evaluable skill set for coding agents

What happened

  • 17 commits today, concentrated on two tracks — the evaluation system and the analyzer capabilities: js: add discipline guide, expectations, daily-grind eval, and 11 analyzer rules (#3525), evals: define benchmark lexicon and align ui, cli, and docs (#3562), and analyzing: 4.5x faster legacy-scan (#3565).
  • The analyzer gained three capabilities, each announced individually: scanning .scss files and blank // comments inside preprocessor style blocks, extracting Lit CSS template literals via the TypeScript AST, and no longer misreading <script-*> / <style-*> custom elements as script or style blocks.
  • The project's asset strategy is stated plainly: the guides are "designed to be token-efficient", and evals are run "enabling us to prune lowest-common-denominator content that models already know" — content models already know is cut outright.
  • Delivery is via CLI: npx modern-web-guidance@latest install runs an interactive wizard, and search / retrieve / legacy-scan can each be called on their own. The repository also hosts a public Eval Dashboard.
  • The README organizes skills by discipline (user experience, CSS layout, accessibility, built-in AI, language detection and so on); it currently lists 203 guide entries.

Why it matters

  • This picks up exactly where last issue's thread left off — skills are engineering assets that need CI gates. "Prune low-value content models already know, using evals" can be copied straight into my 4P expert-package spec: every intervention-report template I produce today carries a lot of generic nutritional common sense that models certainly already know, while what genuinely deserves context is my own decision framework and threshold table.
  • The official Eval Dashboard matters a great deal to me: if my 4P platform emits a report without a visible panel showing which skill segments and which rules produced it, I am effectively hiding the most important layer.
  • Names like "11 analyzer rules", "daily-grind eval" and "benchmark lexicon" show they treat evaluation as a continuous daily pipeline rather than a one-off acceptance test. That is the same discipline as "a failed arm is not an unrun arm", phrased differently.
  • A sober reminder: this whole stack is maintained jointly by browser vendors and MDN, which means the "general domain knowledge" portion of skills is being absorbed and standardized by the giants. The part of my 4P expert package that cannot be replaced is nutrition-intervention decision logic and clinical boundary rules — not general medical common sense.

2. Clinical knowledge gets an official skill-library shape for the first time: CQF turns CQL, FHIR and clinical reasoning into Agent Skills that ship with evals

URL: https://github.com/cqframework/cqf-skills ｜ ★0 ｜ Apache-2.0 ｜ Open Agent Skills maintained by the Clinical Quality Framework community for authoring, reviewing, testing and packaging clinical knowledge artifacts (CQL libraries, measures, PlanDefinitions and the IGs that publish them)

What happened

  • 21 commits today, every one of them adding a skill and its paired evals: Add usqualitycore and cms-qmd skills, from usqualitycore*, with evals (#10), Add uscore and us-cql-ig skills, split from uscore, with evals (#9), Add cql-ig skill for Using CQL With FHIR 2.0.0, with evals (#8), Add fsh skill (FSH 3.0.0, SUSHI 3.x) with evals (#7), Add fhir-extensions skill for the R4 Extensions Pack, with evals (#6).
  • The repository currently contains 12 SKILL.md files covering 11 named skills (cql, cql-ig, us-cql-ig, cms-qmd, fhir, fhir-extensions, uscore, usqualitycore, crmi, cpg, fsh), grouped into four installable plugins — cql / fhir / clinical-reasoning / fhir-ig.
  • There are 114 files in the repository tree related to evaluation, meaning every skill carries its own set of evals rather than one shared suite.
  • Skill content is pinned to specific specification versions: CQL 1.4 / 1.5.3 / 2.0.0, FHIR R4, US Core 6.1.0 and 9.0.0, US Quality Core 0.5.0, CRMI 2.0.0, and FHIR Extensions Pack 5.4.0.   • The skills follow the open Agent Skills format, so they work directly in Claude Code, Claude.ai, the Claude API and any other agent that supports SKILL.md.

Why it matters

  • This is the sample I have been waiting for: clinical domains now have a community-recognised skill library with version numbers and evals. My homework from the last issue was "the 4P expert package should get a 30–50 item pairwise comparison eval" — CQF supplies three things I can copy directly: ① one eval suite per skill, never a single omnibus eval; ② skills grouped by plugin and individually installable; ③ knowledge version numbers written into the skill names and content (US Core 6.1.0 and 9.0.0 sitting side by side).
  • It does not solve the question of "who adjudicates clinical correctness". FHIR and CQL have published specs to defer to; clinical nutrition intervention does not — which is exactly why my 4P package must write its own eval set and cannot wait for an upstream solution. Today's evidence supports that judgement.
  • One honest detail worth recording: the repository labels itself early development. "Official" does not mean "mature" — I should hold my own spec documents to the same standard.

3. An evidence-grounded skill library reaches industrial scale: ASB distils 11,830 metabolomics skills out of methods papers

URL: https://github.com/HolobiomicsLab/asb-skill-collections ｜ ★16 ｜ Apache-2.0 ｜ The public registry of the AgenticScienceBuilder pipeline, distilling published method papers and their code into scientific AI skills and tool records anchored to verbatim evidence

What happened

  • 11 commits today, almost all of them closing gaps in the PII redaction gate, each describing a concrete hole: fix(screen): redact an address whose domain goes on after a hyphen (#162), fix(screen): redact a labelled phone number with a space after the plus (#163), fix(screen): redact an address at any root-zone domain, not only the 35 listed (#161), fix(screen): stop leaving builds out for mentions that name no machine (#160).
  • The pipeline's core mechanism is spelled out: each skill is written from a published methods paper (journal article or preprint) and, where one exists, its public code repository; it is anchored to verbatim evidence from those sources, annotated with EDAM terms, and passes through licence and PII gates before release.
  • Scale of the published collections: metabolomics v3.0.2 carries 11,830 skills, 1,989 tools, 20 workflows and 477 papers; alongside it sit genomics (3,246), metagenomics (2,754), epigenomics (2,295), astronomy (1,671), multi-omics (787), metabarcoding (803) and agentic-ai (668) — ten domains in all, each release deposited to Zenodo and pinned to a specific commit and tree digest.
  • Code licence and content licence are stated separately (Apache-2.0 and CC-BY-4.0); the per-domain repositories are private while the full collection lives in the Zenodo record. The project began at the Dagstuhl Seminar on Computational Metabolomics in April 2026.

Why it matters

  • This is the one my readers should see most: 11,830 metabolomics skills anchored to 477 papers turns "evidence-based" from a slogan into a checkable pipeline (paper → verbatim evidence → term annotation → licence gate → PII gate → versioned release). If every supplement recommendation in my 4P platform is to carry literature, each one should be pinned in this way: source, verbatim evidence, version.
  • All 11 of today's commits being PII-gate edge cases shows that the real cost of a gate is not designing it but continuously fixing holes in it. Any "automatically filter sensitive information" flow I build should be expected to need long-term edge-case patching rather than being written once and done.
  • Separating code and content licences, keeping domain repositories private while shipping full collections via Zenodo — this is a realistic and sustainable way to distribute academic assets, and steadier than cramming everything into one MIT repository.
  • The most useful point for my one-person company: these skills can serve as a ready-made methodological reference for my GRPM nutrigenomics system and multi-omics intervention work, instead of inventing the "paper to actionable recommendation" chain from scratch.

4. Medical imaging models grow their own MCP surface: MedMLX moves CT / MRI segmentation onto Apple Silicon, locally

URL: https://github.com/MedMLX/medmlx ｜ ★29 ｜ Apache-2.0 ｜ A native medical-imaging inference layer for Apple Silicon, running TotalSegmentator, nnU-Net, MedSAM2, SynthSeg and more through one Python API, CLI and MCP server

What happened

  • 6 commits today, plus two releases — v0.9.1 and medmlx-core v0.2.7 (published 2026-11-13 23:00 UTC).
  • Today's commits concentrate on tightening interfaces and error classification: Return a typed RunResult from run and wait, Key run outputs by role and keep provider error categories, and Use MedSAM2's pixel-named prompt arguments.
  • The model catalogue covers real clinical tasks: musclemap (113 muscle and bone structures), totalsegmentator (whole-body CT segmentation), the nnunet family (liver / pancreas / custom PET / BraTS2021), mrsegmentator, siam (whole-head segmentation), synthseg (brain segmentation and parcellation), medsam2 (box / point / mask prompting), sam3 and biomedparse-v2 (text-prompted segmentation).
  • The three-stage CLI is worth noting: describe lists arguments, readiness checks only Metal and input paths without downloading weights, and run actually executes. medmlx setup --all --progress pre-downloads every model's weights for offline use.
  • An MCP server and a PyPI package are provided, requiring Python 3.13 and Metal. Model weights download on first use and keep their own separate terms.

Why it matters

  • This is concrete cost-reduction information for my readers in the health line: running CT whole-body segmentation, organ and lesion segmentation natively on an Apple Silicon machine means imaging-adjacent analysis no longer has to call a cloud API every time. It connects directly to 4P precision nutrition's long-run direction of folding multi-omics and imaging metrics into an intervention plan.
  • "readiness checks without downloading, weights pre-staged for offline use" is directly useful to me — my local-inference operations experience with Ollama is reproduced here: take an environment and path health check first, then decide whether to pull a large file.
  • Today's commits on "keying run outputs by role and keeping provider error categories" are textbook engineering discipline: separating errors by source is what lets an upper layer give an explicable failure reason. My 4P platform's OCR path for lab reports should do the same — distinguish "image quality insufficient", "model not installed" and "field parse failed" rather than reporting a blanket "recognition failed".
  • The Apache-2.0 code licence alongside weights carrying their own terms is worth flagging to readers too: open-source code does not mean commercially usable models, which is exactly the distinction I need to make when attaching a "evidence-based, zero-hallucination" label to content.

5. The DSH ecosystem advances on three fronts at once: Tobs tightens private-Bot authority, DSH gains native ACP, and an enzyme-function-mining microbiome skill package ships as a plugin

URL: https://github.com/BotHarness/DeepSeekBot ｜ ★845 ｜ MIT ｜ Tobs (formerly DeepSeekBot), an open-source GrokBot alternative that runs as a plugin on DeepSeek Harness, where several bots with their own identity, persona and long-term memory work as a team

What happened

  • 95 commits today, one of the highest commit densities in this issue; the latest release is Tobs v1.7.0 (2026-11-12), and the rename from DeepSeekBot to Tobs plus its npm package migration were completed.
  • Almost every commit today concerns permission boundaries, and all of them move in the same direction — tightening: Preserve Owner bridge composition and close private Bot authority gaps, Merge published Team and private Bot boundaries into E1, fix(client): offer members only a blank Bot to create, Merge pull request #4132: reciprocal Host relationships.
  • The project runs as a plugin inside DSH. Multiple bots handle research / writing / coding respectively, each keeping its own identity and persona; they can be chatted with privately, pulled into group chats, and @-mentioned for task assignment, with support for Slack, Discord, Feishu / Lark, QQ and WeChat. Bots can create their own scheduled tasks.
  • Two related DSH repositories also moved today: xintaofei/deepseek-acp (★20, 11 commits) turns DSH into a complete editor-facing coding agent over the Agent Client Protocol; AskTheWay/dsh-auto-memory (★132) turns DSH memory into a four-state trust machine with evidence chains and auditability; Liuyixin-lily/dsh-bio-human-microbiome-function-mining (★0, 10 commits) packages human microbiome function mining as a DSH plugin with 9 built-in skills and 25 scripts, where external tools are executed by the agent only when "the path is accessible and the user allows it".

Why it matters

  • "Members can only create a blank Bot" and "private Bot authority gaps closed" tell me more than any marketing line does: the real risk in a multi-agent system is not that the model is too weak, it is that permission boundaries are vague. Tobs spent today tightening exactly that line — the mark of this ecosystem moving from toy to usable.
  • This is the first time in four issues that the DSH ecosystem shows up on three tracks at once — application layer (Tobs, 95 commits), protocol layer (ACP wiring into editors), and methodology layer (a microbiome skill package producing evidence chains and falsifiable experiment plans). Together with dsh-context / dsh-multitask / dsh-as-mcp from 2026-11-13, DSH has moved from "personal plugin" to "industry-scenario adaptation" to "enterprise delivery boundary" — it should be formally promoted to its own tracked line rather than treated as a subclass of agent frameworks.
  • The microbiome plugin's rule that "whether the agent executes an external tool is decided by whether the path is accessible and the user permits it" is exactly the boundary design my 4P platform should copy: tool execution authority is not decided by the model, but jointly by user authorization and path reachability. That is an order of magnitude stronger than a line of caution in a prompt.
  • A practical note to myself: I should settle one thing for the 4P platform today — for any step that calls an external bioinformatics tool, the default is "generate the command, do not run it" unless the user explicitly flips the switch. That requires no external capability to adopt.
