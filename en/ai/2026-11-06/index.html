1. santiagopatinoserna/AdelIA: moving the "clinical promise" out of the prompt and into code — every clinical statement must carry a citation, no evidence means a full refusal, and red-flag signals short-circuit the model entirely

URL: https://github.com/santiagopatinoserna/AdelIA ｜ ★0 ｜ AGPL-3.0 ｜ Python ｜ Personal medical vault plus AI analysis (self-analysis and doctor briefing), FastAPI + pgvector RAG + Next.js, in Spanish/English/French

What happened

38 commits inside the window (11-05 02:11Z ~ 11-06 02:11Z), with the main line being clinical rules written into code and pinned by tests rather than "asked of the model" in a prompt.

  • ⭐ The central move this issue is that the "answer contract" (services/answer_contract.py) became the single source of truth: the contract is written once, and both the RAG chat and the tool-using agent behind /dashboard compose their system prompts from it, so the two can never drift apart. The contract is hard: every clinical statement must carry an [ev_N] citation, and an interpretation without one is not allowed; the refusal wording and the language are also fixed in the contract; and the disclaimer is a fixed UI component (clinical-disclaimer.tsx) — not "please write a disclaimer yourself".
  • Red flags completely short-circuit the model (clinical/red_flags.py): eleven deterministic detectors (fever ≥38°C under 3 months, non-blanching rash, respiratory distress, cyanosis, seizure, choking, anaphylaxis, bulging fontanelle, lethargy, no wet nappy for 12 hours, dehydration). When one fires, the code returns a fixed referral naming the emergency number along with the guideline behind it, and makes no retrieval, embedding or generation call at all. It deliberately over-triggers: a false positive costs a phone call, a false negative costs far more.
  • "No evidence, no answer" is a number that was calibrated against real measurements: clinical retrieval is cut at evidence_max_distance = 0.19, and the accompanying document CALIBRACION_UMBRAL_EVIDENCIA.md gives the method and the numbers — keeping 240 of 240 in-corpus probes and rejecting 14 of 14 off-corpus ones. When neither the guideline search nor the user's own records return anything, the chat returns no_evidence_reply() straight from code and never calls the generative model; the agent reaches the same pipeline through its buscar_en_expediente tool and receives the same refusal.
  • Extracted quotes must be literal (workers/extract.py): the model must supply a verbatim raw_quote, and any entity whose quote is not a substring of the source document is discarded. That rule is asserted by test_extract.py against the live Mistral API — and the README honestly flags the gap: a run without API keys does not exercise it.
  • The patient-side threshold patient_max_distance = 0.45 is explicitly labelled "not yet calibrated" and pushed to the roadmap, rather than being treated as an established number. The whole promise is pinned by five test files: test_red_flags.py, test_answer_contract.py, test_chat_orchestrator.py, test_agent_orchestrator.py, test_evidence_threshold_integration.py.
  • Concrete commits inside the window include: pinning the e2e job to ubuntu-24.04 (Playwright ships no Chromium for 26.04), passing LAY_QUERY_EXPANSION to the production API with it off by default, and feat(agent): search the corpus with her words and the clinical terms — letting the agent query the same corpus using the patient's own wording alongside clinical terms.

Why it matters

  • ⭐ This is the hardest engineering form of my WeChat accounts' rule that evidence-based content must carry references and must contain zero AI hallucination — and it puts the promise in code, not in a prompt. My current position: the mechanism descriptions in my articles are written by AI and the references are added afterwards, with nothing enforcing a link between them. AdelIA's approach is that any clinical statement without an [ev_N] citation simply cannot appear in the output, rather than "please try to cite". That rule can go straight into my content pipeline and the GRPM report generator: every conclusion field in a report must carry an evidence identifier that traces back to an input document, and a conclusion without evidence is not emitted.
  • ⭐ "The threshold must have been calibrated by measurement, and the calibration method and numbers must be published" — this is the same family as aureproof's "evidence package can be recomputed offline by a third party", but implemented more concretely. evidence_max_distance = 0.19 is not a guess: it is the reproducible outcome of "240 in-corpus probes all kept, 14 off-corpus probes all rejected". The direct translation to my work: each of the 40 SNP decision rules in GRPM, and each of the 24 risk dimensions in an intervention report, needs a number for "how confident am I before I dare conclude", plus the evidence for how that number was derived. Particularly worth copying is how it handles the uncalibrated patient-side number — writing down plainly that it is not calibrated, instead of letting it look exactly as trustworthy as the calibrated one.
  • ⭐ "Quotes must be verbatim" closes a hole that currently costs me manual proofreading on every article. raw_quote is not a document substring, so the entity is dropped — which means an AI-invented quote cannot pass structurally, with no separate fact-checking step needed. I should add this gate to both the GRPM gene report and the 4P platform's lab interpretation.
  • "Two entry points, one contract" is the correct fix for the biggest structural weakness in my 4P platform. Right now three places generate explanations from the same lab data — the dashboard's AI advice, the Excel export and the body of the intervention report — and those three are three separate code paths, so the numbers inevitably drift. AdelIA writes the contract once and assembles both prompts from it; I can build one answer_contract and have both the dashboard and the report read from it.
  • AGPL-3.0: readable, not copyable. For a one-person company that does not block me from learning the design, but the code cannot be lifted directly into the 4P platform I intend to sell. Any real use needs a separate licensing path or an equivalent implementation written from scratch.

2. 12burb/hermes-fledge: taking the job of grading agent-written skills away from the model — skills have to earn their wings on evidence, and a skill born from a bad run goes on probation instead of shipping

URL: https://github.com/12burb/hermes-fledge ｜ ★0 ｜ MIT ｜ Python ｜ A plugin for Hermes Agent that moves the job of reviewing skill saves and rewrites out of the model and into an auditable evidence-scoring rule set

What happened

27 commits inside the window (11-05 02:12Z ~ 11-06 02:12Z), with the main line being patching the edge conditions of Fledge's own decision logic and writing the validation process up as a reviewable document.

  • ⭐ The premise comes from a concrete user complaint: the README quotes Kilo's read of 1,300+ r/openclaw comments — the thing people dislike most about Hermes is that "self-evaluation always passes" ("It always thinks it did a good job. ALWAYS."). A skill learned from a run that quietly went wrong carries the mistake forward, and the next "self-improvement" can overwrite the skill you spent an evening tuning. Fledge's position: before Hermes saves or rewrites a skill, look at what actually happened in the run it learned from — no model grades the model.
  • Scoring is entirely based on facts Hermes reports through plugin hooks, each with an explicit value: the turn ended in an error 3 points; the turn was interrupted 2; your next message is a correction ("that's wrong" / "not what I asked" / "still broken") 3 (a softer "try again" / "not quite", or a bare "No.", counts as only 1); you ran /undo or restored a /rollback right after (3, /retry is 2); a task tool was still failing at the end of the turn 2 points each (terminal tools are judged per program — a later rm tmp.txt does not mean the earlier ./fetch.sh recovered); failing two or more times in a row without recovering +1; any other tool still failing at the end 1 point each (tool failures cap at 4 in total); denying an action at an approval prompt 1 point each, max 2. A score of 3 or more is bad (strictness is tunable: lenient 4 / standard 3 / strict 2). Zero with a clean finish is clean; anything in between is unclear — it neither helps nor hurts.
  • Three mechanisms make up the full lifecycle: the save gate — a skill learned from a run that went wrong is held in Hermes' own review queue instead of going live, and you see why before keeping or dropping it; probation — new and rewritten skills start as fledglings, and clean real runs graduate them while runs that keep going wrong ground them (archived, recoverable), with a save from a run you corrected immediately grounded at once; and hand-edit protection — skills you edited by hand stop being overwritten, so an agent's autonomous rewrite or delete becomes a proposal you approve or reject.
  • Almost every commit in this window hardens a decision boundary: engine: an agent write Fledge failed to record is not mistaken for a hand edit (an agent-authored write the Fledge ledger missed must not be misread as a manual edit); engine: a write already staged in Hermes' queue stays held if Fledge's ledger fails (if the ledger breaks, the write stays held — nothing is let through); engine: don't resurrect a skill that was deleted before its use was judged (a skill deleted before its use was judged must not come back). There is also docs: VALIDATION.md with live results; fail-open exception disclosed; 138 tests plus VALIDATION.md: install from GitHub verified and VALIDATION.md: no local username in paths — it writes both its validation results and its single fail-open exception into the docs. The test suite is 138 tests, and it does not require Hermes to be installed (every Hermes surface is faked).
  • The disclosure is deliberately narrow: it reads hook payloads (tool names, statuses, error text, turn outcome, and the first 280 characters of your next message to spot a correction) plus skill folders for fingerprinting; it writes its own SQLite file (skill names, fingerprints, verdict reasons, session/turn ids), and verdict reasons quote only short excerpts (the matched correction phrase up to 60 characters, a failing tool's error text up to 80); it never makes network calls, model calls, reads credentials, runs shell commands, spawns background processes or reports telemetry. It only adds friction, it never approves anything, and when nobody can answer, its questions are queued rather than waited on.

Why it matters

  • ⭐ This hits the core hole in my "standardised expert package generation with WorkBuddy's expert-manager skill" line: how I decide whether an expert package is any good currently rests on the model grading itself. Fledge's entire README is about how unreliable that is — "it always thinks it did a good job, always". And I am mass-producing expert packages, articles and GRPM reports, where every one of them depends on the judgement "is the previous step's output trustworthy". What I need is a table of "evidence → points", not a sentence telling a model to judge for itself.
  • ⭐ That points table can be turned directly into one hard rule in my intervention-report write-back checklist. The two most valuable rows are: "the user's next message is a correction" carries the highest weight (3 points) — which is exactly the objective signal Calibrate calls "did the human believe it or push back", and far more reliable than asking a model whether the user approved; and "an error the agent recovered from costs nothing" — which is the exact inverse of the "judging only model output systematically overestimates reliability" finding from a previous issue. Both directions of bias have to be avoided. Fledge's own framing is better still: the points are about observable facts — errors, interrupts, corrections, undos, still-failing tools, denied approvals — not about how good the output looked.
  • ⭐ "Hand-edit protection" is a hard requirement for my expert package production flow. The expert packages I have carefully tuned (edited prompts, fixed output formats, curated reference rules) are most at risk from the next agent "self-improvement" silently overwriting them. Fledge's rule is that any agent rewrite of a hand-edited skill is demoted to a proposal. That belongs in my quality-check flow as a hard clause: once a human has edited an expert package, the auto-optimisation flow may not write to disk — it may only emit proposals.
  • ⭐ "Probation and graduation" is the state machine I have been looking for to answer "how can an AI-produced artifact be trusted". Two issues ago I recorded aureproof's three-state gate (pass / fail / inconclusive) and Calibrate's 2×2 dependency matrix; this issue is the third form of the same idea: not scoring the conclusion, but giving the artifact itself a probation period. Clean real runs graduate it; persistent failures archive it — which is closer to real reliability than "it passed the eval, ship it".
  • ⭐ It is unusually honest about what it cannot observe: the README states outright that a run which finishes cleanly with a wrong answer and no reaction from you looks clean, that correction detection is a phrase list tuned to miss rather than misfire, that a compound shell command only reports the exit status of its last part (./fetch.sh; rm tmp exposes only rm's result), and that turn-level evidence lives in memory, so a restart forgets runs in flight. It even says it never guesses from other output text. That "I know the boundaries of my observation" section is a mandatory column whenever I evaluate any AI quality-control tool.
  • MIT licensed — readable, modifiable and commercially usable, the cleanest license of this issue's five picks.

Why it matters

My current shape is the inverse: AI directly recomputes and writes an entire plan, with the constraints living in a prompt.   • ⭐ "Danger alerts can be acknowledged but never dismissed, and no AI reply or MCP tool can remove a locked safety item" — a semantic tier my 4P platform is missing. In my current plan, "the user asks to remove a supplement recommendation" is something that can happen (changing the prompt is enough). Gaskin grades it: an alert can be acknowledged but not ignored; a locked item can only be changed by a human, and never by AI. This matters for supplement safety — "stop it" and "ignore it" must be treated as two different things.
  • ⭐ "The audit log records only the type, the destination and the byte count — never the content" — this is a log-redaction shape I can copy directly into the 4P platform. I noted in a previous issue that agent-desktop's snapshots contain the user's real screen content, clipboard included. A log must be able to prove that nothing leaked while itself not being a leak — Gaskin's design is exactly that answer.
  • ⭐⭐ It is also a complete counter-sample of what a health AI should look like, and it puts the boundaries where they are most visible: the README states outright that "Gaskin is not a doctor", every screen nudges the user to register at a clinic and see a health worker and shows her country's emergency number, and the skill side states it is "not a medical device, not a clinical tool, not a claim about treatment." As a health-content creator, the way this project handles identity boundaries is an unusually clean reference: put "I am not a doctor" in every place the user will actually see it, not only in a footer.
  • "One plan per mother-child pair, recomputed on every new record across 1,000 days; every item, alert and vaccine says which child it is about" — that multi-subject attribution design transfers directly to the GLP-1 nutrition companion's "mother plus child" or "an elderly parent plus a family member" scenarios.
  • AGPL-3.0: readable, not copyable; and since it states "not for patient care yet", any citation of its clinical rules must carry that status.

5. lud3nb3rg/DataNyx: letting an AI agent work with your data while never seeing it — what you hand over is a value-free schema and synthetic rows, not your patients' data

URL: https://github.com/lud3nb3rg/DataNyx ｜ ★0 ｜ MIT ｜ Python ｜ Turns files and databases into value-free schemas an agent can write code against, and replaces names and identifiers in free text with placeholders

What happened

25 commits inside the window (11-05 02:11Z ~ 11-06 02:10Z), with the main line being pushing an idea into a complete working pipeline in one pass: schema / anonymisation / synthetic data / multi-format sources / MCP server / CI / leak fuzz tests.

  • ⭐ The core contract fits in one table and is remarkably clean: for structured data (datanyx schema) the agent gets field names, types, formats, nesting, primary and foreign keys — and never values, examples, enum labels, counts or statistics; for free text (datanyx anonymize) the agent gets the text with names and identifiers replaced by placeholders such as <PERSON_1> and <EMAIL_1> — and never the identifiers themselves, with the documentation stating this is best-effort and needs human review.
  • ⭐ The agent gets "the shape of the table and the story in the text, and none of the values", and can try its code on fake rows generated from the schema (docs/synthetic-data.md).
  • ⭐ The commits inside this window show the pipeline forming in order: Add DataNyx: value-free schemas of data for AI agents → Add text anonymization with NER and ignore data files in git → Add opt-in mapping and restore for anonymized text (the mapping is not given by default, must be enabled explicitly, and can be restored) → Add CSV, TSV, Parquet, Excel, YAML and XML sources → Add streaming JSON, folders, library API, MCP server and new output formats → Add CI, lint and type checks, doctor command, Windows mapping permissions and leak fuzz tests → Add MIT license and move development to uv → Update README.
  • ⭐ "Leak fuzz tests" and CI landed in the repository together — meaning "can this leak?" is not something a human eyeballs but something fuzzing keeps pressing on continuously.
  • It is not a "redaction library" but a whole workflow: the documentation index contains docs/agents.md (three ways in: datanyx protect, a guard hook and the MCP server), docs/security.md (what is guaranteed, what is not, and the known limits), docs/schema-diff.md (detecting schema changes in CI), and docs/deployment.md (PyPI, Docker, a pre-commit hook, a GitHub Action, a shared MCP server). docs/schema-diff.md is especially important — it turns "the data shape changed" into a CI failure rather than a production incident.

Why it matters

  • ⭐⭐ The biggest practical risk my 4P precision-nutrition platform carries right now is the moment "patient data is fed to a model". Lab sheets, physical-exam reports, questionnaire answers — once they leave the machine they are gone. What I do today is basically "write my own regex redaction, then send it to the model", whereas DataNyx offers a different route: the values never leave the machine; the model only receives a schema and fake rows, and the code it writes then runs against my real data locally. For needs like "write me a script that interprets this lab panel" or "write me an importer for my supplement records", this route is more thorough than redaction.
  • ⭐ The "value-free schema" shape is an order of magnitude stronger than describing column names by hand, and it is naturally reusable. My 4P platform's lab data structure (field, unit, reference range, required or not) should be a version-controlled schema anyway — and once that exists, "hand the model a description without the values" is free. The docs/schema-diff.md rule matters especially: any change to my 140-item lab field table should trigger a review in CI, rather than being discovered when some report quietly omits a marker.
  • ⭐ "The mapping is not given by default, must be enabled explicitly, and can be restored" — this is the part redaction tools most often get wrong. Many redaction schemes are one-way and irreversible, so once the mapping is lost nothing can be cross-checked; DataNyx makes the mapping an explicitly enabled separate artifact, which lets "I can restore it when I need to" and "the model does not get it by default" coexist. My lab-report OCR pipeline has no "keep the original reference for cross-checking" layer at all — that mapping layer is what I should add.
  • ⭐ MIT licensed — readable, modifiable and commercially usable — and it is a self-contained small tool (schema / anonymize / protect / MCP server / doctor / schema-diff) rather than a heavyweight framework. For a one-person company, exactly the kind of independent capability that can be dropped into a product.
  • ⭐ It is the other half of a problem I recorded in a previous issue: "the OCR only recognised 18 of the dimensions without knowing it." DataNyx solves "don't let data go out"; it does not solve "is the extraction complete" — both are needed to close the loop: one governs the outbound boundary, the other governs completeness and reviewability of extraction.

3. Trends today

The clearest thread this issue is that "write the promise into code, not into the prompt" is spreading from medical AI into agent engineering as a whole. AdelIA turns the clinical contract, red-flag short-circuiting, verbatim quotes and the refusal threshold into code with tests; cf-skills turns evidence collection into 47 commands that never touch a language model; hermes-fledge turns "who does the grading" into an auditable points table; Gaskin turns danger signals into locked rules AI cannot move; DataNyx turns "data never leaves the machine" into a value-free schema. Four unrelated projects, one shared question — under what conditions should I refuse to output, and who proves I did not cross the line. This is the third stage of a thread I have been tracking: aureproof's three-state gate and Calibrate's 2×2 dependency matrix made uncertainty executable, and now the constraints are sinking into code with CI and tests keeping watch.

Second, "evidence" is turning from a citation format into a data structure with fixed fields. cf-skills's evidence records have four fixed fields (source / date read / the exact fields relied on / a limitation that may not be left empty); every plan item in Gaskin carries an evidence grade and a source; every clinical statement in AdelIA carries an [ev_N]; every verdict reason in hermes-fledge carries a short excerpt with a character cap. The common thread: evidence is no longer prose, it is schema — comparable and regression-testable. The implication for content production is direct: evidence-based content that cannot be structured can only be proofread by hand; once it is structured, regression tests have somewhere to land.

Third, low-star projects remain the richest seam to mine, and this issue brought two new shapes — "skills and rules grading themselves" (hermes-fledge, skill-studio's blind review queue, skilltrim's token review) and "the outbound boundary for health data" (DataNyx, Gaskin's default de-identification, cf-skills's network rules as code). Forty of the 89 entries have 100 stars or fewer, and the six densest of them all sit in those two shapes. Stars measure attention, not portability — and for a one-person company, "can this design be dropped straight into my platform" matters far more than "how many people starred it".

Fourth, the model-routing layer keeps getting more homogeneous in form, but two drifts this issue are worth noting. Of the 37 infrastructure entries, ClawRouter, weave-os router, HiRoute, codex-router, dsh-model-router, brick-SR1 and NadirClaw are all "local gateway + multi-model routing + cost optimisation" and look almost identical; the real differences live in the details — Hermes-router specifically preserves output budgets given to reasoning models by coding clients, Switchyard insists on keeping each provider's native response format, dsh-model-router plugs straight into the local dsh ecosystem, and speakeasy's gram lifts the battlefield to an enterprise AI control plane (permissions, threat detection, token cost visibility). The implication is that this layer's competition has shifted from "can it connect" to "will it eat other things on the way" — budget, format and credential ownership are becoming the real battleground.

Fifth, license misclassification remains alarmingly high, and this issue again produced cases where the API and the file disagree. Of the 89 entries, eight reported NOASSERTION; reading the LICENSE text one by one showed four of them are actually MIT / MIT-with-rider / Apache-2.0 — commercially usable — and two are PolyForm Noncommercial, FSL-1.1-ALv2 and BUSL-1.1 — commercially restricted. Plus 16 repositories have no LICENSE file whatsoever (each individually confirmed via the core endpoint). For a one-person company this is a matter of survival: MIT and Apache-2.0 account for 60 entries (67%) and are safe to build on; the 5 AGPL-3.0 repositories plus the 1 PolyForm Noncommercial can be read but not copied; and for the 16 "undeclared" entries I must ask the author before writing a single line.
