2. An evidence-first clinical research harness merged 31 commits today and gave author-supplied literature its own label — MANUAL — so it can never be mixed into the "verified" column

URL: https://github.com/drtranquanghung91-vn/clinical-research-orchestra ｜ ★0 ｜ MIT ｜ A multi-agent harness for evidence-first clinical research: references verified one by one, numbers taken from files, four human gates

What happened

  • 31 commits inside 24 hours, the last at 2026-11-21T10:43 UTC. The core commit is fix(orchestra): one rule for sources without PMID/DOI, [@id] citing rule, gates never opened by "just do it" — one uniform rule for sources with no PMID/DOI, in-text citations keyed as [@id] and required to exist in the ledger, and gates that are never opened by a "just do it" excuse.
  • Two companion commits push the rule into the specification: docs(spec): author-supplied (MANUAL) references in the ledger rule and docs(spec): P2 becomes Analyse and report results; design for data-preparation, statistical-analysis, results-writing.
  • The README compresses the whole method into one sentence: "The agent reasons; scripts measure. Anything a script can verify (an identifier, a number, a sample-size calculation, a poster's print resolution) is not left to the model's word." — the agent reasons, the scripts measure.
  • The citation rule is concrete: every reference enters through search_lit.py add and is then checked by verify_refs.py against PubMed, Europe PMC or Crossref; a source with no PMID or DOI can only enter via add-manual and is marked MANUAL, and is never listed as verified; in-text citations use [@id] keys and cite_render.py numbers them from the ledger in Vancouver style.
  • The number rule is equally concrete: results come from a results ledger rather than the model's memory, a sample size comes from samplesize.py with a sensitivity table, and every parameter is either sourced or labelled as an assumption.
  • Four human gates G1–G4 sit before the research question, the protocol design, the results lock (G3 computes a SHA-256 hash over the analysis outputs) and any external release; a gate can only be waived with a written reason in decisions.md.
  • A separate phi-guard plugin works as a hook scanning every outbound tool call (web search, fetch, MCP tools, network commands) for patient identifiers and blocking or asking. The README is candid that its detection is heuristic — "Detection is heuristic and not proof that a text is clean."

Why it matters

  • "MANUAL is not verified" is the one thing I most want to copy into the 4P platform today. I deal with "the model casually invents a PMID" every day, but the direction I had in mind was "block it"; this project offers a better direction: give the reference ledger one more field so that "I could not find the original source" has somewhere to live, and that column can never be treated as evidence by the system. In my supplement recommendations, "I am basing this on a study" and "this is common practice" are currently two tones of the same sentence, and they should be two separate states.
  • "The agent reasons, scripts measure" belongs directly in my specification template. What I actually do today is "move numeric computation out of the prompt into tables as early as possible" — but I have never written that as a division of labour. Once it is a principle, "did this number actually run" stops being personal diligence and becomes something checkable.
  • A gate cannot be opened by "just do it" is the plainest and hardest rule among today's five projects. The "3-month customer usage issues" and "forbidden supplements" modules in version 61 of my GLP-1 nutrition companion are naturally gates: a supplement on the forbidden list should stop the flow, not "continue but print a warning". My forbidden-supplement determination today is a prompt, not a gate.
  • phi-guard's restraint is worth recording: it states outright that detection is heuristic and not proof a text is clean. A guard tool declaring its own detection ceiling is the posture my 4P platform should have — my health-data de-identification has exactly one claim available to it, "de-identified", and no "de-identified as far as we could, possibly with gaps".
  • Honest boundary: the README itself says Status: early, "Do not rely on it for real studies yet", and P2 through P4 are all planned. So this issue treats it as a methodology sample, not as a tool recommendation.

3. A medical-AI-first "registry · evidence · gates" protocol tagged its first release today: PASS only means "no violation found within the observed boundary", and the third state is called INCONCLUSIVE

URL: https://github.com/zhaoxinghua09-cell/uibc-core ｜ ★12 ｜ Apache-2.0 ｜ An executable protocol for bounded-lifecycle autonomy: registry, evidence and gates, with a conformance test suite

What happened

  • 57 commits inside 24 hours, the last at 2026-11-21T13:07 UTC. v0.1.0 was published today (2026-11-21), and the release note reads: "First tagged snapshot of the UIBC core specification and tooling. Contents are the working tree at tagging time; the tag is immutable under repository policy." — tagging freezes the content, which is the first rule it sets for itself.
  • The largest commit is [audit] version gate, test ledger, anchor registry, revocation feed, interop + GTP-1 repro kit (#371) — version gate, test ledger, anchor registry, revocation, interoperability and a reproduction kit, laid down in one move. The two terms "GTP-1 repro kit" and "revocation feed" are not defined in that repository's README body; the README-verifiable part is a signable revocation overlay, and the terms are quoted here from the commit message.
  • The verdict is three-valued: PASS / FAIL / INCONCLUSIVE (insufficient evidence or an inability to judge). The README defines PASS extremely narrowly: "A uibc PASS means: within the observed evidence boundary, no violation was detected." It then states explicitly that this does not claim the agent was correct, safe or wise, does not claim the recorded inputs were true or complete, and does not claim any real-world outcome followed.
  • The three laws are stated plainly: "whatever acts autonomously must have a Registry, Evidence and a Gate". The verifier recomputes the SHA-256 of each evidence file, recomputes the Evidence Root, and checks Ed25519 seals and the linear receipt chain itself rather than trusting the package's self-description.
  • The published conformance corpus carries a fingerprint: uibc-conformance-0.5.0.zip, SHA-256 ad2b73ccdd8e5606364372350fc35134d8efe897f0382b36dd4ee65af341bfc0, 231,243 bytes, expected result strict 36/36; the README states plainly that a verifier which accepts every input scores only 6/36. It also ships the 41 RFC 9162 vectors and 29 language-agnostic vectors.
  • Revocation changes the gate: with a verifiable owner revocation the decision flips from ALLOW to DENY, and when a revocation cannot be verified the answer is HOLD — never a speculative allow.
  • The README is careful about "external validation": "One node is a node, not a sample — it is third-party execution, not third-party interest." It also keeps its own ledger: 7 external machine reviews, 2 independent human reproductions, 0 external documentation citations, 0 organisational adoptions; the status is PROPOSAL, not a formal standard; the theory SSOT lives in a separate lgd-theory repository with a Zenodo DOI.

Why it matters

  • "PASS only means no violation was detected within the observed boundary" is the most useful sentence I have seen in place of any "this report is for reference only" disclaimer. Every conclusion in my 4P intervention report is currently written as an assertion — "consider adding magnesium", "recommend rechecking ferritin" — and readers will take it as a claim. Rewriting it as "no risk of category Y was detected within the X indicators this report relies on" costs no persuasiveness and buys a clear boundary of responsibility. That is a one-wording change I can make tomorrow.
  • The third state, INCONCLUSIVE, is the most valuable thing today. The thing I fear most when writing evidence-based content is turning "never verified" into "no problem" — that is not a typo, it is missing state modelling. Every risk dimension in the 4P platform should move from two states (problem / no problem) to three or four (problem / no problem / insufficient evidence / conflicting evidence).
  • A conformance corpus with a SHA-256 that also publishes in advance how well a cheating verifier scores (6/36) treats the evaluation itself as an artefact that can be attacked. One small thing my 4P expert pack could do with the 30–50 item evaluation set: compute a fingerprint for the set and print it in the report, so a client holding the report can prove which item set was used.
  • "One node is a node, not a sample" is a reminder not to mistake "cites 8 papers" for evidentiary strength — real strength depends on the independence and reproducibility of the sources.
  • But I must be clear about its limits: it states its own status is PROPOSAL rather than a formal standard, with zero organisational adoptions and only two independent human reproductions. So my conclusion is "this protocol's state model is worth copying", not "this project is ready to use".

3. Trends today

  • The single most memorable thing about today is that six unrelated projects simultaneously gave "not yet verified" a state of its own. conveyor-belt splits an ungraded attempt out of the score and its 95% range; clinical-research-orchestra lets a source without PMID or DOI be marked MANUAL and never counted as verified; uibc-core's verdict is three-valued and outputs INCONCLUSIVE rather than FAIL when evidence is insufficient; body-model stores "not measured" as null rather than 0; verifylens exists to catch the fake pass where a test was edited to make the suite green; kaijian-kaichi splits its health verdict into "insufficient data" and "data pending", and generates no conclusion when data is short, only naming what is missing. Six teams, five ecosystems, one thing: "never verified" has to be a state that can be expressed, stored and queried — not a synonym for "no problem". I learned this from mirobody-eval last issue and again this issue, in two completely different shapes pointing at the same gap, which tells me it is the structural defect my kind of project is most likely to miss.
  • "A conclusion outsiders can recompute offline" turned from an idea into a downloadable artefact today. uibc-core's corpus ships with a SHA-256 and a 231,243-byte size declaration, and publishes in advance how well a cheating verifier scores (6/36); yuxuan-huang-data released v2.1.0 today, measuring the precision of two hospital crosswalks against a blind human reference and publishing the labels (the release note reads "Until now their quality was assessed indirectly; it is now measured against a blind human reference, and the labels are published"); body-model makes source fingerprints, generations and currentness fences part of model publication. All three replace "please trust me" with "please compute it yourself." My intervention-report export still has no verification package — a report should be checkable by a third party, not merely readable.
  • Separating execution from acceptance became a hard rule in three ecosystems today. conveyor-belt uses a second model for review plus a separate fix session; wicked-crew states it plainly: "Runs your coding agents in sandboxes; a different agent reviews the work against your rules, and app changes pass acceptance testing before delivery"; Arc-Science writes it into the product definition — "The agent that does a task never accepts its own work, and each step goes into a hash-chained ledger." Add verifylens' v0.19.0 today, which is precisely about detecting rewritten tests, and these four pieces add up to a complete answer to "who is allowed to grade themselves". My 4P expert pack's 30–50 item pairwise evaluation has both the questions and the grading in my own hands — this whole set should be copied, especially the "the test was edited so the suite turns green" check, which is the most dangerous hole in an evaluation scheme of my kind.
  • Skills and permissions are converging on "publishable, distributable, revocable". mcphub v1.3.0 distributes Agent Skills over MCP endpoints; body-model uses profile-scoped API keys shown exactly once; boxdawn/guard intercepts or asks with a reason before a command runs; TheColliery probes on its public permission matrix whether a deny actually binds to the process, and skips visibly rather than pretending to pass when it cannot tell; uibc-core's revocation overlay yields HOLD rather than a speculative allow when a revocation cannot be verified. The shared form is "permissions must be verifiable, and if they cannot be verified, say so" — the same line as the to-do I set last issue ("third-party keys in the Flask admin backend must be owner-only and never behind a symlink"), except that today someone turned it into a testable mechanism.
  • The health and nutrition track (③) is still thin today, and it is worth saying so plainly. This issue has 36 entries in ③, of which only 4 are above ★500 (ActivityWatch ★19,764, karlicoss/HPI ★1,649, norish-recipes/norish ★1,554, cooklang/cookcli ★1,447) — and none of those is an "AI-assisted nutrition decision" project; the only genuinely on-topic entries are three personal projects at ★0–★1 (krustallik/body-model, justanlogic/kaijian-kaichi, mralexsaavedra/loop). As in the two previous issues (11-18 and 11-19), there is no high-star activity in this track today, and writing that honestly is more credible than padding the count. It is also notable that the two most substantial projects in this track (body-model and kaijian-kaichi) are not adding features but tightening data semantics — which says the bottleneck in this field is not model capability but data definitions and evidence chains.
