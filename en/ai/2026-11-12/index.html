1. awslabs/hcls-agent-skills: AWS turns 43 healthcare and life-science skills into portable standard parts, and proves with 410 pairwise prompts that they beat going without

URL: https://github.com/awslabs/hcls-agent-skills ｜ ★76 ｜ MIT-0 ｜ Open-source healthcare AI agent skills and life sciences agent skills. 42 skills for medical coding, risk adjustment, claims analytics, quality measures, genomics, imaging, and drug discovery across 13 HCLS domains.

What happened

  • The most directly relevant entry for my business this issue: the most widely available, large-vendor-maintained library of medical / clinical Agent skills - and it ships with a credible evaluation report. The README lists 43 skills across 13-14 domains, split into two families: reasoning skills that encode methodology and decision frameworks (ACMG variant classification, target trial emulation, HEDIS measure specification), and pipeline skills that encode runnable tool chains (GATK4 variant calling, RDKit cheminformatics, HL7v2 parsing).

  • Both commits inside the window land squarely on evaluation credibility: fix(eval): Extend fail-loudly to independent judge, fix stale docs extends the "a tie is a failure" principle from local review out to an independent judge model; the other merges the roda-open-data skill (the ODAC open-data access standard).

Why it matters

  • This is the industrial-grade sample of "packaging expert judgment into a portable asset" - exactly the template my expert-package workflow is missing. My quality check today is still "have the model grade itself", while hcls-agent-skills does something different: skills are written as files carrying explicit decision thresholds (ACMG grading, HEDIS definitions), then measured with pairwise comparison plus an independent judge. Its reasoning vs pipeline split is directly transferable - in my 4P precision-nutrition reports, "interpretation rules" (the ordering of mitochondrial, methylation and OAT criteria) are reasoning, while "lab-indicator parsing and export" is pipeline.
  • "Skills portable across 20+ platforms on an open standard" matters enormously for a one-person company. My assets must not be welded to a single client; standardization means the same rule files are reusable across Claude Code, Codex and my local dsh without rewriting for each harness.
  • It confirms the through-line I have logged for four consecutive issues and finally supplies the evaluation-side recipe. I noted assay's "a read claim must carry its file list", groundedmed's "a critic model checks each claim against source text", and bpf-benchmark's "third parties independently evaluate artifacts" - this issue, hcls-agent-skills bundles all three into a downloadable asset manifest: the skills are the methodology, the independent judge is the referee, the pairwise comparison is the scale. If I build a 30-50 prompt pairwise evaluation for my 4P expert package, I can copy this methodology wholesale.
  • The claim that a skill should be a practitioner's decision chain rather than a long prompt is directly valuable for my content work. The README's line - that models know facts but not procedures - explains the recurring gap in my public-account writing: readers need "what decision comes next", not a list of concepts.

3. awslabs/unified-kg-rag-on-aws: four graph RAG methods on one shared index - and renaming an entity is now treated as a migration that can be rolled back

URL: https://github.com/awslabs/unified-kg-rag-on-aws ｜ ★39 ｜ Apache-2.0 ｜ AWS-native knowledge graph RAG framework. Runs GraphRAG, LightRAG, HippoRAG 2 and RAPTOR on one shared index, each selectable at index and query time, with hybrid BM25 + vector + graph retrieval and source provenance. Amazon Bedrock, Neptune and OpenSearch, or fully local. Incremental indexing, multilingual, bring-your-own KG, built-in evaluation.

What happened

  • Four published methods run on the same index: Microsoft GraphRAG (community summaries), LightRAG (dual-level keywords), HippoRAG 2 (Personalized PageRank over entities and passages) and RAPTOR (summary tree, opt-in) - sharing ingestion, indexing, caching and search, with only the retrieval algorithm differing, and it builds only what the selected methods actually read.
  • Answers carry [n] citation markers naming the document and PDF page behind them (the global and drift strategies omit them by default); opening a source shows the provenance trail leading into a force-directed graph with the traced entity ringed and its neighbours labelled. Retrieval is BM25 + vector + Neptune graph traversal, fused with Reciprocal Rank Fusion and reranked by a Bedrock rerank model.
  • All three commits inside the window deal with entity renaming: first fix: re-key bundle - name folding and legal forms, prompt-aware stage cache keys, then fix: legal forms read as written, idempotent name keys, SUSPECTED claims, prompt digests, then fix(indexing): strip a vertex holding a kept edge, identifier tokens from the entity key, record ids mint. The core idea is that renaming must be idempotent - the old and new names of one entity must map to the same key, and a vertex still referenced by another edge must not be swept away during the move.
  • Evaluation defaults to no LLM at all: built-in answer match, retrieval hit rate and graph coverage metrics, with RAGAS and assertion-style judges as opt-in, plus paired-interval strategy comparison and per-query cost metering.

Why it matters

  • "Renaming is a migration that can be rolled back" lands squarely on GRPM's terminology-drift problem. On 11-10 I noted cortexdb's answer - aliases must resolve on both write and read - and here is a harder path: renaming is not adding an alias, it is migrating every edge off the old key, keeping vertices that cannot be moved, and doing it idempotently (renaming one entity twice must not create two identities). My terminology upgrades (merging "omega-3" with "EPA+DHA", renaming a biomarker) will eventually rewrite historical conclusions, so I need to know now how others handle whether old conclusions still count after a rename.
  • "A vertex referenced by another edge must not be casually deleted" is a rule I never considered on the content side, and it turns out to matter. I retitle posts and change terminology in my public-account A/B tests; if the old title's conclusion is simply deleted, the historical test can never be reproduced - which is structurally the same problem as deleting a vertex on the data side.
  • "No LLM judge by default" points in exactly the same direction as my recent notes. I have logged four consecutive issues about "let an uninformed third party decide" and "machine verification beats model self-report"; this goes further: three LLM-free metrics as the default, LLM judges demoted to an opt-in switch. That default choice is worth copying more than the feature list.
  • Cost metering plus paired intervals is what content experiments should look like. My public-account content tests are currently as coarse as "this post got more reads"; the structure of "paired intervals per strategy + cost per query" can be turned directly into a template for "paired intervals between two copy variants + generation cost".

3. Trends today

  • ⭐⭐⭐ Skills are turning from "prompt fragments" into portable, evaluable, updatable methodology assets - and a public industrial-grade sample now exists. This issue, awslabs/hcls-agent-skills splits 43 healthcare and life-science skills into reasoning (methodology and decision frameworks) and pipeline (tool chains and parameter tables), backed by a 410-prompt pairwise evaluation showing the skill-equipped version winning 70-86%. This matches the through-line I have logged for four consecutive issues exactly: 11-08 "a failing test must name the scenario", 11-09 "specs/docs/matrix aligned with code plus regression guards", 11-10 "let an uninformed third party decide", 11-11 "a read claim must carry its file list" - this issue is the first time those mechanisms have been packaged into a downloadable asset manifest.
  • ⭐⭐⭐ The evidence chain is now extending in both directions: one end toward the provenance of modifications, the other toward historical conclusions after an entity rename. codex-security carries AWS-generated patches into third-party scanner finding entries (ArmorCode / AWS Continuum) and exports SARIF/JSON/CSV; unified-kg-rag-on-aws turns a rename into a migration that needs an idempotent key and must preserve still-referenced vertices. Read together, mature systems are answering one question: three months from now, how do I know how that report, that modification and that term came about? That is precisely the part of the GRPM credibility path (data archival -> decision rules -> reproducible artifacts) I have not yet completed.
  • ⭐⭐⭐ The dividing line in the health line has shifted from "can it record" to "does the data stay, and is the rule set honest". openfit turns lab-report OCR into "delete the camera capture once read" and publishes the verification status of its own 95 rules (53 pinned / 13 merely proposed / 21 manual / 8 unverified); uniprot-mcp makes protein data auditable with per-response SHA-256 provenance, release pinning and offline replay; openmed ships 72 medical skills with a local de-identification pipeline, and SAGEAgent has the agent decide whether the next diagnostic modality is worth acquiring (average acquisition burden down 55% with no significant C-index change). The common thread: this issue's health projects are answering "where does my data go and why should I trust my conclusion", not "here is yet another photo-to-calorie feature".
  • ⭐⭐ Constraints enforced at the architecture layer are harder than constraints written into prompts. clinmesh states that "the final Actor is always the logged-in human who clicks the native review box" - the agent cannot reach the submit button; codex-security splits "configuration error" and "policy refusal" into separate diagnostics; unified-kg-rag-on-aws defaults to three LLM-free metrics with LLM judges merely optional. All three say the same thing: turn "please do not do this" into "the system does not allow this".
  • ⭐⭐ The three-tier licensing split still holds this issue, with one exception worth remembering on its own. Of the 273 entries, permissive licenses (MIT / Apache-2.0 / BSD / MPL / CC0) account for 164; contagious copyleft (AGPL / GPL / LGPL) 11, source-visible but not open source 0, proprietary 0; and 0 entries have no LICENSE file whatsoever - the methodology can be read, but the code cannot be depended on directly, and that boundary has to be re-confirmed every single issue.
