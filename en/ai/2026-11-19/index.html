1. Microsoft formally turned the "skills ecosystem" into a dependency management problem: APM logs 28 commits today, pulling an agent's skills, plugins and MCP servers into one manifest plus a lockfile

URL: https://github.com/microsoft/apm ｜ ★4,404 ｜ Apache-2.0 ｜ An open-source dependency manager for AI agents that declares skills, plugins, MCP servers and prompts in apm.yml, and reproduces the same environment on any harness with a single command

What happened

  • 28 commits inside the window, the last at 13:32 Beijing time today, with v0.36.1 published at 14:38 yesterday. The README's self-positioning is unambiguous: "Think package.json, requirements.txt, or Cargo.toml — but for AI agent configuration."
  • The single most consequential commit today is a breaking change: feat!: Copilot project MCP in root .mcp.json; vscode a deprecated alias; drop apm manifest migrate (#3875), paired with feat(manifest): deprecate target: and add apm manifest migrate (#3801) which supplies the migration command. A companion fix, fix(targets): deploy a targets: [vscode] dependency to copilot projects (#3864), closes the path where the old spelling landed in Copilot.
  • The governance layer moved forward too: fix(policy): check mcp.transport.allow on the effective MCP transport (#3788) moves the policy check from the declared transport to the actually effective one; fix(registry): follow redirects only within the configured registry origin (#3785) tightens where redirect-following is allowed; fix(audit): audit --ci after update -g no longer demands empty ~/.apm/apm_modules (#3797).
  • Dependency resolution got more precise: fix(deps): exact per-edge skills x targets pairing for diamonds (req-rs-018) (#3769) handles diagonal dependency pairing when one skill spans multiple harnesses; fix(init): stop defaulting scaffolded plugin licenses to MIT (#3799) stops writing MIT as the licence of scaffold-generated plugins.
  • Supported harnesses cover GitHub Copilot, Claude Code, Grok Build, Cursor, OpenCode, Codex, Gemini, Windsurf and Kiro; apm.lock.yaml pins the resolved dependency tree the way package-lock.json does for npm. The README states plainly that it is a drop-in for npx skills add: apm install vercel-labs/agent-skills (whole bundle) or --skill deploy-to-vercel (one skill), written into apm.yml.

Why it matters

  • This closes the one layer my 4P expert packages have always lacked: reproducible dependency declaration. The packages I build with the expert-manager skill are currently "the files are in the package, the versions are in my head" — clone them onto another machine, reinstall them a month later, and the skill versions and MCP server lists no longer line up. APM's apm.yml + apm.lock.yaml is exactly the pair I am missing: one declaration plus one lockfile. I do not need to invent it — I can copy the format.
  • "The policy check must look at the transport that is actually in effect, not the one on paper" is a real security lesson. My 4P platform is going to take an MCP connector (the 4pwellness.org.cn line). If the policy only inspects the transport written in the manifest while the runtime takes a different path, that layer of control is hollow. This goes straight into the connector acceptance checklist.
  • The apm install vercel-labs/agent-skills command shows the ecosystem converging on one install gesture. If my skill marketplace content still requires a customer to copy directories and edit config by hand, it will never spread beyond me. A skill that can be installed by one command is the only kind a third party will actually pick up. This bears directly on my minimal viable version of the "certification hook + nutrition AI core" line: the delivery form should be "one install command", not a zip file.
  • The breaking change itself is worth studying. A feat!: prefix, a matching apm manifest migrate migration command, and a separate test commit — this is textbook "changing behaviour ships with a migration path". Every time I change the structure of my 4P intervention reports or my data model, there will be a batch of existing client records sitting in the database. That one lesson is worth more to me than any new repository I saw today, and it goes into my specification document template.
  • Reality check: this is ecosystem infrastructure produced by Microsoft, and the adoption pace is not mine to decide. What I can do is align my format, not bet that it will win.

2. Someone built a ruler for "UI written by AI": renderlint ships v0.2.0 today, turning mobile overflow, low contrast and overlaps into build failures

URL: https://github.com/ngocanhnckh/renderlint ｜ ★686 ｜ MIT ｜ A "rendered UI" checker built for AI coding agents, using headless Chromium to screenshot at phone, tablet and desktop widths and report text overflow, low contrast, element overlaps, broken responsive layouts and more

What happened

  • v0.2.0 was published at 15:31 yesterday, the project's first tagged release and the first version shipped to npm as @yitec/renderlint. 14 commits inside today's window.
  • The checking principle is "after rendering", not "the source": the README says outright, "TypeScript and ESLint can't see any of this, because the code is fine. It's the pixels that are wrong." The tool renders every page at phone, tablet and desktop widths plus dark mode, sweeps the widths in between, and re-checks with longer copy, larger numbers and longer API payloads. Each defect is reported with the element, the source file, an annotated screenshot and a concrete fix, in plain text an agent can act on. 58 rules at present.
  • Today's three moves map onto exactly what I care about: ① "Phones: zoom-disabled, input-zoom, html-lang, safe-area" — phone-specific checks; ② "Fewer false positives from real sites: covers you can scroll clear of, negative margins, dev-server chunks" — false positives suppressed against real sites, with only "floats you can scroll clear of", "small negative margins" and "dev-server chunks" staying unreported; ③ "Audit cleanup: disclose network and processes, SECURITY.md, regex exec → match" — audit cleanup, regex changed from exec to match, network access and subprocesses disclosed, SECURITY.md added.
  • The new rule text-near-overlap (warn): fires when two pieces of text sit side by side, less than ¾ of the font size apart and out of line, with at least one of them inside an absolutely or fixed positioned layer. The typical case is a centred empty-state message laid over a panel whose title is pinned.
  • One commit is notably honest about workflow: "Baseline and progress: adopt renderlint on an app that already has findings" — adopting it on an application that already has problems, rather than demonstrating it on a clean sample.
  • The installation flow targets agents: npx -y @yitec/renderlint init writes the config, the build gate, the AGENTS.md instructions and a Claude Code hook; after that npx renderlint exits with code 1 as soon as it finds an error.

Why it matters

  • "Mobile text readability" is something I have raised repeatedly and been repeatedly dissatisfied with, and this tool aims straight at that hole. I build single-file offline HTML applications (the personal workbench, the GLP-1 nutrition companion V2, this very daily-report site), and every time I have to manually re-check phone-side font size, layout and tappable area by eye. That class of check belongs in the build gate, not in my re-reading of the screen before every release. Wiring it into my build flow is one of the three things I can land next week.
  • "Validate the tool on an application that already has problems" is a more convincing workflow than any demo. My recurring flaw when validating a method is finding a clean sample to prove it works — which is exactly the "cherry-picking the data" I keep warning myself about in nutrition content. Run it first on the existing app with problems, record the finding count, then report what remains after fixing them. That is the deliverable form of acceptance.
  • The false-positive work directly helps me. It lists "floats you can scroll clear of" and "small negative margins" as things not to report — and those are precisely the legitimate patterns I use most in single-file apps. A checker that does not understand your stack produces false positives, and the false-positive rate decides whether it can enter CI. If I add such a check to my content site, I can copy this "suppress false positives against real sites" process verbatim.
  • The security side is equally clean: regex moved from exec to match, network and subprocesses disclosed, SECURITY.md present. A checker that drives a browser and runs a dev server has a far larger attack surface than an ordinary linter. I will read those three places before letting it into my own repository.
  • Reality check: ★686, first official release, rules still in rapid churn (phone rules and baseline rules both changed this morning). Rules will move and false positives will rebound; if I put it in CI I need to leave room for a "temporary waiver" path, otherwise I will be forced into editing CSS every day.

3. An agent browser for regulated health settings shipped six versions today: oya-browser writes every action into a tamper-evident audit chain

URL: https://github.com/OyadotAI/oya-browser ｜ ★350 ｜ Licence not declared (README marks it Sustainable Use + MIT SDK) ｜ An AI browser for medical and regulated work — on the desktop for people, in the cloud or self-hosted for agents — with every action landing on a tamper-evident audit trail

What happened

  • 44 commits inside the window, six versions in a row from 23:53 yesterday to 11:40 today (v1.0.250 → v1.0.255), written in Rust.
  • The core mechanism is "record once, replay deterministically": the README states, "An agent completes a task once in natural language; Oya records the steps as a playbook that replays deterministically, without calling a model, and repairs individual steps when a page changes." A successful ask() is saved with toPlaybook(), play() replays it with new inputs and no model calls, and each playbook is also exported as a Playwright module. In the ten-site benchmark the README cites, nine sites replayed every recorded step with healing disabled.
  • When a page changes, it repairs that one step rather than starting over (Step repair, switchable per call). Browser identity is stable: personas bind a fingerprint, cookie store and proxy that persist across sessions, with the README's anti-detection results reported as 0% headless on CreepJS and 31/31 on Sannysoft.
  • Three items worth recording separately today: ① "Python SDK 0.2.1: ask() and extract() without data or secrets no longer send null" and 0.2.2's "null data accepted" — closing the path where empty data could be sent off as if it were real; ② "Save the signup key owner-only even over an existing config, and never through a symlink" — ownership and symlink protection for keys on disk; ③ "fix(runs): a run that brings its own login signs in itself" — a run carrying its own credentials completes its own sign-in.
  • The compliance surface moved forward in parallel: a new /baa trust-centre page, an explicit statement of SOC 2 Type I, and an explanation that "HIPAA mode keeps PHI off other vendors" — stating exactly where PHI lives and which vendors cannot touch it. The repository is the community edition (browser, control plane, web console, CLI, TypeScript and Python SDKs); the README notes that HIPAA compliance and a signed BAA come with Oya Cloud and the enterprise edition.
  • The latest v1.0.255 fixes the website download buttons pointing at a 1.0.83 file that no longer exists.

Why it matters

  • "Run once in natural language, record it as a deterministically replayable script, and replay without calling the model" solves the same problem my 4P platform's compliance paperwork solves. My partner-vendor qualification review and project compliance documents currently rely on humans leaving a trail through the process. If the process could be run once and recorded as a script, then each new partner replays it deterministically without re-asking the model — that is both efficiency and audit evidence. This is a form I had not thought of at all.
  • "The policy has to live where it actually takes effect" is the same principle as APM's rule today, in a second guise. oya-browser hangs the audit chain on real actions; APM moves the policy check onto the real transport. My counterpart is this: my Flask + SQLite backend keeps every client's lab data in one database, and whether client A's query could ever match client B's rows must be closed at the path that actually executes, not by an if I write somewhere in the code.
  • "Credentials must never land behind a symlink, and must be owner-only even when overwriting an existing config" are two lines my Flask backend should copy today. The keys and third-party API keys on my admin backend currently have no explicit on-disk permission constraint. That gap should be closed today.
  • I can copy the way it phrases compliance. It does not say "we value privacy"; it says where PHI is stored, which vendors cannot reach it, and what differs under HIPAA mode — and it ships a BAA page and an SOC 2 type. My public account and outward-facing materials write promises when they talk about compliance; it writes positions. A position is more credible than a promise.
  • Reality check: ★350, the community edition carries neither HIPAA compliance nor a BAA (those are in the cloud and enterprise editions), and the community licence is "Sustainable Use + MIT SDK" rather than a standard open-source licence. I can borrow the design and the documentation style; I should not assume it can go straight into my production chain.

4. Someone turned "did the intervention actually make people biologically younger, or did it just move the clocks" into a scoreable simulated environment: longevity-gym v0.1

URL: https://github.com/di-omics/longevity-gym ｜ ★0 ｜ Licence not declared ｜ A simulated reinforcement learning environment that answers one question with eight simulated ageing clocks and hidden ground truth: did the intervention make people genuinely younger, or did it only shift the clock readings?

What happened

  • Created today (2026-11-18), four commits the same day (08:25 — 12:41 UTC, all inside the window), first version v0.1. This is a project built from scratch that assembled a complete methodological skeleton on day one.
  • The question takes a single sentence: "did this intervention make simulated people biologically younger, or did it only move the clocks?"
  • The project states its own boundary up front: "Status: v0.1, simulation only. Nothing here is trained on real data. The repo holds no real proteomic or methylation data, no published clock, no participant-level trial data and no stored model or agent." Only two things are fitted, both at run time and both on simulated data only: the eight small ridge regressions that serve as clocks, and the two small learned policies of the shortcut check. The only real numbers are a few aggregate statistics computed from the open supplementary tables of the source paper, used in one section to check the simulator's noise and set one optional noise profile; every other number is an assumed default, all listed in docs/ASSUMPTIONS.md.
  • The simulated world: each simulated person has seven organ ages, systemic inflammation, fibrosis activity and a blood cell mix; biological age is defined as the mean organ age, and inflammation, fibrosis and cell mix leak into the omics but by this definition are not ageing. The omics are 240 simulated protein features and 200 simulated methylation features with plate effects; four lung-enriched proteins are coded as the strongest and least noisy age markers in healthy people and to rise with fibrosis activity as well.
  • The real study it cites is precisely the kind of evidence it exists to question: in September 2026, Insilico Medicine and several academic groups published an exploratory analysis of a 12-week phase 2a trial of rentosertib in idiopathic pulmonary fibrosis, running six published proteomic ageing clocks on serum from 42 participants; of 54 comparisons (6 clocks × 3 dose regimens × 3 visits), 21 showed a larger fall in predicted age than placebo (one-sided tests, false discovery rate 0.10), 11 of them at week 4. The project states plainly that it uses none of that trial's data and none of those clocks, and quotes the paper's own limitation: proteomic clocks alone cannot separate an effect on ageing from the drug's antifibrotic effect.
  • The four commits today trace a clear line: longevity-gym v0.1: clock_trial environment, eight simulated aging clocks, QC card → Rebuild from the paper: verified clock recipes, shared fibrosis proteins, continuous truth, paired QC → Second review: make the reward pay for the cross-modality check, calibrate the reference → Check the simulator's clock noise against real clock readouts; add a calibrated noise option. The sister project drugdev-gym is positioned as "hidden truth, named mistakes, and a QC card that says what the reward can and cannot see".
  • The reward function must be open to challenge: both the README and the commit messages stress the "QC card" — what the reward can see and what it cannot see has to be written down as a card. The second review even changes it so that "the reward pays for the cross-modality check".

Why it matters

  • This is the minimal version of the unsolved problem in my "Hundred Persons Project" observation-metric analysis. When I analyse participant observation metrics, adjust the intervention plan and look at formula effect, the underlying risk has always been: did the metric move because the person genuinely improved, or because some clock reading shifted? This project turns that question into a scoreable simulated task. Its method is: build a world with a known answer first, then see whether the model can read a panel of clocks. I do not need real data to adopt this structure — I can build an offline version with a known answer from historical data and check whether my evaluation logic gets fooled by surface metrics.
  • "Write down as a card what the reward can and cannot see" is a page my 4P intervention report should add. My risk-scoring algorithm currently goes out to the client as a bare number. This project's requirement is: spell out what my rating inputs saw and did not see. With "inflammatory markers improved but creatinine was never measured", what exactly is my score derived from? The client cannot judge whether my risk grading deserves trust if they cannot see that layer. This page is something I can add in my next version.
  • The distinction between "inflammation, fibrosis leaking into the omics but not counting as ageing by definition" is exactly the judgement my precision nutrition reports most need and most easily blur. In my intervention reports, "metabolic inflammation improved" and "biological age improved" get used interchangeably. This is a reminder that metric attribution needs its definition stated explicitly, otherwise the client fills in the causal story themselves.
  • The one thing I most want to copy is the statement of its own boundary. No real proteomic data, no real clock, no real trial data, no stored model or agent — every assumed default centralised in one file. Every single number quoted in my intervention reports should carry the same disclosure: where it came from, and whether it was actually run. This is the same rule I recorded in earlier issues as "if it was not run, do not report the number", but today it goes one step further by registering even the defaults in one place.
  • Reality check: ★0, created today, pure simulation, no real data. This is a methodology template, not a product, and certainly not efficacy evidence. I borrow its thinking structure; I cite none of its numbers.

5. "RAG without a vector database" moved one step further today: PageIndex v0.7.2 binds extraction and billing to the same job

URL: https://github.com/VectifyAI/PageIndex ｜ ★40,478 ｜ MIT ｜ A vectorless, reasoning-based RAG document indexer that replaces chunking and vector retrieval with a directory-tree structure, using one client for both local and cloud

What happened

  • Two commits inside the window, but the key action is the release: v0.7.2 was published at 12:44 Beijing time today, only two days after the previous v0.7.1 (11-17).
  • The README's positioning line comes in four parallel clauses: "No Vector DB, No Chunking. Context-Aware Retrieval. Reads Like a Human." The release notes follow the same four-part shape: cheaper than vector RAG (on both the indexing and the query side), faster (trees are created from layout stats), a unified SDK (local or cloud, for index and chat), and it runs on your Claude subscription.
  • Local mode needs no server, no vector database and no API key: client.submit_document("report.pdf") then client.chat("What does the report conclude?"); PageIndexLocalClient(storage_path=...) is the same client as the cloud one — submit, tree, page content, chat and agent tools are all present in both modes, so code moves between them unchanged.
  • The Flash engine is the local default (mode="standard" keeps the classic LLM pipeline): embedded bookmarks are consumed when trustworthy, tree optimization is on by default — optimize="merge" runs the deterministic, LLM-free pass, while "full" (the default) adds LLM expand and runs a wave of nodes concurrently instead of one round-trip at a time.
  • Today's commit is a billing-attribution fix: feat: PageExtractClient.extract(file) uploads the file with its job, so the upload is not charged on its own (#690) — the upload goes in with the job, so the upload itself is no longer charged separately. The other commit is build: lift the litellm cap.
  • The README's update log records the October Page Search API: "find the pages that answer each question in about a second, and send your LLM only those. Cut 97% token cost on document question answering", with a comparison benchmark repository attached.

Why it matters

  • "Cheaper than vector RAG on both the indexing and the query side" lands directly on the cost structure of my 4P platform's AI assistant, if it holds. Both my GRPM nutrigenomics system and the 4P precision nutrition platform depend on RAG over a knowledge base. Cost is not something I have only read in a table — LLM cost goes into my pricing model. A path that runs without a vector database and runs locally is worth measuring once before I consider touching the architecture.
  • "Local mode needs no vector database and no server" matches my deployment reality exactly. My Flask + SQLite stack runs locally on port 8899, and there is a local Ollama qwen2.5:7b on this machine. If the retrieval layer can run entirely on the machine, client health data never has to leave it — the most direct way to deliver on the privacy promise of my 4P platform.
  • optimize="merge" — a deterministic, LLM-free pass — is a design I genuinely like. I keep recording the same principle across issues: compute anything deterministic outside the model. That holds at the retrieval layer too: the directory tree grows deterministically from layout statistics first, and the LLM only steps in when expansion is needed. It is the same idea as moving numeric calculation into tables in my GLP-1 nutrition companion, landing at a different layer.
  • Today's commit, which specifically fixes "the upload being charged on its own", is worth generalising. My content production line has a long-standing puzzle: how the output generated with AI assistance should be accounted for. Binding the upload to the job, so the upload is not charged separately, is drawing a clean unit of responsibility around "one task". My public-account content pipeline and this daily report's build pipeline need the same kind of unit-of-responsibility split.
  • Reality check: ★40,478 but a very fast release cadence (one version every two days), and the README's performance claims (97% token cost reduction, more accurate and faster) come with its own benchmark repository attached. If I cite it I must run my own comparison — I cannot take someone else's benchmark as my own conclusion, and my content specification says the same thing.

3. Trends today

  • The "skills ecosystem" formally became a dependency management problem today. microsoft/apm brings skills, plugins, MCP servers and prompts under versioned resolution with one apm.yml and one apm.lock.yaml, while whyihaveyou/dsh-suite refreshes a living plugin directory every hour and mattpocock/skills and obra/superpowers hold the top of the star charts. For the past two years "how do I install a skill" was answered by each vendor's own README; from today there is a standard answer. For products I hand to other people (the 4P expert packages, the nutrition AI core), the delivery form has to move from "copy this directory" to "one install command" — and that is something I should start next week.
  • Someone filled the gap of "an AI-written interface needs a human-written checker". renderlint renders in headless Chromium at real widths and turns pixel-level defects into build failures, and its new rule text-near-overlap flags text sitting less than ¾ of a font size apart. It also lands squarely on the block I have been dissatisfied with for long — mobile text readability. Every single-file HTML application I maintain (the workbench, the GLP-1 nutrition companion V2, this site) benefits directly.
  • "The reward function and the basis of evaluation must be open to challenge" took shape today in three projects that know nothing about each other. longevity-gym's QC card states what the reward can and cannot see; oya-browser leaves audit evidence by recording a task once and replaying it deterministically; APM moves the policy check from the declared value to the one actually in effect. All three are the same thing: a conclusion must hang off a step that can be traced and independently checked. My 4P intervention report's risk rating is still "a number", and it is missing exactly this layer.
  • "If it was not run, do not report the number" was executed in full again today. longevity-gym states explicitly that there is no real proteomic data, no published clock, no trial-level data and no stored model, with only a handful of aggregate statistics taken from the paper's supplementary tables used to calibrate noise and every other number registered as an assumed default; NutriTracker shipped a release in the nutrition line and the fitness coach ironm writes that every change asks you first; PageIndex today folds upload billing into the job. These four projects hold the same line in three different places — data, process and cost.
  • Category ③ is still thin today, and that thickness is real. Among 10 repositories the highest star counts are foldseek (★1,332) and matchms (★278), with the rest mostly personal or lab projects at ★0 to ★81; the high-star nutrition and health projects had no activity today. I will not pad the table — the high-star gap in the health line shows up about once a month, which means open-source investment in this direction still comes mostly from small teams. As I build 4P health and precision nutrition, that ecosystem gap is itself a piece of opportunity information.
