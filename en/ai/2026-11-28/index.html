1. Google puts the entire deep-research method into a 16-line text file: blind judges preferred its output more than 90% of the time

URL: https://github.com/google-gemini/demolab ｜ ★1,096 ｜ Apache-2.0 ｜ The Gemini team's experimental skill library, using a plain-text skill file to define the scope, delegation, verification and fallback boundaries an agent should follow when doing deep research

What happened

  • On November 27, Google AI Studio's Philipp Schmid announced that the Gemini team had published an experimental deep-research skill in the google-gemini/demolab repository, which recorded 2 commits that day (feat: add deep-research skill and its corresponding merge commit).
  • The skill file is only 16 lines. It is not a model and not a plugin binary — it is a plain-text instruction file that the agent only loads when a task matches its description, the point being not to stuff specialized guidance into every unrelated prompt. The repository README lists two skills: deep-research and gemini-frontend-design.
  • What actually makes it work are five control points: Scope (answer simple questions in one pass, split broad questions into three to five angles) → Delegate (spin up parallel search or browser subagents, each capped at 8–12 steps) → Verify (require primary filings, papers, reports and PDFs; never treat a search-result snippet as a citable source) → Recover (cancel stalled subagents and allow at most one follow-up round) → Report (a two-sentence summary with inline links, and flag where sources conflict).
  • The README offers its own comparison figures: the deep-research skill was "preferred by judges more than 90% of the time" across hundreds of blind evaluations with Gemini 4 models; gemini-frontend-design was "preferred by users 67% of the time against frontend designs with no skills, and 75% of the time against popular third-party frontend design skills".
  • Its distribution method is arguably more notable than its content: the README documents six install paths in one place, covering the Vercel skills CLI, the Context7 skills CLI, Antigravity, Claude Code, Cursor and OpenAI Codex. The repository ships four plugin directories: .agents/plugins, .claude-plugin, .codex-plugin and .cursor-plugin. The license is Apache-2.0, and the README explicitly states that it is "not an officially supported Google product".

Why it matters

  • This is the entry today that lands most directly on how I work. I run a one-person company on roughly eight hours a week with about a month of cash runway, so every output has to be multiplied by AI tooling. But I have been making one mistake consistently: writing research methods into prompts means paying for them in tokens on every single call; writing them into a skill file means they load only when actually needed. demolab's README says this in its very first line — "without bloating every prompt". I can move this "load specialized craft on demand" approach straight into how I design my expert packages and skill packages: one skill file = one clearly defined task type + a statement of its boundaries.
  • The number "16 lines" is a sharp warning for me. My habit when building skill packages is to write them comprehensively — one SKILL.md stuffed with dozens of rules and caveats. The result is that the longer the instruction, the more the agent behaves like it is reading a manual. demolab proves a different point: constraints do not need to be long; what they need is "what to do in this situation, and where to stop". That "cap each subagent at 8–12 steps" and "allow at most one follow-up round" are far more useful to me than any ten lines of "please be careful…". This is directly copyable into my skill acceptance criteria: if I cannot write a skill on one page, I probably have not thought it through.
  • "Never treat a search-result snippet as a citable source" is exactly the rule that most needs to be hard-coded into my own content production. I have always told myself to "cite only primary conclusions traceable back to the source text", but that rule lives mostly in my own discipline. demolab turns it into a gate inside the agent's execution flow — Verify is one of the four control points, not a footnote. That positional difference matters: when a constraint is written as a pipeline step rather than a caution, the odds of it being followed are completely different.
  • The "at most one follow-up round" limit I intend to copy verbatim into my own content discipline. My most common failure in deep-diving a topic is not searching too little — it is infinite follow-up: one question spawns three, three spawn nine, and two weeks later I have no publishable conclusion. Capping follow-up at one round forces me to start writing at the moment the information converges.
  • "Flag where sources conflict" is the phrasing I have been looking for without knowing it. When I write evidence-based content for the WeChat accounts, I constantly hit literature that disagrees. Most tools handle this by picking one and writing it up. demolab's answer is to flag the conflict — which is both honest and hands the judgment back to the reader. For health content this matters especially, because when two sources conflict the correct answer is usually "the available evidence is inconsistent", not a forced choice.
  • To be fair, there are two caveats I want to keep in mind. First, the "90%" is the team's own blind-evaluation number, not an independent replication, so I should not cite it as "using this improves output by 90%". Second, it is explicitly positioned as experimental and declared to be a non-officially-supported Google product. So my conclusion is: I treat it as a writing template to copy, not as an efficacy claim to believe.

2. A local deep-research agent makes "citation auditing" the final stage of the pipeline — and one of its example reports is on GLP-1 semaglutide cardiovascular trials

URL: https://github.com/jolovicdev/shandu ｜ ★16 ｜ MIT ｜ A deep research agent running locally in the terminal and browser: decomposes questions, researches in parallel, audits every citation sentence by sentence, and produces a report sized to the evidence

What happened

  • Version v4.0.0 shipped on November 27 with 12 commits that day, centered on a Gradio web GUI redesign (Redesign the Gradio web GUI with live activity, run options, and linked reports) and tightened release packaging.
  • It splits research into six explicit stages, each backed by deterministic Python checks (the full diagrams live in the repository's ARCH.md): research brief (turn the question into three to eight concrete sub-questions and pick a deliverable shape) → parallel research (subagents work the open sub-questions in parallel across web search and, where papers apply, arXiv, OpenAlex and PubMed; pages and PDFs are read whole rather than from search snippets) → quote and credibility checks (every page is classified — peer-reviewed, official, journalism, vendor, blog — and scored; claims must carry verbatim quotes, and any quote not found on the page is dropped in code) → coverage-driven loop (code scores each sub-question by how many independent credible sites support it; the loop stops once coverage is strong, an iteration adds nothing new, or the budget runs out) → dynamic reports (under the default --detail-level auto, the outline and length follow the question and the evidence, under 300 words per cited source, floor 400) → post-write citation audit (an auditor checks every cited sentence, bullet and table row against the actual evidence behind each [n] marker and strips citations the source does not support).
  • The README gives citation-audit counts for three example reports, and these numbers are more persuasive than any adjective would be: the speculative decoding report has 36 sources, 112 supported, 19 partial, 1 removed; the HTTP/3 comparison report has 25 sources, 101 / 20 / 0; and the SELECT and SOUL semaglutide cardiovascular trials report has 12 sources, 78 / 6 / 0. Costs are given as $1.22 / $0.55 / $0.41, with deepseek/deepseek-flash as the default model and any LiteLLM-supported model substitutable.
  • The interface is a complete product: the terminal UI shows the current iteration, stage tracker, active subagents, pages read and model-call count; the web GUI allows overriding depth, researcher mode, report length, a USD cap, site allow/deny lists, publication start date and whether citation auditing is on; and it can produce a password-protected temporary public link via --share --auth user:pass.

Why it matters

  • This one is close to tailor-made for me, because its example report happens to be about my own GLP-1 project. My GLP-1 Nutrition Companion V2 handles semaglutide dosing, discontinuation and lab-trend tracking, and shandu happens to ship "SELECT and SOUL semaglutide cardiovascular trials" as a fully citation-audited example report — 12 sources, 78 supported, 6 partial, 0 removed. I can use it directly as a reference against my own writing: how its partials are marked, what its one removed citation looked like — things I currently handle purely by instinct.
  • "Claims must carry verbatim quotes, and any quote not found on the page is dropped in code" turns "zero AI hallucination" from an attitude into a code path. In my WeChat posts and courses I have always talked about evidence-based work, but my actual method is "go back and check it myself afterwards" — which is human execution, and unreliable. shandu's approach lets code drop the unfindable citation: this is not "prompt the model not to invent", it is "catch it if it invents". That is exactly the mechanism I want for the references module of my GLP-1 companion: validation should be an independent stage from generation, not a sentence inside generation.
  • That third tier, "partial", is the most valuable design I saw today. My habit when writing is binary: this has a citation / this does not. shandu uses three tiers — supported (the source fully backs it), partial (the source backs part of it), removed (unsupported, so it is stripped). Most real-world conclusions land in partial: the paper describes a subgroup, my headline says the general population. The discipline of marking partials addresses the hardest failure mode in my content — turning limited evidence into a universal claim.
  • "Report length follows the evidence, under 300 words per cited source" is a hard requirement for my time budget of eight hours a week. shandu states plainly that "a narrow factual query stays short instead of getting padded with filler sections; a dense technical or clinical survey expands with comparison tables and caveats". In my previous issue I noted that infinite follow-up is the number-one killer of content production; this is the other face of the same coin — do not pad to look complete.
  • The "USD cap" and site allow/deny list switches are worth copying too. The real cost of running AI as a one-person company has to be predictable and hard-capped. shandu turns the cost ceiling into a per-run parameter rather than something I discover from a bill later. That matches the other note I made: per-pass limits are not a session-level spend ceiling — the budget must be a hard session-level or run-level constraint.
  • To be fair, it has only 16 stars and is a small project. But its value is not scale — it is that it turns "citation auditing" from a phrase in a prompt into the sixth stage of a pipeline plus a published report with counts. I will use it as a methodological reference, not as a dependency.

3. Writing "a 7 mm asymmetric lesion" slips past 99% of privacy rules — someone solved it with 1,024 weights

URL: https://github.com/YauhenBichel/privacy-gate-llm ｜ ★2 ｜ Apache-2.0 ｜ A prompt PHI/PII detection gate: before text leaves the machine for a cloud model, it decides "should this stay here?"

What happened

  • 4 commits this window, centered on hardening after stress testing: fix(guard): stress-test findings: linear time, NaN fails closed, split and hidden values, alongside a v1.1.0 release.
  • The problem it addresses is spelled out precisely: regex rules are good at anything shaped like a marker (sk-ant-…, AKIA…, patient_id: 40219, a base64 image), but they are completely blind to the same information written as ordinary English. The README gives an example — "The woman from Tuesday's clinic, 34, has a 7mm asymmetric lesion on her left shoulder and a biopsy booked for the 20th." — a sentence that passes every privacy rule in today's ruleset.
  • The gap is quantified: on a 206-example gold set, the regex ruleset alone catches just 9.0% (10 of 111 sensitive examples) at a 1.1% friction rate — meaning 101 sensitive examples sail straight through.
  • Its solution is not a fine-tuned chat model but a bidirectional encoder plus a linear head: BAAI/bge-m3 turns text into 1,024 numbers, and a linear head with 1,024 weights turns those into one score compared against a threshold of 0.1209. The README states plainly that only the head is trained; the encoder is used as shipped — which is exactly why it runs on CPU in tens of milliseconds, and why swapping the embedding model breaks it (the head has precisely as many weights as bge-m3 has dimensions).
  • The README supplies a four-row comparison table that is the most convincing set of numbers in today's issue: regex ruleset alone (no AUC, catch 9.0%, friction 1.1%) → hashed word unigrams (AUC 0.7818, catch 98%, friction 83.2%) → Qwen3.5-0.8B, prompted (AUC 0.4609, chance level) → bge-m3 + logistic head v1 (AUC 0.9927, catch 99.1%, friction 5.3%). Five-fold cross-validated: every score comes from a head that never saw that example. On 20 sentences written after training, it catches all 11 sensitive ones and holds 1 of 9 harmless ones. Latency is 34–43 ms at p50 and under 50 ms at p95, measured on a loaded shared box, and 18 ms per text when batched.
  • The project explicitly declares itself "not a medical device" — it only decides whether text should leave the machine and says nothing about what a lesion is. It was formerly published as molecare-privacy-gate (1.0.0 / 1.0.1); after the rename the old package no longer receives updates.

Why it matters

  • This is the most sobering entry I read today, because the "7 mm asymmetric lesion" example describes a person who is actually in a clinical consultation. If I send that kind of conversation to a cloud LLM, no item on a traditional redaction checklist would catch it. My work in 4P precision nutrition and functional medicine naturally produces exactly this — client case descriptions are health information written in ordinary English: no patient_id, no ID number, just "34 years old, 7 mm asymmetric lesion, biopsy booked for the 20th".
  • The line reading Qwen3.5-0.8B, prompted — AUC 0.4609, chance level is the row I most want to copy into my own notes. I have long assumed that "use a small model to judge sensitive content, just add a prompt." Its evidence is that asking a 0.8B model to reason its way to a word does not work, while an embedding model does one forward pass and a linear head decides. That points the same direction as the self-assessed / observed / grounded three-vector alignment I recorded on 2026-11-27 — hand the judgment to a deterministic mechanism, not to another model's subjective output.
  • The engineering fact of "1,024 weights plus a bias, 34–43 milliseconds" is what determines whether I can actually use it. A one-person company on eight hours a week and a one-month cash runway cannot deploy a heavyweight service for a single call. A checker that runs against bge-m3 on my local Ollama, at millisecond latency, needing no GPU, is the kind of thing I can keep in a real workflow long term.
  • Its architectural position is copied too: it is a second gate, sitting behind the regex rules, and it "may only ever add a hold". That means it does not replace my existing redaction rules, only supplements them. This is a far more stable design than "swap in a smarter detector" — any false positive is more acceptable than a false negative here, because it only triggers a human confirmation without changing where the data flows.
  • One particular self-limiting statement in the README is worth remembering: "Not a medical device. This is a privacy tool. It decides whether text should leave a machine and says nothing about what a lesion is." A tool that actively draws the line around what it does not do is rare in what I read. For content work that is the thing I value most — stating boundaries clearly is more credible than claiming capability.
  • To be fair, it has just 2 stars, is a brand new project this week, and the README explicitly notes that "the head was fitted on Ollama's output" and that whether the other two backends give the same verdicts is measured rather than assumed. So my conclusion is: the architecture and the numbers are worth copying, but I will not put real client data through it directly — I will first run its own gold set against my Chinese-language corpus to measure the miss rate before deciding on production use.

4. Nutrition management finally grows a deterministic rule-engine layer: NutriVision writes diabetes, PCOS, hypertension, CKD and pregnancy as explainable rules instead of leaving the judgment to a model

URL: https://github.com/drmedhealth/nutrivision ｜ ★0 ｜ MIT ｜ An open-source, local-first app that turns a meal photo into a condition-aware nutrition score: bring your own key, no backend, no account, with deterministic scoring and swap suggestions for type 2 diabetes, PCOS, hypertension, chronic kidney disease, high cholesterol and pregnancy

What happened

  • 29 commits and one release today, making it the highest-activity repository on today's health line. Its core idea is not "let AI look at a photo and talk about nutrition" but splitting the scoring into two layers: recognizing the food and its grams is one layer, and scoring is a separate layer handled by a deterministic rule engine.
  • The rule engine names the specific item behind each condition: glycemic load for diabetes and PCOS, sodium for hypertension, potassium, phosphorus and protein for CKD, saturated fat for high cholesterol, food-safety warnings for pregnancy, plus allergens and diet-style conflicts (vegan, keto, halal and more). Every result carries its reasons and concrete swap suggestions rather than a bare score.
  • How it handles "zero" shows the author's care: zero-calorie items (water, black coffee) are marked n/a rather than a misleading 0, and anything you manually set to 0 g is not counted, not scored and not saved. These are exactly the two details I am most likely to get wrong in my own engine.
  • Fully local-first: images are decoded, downscaled and JPEG-compressed on your device, and stripped of EXIF/GPS data before anything is sent; food data lives in IndexedDB; keys sit in a Keystore (AES-GCM plus an IndexedDB device key); there is no backend, no account and no tracking.
  • The model side supports Ollama: ollama pull llama3.2-vision, then allow the origin via OLLAMA_ORIGINS to run it locally. That is exactly the shape my local Ollama setup can use.
  • The README is deliberately restrained about its limits: "estimates only, not medical or dietetic advice", explicitly naming CKD, pregnancy, diabetes medication and a history of disordered eating as the cases where you must consult a registered dietitian or your clinician. It states it is not FDA-cleared, does not diagnose, does not treat and does not replace professional care.

Why it matters

  • This is the only project on today's health line that explicitly separates "AI recognition" from "rule-based judgment" into two layers, and that is precisely the structure my own nutrition engine most needs to copy. I have been wrestling with the same problem for a year or two: once a model's output flows straight into a plan, there is no second gate. It confines the model to the layer it is good at (what is this, roughly how many grams) and hands "should I eat it, and what does it do to me" to auditable rules. I can move that layering straight into my GLP-1 nutrition companion and the 4P precision nutrition platform.
  • "Rules written per condition" is directly usable for my precision nutrition business. Four of its six conditions (diabetes, PCOS, hypertension, CKD) land exactly on the populations I have been dealing with all year, and each one is judged by the metric that condition actually cares about — CKD looks at potassium and phosphorus rather than only total calories, which is far more precise than the generic scoring I have been doing. The next step for my engine should be to make "bucket by condition" a structural feature rather than one universal rule set for everyone.
  • "Every result carries reasons and swap suggestions" is exactly the tier my public-account content is missing. When I write nutrition intervention content, the thing I most fear is "eat this" — but what readers actually need is "why, and what to swap in instead". A rule engine naturally produces reasons and replacements rather than conclusions — the same direction as the "attach references, attach evidence grades" discipline I have been pushing for half a year, only that it does it in the product layer while I do it in the content layer.
  • I will copy both of those "zero" rules directly. Marking a zero-calorie food n/a instead of 0 — in a nutrition table, "unknown" and "is zero" are two entirely different things, and I have always relied on the human eye to tell them apart; this time I can make it a rule. And anything manually set to 0 g not being counted, scored or saved — that closes the hole where deleting an item you dislike lifts your score. My engine faces exactly the same problem.
  • Its privacy design is directly relevant to anyone handling client medical data like me: strip EXIF/GPS before sending. When I work on the "Bai-Shi" health project and the 4P precision nutrition thousand-person pilot, I handle client-uploaded lab report photos, and the EXIF on those photos may carry geolocation or device information. I had never written that into my process at all — that is a real gap.
  • To be fair, it is at 0 stars, brand new, and its own disclaimer is longer than its feature list. I will not treat an elegant architecture as a mature product. But it turned "keep the rule layer and the model layer apart" into running code, which is worth more to me than any architecture diagram.

5. The most solid move on today's clinical research line: turning chemical structures in paper PDFs into checked, directly ingestible data

URL: https://github.com/Kohulan/MARCUS ｜ ★31 ｜ MIT ｜ Turns chemical structures in chemistry paper PDFs into checked chemical structures, producing data that can be written directly into the COCONUT natural products database

What happened

  • 23 commits this window, making it one of the densest movers on the ② line. The commit storyline is not new features but reliability: fix(coconut): Send waits for a DOI; a 403 login says to verify the COCONUT email (the wait-for-DOI behavior must be correct, and a 403 login state must point at verifying the COCONUT email), and fix(coconut): the form fills its organism, parts and place when the annotation ends after it opened (form-filling timing when annotation completes after the form already opened).
  • Its processing chain is a full stack: structure recognition with the DECIMER, MolScribe and MolParser models, plus text annotation, R-group (Markush) table handling, and a human review step, finally producing data written straight into the COCONUT natural products database.
  • It is worth calling out that it treats COCONUT's interface boundaries as first-class concerns: wait for the DOI, recognize a 403, ask the user to verify their email when it is missing, and get the ordering of annotation and form opening right. These are exactly the edge cases that only surface when you write data into a real external database.
  • The license is MIT, with dependencies including llama-cpp, docling and ketcher, and topic tags covering chemical structure recognition, cheminformatics, COCONUT, data curation and Markush.

Why it matters

  • MARCUS shows me what an evidence production line looks like when it is not about text — but the underlying logic is identical to what I do in content. It takes raw material out of papers and, through "recognition → annotation → validation → ingestion", produces data that downstream systems can use directly with confidence. What I do is structurally the same: turning research literature into conclusions with provenance that others can use directly. The difference is only the carrier — a chemical structure versus a sentence.
  • "Treating COCONUT's interface boundaries as first-class concerns" is the engineering habit I most need to learn right now. In my evidence-based content, the citation-verification step is usually "I open the original myself and take a look" — with no systematic handling of "the link needs to settle, a 403 needs to be recognized, the source may have changed." MARCUS spent 23 commits fixing exactly those cases. That is a reminder that any automated verification pipeline must treat upstream interface failure modes as formal requirements, not as edge cases.
  • "Structure recognition with three models plus human review" also answers a question I have been carrying. I keep going back and forth: fully model-based recognition, or fully manual? MARCUS's answer is "models first, humans as backstop" — structurally identical to what I do with content: AI drafts, I verify each citation. It gives that structure a concrete, model-level implementation template.
  • It also quietly solves a practical problem I have never resolved: R-group (Markush) structures. Natural products databases contain a lot of "a family of compounds" rather than single molecules, which ordinary SMILES cannot express. I occasionally hit phrasing like "a class of polyphenols" in nutrition and functional medicine reviews and have never found a good way to structure it. MARCUS handles this category specifically, which is a real tool for my ingredient-level content.
  • To be fair, it has 31 stars and is a project narrowly scoped to "feeding COCONUT with data", which is far from my business. I read it as "watching someone take a seemingly simple automation all the way to the point where it can write into a real database" — which is the same class of engineering reference for my content factory and for turning my GRPM nutrigenomics reports into reusable data.

3. Trends today

  • The main thread on today's coding line is "making an agent's trustworthiness into something with a state machine." signet turns skill versions into an eight-state lifecycle — draft → validated → published → certified, plus rejected / deprecated / revoked / archived — where every publication must pass W3C SHACL graph-shape validation, ontology validation, LLM semantic analysis and human review, and is signed with a detached signature after canonicalization in both RFC 8785 JCS and RDFC-1.0. This answers exactly the layer above what I recorded last issue with dokimi — "an instruction existing is not the same as an instruction being loaded." signet tackles the next layer: it was loaded, but is it trustworthy, and is it still current? When I build expert packages with WorkBuddy's expert-manager, there has never been a notion of version, expiry or revocation.
  • On the clinical line, the protagonists are still "verification," but what gets verified has changed. Last issue it was verifying literature and chemical structures (linkml / MARCUS / GroundCheck); today there is an additional layer of verifying "whether a machine may even see this." privacy-gate-llm uses 1,024 weights to decide whether a piece of text should leave the machine, med_fabric explicitly writes that commit-time failures are final and cannot be rolled back, and agentic-orchestration simply has the AI produce only a spec, with plain code validating and executing it while a human approves. All three point at the same judgement: AI output must pass a check that is not itself AI. That is exactly the shape my own "zero AI hallucination" rule should take.
  • On the health line a real structural shift appeared today: from "recording tools" toward "rule engines." In today's group, NutriVision writes diabetes, PCOS, hypertension, CKD and pregnancy as explainable deterministic rules with swap suggestions, and its two "zero" rules (zero-calorie marked n/a rather than 0, manually set 0 g not counted or saved) expose a more fundamental issue — the value of a nutrition score lies not in how well the model sees, but in how well the rules judge. This matters most for my line of work: I have been doing "use a model to estimate nutrition," and today I saw the first runnable implementation that explicitly separates the model from the rules.
  • What deserves its own note on the infrastructure line is that "throttling" has become a product category in its own right. token-goat optimizes prompts and cost, nexus-llm-router provides a drop-in LLM routing layer, Xolotl runs a 552B model as a local coding agent, and mnemo-cortex combines SQLite FTS5 with semantic search for cross-agent memory. For a one-person company working 8 hours a week with roughly a month of cash runway, "saving tokens" and "running locally" are not nice-to-haves — they are the variables that decide whether I make it to next month.
  • One cross-cutting signal: the 87 repositories in this issue account for 1,270 commits inside the window, and 25 shipped a formal release. "Shipped a version number" is becoming the primary way an open-source project says "this is usable now" — and the same holds for this site's content: a daily issue saying "this project is active" is worth less than saying "it released v4.0.0 today."
