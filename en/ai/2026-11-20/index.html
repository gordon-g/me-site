1. A medical and health AI evaluation harness shipped two versions today and split "never graded" clean away from "graded zero": mirobody-eval v0.2.0 and v0.1.0 released on the same day

URL: https://github.com/thetahealth/mirobody-eval ｜ ★389 ｜ MIT ｜ An evaluation harness for medical and health AI agents — the simulated user, the system under test and the judge are all pluggable plugins, and five benchmark suites are reproduced through one basic_runner command

What happened

  • Two versions were published today, v0.1.0 and v0.2.0, with their release timestamps two seconds apart; the repository had 6 commits inside 24 hours, the last at 2026-11-19T13:21 UTC.
  • The core change of v0.2.0 is in the commit message: feat(cli): one line per case by default, and no pass rate where nothing was graded pass/fail — one line per case by default, and no pass rate is printed where nothing was graded pass/fail.
  • The README makes this rule a design point under the heading "Ungraded is not zero": timeouts, connection failures and judge outages are all recorded as error and excluded from the average, and every summary must print the ungraded count next to the graded denominator.
  • The web side added feat(web): show where continuous scores fall in the report and tag bars, so continuous scores show in the report which band they fall into.
  • Another detail is worth noting: feat(web): lay the report list out as a table, and stop pricing unknown models as gpt-4.1 — unknown models are no longer priced as gpt-4.1.

Why it matters

  • This is the same direction as the "don't report a number you didn't run" rule I picked up last issue from nutrition-rag and schemagate, but today it takes a harder form: it's not that nothing is reported, it's that "not graded" is physically separated from "graded and failed". Mixing timeouts and failures into one average lets infrastructure outages masquerade as model weakness.
  • My 4P expert-pack evaluation of 30–50 pairwise comparisons still has a single total score. The first field to add today is an "ungraded count" — which items never ran, and why they never ran (timeout / parse failure / judge unavailable), must sit next to the score rather than inside the denominator.
  • The "don't price unknown models as a known model" rule is even more worth copying. In version 61 of my GLP-1 nutrition companion, if a module runs on a local model, the cost table lists a cloud model's price — that's using someone else's unit price to invent my own accounts.
  • basic_runner running all five suites through one command, with reports carrying a batch id and a sha256 checksum, is the "results carry their own fingerprint" shape — my intervention report export doesn't do that yet: the data and code version that produced a given report should be reproducible and checkable.

2. A medical research agent skill library merged four PRs today and wrote "every skill must pass a domain audit before release" into a hard rule — while its own README skill count doesn't add up

URL: https://github.com/aipoch/medical-research-skills ｜ ★2,073 ｜ MIT ｜ An agent skill library for medical and biomedical researchers, covering five research stages: evidence discovery, protocol design, omics analysis, data analysis and academic writing

  • The README states plainly: every skill is reviewed and evaluated through MedSkillAudit — a domain-specific audit framework for medical research agent skills — before going live, with the auditor open-sourced in the repository's skill-auditor subdirectory.
  • Skills are divided by research stage into eight categories, and the README gives a specific number for seven of them: evidence discovery 79, protocol design 68, omics and bioinformatics 52, clinical research and meta-analysis 61, drug discovery and cheminformatics 26, manuscript writing and submission 66, research workflow and lab management 77.
  • But the repository's own figures don't reconcile: the README header says "550+ medical research agent skills", the body section "What is Awesome Med Research Skills" says "currently including 140 high-quality skills", and tallying independently through the GitHub git tree endpoint gives 605 SKILL.md files (463 under scientific-skills, 141 under awesome-med-research-skills, 1 under skill-auditor); the seven category figures above sum to 429, matching none of the three totals.

Why it matters

  • "A skill must pass a domain-specific audit before release" is happening in medicine and code on the same day (on the code side, mattpocock/skills added a frontmatter parse check today, see pick 4 below). The difference is that the medical-side audit framework is domain-specific — MedSkillAudit is not a generic lint, it's the kind of audit that knows which guideline a medical skill should trace back to.
  • That's exactly what I'm missing for my 4P precision nutrition content and expert packs. My evidence constraints today live entirely as natural-language requirements inside a prompt, with no machine-executable audit layer. If a skill cites literature that was never verified, or writes a "recommendation" as a "conclusion", nothing stops it today.
  • This repository demonstrates the exact failure mode it exists to prevent: a project dedicated to auditing skills before they land has header, body and actual file counts that disagree three ways. It follows that the audit has to cover not just skill content but every number the repository itself publishes. Every "we cover 550 items" claim in my intervention reports has to survive the same tally.
  • Splitting "citation chasing and report standards" into a standalone documentation layer (today's #26 and #21 are both docs PRs) is plain but exactly right: standards evolve on a different cadence from data, and binding them means every standards change touches data and vice versa. In my specification template, the evidence-citation rules should be their own layer.

3. The wearable health data layer landed 27 test-rewrite commits in one go — and the sharpest one is "don't testify on your own behalf with mocks"

URL: https://github.com/the-momentum/open-wearables ｜ ★2,808 ｜ MIT ｜ A self-hosted wearable data layer that unifies Garmin, Oura, Whoop, Polar, Apple Health, Samsung Health, Google Health Connect and others into one schema, served through a REST API with a built-in MCP server for LLM queries

What happened

  • 32 commits inside 24 hours, the last at 2026-11-20T12:10 UTC — of which 27 focus on reworking the test system, and only the remaining 5 are backend features and security fixes.
  • The direction of the test rework is remarkably consistent: test: replace MagicMock httpx patches with respx routes (real route stand-ins instead of mock patches), test: replace sleeps and freezegun with time-machine (frozen time instead of a stubbed clock), test: hash passwords with 4 bcrypt rounds instead of faking them (4 real bcrypt rounds instead of faked password hashes), test: assert API and SDK payloads with dirty-equals, test: generate provider payloads with Polyfactory, test: run tests in parallel with pytest-xdist.
  • The other 5 backend commits are all boundary tightening: fix(backend): fetch Garmin FIT files only from Garmin (Garmin FIT files may only come from Garmin's own source), fix(backend): persist rotated application secret (a rotated application secret must be persisted to disk), fix(backend): limit failed developer logins (limit failed developer logins), docs: correct provider token storage notes (correct the documentation's account of where tokens are stored), feat(backend): let extensions run their own Celery queues and emit webhook events.
  • The README's architectural principle takes on particular weight today: "Provider apps and tokens belong to you" — you register the developer apps with Garmin, Oura and Whoop under your own account, and OAuth tokens are stored in your own database.

Why it matters

  • "Garmin FIT files only from Garmin" is the minimal implementation of data source unforgeability: if device files can enter from another channel, a user can edit the file and set their own heart rate, step count and activity to any value — and those numbers go straight into health models and insurance pricing. If my 4P platform ingests third-party device data, the first check has to be source validation.
  • "Don't testify on your own behalf with mocks" is worth more than those five security fixes. A mock only proves "the code ran under the assumptions I wrote"; it cannot prove "a real provider's response is parsed correctly by me" — test: replace MagicMock httpx patches with respx routes and test: hash passwords with 4 bcrypt rounds instead of faking them are about pulling the tests out of that self-referential loop. My Flask+SQLite backend currently writes third-party API keys straight into a config file and mocks everything in tests; this says exactly what needs to be added: a pass against a real provider's real response.
  • "A rotated secret must be persisted" is a very concrete operational trap: rotate the key, don't persist it, and after a restart the system uses the old key again — the rotation never happened. My Flask+SQLite backend writes third-party API keys directly into a config file — this says rotation and persistence have to be designed as a pair, otherwise rotation is a fake action.
  • The README's "a data platform must not become the middleman" is the architecture principle in this field most worth copying: when my 4P platform ingests third-party health data, the first check is the source, not the format.

Only end-to-end CI finds bugs where the two sides disagree. My 4P expert packs ship via npx skills add, and I have never run my own skills through my own install path — that is an acceptance action due this week.

That's the same structural signal as MedSkillAudit on the medical side in pick 2, just in a different domain.

5. A health data engine turned Chinese symptom coding into explicit rules today: one complaint said twice counts once, and "dizziness plus drowsiness" has to split into two to be coded

URL: https://github.com/thetahealth/mirobody ｜ ★1,644 ｜ Apache-2.0 ｜ A self-hosted health data engine that merges lab reports, wearable data and clinical records into one unified data layer for clinical and nutrition research

What happened

  • 7 commits inside 24 hours, the last at 2026-11-20T04:47 UTC; version 1.6.2 was released the same day (2026-11-19 09:16 UTC).
  • The hardest of them is journal: write 头晕嗜睡 as two coded complaints, and code 嗜睡, 视线发糊 and a temple pain — the commit message spells out why: a self-hoster's journal sentence (a temple throb followed by dizziness and drowsiness, in Chinese) left both complaints uncoded. The reason is that the dizziness-plus-drowsiness compound matched as a whole word cannot be coded, while only the dizziness term alone codes on its own; DeepSeek returned it as one symptom entry on one run and as two on the next.
  • The new rule is deliberately conservative: collect.sentence.plan now attempts a split only when the symptom name is CJK-only, and only when exactly one cut leaves two halves that each code on the symptom axis; a negated compound (dizziness plus drowsiness with a "not"), three complaints, names that code as a whole, and names with two possible cuts all stay as one entry exactly as the model wrote it.
  • At the same time symptoms_zh.tsv gained Chinese vocabulary: three drowsiness variants (somnolence, dozing off, sleepy) → AS99, three blurred-vision variants → FS05, and three temple-pain variants → NS01.
  • Two more commits in the same spirit of "refusals must also be explainable": resolver: refuse a hyphen split only on an immunoassay role word (refuse a hyphen split only when the second half is an immunoassay role word) and resolver: a role tail refuses only when the answer is the other role (a role tail is refused only when the answer really is the other role — that is, the refusal itself is conditional).

Why it matters

  • A Chinese symptom vocabulary plus "CJK-only attempts a split" plus "cut once and both halves must code" — I can adopt this rule set directly. My 4P platform's Chinese chief-complaint and lab-item structuring will hit exactly the same wall: is a dizziness-plus-drowsiness compound one symptom or two, how do you cut a headache-plus-dizziness compound, and how do you read a negated dizziness-plus-drowsiness phrase as a denial? mirobody's answer today is not "make the model smarter" — it is to expand the vocabulary (so somnolence, blurred vision and a throbbing temple can be coded at all) and write the split conditions down as rules that can be looked up, tested and regressed.
  • "One complaint said twice counts as one" is really the easiest thing to get wrong in longitudinal follow-up cleaning, and the one that most distorts trend judgement. My 4P platform tracks metrics and chief complaints across a client's three months; if a client mentions "fatigue" at two visits and that becomes two events, the trend line grows a false inflection point.
  • The "refusal must be conditional" layer is subtler: with immunoassay role words (assay, antibody and the like) as suffixes, the parser can neither split on the hyphen unconditionally nor never split — splitting in the wrong direction turns one test into two, and one marker into two names.
  • The common thread across these three commits is "write edge cases as explicit rules rather than relying on a fallback." That is precisely what I am missing on my lab-report OCR → structured path: parsing today is left to model improvisation, with no lookupable, testable, regression-capable rule table for synonym merging or role-word retention. And the rules belong in the vocabulary file, not in a prompt.

3. Trends today

  • "Not graded" and "graded zero" were split apart for good, and today two projects that have never heard of each other converged on that same principle. mirobody-eval shipped two versions today, recording timeouts, connection failures and judge outages as error outside the average and forcing the ungraded count to be printed next to the graded denominator; fud-ai's Distinguish unreadable diary data from empty export range is doing almost exactly the same thing — unreadable is not the same as an empty export range. A missing value needs its own name and must not borrow the meaning of zero. This should go straight into my report spec: every number must be able to answer "was this never measured, was it measured and failed, or should it not be here at all?"
  • The skills ecosystem grew two "must pass a machine check before release" rules today, one in code and one in medicine. mattpocock/skills validates every SKILL.md's frontmatter with the installer's own YAML parser; aipoch/medical-research-skills runs its medical skills through the in-house MedSkillAudit domain audit framework. The common point isn't "add a lint" — it's "validate along the path the user will actually take." My 4P expert packs' evidence constraints are still natural-language requirements inside a prompt, and that slot is empty.
  • What the wearable health data layer did today was infrastructure for "source authenticity and test honesty," not new features. Of 32 commits, 27 were test rework: respx instead of MagicMock, time-machine instead of freezegun, 4 real bcrypt rounds instead of faked hashes; the other 5 tightened Garmin FIT to Garmin only, persisted rotated secrets, limited failed logins and corrected the token storage notes. The shared premise of that batch is "trust comes from being traceable to its source and not being fooled by your own mocked results" — if numbers can be edited, sources can be spoofed and tests can self-certify, every downstream model is just computing noise. When my 4P platform ingests third-party health data, the first check is the source and the second is a pass against a real response.
  • Chinese health-data coding rules are becoming explicit, and this is today's closest fit to my own work. mirobody today wrote somnolence, blurred vision and a throbbing temple into the Chinese symptom vocabulary and made "attempt a split only for pure CJK names, cut once, and both halves must code" a regressable rule. It also stated honestly why it failed before: the dizziness-plus-drowsiness compound cannot be coded as a whole word, only the dizziness term codes on its own. That is precisely the wall my 4P platform hits when structuring Chinese chief complaints and lab items — and the answer is not "make the model smarter," it is to write the vocabulary and the split conditions as rules.
  • The medical and bioinformatics side is still a day of "solid infrastructure, no flagship project." Only 5 of the 31 repositories on track ② are above ★1,000, and most of the rest are decades-old scientific infrastructure — Galaxy, anndata, salmon, histolab, ProDy — under continued maintenance; the most interesting project in that batch is aipoch/medical-research-skills, which openly admits its own README figures don't reconcile — because being willing to spread an inconsistency out in the open is itself part of having an audit culture. Compared with the health and nutrition track (③, 25 entries), track ③ has even fewer high-star projects, but today it produced several reusable concrete practices: round-robin retry across multi-key providers, stripping account ids and coarsening coordinates during privacy hardening, and using real bcrypt instead of faked hashes.
