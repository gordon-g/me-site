1. 「你的技能到底有没有用」终于可以被测量了：Intel 的 dokimi 给智能体技能做配对 A/B 实验

地址：https://github.com/intel/dokimi ｜ ★39 ｜ Apache-2.0 ｜ 面向智能体上下文的 A/B 测试框架：用配对的开关臂实验，判断技能、MCP 文档源、智能体画像或仓库指引到底有没有提升产出

事件内容

  • 今日 30 次提交，主线是把一条「跑不完的任务」波次收尾：fix(dokimi): leftovers of the trace/bench wave (#1199)、feat(catalog): rank the novelty sweep by new share (#846)、fix(repo-scan): a code span naming the repository's own owner/name is ok (#1252)、fix(repo): a cd after the first command of an if or loop body may not run (#1182)。这些提交共同指向的是「让测量工具本身在边界情况下不出错」，而不是加新功能。
  • 它要回答的问题写得很直白：「Does this context help?（这些上下文有帮助吗？）」 方法是把同样的问题或编码任务放在不同上下文条件下各跑一遍，比较结果，再去看差异来自哪里。
  • 它的功能被拆成 39 张独立的功能卡，每张卡都写明「今天能做什么、在哪里停下」，并且 README 明确说开放 PR、未完成的流程与研究方向都会被收录，但会标注为未发布功能，不当作已发布能力宣传。
  • 「技能里哪一部分有用」这一问，它用 novelty（新颖性）来量化：把技能里的每一条断言问模型两遍——一遍不带技能、一遍带技能——然后由另一个模型来评分，每条断言落入四种结论之一。
  • 它把几个问题拆得很干净：技能是否被真正加载（发现、路由、工具偏好、指令加载）、仓库指引是否起作用（静态断言、作用域、可执行任务、规则证据）、评分是否可信（评分方法、裁判检查、grounding）。
  • README 里最有分量的两句话是自我限定：「Read the measured delta, uncertainty and task-level evidence together; one passing example does not establish a general benefit.」以及「A skill can teach something new without improving a task, and an instruction can exist without being loaded.」——它明确区分「教会了新东西」与「让任务做得更好」，也明确区分「指令存在」与「指令被加载」。

值得关注的原因

  • 这一条正面命中了我做专家包与技能包时最想做、但一直没有方法的一件事：证明它们真的有用。 我用 WorkBuddy 的 expert-manager skill 建了一整套标准化专家生成工作流，也有一堆自建技能。但到目前为止，我判断一个技能好不好，靠的是「我自己用它顺不顺手」——这是印象，不是证据。 dokimi 给的正是我缺的那一环：同一批任务，开臂与关臂各跑一遍，报告实测差值与不确定度。 落到我的项目上，就是给我的「4P精准营养观察」内容生产流程做一组配对实验：带技能包 vs 不带技能包，看引用核验的漏检率、方案完整度、耗时各差多少。这个数字一旦有了，我的技能包就从「我觉得有用」变成「实测有效 N%」。
  • 「一个通过的样例不构成普遍收益」这句自我限定，和我上期记下的 Empirica 那条「weaker evidence cannot carry a higher confidence」是同一条纪律的两个版本。 我一直在给自己的内容生产定规矩：「只引用能追溯到原文的一手结论」。这条规则反过来也适用于我自己的工具：用一个案例跑通了，不等于这个技能在所有任务上都有用。 我准备把这句话直接写进我的技能验收标准——要「均值 + 不确定度 + 任务级证据」一起看，不接受单点成功。
  • 「指令存在 ≠ 指令被加载」这一条，戳中了我一个真实的盲区。 我一直假设我把规范写进 SKILL.md 之后，智能体就会照做。dokimi 专门把「发现、路由、工具偏好、指令加载」拆成独立维度来测——这说明「我写了」和「它读了并执行了」是两件事。 我可以拿它去测我自己的技能包：我写的「强制循证 + 参考文献」到底有多少比例真正进了输出？这个测量方式，比我凭感觉判断「好像有在遵守」要可靠得多。
  • 它把「评分是否可信」单列成一层，这个设计比多数评测工具严谨。 README 写得很诚实：「Grader controls help expose blind spots; they do not prove a verifier is infallible.」——裁判本身也会出错。 这意味着它不会给我一个「通过率 87%」就收工，而是继续追问这个 87% 是怎么算出来的。这个态度，比它给我的任何数字都更值得我抄。
  • 诚实地说，它今天只有 39 星、30 次提交，README 里多处写明「这测的是检索已知答案段落，不是生成答案的质量」这类边界。 所以我的判断是：它是目前我见到的唯一把「技能有没有用」当成可测量问题来对待的开源项目，但它的输出仍然需要我自己的任务集来验证。 我会用它测我的技能包，但不会把它的分数当成对我产品的评价——它测的是「在给定任务集上」，不是「在我的全部业务上」。

2. 营养科研终于有了完整的技能包：墨尔本大学 Food Science Group 把食品营养的证据纪律做成了可复用技能

事件内容

  • 今日 5 次提交并发 v1.53.0，主线非常明确且非常「我这类人该关心」：「核对期刊规则」。提交信息逐条写着：Audit journal guidelines, add section renumbering rule (v1.53.0)、Verify 14 journals against official guides and correct their rules、Check two journals per publisher and add publisher-wide guidance、Align formatting-constraint blocks with verified per-journal rules。也就是说这一版的全部工作量，都花在「把期刊的投稿格式规则逐条核实并修正」上。
  • 技能集分两套：food-*（食品与营养科学）与 agri-*（农业科学），后者复用前者的引擎，只替换「人格、证据库与期刊路由」。
  • 期刊覆盖以类别计数：食品科学与技术 60 种、营养与饮食学 59 种、农业科学 Q1/Q2 230 种、多学科与跨学科 35 种。农业期刊清单来自 JCR 2025，覆盖七个农业类别（Agronomy、Dairy & Animal Science、Soil Science、Agricultural Economics & Policy、Horticulture、Agricultural Engineering）。
  • food-deep-research 由 12 个 subagent 组成，流程写得很细：scope → design → discover → screen by journal ranking → validate every source → extract & verify evidence → synthesize → stress-test → write & format → editorial + integrity review loop，输出 APA 7.0 格式完整综述。
  • 系统综述模式内置 PRISMA 2020：固定研究方案、至少 3 个数据库、标题/摘要/全文三步筛选、两名独立审阅者 + 仲裁者、PRISMA 流程图、结果表、OHAT 偏倚风险评估，且明确要求「基于纳入标准而非期刊排名来设计检索策略」。
  • README 里有一段自我限定写得非常克制：拿不到全文的付费墙来源「只读摘要级，并标记为未核验，绝不会被当作读过全文来总结」；food-fetch 明确「不会绕过付费墙、DRM、登录或 2FA」；模型「没有自带的实时文献数据库，所有文献都通过工具进来」。
  • 免责声明原文：「AI can make mistakes. Large language models can produce fluent but incorrect statements, invented references, and unsupported conclusions.」以及「These skills are research assistants, not authors.」同时要求使用者「诚实披露 AI 使用」，并明确写「This is a quality edit, not a disguise. It is not a way to hide AI involvement, defeat an AI detector, or evade a journal's or university's AI policy.」

值得关注的原因

  • 这是本期唯一一个「正好长在我的业务上」的仓库，而且它是我做循证内容最缺的那块能力。 我每天在公众号和「4P精准营养观察」里写营养干预内容，引用文献这件事我一直靠人工把关——但我没有一套成体系的检索、筛选、取证、写作、审稿流程，全靠临场发挥。 它把这条链路做成了可复用技能，而且明确区分「读了摘要」和「读了正文」——这个区分我自己都未必每次都做得干净。
  • 「Verify 14 journals against official guides and correct their rules」这一条，就是我该学的工作方式。 我写营养内容时也会引用期刊标准（比如某个营养学会的营养素参考摄入量、某个期刊对补充剂冲突声明的写法要求），但我从来没有系统核对过「这条引用的是哪个版本、原文到底怎么写的」。 它的做法是：去官方指南逐条核，核完再改。 这正好补上我「引用了但没核对原文」这个最常见的漏洞。
  • 它那几句自我限定，我准备逐字抄进我的写作规范。 特别是「拿不到全文的付费来源只读摘要级并标记为未核验」——这条把我的内容分成了「我读过原文」和「我只读了摘要」两档，而这两档在我过去的文章里是不分的。 分了档，读者才知道我哪句话的证据强度更高。这恰好是我一直想推的「证据分级」在内容侧的具体做法。
  • 「These skills are research assistants, not authors.」这句话，回应了我最担心的一件事。 我这半年反复强调「零 AI 幻觉」，但我自己也在用 AI 写内容。它给出的边界很清楚：AI 负责检索、组织、格式与找茬，作者负责判断与署名。 我把这条边界用在自己身上反而更站得住——我不需要假装没用 AI，我需要保证用 AI 之后每一条引用都回到原文。
  • 它还提醒了一件我差点忽略的事：「披露 AI 使用」。 我写的是面向大众的营养科普，如果我在里面用了 AI 做检索或组织，是否需要声明、在哪个平台怎么声明，这是一个我该正面回答而不是含糊过去的问题。 它把「披露是义务，不是选择题」写清楚了。这对我做「4P精准营养千人先锋项目」这类面向客户交付的内容也有直接影响——SOP 里如果没有这条，交付时就是风险。
  • 需要说清楚的边界：它今天只有 48 星，且它整条能力链依赖外部检索工具与可访问的全文。 我本地跑 qwen2.5:7b 撑不起「12 个 subagent 并行 + 引文网络爬取」这一档。所以我的用法是：借它的流程纪律（尤其是取证分级与期刊核对），而不是直接装来跑。 技能包可以抄进我的规范，模型能力得另外解决。

3. 每一条引用都能被点开看原文：TraceableAI 把 PRISMA 系统综述做成了可核验的流水线

地址：https://github.com/lauPhilip/au-btech-literature-review-agent ｜ ★2 ｜ Apache-2.0 ｜ 丹麦奥胡斯大学 BTECH 出品的文献综述智能体：跑完整 PRISMA 2020 系统综述，并把每条引用逐句与原文比对，标绿 / 标橙 / 判定为不支持

事件内容

  • 今日 100 次提交并发 v0.6.0，是本期提交量最高的项目之一。本期提交集中在两条线：一是合并 PR 与补 changelog（Merge pull request #694 from lauPhilip/docs/changelog-688-690 等），二是修功能（fix/selfcheck-and-search-cap、fix/report-page-paging）。
  • 它先写综述方案，再检索、再筛、再写——最后一步才是自查引用。README 的流程图明确写着 A[Artifact] → C[Citation check and repair] → R[PRISMA report + verifiable archive]。
  • 引用判定的粒度是「句」而不是「篇」：每条被引用的句子，都要找出论文里支持它的那一段原文，找不到就明说找不到。判定结果分三档：supported（论文这么说）/ partly supported（只被部分支持）/ not supported（论文不支持），报告里用绿色与橙色区分。「A sentence that claims more than its paper is rewritten to fit the quote and checked again」——说得比论文多的话会被改写到与原文相符再复核一次；论文完全不支持的引用会被移除，连同它的主张一起移除。
  • 「Two of everything」：每条记录都由两个独立提示各筛一次，主题也各自分配两次，一致度按 Cohen's kappa 报告，和人类审阅者一个口径。
  • 「The methods are facts, not prose」：方法部分由这次运行实际做过的事情生成，因此不会描述一个没检索过的数据库或没发生过的步骤。
  • 「Everything is on file」：综述方案、原始数据库返回、每条筛选决定及其理由、每次模型调用、引用审计结果，全部用 SHA-256 指纹化保存，可作单个压缩包下载，内含可编译的 LaTeX 稿件与 BibTeX/RIS 文件。
  • 它自己给自己划了边界：README 原话是「TraceableAI is a co-pilot for a human reviewer, not a replacement. Its checks make errors findable; they do not make them impossible.」

值得关注的原因

  • 这一条直接解决了我内容生产里最具体、也最要命的一个漏洞。 我公众号里引用文献，读者点进去看到的是「参考文献列表」——但没人知道我说那句话的时候，是不是真的读完了那篇论文，还是只读了摘要。 TraceableAI 把这件事做成了产品功能：每个引用后面挂着原文出处与判定结果，点开就能看。 我的读者是拿结论直接做决策的人，他们需要的恰恰是这个「回去查」的入口。
  • 「说得比论文多的话会被改写」这条规则，正是我转述研究时最容易犯的错。 我最常见的一类问题是：原文写的是「在小样本中观察到相关性」，我写成「研究证明」。它把这句话变成一条机器可执行的改写规则——超出原文的部分必须收回到原文能支撑的范围内。 我可以把它当成我自己稿件上线前的一道自动检查。
  • Cohen's kappa 这个细节让我对它的信任度上了一个台阶。 多数 AI 综述工具只报一个「引用准确率」，而它报的是双筛一致度——这是人类审阅文献的方法学标准，不是 AI 工具的 KPI。 一个愿意用审稿人口径衡量自己的项目，说明它知道自己在做什么。
  • 「Everything is on file + SHA-256 指纹」这个做法，对我的「百十工程」数据有直接参考价值。 我手上那批 2022–2025 的参与者观察指标分析，如果我要写出来，最怕的是「我说的是否真的来自那批数据」。 它的做法是：把原始返回、每一步判断与理由、每次调用全部留档并指纹化。 我的项目文档体系里缺的正是这一层。
  • 它把「方法部分由实际做过的事生成」这条规则也用上了，这一条我该抄。 我写的干预方案文档里有一节「研究方法」——那一节如果是照着理想流程写的，而不是照着我实际做过的事写的，那就是一份不诚实的文档。
  • 但它只有 2 星，而且它自己明说「不能取代人类审阅者，只是让错误可被发现」。 我要看清楚的边界是：它把「引用存在」和「归因准确」这两件事分开了——引用真实存在 ≠ 这篇论文支持这句话。 这两件事我过去也是混着做的。我的结论是：借它的判定机制和留档方式，不把它的三色标记当成「已验证」。

  • 五层认知简报 + 连贯性审计 + 修补循环这一套，对应的是我的公众号文章结构问题。 我最常犯的错不是事实错，是「文章读起来前后不一致」——第一节说的结论，第四节悄悄换了个口径。它把这件事变成了一个可运行的审计动作（先审连贯性，再按优先级修补），而不是「写完自己通读一遍」。 这是我可以直接用的工作流。

  • 它把 CI 的重检查挪到本地 pre-commit / pre-push，这条对一人公司比我想象中更值钱。 我每周只有 8 小时，任何「每次都要等一遍完整检查」的流程，对我来说都是直接的成本。 它的解法是：远端只跑关键门禁，重检查放本地、放在你本来就要提交的时刻。 这条我要抄进我的技能包验收流程。
  • 「证据包」（evidence_pack）这个概念，是它把「证据」做成了可传递的物件，而不是散落在对话里的一段引用。 我上期记的判断是「证据要单独成层」，它就是那个形态的一个可运行实现。
  • 边界要说清楚：它今天只有 15 星，v1.2.0 刚发；而且它的重心是临床与生物医学论文写作，不是营养科普。 它的质量钩子有 79 个、新颖性阈值是 75/100，这些数字我只能当它自己的设定来读，不能当成通用标准。 我的用法是借它的角色分离与证据分层结构，不是用它产出内容。

5. 证据账本被写成了可执行脚本：ai-research-workflow 用五层审计和「幻觉率」卡住 AI 编造

地址：https://github.com/zhuowenzhang288-web/ai-research-workflow ｜ ★2 ｜ MIT ｜ 现象驱动的跨平台科研工作流 skill：查新取证、选题漏斗、实验日志、引用核验与五层审计，含 8 个零依赖脚本，装在 Claude Code / Codex / Cursor / opencode / DSH 上都能用

三、今日趋势观察

  • 「有没有用」正在从一个感觉问题变成一个可测量问题。 今天三个项目各自从不同角度撞向同一件事：intel/dokimi 用配对 A/B 实验测「这份上下文有没有提升产出」，zhuowenzhang288-web/ai-research-workflow 用「引用核验 + 幻觉率 HR>0 即 FAIL」测「这份说法有没有证据」，lauPhilip/au-btech-literature-review-agent 用逐句原文比对测「这条引用撑不撑得住这句话」。三者的共同点是：都把判定从「看起来对」换成了「跑一遍看数字」。 对我来说，这三个项目合起来构成了一套完整的自查链——产出 → 独立检查 → 量化差值 → 保留不确定度。
  • 证据分级从「有/无」走向了「三档 + 可点开回溯」。 u9401066/med-paper-assistant 用 🔒VERIFIED / 🤖AGENT / ✏️USER 三层标记区分证据来源；lauPhilip 用绿/橙/不支持三色标注每个引用句的支持度，并把原文出处挂在编号后面；PangenomeAI 则干脆把「拿不到全文就只读摘要级并标记为未核验」写成硬规则。三套做法形态不同，但都在回答同一个问题：读者点开这条引用时，应该知道多少。 这对我最重要的一点是——分级不是发表后才加的严谨，它是产出流程的一部分，不是补救措施。
  • ③ 健康营养这条线今天最值得注意的不是产品，是三个仓库同时暴露的同一个结构性问题：数据从哪来、以及是不是只有一个数据源。 mandalarigabriele/intake 选择「实时读取、绝不落库」，代价是它的长期历史能力完全依赖 Nutrition 这一个服务；gerardrecinto/robo-trainer-mcp 明确「唯一会外发的是食品搜索」，其余训练与营养数据留在本机；jare0014/obsidian-health-connect 走的是另一条路——直接对接 Google Health v4 REST API，并且因为 Google 写接口不支持正念写入，正念数据只能留在本地 Vault。三个项目在「数据归谁」上给出了三种不同答案，但没有一个项目假设自己只有一种数据源。 这对我做「百十工程」数据整理是个直接提醒：单一数据源的方案在我这里是风险，不是我能接受的简洁。
  • 「本地优先」已经从口号变成了具体的架构选择，但代价各不相同。 juyterman1000/entroly 的代价是「压缩必须是可回溯的」——它给每份证据出回执、连被省略的原文都能字节级取回（README 报 66/66）；angelnicolasc/graymatter 的代价是「记忆要能被导出」；kele551/health-db-skill 的代价是「脚本默认不联网」；mandalarigabriele/intake 的代价是「数据不落库」。「本地优先」这四个字本身不构成保证——它必须搭配一条「怎么证明它真的本地、真的可回溯」的机制。 这几期下来我越来越确定这一点：任何隐私与本地性的主张，都得配一个可验证的证据出口，否则只是文案。
  • 今天④线的主题词是「省」与「护栏」，而不是「更聪明」。 entroly 按 token 预算选证据、graymatter 号称减 90% token、tokenx 做 2KB 的高精度 token 估算、predikit 把训练好的模型接进智能体省掉重训、OpenAPPA 做确定性护栏、pi-warden 拦截破坏性命令与密钥外泄、QuesmaOrg 整理 token 经济学、jjiantong 收录 KV cache 优化综述——八条线指向同一个现实：智能体的成本与风险，已经和它的能力一样成为一等公民。 对我这种「每周 8 小时 + 约 1 个月现金跑道」的一人公司，这批项目比任何新模型都更该看。
