值得关注的原因

  • 这条对我这一行是方法论级的信号，不是一个工具推荐。我此前一直担心的那件事——「AI 参与临床研究，但推理过程不可查、数据要出本机」——这里给出了一个工程解：把「数据不出基础设施」做成开关，而不是靠承诺。三道闸门（容器禁网、默认拒绝防火墙、本地文献库）都是可验证的配置项，不是文档里的一句承诺。

3. 代码评审开始用确定性规则引擎压制自然语言技能：阿里的 v1.14.1 把「质量不稳定」写进 README

地址：https://github.com/alibaba/open-code-review ｜ ★55,440 ｜ Apache-2.0 ｜ 阿里的混合架构代码评审工具：确定性流水线 + LLM Agent 双向复核，行级精确定位，内置多语言规则集（NPE、线程安全、XSS 等）

事件内容

  • 今日 7 次提交，窗口内发 v1.14.1；提交类型分布很杂：feat(i18n): add Turkish README, site docs and VS Code localization、fix(rules): recognize BOM-prefixed Objective-C source、refactor: adopt modern Go stdlib helpers、fix(tool): reject workspace named pipes before opening、fix(examples): fail GitFlic and Gerrit jobs when ocr review fails。
  • 其中两条直接关系到评审口径本身：docs(skill): respect review-only intent for mispositioned findings（尊重「只审不改」的意图）与 feat(skills): include behavior and impact in native and delegated reviews（在原生与委派两种评审里都带上行为与影响）。
  • README 把设计前提写得很清楚：「用 Claude Code 这类带 Skills 做代码评审的人大概都遇到过这些问题——质量不稳定：自然语言驱动的 Skills 难以调试，评审质量会随提示词的细微变化而大幅波动。」
  • 对应的解法是核心设计：确定性工程 × Agent 混合——规则按文件特征精细匹配，把模型的注意力收窄，README 明确称模板引擎式的规则匹配「比纯语言驱动的规则引导更稳定、更可预测」。
  • 两种使用模式：原生模式与委派模式（delegate），各自有独立的 skill（open-code-review 与 open-code-review-delegate）；两者都要求 Git ≥ 2.41 与 ocr CLI，只有原生模式需要 OCR 模型供应商。安装方式是 npx skills add alibaba/open-code-review。

值得关注的原因

  • README 里那句「自然语言驱动的 Skills 质量不稳定」是我今天读到最扎心的一句，因为它描述的正是我自己那条路的现状：我的 4P 专家包两两对比评测，本质上就是「LLM 出题 + LLM 出答案 + LLM 打分」的全闭环自评，而 README 明确说这类做法会随提示词细微变化而波动。阿里的解法不是让 prompt 写得更好，而是把一部分判断挪回确定性规则引擎——这是「自评闭环必须有外部钉子」的一个具体工程形态，比我上期记下的「加确定性外部测试」更具体：规则匹配要落到文件特征上，而不是落到模型的注意力上。
  • 「评审只审不改」这件事被写成了 skill 层的意图约束，这正是我的报告生成与自评系统缺的边界。我的干预报告生成器目前没有「只评不改」这种模式：一旦触发自评，产物就可能被顺手改掉。意图需要是产物的一部分，而不只是调用方的一句叮嘱。
  • v1.14.1 里 fix(tool): reject workspace named pipes before opening 这一条值得单独看：在打开工作区文件之前先拒绝命名管道，这是把「打开一个路径」当成潜在不可信输入来处理。我的 4P 平台会导入化验报告 PDF 与图片，这类「路径即输入」的地方同样该有这一道检查。
  • MIT 之外它是 Apache-2.0，★55,440，且支持 npx skills add 一条命令装到 Claude Code / Codex / Cursor / Kimi Code——这正是我在 4P 专家包交付形态上想要的样子：交付物必须是一条安装命令，且能在用户已有的任何一个 agent 里跑起来。

4. 网关开始替模型兜底：Manifest 把「失败自动换模型」和「每一分钱都记账」做成默认

地址：https://github.com/mnfst/llm-gateway ｜ ★7,650 ｜ MIT ｜ 开源 LLM 网关：把 API key、订阅与本地模型接到同一个 OpenAI 兼容端点，按需路由、失败自动回退换模型、逐笔记账

事件内容

  • 今日 4 次提交，窗口内发 manifest@6.29.3；提交全是修实际故障的：fix(backend): map saved reasoning_effort/max_completion_tokens on Responses routes、fix(backend): map Gemini LANGUAGE and IMAGE_* block reasons to content_filter、List the GPT-6.1 Sol Bedrock Runtime profiles in model discovery。
  • README 的定位句是 "AI Agents that don't break"，核心能力列了五条：自定义路由（API key、订阅、本地模型、自定义供应商）、成功与失败的完整 body 日志、逐笔记账并设置提醒与限额、查询失败时回退到其他模型并自愈坏请求。
  • 部署路径给得很全：Render、Railway、AWS CloudFormation、GCP Cloud Shell 一键部署，Docker 镜像 manifestdotbuild/manifest。
  • 注意这三个修复的方向：把保存的 reasoning_effort 与 max_completion_tokens 映射到 Responses 路由上（此前参数存着没生效）、把 Gemini 的 LANGUAGE 与 IMAGE_* block reason 统一映射为 content_filter（此前安全拦截与其他原因混在一起）、在模型发现里补上 GPT-6.1 Sol 的 Bedrock Runtime profiles。

值得关注的原因

  • 「失败自动回退换模型」+「逐笔记账」这两条合起来，是我这一行正在做的事的现成参照。我本机既有本地 Ollama，也接了 OpenRouter 这类网关，还踩过「国内版客户端把国外供应商硬编码隐藏」和「中转站质量参差」的具体坑——但我的所有调用都没有统一的记账层，也没有任何自动回退。一次调用失败就是失败，然后我手动换一家重试。把这个「失败—换模型—重试」自动化，等于把「模型不可用」从我每天的偶发故障变成一个已被处理的分支。
  • reasoning_effort 存着没生效这个 bug，是一个只有大规模使用才会暴露的问题。我在 models.json 里手写过 reasoning_effort 之类参数——参数存了、请求发出去了、服务端忽略了，而我这边看不到任何提示。这正是「静默失效」最典型的形态：一切看起来正常，除了效果比预期差。网关把它修掉，等于承认「参数被吞掉」是真实存在的故障类型。
  • 把 Gemini 的安全拦截与其它 block reason 分开映射到 content_filter，是一个诚实的错误分类设计。内容被安全策略拦下，和请求格式不对、和模型超时，是三件完全不同的事——混在一起报，用户就只能靠猜。这一条和上一期 clinosim 那条「只有医嘱存在才说管理已开始」是同一个原则：错误也要说清楚自己是什么。
  • MIT 协议、OpenAI 兼容端点、可自托管，意味着它可以插在我现有的任何调用链前面而不改客户端代码。对一个「每周 8 小时、约 1 个月现金跑道」的一人公司来说，「不中断 + 看得见花了多少钱」这两件事的优先级高于任何新能力。

三、今日趋势观察

  • ⭐⭐⭐ 「数据不出本机」今天从理念变成了可勾选的配置项。 openscientist-io/openscientist 的气隙模式给出三道具体闸门：分析容器启动即禁网、智能体容器置于默认拒绝防火墙后（仅可达数据库 / 内部执行代理 / 模型端点）、文献检索改查本地 PostgreSQL 里的 PubMed 基线（约 4,000 万篇），且只在自托管安装可用；14790897/sleep-secret 强调「音频不出设备，没有账号也没有服务器」；GeiserX/OwnGenome 是「100% 本地、Docker 驱动」的全基因组流水线；GeiserX/OwnHealth 把化验、病历、可穿戴与基因组收进同一个自托管存储；ulsklyc/yuvomi 与 TraceApps/nutritrace 分别主张「数据留在自己手里」与「无遥测、无云同步」；cactus-compute/cactus 把端侧 agent 整包压到 50MB 以内。六个互不相识的项目在做同一件事：把「隐私」从一句承诺改成一组配置与部署形态。 对我这一行最直接的映射是：我的健康数据平台如果要交付给机构或企业客户，「数据不出基础设施」必须是可配置的开关，而不是文档里的一句话——这一条我目前的 4P 平台还没做。
  • ⭐⭐⭐ 授权、有效期与审计事件今天被拆成了独立的一等公民。 nightscout/nocturne 写明「授权与委托只在主体有效期内生效」、fix(setup): the owner step resumes only the subject it recorded for the tenant、feat(members): joining and leaving are audit events of their own，配套还有团队邀请链接、管理员 / 操作者切换、Caretaker 角色；iflytek/skillhub 把 RBAC 与审计日志做成企业级技能注册中心的标配；GeiserX/OwnHealth 让「未归位的文档与刷新令牌在没有密钥时不可读」；Yinglianchun/Serein 在写事件前先厘清指代与归属。这五条是同一件事的不同切面：权限不是一个布尔开关，而是一串带时间窗、带归属、可审计的事件。 我的 GLP-1 营养伴侣已有「家庭健康档案」的多成员概念，还差的就是主体 + 有效期 + 审计事件这三件套。
  • ⭐⭐ 自然语言驱动的技能被公开指认为「质量不稳定」，确定性规则引擎开始承担判断。 alibaba/open-code-review 把这句话直接写进 README：「自然语言驱动的 Skills 难以调试，评审质量会随提示词的细微变化而大幅波动」，解法是把一部分判断挪回按文件特征匹配的模板化规则引擎（称其比纯语言驱动的规则引导更稳定可预测），并同时提供原生与委派两种模式、两个独立 skill；intellectronica/ruler 做的是同一件事的极简版——把同一套规则套到所有编码 agent 上；chgagne/claude-skills-research 今天的提交记录里写着「comparing-papers closed after C3」「C3 results: axis answer table does not widen comparing-papers reviews (real non-plant issues 0)」，用编号实验与「真实非植入问题为零」的判据来验收评审技能。「真实非植入问题 0」这个指标是我今天读到最实在的一行——它把「评审技能好不好用」变成了一个可数的事实，而不是一个印象。
  • ⭐⭐ 参数被静默吞掉，是今天被反复修的一类故障。 mnfst/llm-gateway 修「保存的 reasoning_effort / max_completion_tokens 在 Responses 路由上没有被映射」，修「Gemini 的 LANGUAGE 与 IMAGE_* block reason 没有统一映射为 content_filter」，并在模型发现里补上 GPT-6.1 Sol 的 Bedrock Runtime profiles；GeiserX/OwnGenome 修「在 INPUT=vcf 时，说清楚 BAM 并没有被读取，而不是报『No BAM found』」；Yanstd888/9routerx 修「用户轮次尾部的空消息被丢掉」；omnicore 之外还有 agentclientprotocol/registry 每天更新 agent 版本号。四个修复指向同一类问题：请求发出去了、服务端照单收下、但有一层没生效，而调用方看不到任何提示。 这类故障最贵的地方在于它不报错——我的所有调用目前都没有这一层校验。
  • ⭐⭐ 健康线的重心今天在「共享与归属」，不在「记录与展示」。 nightscout/nocturne 一天把团队、邀请链接、管理员 / 操作者切换、Caretaker 角色、加入退出审计事件全部铺出来；Paco5687/GlucoPilot 把化验项也纳入临床假设列表（今天的新提交就是这个）；GeiserX/OwnHealth 同时接入 LibreView 与 Dexcom Clarity 的 CSV 导入，并从 FIT 文件导入运动心率、距离与能量；andreroxhage/meal-prep-agents 在做「购物清单别买家里已有的东西」这种家庭场景下的常识约束。四个项目都在回答同一个问题：这份健康数据在几个人之间流动时，各自能看到什么、谁该负责。 我这一行的「家庭健康档案」如果只做到「多成员 + 时间轴 + 导出」，就还差这一层。
