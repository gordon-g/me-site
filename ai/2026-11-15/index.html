1. 把「可验证」写进运行时本体：Atomic 用显式执行图替掉「希望它照做」

地址：https://github.com/bastani-inc/atomic ｜ ★883 ｜ 许可证未声明（仓库内 LICENSE 为自定义条款） ｜ 用自然语言定义编码智能体的流程（阶段、检查点、审批门），把工程过程编译成显式可检查的执行图

事件内容

  • 今日默认分支超过 100 次提交（接口按 100 上限截断，实际更多），主线是「可信执行」：仓库内近期提交包括 fix(fork-source-project-trust): fork another project's workflow only when that project is trusted、fix(worktree-pool-stale-lease): fix/worktree-pool-stale-lease、test(resume): accept records without a tenancy, and keep a renewed lease across checks、fix(snapshot-objects-survive-gc): fix/snapshot-objects-survive-gc。
  • 仓库自我定位写得很直接：「The verifiable coding agent runtime」，并明确把「复杂运行可能要几小时、几天甚至几周」当作设计意图，而非缺陷——理由是快速编码智能体那一遍会留给你的东西，Atomic 自己做完并验证。
  • README 的承诺句是「backed by evidence instead of another round of manual prompting」，即输出物是证据链而不是又一轮人工提示。

  • 近期多条提交集中在「租约 / 快照 / 信任边界」这类失败恢复语义上，而不是提示词调优。

值得关注的原因

  • 这是连续几期「技能要可评测」这条主线的运行时版本答案。 前几期我记的是技能库该配 evals（cqframework 一技能一 evals）、该有版本号（ASB 绑定 commit 与 tree digest）、该显式建模证据缺失（ontology-atlas 写明「missing evidence shows as unknown, never as safe」）。Atomic 补的是最后一环：评测不该只是一堆测试用例，而应该是执行图里一个可以被调度、被审批、被追溯的节点。

  • 「复杂运行可以跑几天」这句话直接回应了我一周 8 小时的硬约束。 我之前一直在纠结「是该少读几个仓库还是该多读」，Atomic 的答案更工程化：不是每次都跑重的流程，而是让重流程成为运行时里一个显式可选的档位——平时跑快档，需要证据时才升级到重档。这比我「每周落地一个」的自律更可靠。

2. 技能开始自带「验证阶梯」：modulestf 把 Terraform 评审写成 L1→L4 分级取证

地址：https://github.com/modulestf/modulestf ｜ ★374 ｜ Apache-2.0 ｜ 为 Claude Code 与 Codex 写的 Agent 技能，按模块家族的成文规则档案评审并修改可复用 Terraform 模块

事件内容

  • 今日 22 次提交，且在四个小时内连发四版：v0.11.0（23:53）、v0.11.1（00:57）、v0.11.2（01:28）、v0.11.3（02:52），节奏是「改一处规则→校准一次→发一版」。
  • 今日两条关键提交把「判断依据」显式化：fix(reviewer): Judge new-input defaults by effect and calibrate doc and gating rules (#155)、feat(pr-fix): Surface a round finding late only for a local text rule on an unchanged span and count a closed item as pro...、feat(pr-review): let known blockers outrank unknowns in the verdict ladder (#148)。
  • README 里最值得抄的是那张「验证阶梯」表：L1 用带类型样本与未知量的离线表达式求值（只需 terraform、mtf-facts、perl、jq 加 macOS 的 sandbox-exec 或 Linux 的 bwrap），L2 走 plan-only 的 terraform test，之后逐级加重。原文有一句硬约束：「Reading the code supports a claim and never verifies one.」（读代码只能佐证主张，永远不能验证主张）
  • 仓库共 6 个具名技能（pr-review / pr-fix / pr-merge / reviewer / maintainer / change-scope），规则本身不在代码里，而在 profile 文件里（当前首发 terraform-aws-modules 的 PROFILE.md）；PR 评审调用 reviewer，两者都调用 change-scope，合并前还会核验完整 head SHA。
  • 评审技能是只读的，只输出 findings 不给 verdict；verdict 与评论要人确认后才发出。

值得关注的原因

  • 「读代码不能验证主张」这一句，是我 4P 专家包最该抄进去的一条规则。 我的营养干预报告里最危险的错误模式恰恰是「我读了文献所以这个剂量是对的」——文献只能支撑，不能验证剂量上限、禁忌与相互作用。今天这个仓库把这句话写成了一条工程原则，而不是一句提醒。
  • 「已知阻断项优先于未知项」（known blockers outrank unknowns in the verdict ladder）这个裁决顺序，和我前几期记的「证据缺失要显式建模」是同一件事的两种写法，但它更进一步：不仅要知道「缺证据」，还要知道「缺证据这件事在裁决时排第几」。我的 4P 报告如果有风险分级（比如 6 个级别），现在有了排序依据。
  • 规则放在 profile 文件而非代码里，这个分离值得抄。 我的 4P 包目前把「判定逻辑」和「输出格式」混在一起；拆成「知识与规则层（可版本化、可审计）+ 输出层（可快速迭代）」会让循证更新与产品迭代互不阻塞。
  • 从 23:53 到 02:52 四小时四版，说明技能维护本身是高频迭代的工程对象，不是一个季度更新一次的文档。这直接改变了我对「我的专家包该多久更新一次」的假设。

4. 营养线今天最扎实的一格：foodswap 把「只写在品名里的过敏原」判为不可验证

地址：https://github.com/sahil-gidwani/foodswap ｜ ★0 ｜ GPL-3.0 ｜ 约束感知的包装食品替换引擎，用词法-语义混合检索、营养排序与 Open Food Facts 做同位替换

事件内容

  • 今日 16 次提交，四个功能块各配一篇说明文档与一个「explainer」：搜索（Add keyword and meaning-based search）、过敏原检查（Add the allergen check）、数据清洗（Build the cleaned US product table）、请求与约束裁决（Add shared types for requests and constraint verdicts）。
  • 最有分量的一条是 Treat an allergen named only in the product name as unverifiable——只出现在商品名里的过敏原，判为「不可验证」而不是「没有」。这个区分是整条流水线的地基。
  • 数据链路写得很完整：先 download 拉约 8 GB 数据并做完整性检查，再 build 清洗成 US 产品表（约 1 分钟，附带过敏原裁决结果），最后 foodswap.search build 建检索索引（完整约 18 分钟，样本模式约 1 分钟）。
  • 文档目录本身就是一个方法学骨架：01 范围与特性、02 数据来源、03 数据流水线、04 架构、05 查询理解、06 检索与排序、07 约束与安全、08 解释与 UI、09 评测、10 计划、11 交付物、12 方法学调研、13 相关工作，另有 decisions.md 与 explainers/ 目录。
  • 许可证与数据来源都写明：代码 GPL-3.0，数据来自 Open Food Facts，遵循 Open Database License。

值得关注的原因

  • 「只写在品名里的过敏原 = 不可验证」这条判据，我要原样搬进 4P 补剂系统的标签校验规则。 我的场景比食品更严：保健品标签上的「含某某成分」经常来自供应商的宣传页而非检测报告。如果成分只在商品名里出现，正确处理是判「来源不可追溯」并触发人工复核，而不是默默放行。这条比任何 prompt 都更能防止我的 AI 助手给出「这个产品不含某某成分」的幻觉结论。
  • 「不可验证」和「没有」被显式区分，是我前几期记的「证据缺失要建模成一等状态」的第三个独立实现。 前两个是 ontology-atlas（missing evidence shows as unknown, never as safe）和 cqframework（每个技能标注依据的规范版本号）。三个互不相识的团队收敛到同一原则，说明这已经是这类系统的行业默认解法——我 4P 专家包的规范文档模板里，这条可以直接定稿。
  • 它的文档结构（12 章 + decisions.md + explainers/）几乎就是一份营养学检索系统的方法学论文，而且第 12 章叫「方法学调研」、第 9 章叫「评测」。这是我做 4P 补剂平台内容体系时最需要照抄的骨架：每个查询能力都要有独立的 explainer 和评测章节，而不是散落在代码注释里。
  • 现实提醒：★0 是全新仓库，作者一个人一天推 16 次提交，工程质量高但完全没有社区验证。这类项目适合当设计参考，不适合当依赖。

5. 时序上下文被当成基础设施来做：TemporalStore 用 Rust 把「记忆」拆成 cell / 锚点 / 配额 / 衰减

地址：https://github.com/matrixarkai/TemporalStore ｜ ★212 ｜ Apache-2.0 ｜ 面向 LLM 上下文管理的开源 Rust 时序存储，提供时间特征、成员集、锚点与配额衰减等原语

事件内容

  • 今日 17 次提交，主线是把「上下文」拆成一组可组合的时序原语：The cell protocol maps member sets, anchors, quotas, decay, merged reads and batches (#3122)、A ranked read command carries a member set, an anchor, a quota and a decay score (#3115)、Roll old cell snapshots up in tiers, by age, with a truncation and cap controls, through the command (#3121)。
  • 存储层的可靠性细节写得非常硬派：Price the WAL placement map apart from the key-entry guard (#3119)、Guards for every way a failed compaction round must keep its slabs (#3117)、The periodic loop declines a shard that is still replaying its log (#3116)、Write the WAL records of concurrent writers as one batch per shard (#3106)。
  • 一条关于大对象处理的提交值得单独记：An oversized SequenceAdd is split by a running total, not by serializing every candidate (#3108)——超大序列写入按累计量切分，而不是把所有候选逐个序列化。
  • 仓库自述定位是「LLM context management, temporal features, and risk control」，topics 里明确列了 context-engineering、context-runtime、llm-context、memory、temporal-features、risk-control。
  • README 的「cell」概念可理解为记忆的最小单元：一次读取要同时带成员集、锚点、配额与衰减分，这四个参数共同决定「现在能想起什么」。

值得关注的原因

  • 「一次读取同时要说明成员集、锚点、配额、衰减分」这套参数，正是我 GLP-1 营养伴侣里化验指标趋势追踪的完整语义。 我现在的实现是「按指标名查最近 N 条」，没有锚点（这份数据是什么时候的基线？）也没有配额（同一指标最多召回几条？）更没有衰减分（三个月前的数值和昨天的数值该有不同权重吗？）。今天这个仓库把「召回什么」变成了四个必须显式声明的参数，我可以直接照抄这个参数集。
  • 「记忆会衰减」被写成基础设施原语，而不是应用层的启发式规则。 我的 4P 平台里有一条业务规则：三个月前的客户体重不该和今天的体重等权。现在这条规则散落在业务代码里，搬到存储层做成 decay score 才是正确位置。
  • WAL 与压缩那一组提交（崩溃恢复、并发写批量、失败压缩要保留哪些 slab）是我目前完全没碰的层面。 我的 Flask+SQLite 4P 平台本地跑着 8899 端口、客户数据在库里，现在没有任何 WAL 级别的保障。这条提醒我：「个人能跑」和「数据经得起重启」是两件事，我这边只做到了前一半。
  • Rust + Apache-2.0 的组合也值得记：这类要长期演进的基础组件，用内存安全的语言写是省心的。

三、今日趋势观察

  • ⭐⭐⭐ 「可验证」今天从技能层下沉到了运行时层。 前几期我记的是技能该配 evals（cqframework 一技能一 evals）、该有版本号（ASB 绑定 commit 与 tree digest）、该显式建模证据缺失（ontology-atlas 写明「missing evidence shows as unknown, never as safe」）。今天 Atomic 把整套搬进了运行时：阶段、检查点、审批门、租约与快照存活。三个层级（技能自证 → 规则可校准 → 运行时可审计）在一周内先后落地，说明这不是个别团队的偏好，而是这类系统正在收敛的默认架构。 我 4P 专家包该做的不再是「加一批评测题」，而是把评测变成执行图里可调度的节点。
  • ⭐⭐⭐ 「证据缺失 = 不可验证」今天有了第三个独立实现，而且是最贴近我业务的一个。 前两个是 ontology-atlas 与 cqframework（规范版本号标注），第三个是 foodswap 的 Treat an allergen named only in the product name as unverifiable。三个互不相识的团队、不同技术栈、不同领域，收敛到同一条判据——这已经不是「最佳实践」而是事实标准了。 我 4P 补剂系统的标签校验规则可以直接定稿：成分来源不可追溯 → 判「不可验证」并触发人工复核，绝不静默放行。
  • ⭐⭐ 规则与代码分离今日有了工业级样本。 modulestf 把 Terraform 模块家族的规则放在 profile 文件里而非代码里，技能只负责按 profile 执行；今天三次提交全在校准「按效果判断默认值」「校准文档类与门禁类规则」「让已知阻断项在裁决阶梯上压过未知项」。我的 4P 包目前把「判定逻辑」和「输出格式」混在一起，拆成「知识与规则层 + 输出层」会让循证更新与产品迭代互不阻塞——这条我今天就落进规范文档。
  • ⭐⭐ 「读代码只能佐证、不能验证」是一句可以整体照抄的硬约束。 modulestf 的验证阶梯原文写着「Reading the code supports a claim and never verifies one」，并给出 L1 离线求值 → L2 plan-only test → 更重层级的分级取证路径。这正是我营养干预报告最危险的错误模式：「我读了文献所以这个剂量是对的」。文献只能支撑，不能验证剂量上限、禁忌与相互作用。 这句话我要原样进 4P 专家包规范。
  • ⭐⭐ 上下文记忆开始被当作存储工程问题，而不是应用层技巧。 TemporalStore 把一次召回拆成成员集 + 锚点 + 配额 + 衰减分四个必须显式声明的参数，并配套 WAL、并发写批量与压缩失败保护。我的 GLP-1 营养伴侣现在是「按指标名查最近 N 条」，锚点、配额、衰减三项全缺——这三项直接对应我业务里的「三个月前客户体重该不该和今天等权」。参数集照抄即可，成本极低。
  • ⭐ DSH 生态今天三线并行（企业平台 / 图像视频 / 角色扮演），正式成为独立跟踪项。 dsh-ee 今日 67 次提交推进多语言协议面，dsh-imagegen-video 29 次提交把画布 Agent 的「提案—待确认—已确认」状态机做得更严（read_canvas 读得到自己刚提议的改动、过期提案不再让整个读取失败、删除节点连带从分组移除）。这条对我直接有用：我本机就跑着 dsh，画布这套「改连线角色不被当成什么都没改」的状态设计，正是我 4P 平台做干预记录该抄的。
  • ⭐ 一人公司的现实提醒。 本期 41 个仓库里，下周就能动手的仍然是 3 个（foodswap 的「不可验证」判据 / modulestf 的「读代码不能验证主张」/ TemporalStore 的召回四参数）。别为凑条目把自己拖进「每周读完 41 个仓库」，每周落地一个即可。 其中 TemporalStore 的召回四参数改造成本最低——它本质上是改查询函数签名，一两小时能落。
