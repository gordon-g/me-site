一、今日精选 5 条

1. Prabh54/groundedmed：让生物医学 RAG 自己证明自己没编——每条结论都带引用校验，批评者模型还能打回重写

地址：https://github.com/Prabh54/groundedmed ｜ ★0 ｜ 未声明 ｜ Research demo: agentic RAG that gives citation-checked answers to biomedical yes/no/maybe questions, refuses when evidence is weak, and publishes its results from a frozen 200-question PubMedQA test. Not medical advice.

事件内容

  • v1.1.0 于 2026-11-11 02:24 发布，距 v1.0.0 公开版只隔一天多，主打「critic 引导重写 + 第二套锁定测试集」；同期还在 README 与 /eval 页面补上了生产冒烟测试结果。
  • 架构是四段式 agentic RAG：planner（规划）→ retriever（检索）→ answer writer（作答）→ critic（批评），回答以 yes / no / maybe 三态给出，每条发现都必须指向它所依据的那篇摘要。
  • 引用校验是代码干的，不是模型自己说的：程序逐条核对引用，critic 再把每条发现与被引摘要原文对照。critic 判定该拒答时，writer 获得一次「有引导的重写」机会，随后 critic 再审一遍。
  • 评测用的是哈希锁定的 PubMedQA 测试集：第二套 400 题的判定规则在跑之前就写死落盘，README 与 /eval 页面同步公布 baseline 与 agent 两轮的分数。

值得关注的原因

  • 这正是我公众号内容缺的那把尺子。 11-09 我给自己列的待办是「每次抽取附原文定位区间，拿不到就不许写进报告」——groundedmed 的做法比我的设想更严：不是「写清出处」就完，而是先做机器校验，再让一个不知道答案的批评者模型逐条对原文。它跟我 11-10 记的 bpf-benchmark 是同一个思路的两面：把「我自己说自己对」换成「一个不知情的第三方来判」。
  • 「证据不足就明说」这条是可复制的。 我 GRPM 的干预报告一直担心模型在证据薄弱时会硬凑一个结论，groundedmed 直接把 not enough evidence 写进产品行为里——这是产品级设计，不是提示词技巧。
  • 哈希锁定的测试集值得整套搬。 第二套 400 题「判定规则先于运行落盘」，这一条能治我公众号 A/B 测试「先看结果再定标准」的通病。下一步我可以把 GRPM 的 SNP 提取规则按同样的方式冻结一版。

2. Muratovnik/assay：给 coding agent 装上「读过的文件必须列全」的门禁——它把「我读过代码」这句话变成可自动核对的声明

地址：https://github.com/Muratovnik/assay ｜ ★1 ｜ MIT ｜ Evidence-grounded methods for coding agents: skills and agent profiles for Claude Code, Codex, Cursor and Gemini CLI

事件内容

  • v0.44.0 与 v0.44.1 在 2026-11-10 一天内连发两版，v0.44.1 直接针对 skill 文件签出的可见性。
  • 核心是一组 hooks：把「读声明」与它所命名的文件绑定。 提交信息明确写着「keep a read claim's file list going past a name with no Read」「tie a read claim to every file its sentence lists」「compare a full-read claim with the file its own clause names」。
  • 另一条是技能加载的条件化：只有 planning skill 被加载时，才向 plan 索取其 existing-solutions 段落；「skill-evaluation 签名」只对非插件仓库里的 skill 生效。
  • 自评为「Evidence-grounded methods for coding agents: skills and agent profiles」，定位不是提示词库，而是给 agent 装上可执行的证据纪律。

值得关注的原因

  • 这条直接命中我专家包质检最大的漏洞。 我现在的做法是「让模型自评」——它说读了某文件，我信。assay 的做法是让「我读过」这句话必须附带完整文件清单，并且清单里每个文件都有对应的 Read 记录，缺一个就红。 这正是我 11-09 给自己的第二件待办（「每次抽取附原文定位区间」）的可执行版本——我的版本是「要求模型写」，它是「让机器查」。
  • 「read claim 挂在没有 Read 记录的名字后面」这种失败模式，我几乎肯定在自己专家包里也犯了。 报告里写「依据该文件的方法学」，但模型其实只看到了文件名——这两者在人眼审阅里完全一样，在 assay 的门禁下会立刻暴露。这条应该进我的专家包 checklist 第一行。
  • 「只有技能加载了才问对应问题」这条对按需检索同样成立。 我的 GRPM 流程里，SNP 提取规则只在遇到营养相关变异时才该加载；如果无条件全量喂给模型，token 成本和幻觉面都会双涨。

3. vxxqv/openomicsbench：把「组学软件怎么验」做成能离线跑的包——v13 刚把 RNA-seq 输入包与校验和一起发出来

地址：https://github.com/vxxqv/openomicsbench ｜ ★2 ｜ Apache-2.0 ｜ Offline RNA, DNA, protein, single-cell and genomic interval benchmarks with a five-assay demo and traceable reports.

事件内容

  • v13.0.0 于 2026-11-10 17:30 发布，距 v12.0.0（11-08）两天一个版本，节奏很紧。
  • v13 的新增内容是 RNA-seq 输入包：既可按单个研究打包，也可为全部 12 个生物对象一起打包；每个包把 count matrix、sample sheet 与声明的 contrast 放在一起，并带校验和与设计预检（design preflight）。
  • 结果表可原生对接 DESeq2、edgeR、limma 的风格并直接打分或转换；仓库同时保留参考结果（reference results），因此它明确声明这不是盲测挑战。
  • 离线可运行是硬承诺：装完之后无需网络，序列文件留在本机；内置工具只覆盖检查与轻量预处理，不宣称替代比对器、变异检测器或分类器。

值得关注的原因

  • 「校验和 + 设计预检 + 参考结果与盲测的区别写在明面上」这三件事合起来，就是我 GRPM 报告最缺的东西。 我 11-10 记的「数据归档 → 判定规则 → 可复现制品」三段路径，openomicsbench 已经把它做成了可 pip 安装的包——尤其是「这不是盲测挑战」这句自我限定，比多数论文都诚实。
  • 它把「方法学可复现」的标准从「我说了算」降到了「我公开我的判定口径」。 12 个生物对象、7 组确定性序列与分类夹具、10x 风格单细胞基准、peak calling 基准——这些是可以直接对照着看的参照物，而不是各家口径不同的排行榜。
  • 对我最实际的用法是「拿来当反例库」。 我的 GRPM 流程里，40 个营养相关 SNP 的提取与解读逻辑各不相同，如果每次换一批 SNP 就重新定义一遍「这条建议的证据强度」，那报告之间的横向比较就是假的。openomicsbench 的做法提醒我：判定规则要冻结成版本，而不是随报告走。

4. shubhampawar05/nutrikit：把营养数据库做成能自托管的 API + MCP——还顺手修了「印度菜配不上海数据库」这种真问题

地址：https://github.com/shubhampawar05/nutrikit ｜ ★0 ｜ 未声明 ｜ Self-hostable nutrition API: food search, portion-aware nutrients, meal logging from text, voice, photos, barcodes and labels, meal plans and an AI nutrition advisor. JS SDK on npm (@nutrikit/sdk).

事件内容

  • 窗口内 3 次提交，最新的是 #21「fix/regional-food-matching」，同时补上了拼写纠正：拼错的食物名会给出纠错建议（"Suggest respellings for misspelled foods"）。
  • 具体修的案例：把 dal makhani 匹配到 CoFID 的 black gram（黑豆）与 kidney bean curry——这是一个真实的跨数据库命名断层，不是造出来的演示。
  • 形态是完整的可自托管栈：营养 API + 官网 + 开发者门户 + JavaScript SDK + MCP server，npm 上有 @nutrikit/sdk，Render 上有可试用的免费 API key 实例。
  • 数据面覆盖 13,000+ 食物、每种最多 33 项营养素，且支持「2 medium」「1.5 cups」这类份量表达；另含文字/语音/照片三种记录入口与条码扫描。

值得关注的原因

  • 这是本期健康线里唯一一个「数据库语义」而非「拍照算热量」的仓库，而后者占了 GitHub 健康线的大半。 拍照识别食物的项目很多，但把食物名对齐到营养数据库标识符这件事只有真正被生产使用过才会碰到——dal makhani 这个案例说明作者已经撞上了同一堵墙。
  • 它同时提供 MCP server，这直接对上我 GLP-1 营养伴侣和 4P 平台的接入需求。 我现在的营养数据来源散在各处，统一到一个可自托管、可编程调用、带版本的数据源，正是我要的方向——而且自托管意味着患者的饮食数据不必出本机。
  • 「纠错建议」这个功能看着小，实际是数据入口的第一道防线。 用户/患者输入食物名时打错字，如果系统静默匹配不上就返回空，用户就会放弃记录；给出候选纠错，记录成功率才立得住。我营养伴侣的输入层应该抄这个交互，而不是直接返回空结果。

5. chainloop-dev/chainloop：把「AI 写了什么」变成可留痕的 trace——今天把 Copilot、Pi skill 加载都纳进了记录范围

地址：https://github.com/chainloop-dev/chainloop ｜ ★611 ｜ Apache-2.0 ｜ Agentic SDLC infrastructure. Define guardrails. Collect signals. Enforce continuously. Signed records of what your AI coding agents and CI/CD pipelines did, checked against policies as code, with the loop closed in CI/CD. AI sessions, SBOMs

事件内容

  • 窗口内 6 次提交，主线是 GitHub Copilot 接入：#3801「feat(trace): GitHub Copilot support (spec, plan, and M1)」，#3804「Copilot skills, spec pointers, and pasted images (M2)」，#3805 启用 Copilot 的 Chainloop Trace hooks。
  • 同期还把 Pi 的 skill 加载纳入记录（#3759「feat(trace): record Pi skill loads」）——即「加载了哪个技能」本身成为可审计事件。
  • 自我定位是 agentic SDLC 基础设施：定义护栏、收集信号、执行一致性检查（"Define guardrails. Collect signals. Enforce contracts"）。
  • Apache-2.0，v1.134.0 于 2026-11-09 发布，v1.133.0 于 11-06；另有一次「让 lab compose stack 端到端跑通」的修复（#3797）。

值得关注的原因

  • 「加载了哪个技能」成为可审计事件，这一条比 trace 本身更重要。 我 11-09 的第三件待办是「每条规则加『最后验证时间 + 指向目标是否仍存在』两个字段」——但如果连「这条结论当时是用哪套规则算出来的」都没记，我连判断结论是否过期都无从下手。 chainloop 记的是这一步。
  • Copilot / Claude Code / Pi / Codex 多宿主并存已是常态，单靠某个宿主的日志不够用。 我本机就同时装着 dsh、WorkBuddy、Ollama，任何跨宿主的合规要求都需要一个宿主无关的记录层——这正是 chainloop 的位置。
  • 对 4P 平台最直接的启发是「契约」这个概念。 干预报告的输入数据快照、判定规则版本、引用清单，如果三者都带哈希并串成一条 trace，报告的可审计性就从一个愿望变成了一条流水线的一环。这和我 11-10 记的 bpf-benchmark「哈希绑定证据」是同一条路的两种实现。

  • ⭐⭐⭐ 「读了没有」正在变成一个可以被机器判红的问题。 11-10 我记的 astryx 是「测试失败报具名场景」，11-09 我记的 squad 是「规范/文档/矩阵三者对齐代码 + 回归守卫」，今天 assay 直接把这件事做到了 agent 身上：tie a read claim to every file its sentence lists——模型说「我读了某文件」，必须给出完整清单，清单里每个名字都得有对应的 Read 记录。我专家包质检目前还是「让模型自评」，这条是可以整套抄的。
  • ⭐⭐⭐ 「把结论钉在原始材料上」出现了三种不同实现。 groundedmed 让批评者模型逐条对照摘要原文；openomicsbench 让判定规则连同校验和一起冻结成可安装的包；chainloop 让「加载了哪个技能」本身成为可审计事件。技术栈毫无交集，但都在回答同一个问题——三个月后我怎么知道当时那份报告是怎么得出来的。 我 GRPM 的「规则加验证时间字段」只解决了一半：字段加了，但产出这份结论时用的到底是哪套规则、哪份原始数据，仍然没有留痕。
  • ⭐⭐ 健康线的分水岭：数据库语义 vs 拍照算热量。 本期健康线 28 个条目里绝大多数仍是「拍照识别食物 + 算卡路里」，而 nutrikit 做的是把食物名对齐到营养数据库标识符——它修的那个 dal makhani → black gram 案例，是只有真正把这件事用在生产上才会撞到的墙。这一条的分量在于：它证明营养 AI 的难点不在识别，在于对齐。 我做补剂配方与功能医学干预评估时，卡住我的也正是这一层。自托管 + MCP 组合还直接对上了我 GLP-1 营养伴侣的接入需求。
  • ⭐⭐ dsh 生态继续在榜。 AdamPlatin123/dsh-plugin-radar（★1,500，窗口内 238 次提交）是一个开源生态雷达，持续快照 + 渲染 dsh 插件生态的变化——我本机装着 dsh，这条线应该持续优先跟踪。上一期还有 dsh-Go、dsh-blender-plugin、dsh-mnemon、dsh-memory 四个不同团队的 dsh 扩展同时在榜，说明这不是单人项目，而是已经长出生态。
  • ⭐⭐ 授权形态这一期出现了一个新的三档样本。 真开源（MIT 与 Apache-2.0 合计 128 个，66%；加上 BSD / ISC / MPL 等宽松型授权后共 146 个，75%）、源码可见但非开源（orionbelt-semantic-layer 的 BUSL-1.1、phoenix 的 ELv2、TrenTorch 的 PolyForm NC 各 1 个）、完全不开放（forma-ai 与 meliusme 的专有许可、rakaia 的保留所有权利、CRISPResso2 的学术非商用 4 个）。对一人公司的含义仍是三件不同的事：第三档连读都不行、第二档可读可学设计但绝不能进产品依赖、只有第一档是选型候选。 而本期最刺眼的一条是：两个精选仓库（groundedmed 与 nutrikit）根本没有 LICENSE 文件——它们的方法论值得抄，但代码不能直接依赖。
