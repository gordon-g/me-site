值得关注的原因

  • ⭐⭐ "PICO 的每一部分都必须由论文自己引述的原文段落支撑"这一条，就是我公众号循证内容一直缺的那条硬约束。 我写"某某营养素对某指标的影响"时，AI 会给我一个结构化的 PICO，但它引的那段文字经常是我原文里根本没有的——而我恰恰因为它格式正确就放进去了。bmlib 把"每一段引文必须是论文原文"做成了代码级强制：抽取不到原文段落，PICO 就不能成立。对应到我的管线：每次 AI 抽取必须附上它在原文里定位到的字符区间与原句，拿不到就不许写进报告——这跟我在 11-08 期记的 assay 那句"工具返回 success 只是提供方的断言，永远不是证明"是同一条线，但这一期给出了更具体的落地形态。
  • ⭐⭐ 撤稿状态四态判定（retracted / concern / clear / unchecked），是循证内容里最该有而我最缺的一层。 我引用文献时从不查它撤没撤稿——一篇被撤稿的论文被我的公众号引用，读者看不出任何异常。而 bmlib 把这一步做成了摄取时的自动字段，而不是发布前的临时检查。"unchecked"这一档尤其诚实：它承认"我查过，但没查到"，而不是默认"没问题"。
  • ⭐⭐ Cochrane 九域偏倚风险评估被做成了分级库，这件事的意义超出了医学圈。 九域评估的价值不在"给个分"，而在它把"这篇研究可能在哪些地方骗我"拆成了九个可以逐项回答的问题。对应到我的 GRPM 与干预报告：SNP 与表型的关联也应该有一份九项清单（样本量、重复性、效应量、混杂控制、发表偏倚、跨族一致性……），每项独立标注"已评估 / 未评估 / 不适用"，而不是给出一个总评。这正是我在 11-02 期记的 Calibrate "2×2 依赖度矩阵"和 assay "拒绝输出单一总分"的同一条思路——但九域是医学界已经验证过的清单，比我自造的矩阵更该直接采用。
  • ⭐ "跨两种语言把系统提示词钉死（pin）"这条，是对我多模型内容生产流程的直接警示。 我的公众号内容会在多个模型上跑（WorkBuddy 本机已接 OpenRouter 单 key 全家桶），同一套提示词在不同模型、不同版本下会漂。bmlib 的做法是在代码里钉死提示词文本，并在重试时明说这次重试带了什么——这正是我 11-07 期记的"答案错了而你没反应，这样的运行看起来就是 clean"的反面：重试必须留痕。
  • ⭐ "密钥在 OS keychain 里、且 Python 与 Rust 两侧必须是同一条目"这条，对我的部署形态有直接价值。 我的 4P 平台是 Flask + SQLite、GRPM 报告链路需要调多个模型供应商——API 密钥现在散在环境变量与配置文件里。"多语言/多模块访问同一份凭据必须是同一个 keychain 条目，且遇到别的账户的凭据要拒绝而不是覆盖"，是一条可以直接抄的规则。
  • ⭐ "推理轨迹（reasoning traces）"作为一等输出，这个能力我目前完全没有。 我所有的模型调用只留最终答案，不留中间推理——于是当一个结论出错时，我既无法判断是检索错了、推理错了还是引用错了。bmlib 把推理轨迹做成了可取回的产物，这在内容生产的合规与复查场景里价值极高。
  • ⚠️ 授权是硬墙：AGPL-3.0。 我可以读它的设计、抄它的思路，但不能把它作为我产品里的依赖（除非我的产品也以 AGPL 开源）。要落地的是那份"证据结构化"的规格，不是这份代码——"PICO 每段必须有原文支撑""撤稿四态""九域清单"这三条是规格，可以自己实现；bmlib 的代码只适合当参考实现来读。

4. vostride/agent-qa：一个会自己变好的 QA agent——它把经验写成仓库里可审阅的文件，并且公开承认"干净运行率"这个指标有根本缺陷

地址：https://github.com/vostride/agent-qa ｜ ★847 ｜ FSL-1.1-ALv2 ｜ TypeScript

事件内容

窗口内 33 次提交（11-08 一日之内密集提交），主线是一批以 fix(467) 为编号的修复，覆盖了 agent 与 skill 的安装、卸载与配置文件处理。README 的一句话定位："Your AI QA engineer, with memory. Describe a user journey in plain language. agent-qa tests it on web, Android or iOS and keeps the evidence."

  • ⭐⭐ "记忆不是数据库里的黑盒，而是仓库里可审阅的文件"：memidex 把事实与工作流程记成你仓库里的文件，因此任何一条记忆都能被人打开来看、能被 git diff、能被 code review。README 同时给出两条机制：自我改进（self-improvement）会验证从运行中学到的经验、淘汰已经过时的知识，并用你的反馈纠正错误。

  • ⭐ 基准成绩写得很硬：AndroidWorld 排名第一，100% pass@1（116/116 任务）；AppControlBench 排名第一，99.6% 完成度（114.5/115 分）。README 特别注明两项都用 gpt-6-sol 且关闭了记忆与自我改进，且 AppControlBench 对部分完成给一半分。基准、模型、开关、计分方式全部写明——这本身就是一个可信度信号。
  • ⭐ 证据是留档的，不是打印的：演示里"购物车显示 $29 而不是 $53"这个故意埋的缺陷，被抓出来时失败步骤与截图并排显示；CLI 输出给出"一个测试通过、一个测试失败、九步里八步通过"。
  • ⭐ 窗口内的修复序列能看出它在处理哪些"脏活"：.mcp.json 与 .codex/config.toml 的读写要和 AGENTS.md 一样小心；移除 agent-qa 的 .mcp.json 条目要保留用户自己的注释；重装时要逐个列出被删除的技能里它删掉了哪些被编辑过的文件；一个删不掉的空文件夹要在说明里写明，而不是当成它的文件上报；一个没有 agent 的安装不写 manifest，卸载时也要删掉列出空 agent 的 manifest。

值得关注的原因

  • ⭐⭐ "把经验写成仓库里可审阅的文件"这一条，正是我用 WorkBuddy 的 expert-manager skill 批量生产专家包时最该补的一环。 我现在的专家包质检流程，评估依赖"模型自评"——这正是我在 11-06 期记的 hermes-fledge 要解决的那个漏洞（"把评分从模型手里拿走"）。agent-qa 的答案更朴素也更可靠：记忆是仓库里的文件，因此它天然可 diff、可 review、可 blame。 对应到我的动作：专家包的质量记录（哪些 prompt 变体通过了、哪些被拒绝了、依据是什么）应该是仓库里的一组文件，而不是模型输出里的一段话。
  • ⭐⭐ "验证从运行中学到的经验、淘汰已经过时的知识"——这条直接对应我专家包迭代时最危险的一个坑。 我在 11-04 期记过"改 description 一行就让 Kimi 通过率 78%→98%"，但这同时也意味着过时经验会一直留在包里，而且没人知道它该退休。"retire stale knowledge"应当成为专家包发布的固定工序：每条经验带一个"最后验证时间"，超过阈值自动降级为待复核。
  • ⭐⭐ "把知识追溯回使用它的步骤"这个功能，是评估质量的硬指标。 我现在的做法是看"通过率"这个数字——但 11-07 期 navigator 已经指出过这个指标的根本缺陷：答案错了而你没反应，这样的运行看起来就是 clean。 agent-qa 的做法是把"这次运行为什么用到了这条知识"变成可点开的事实。对应到我的平台：任何一条被写进干预报告的规则，都要能回答"这次它凭什么是被应用的"。
  • ⭐ "基准、模型、开关、计分方式全部写明"——这条是对我内容生产的直接提醒。 我在公众号文章里引用"某某 benchmark 得分"时，从不说清它跑了什么配置。agent-qa 的写法是：用了哪个模型、记忆开没开、自我改进开没开、部分完成给不给一半分——四个条件缺一不可。 这应该成为我引用任何评测结果的固定四件套。
  • ⭐⭐ 窗口内那批 fix(467) 提交，主题几乎全是"不要弄丢用户的东西"：移除 .mcp.json 条目要保留用户的注释；重装要列出技能里被删掉的每个被编辑过的文件；没有 agent 的安装不写 manifest。 这与我在 11-07 期记的"读回校验"是同一条线，但角度不同——读回校验管的是"写进去的对不对"，这批提交管的是"动别人东西的时候别弄丢"。 我的 4P 平台改方案、改基线、改用户档案时，同样需要"先备份、再改动、列清单"三件套。
  • ⚠️ 授权是 FSL-1.1-ALv2，不是 MIT。 Functional Source License 允许使用、修改与自托管，但在达到一定规模对外提供服务时必须转为 Apache-2.0 许可（该变体的附加许可）。对一人公司来说这比 AGPL 宽松、比 MIT 严格——如果要做成产品，必须在上线前确认转化条款是否已触发。

5. trailhq/Trail-Code：给整个团队的 coding agent 一份共享的"代码地图 + 团队已经学到的东西"——162 次运行下工具调用少了 46%，SWE-bench Verified 从 54% 涨到 66%

  • ⭐⭐ "SWE-bench Verified 从 54% 到 66%"这组数字，是这两年我看到的关于"上下文层"最有说服力的证据。 之前我记录过的同类项目（skill-diet 的"砍 token"、sprag 的"账单降 72.6%"）都在优化成本，只有这一条同时给了成本（工具调用 −46%、token −42%、时间 −60%）和结果（通过率 +12 个百分点）。成本与质量同向改善的案例极其罕见——这说明"给 agent 更好的上下文"不是拿质量换钱，而是两头都赚。

三、今日趋势观察

本期最清楚的一条主线是：AI 生成的产物正在被系统性地要求"自己证明自己站得住"，而这一次要求落实到了三个不同的层面——证据的适用条件、执行的可回放性、以及改动的可追溯性。 mTOR Atlas 要求每条结论带"测量条件"与"失效边界"，并把研究按证据能支持的结论类型而非质量高低分级；bmlib 要求 PICO 的每一段都由论文自己的引文支撑，并把撤稿状态做成四态字段；agent-qa 把知识存成仓库里可 diff 的文件，并给每次运行留证据；Trail-Code 把"指向已消失代码的 learnings"标出来。这四家来自四个完全不同的技术栈，在同一天各自独立地做了同一件事：让"AI 说的话"和"AI 做过的事"都能被第三方翻回去看。 这与我在 11-08 期记的 assay（证据包可离线重算）、lights-out（八道闸门）是同一条线索的第三阶段：前两期把要求下沉到运行时，这一期把要求下沉到"证据本身的结构"。

第二条线，也是对我最刺痛的一条：本期出现了两个把"知识"当成会腐烂的东西来管理的项目，而且都给出了具体的腐烂检测机制。 agent-qa 明确说它会验证从运行中学到的经验、淘汰已经过时的知识；Trail-Code 明确有一个提交是把指向已消失代码的 learnings 标出来。两条独立路径指向同一个判断：知识如果不带失效标记，它就一定会骗人。 而我目前的处境恰恰是"知识只增不减"——我的公众号文章库、GRPM 的 SNP 判定规则、4P 平台的干预方案模板、专家包里的提示词，全都在持续增长，从没有任何一个被标记为"已过期"。 最该立刻动手的是这一件：给每一条进入我内容与报告生产链的规则，加上"最后验证时间"与"指向目标是否仍存在"两个字段，然后让一个每周任务把失效的挑出来。

第三条线：授权形态在这一期出现了一个我该特别留意的样本——"用授权条款表达商业模式"。 mTOR Atlas 的做法是数据 CC BY 4.0、代码 MIT 双许可，理由是"数据要能被引用与再加工，代码只要能被审计"；而 novu 的做法是除 enterprise/packages 目录外一律 MIT、其余为自有专有许可，用目录边界直接划出商业版与开源版的分界。这两个都不是"随手选一个许可证"，而是把"我希望谁能用、怎么用"写进了授权结构里。 对我这个一人公司，这给了一条很实际的启发：我的公众号内容库可以走 CC BY 4.0（署名即可传播），而 4P 平台的代码应该保持闭源商用——同一套内容，两套授权，分开声明。 本期 121 个条目里 MIT 与 Apache-2.0 合计 93 个（77%），但仍有 AGPL-3.0 9 个、GPL-3.0 5 个、PolyForm Strict 1 个（研究与非商用）、FSL-1.1-ALv2 1 个（商用需另约）、4 个未声明——这份清单应该直接抄进选型文档的第一行，且在动手前看这一行。

第四条线，给 Gordon 的直接提醒：这一期最值得带走的不是任何单个项目，而是三个可以今晚就动手的断言。 第一，mTOR Atlas 的"证据按研究设计分级、不按质量分级"，以及"字母阶梯读起来像质量等级"的自我批评——这直接指出我给公众号文章设计的"证据强度 A/B/C"标签体系是错的分类轴，该改成分类轴（细胞 / 动物 / 观察性人群 / 随机对照 / 系统综述），而不是强弱轴。 第二，bmlib 的"PICO 每段必须有原文支撑""撤稿四态""Cochrane 九域偏倚"三条，是我 GRPM 报告与公众号循证内容缺的同一把尺子，而且医学界已经把它标准化了，我不该自造。 第三，agent-qa 的"知识存成仓库里的可审阅文件"与 Trail-Code 的"标出指向已消失代码的经验"——这两条合起来就是我专家包质检流程该有的样子：不是让模型自评，而是让每条经验都变成仓库里一条可 diff、可 blame、可标记失效的记录。 具体要做的只有四件：① 证据类型标签替换强度标签；② 每条抽取附原文定位区间；③ 每条规则带"最后验证时间 + 指向目标是否存在"两个字段；④ 每周跑一次失效扫描。 这四件都不需要新框架，只需要四个字段加一个定时任务。
