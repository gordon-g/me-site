一、今日精选 5 条

1. git-ai：把 Anthropic 内部 Scion 的"为 Agent 重做源码管理"公开复刻出来了

地址：https://github.com/feder-cr/git-ai ｜ ★916 ｜ Go ｜ 建于 10-15，当日仍有提交

事件内容
作者基于 Anthropic 工程博客《Redesigning source control》中公开描述的 Scion（Anthropic 内部的、为"成百上千个 agent 同时读写落码"设计的版本控制系统，不对外）做了一份开源实现。核心设计与 Git 的差异有四处：客户端常在线、按需拉取单个对象与稀疏树（graft clone / graft sparse）；历史查询由服务端回答并缓存；变更通过 compare-and-swap 落地而非 merge queue；每次更新写入 changeset 日志，仓库状态放在一致性数据库 + 对象存储里，便于水平扩容。底层仍是标准 Git 仓库，MIT 许可，服务端不调用任何模型，AI 能力与供应商无关。

当日提交是其 PLAN10 系列实验：在 296 个全新构造的 Go 冲突上复现 G1 指标，并加入"有测试/无测试"两个对照组、Python 与 TypeScript 的对照臂（TypeScript 已备好未跑），另有 build check 与 SEM/BIND 度量。

值得关注的原因

  • 这是第一次有人把"Agent 原生 VCS"从论文式描述变成可跑的代码。多 agent 并行时真正的瓶颈不是模型，而是 Git 的假设——"人类克隆一次、干几小时、推一次"。当 50 个 agent 在同一分支上抢着落码，merge queue 会直接塌掉。
  • 它公开了自己的 benchmark 构造方式（自造 296 个冲突 + 分组对照），这比"我们快 N 倍"的口号可信得多，也顺手给出了评估 Agent 协作基础设施的方法论模板。
  • 对我们的含义：如果团队要上多 agent 并行开发，现在有一个可自托管的参照物；即便不用它，"changeset 日志 + CAS 落地 + 每笔变更记名到具体 agent"这三条设计可以直接借鉴到内部流水线。

2. 腾讯混元 Hy-Memory：把"编程记忆"做成独立的双系统认知引擎（MemHub 打通 5 类编码工具）

地址：https://github.com/Tencent-Hunyuan/Hy-Memory ｜ ★1,127 ｜ Python ｜ Apache-2.0

事件内容
混元开源了"生产级双系统认知记忆引擎"及 Python SDK hy-memory，按三类场景给专用记忆流水线：Chat 走分层长期认知记忆；Working 走"事实层 + 可复用经验层"两层；Coding 走版本演化 diff-chain 追踪。当日发布 2.0.5.dev3，并连续合入 SDK 侧能力：按语义精确导入记忆、用现有 search API 检索原始记录、处理存量 raw records（该 PR 后被 revert，说明正在收敛接口）。

配套的 MemHub 是本地优先的桌面端 + CLI：把用户授权的 Claude Code、Cursor、Codex、OpenCode、Qwen Code 的会话历史与编码轨迹，统一到一个受治理的本地运行环境和数据目录，实现跨应用记忆召回。模型侧同步放出 Hy-Memory-30B-A3B 的 FP8 与 GGUF 量化版本。

值得关注的原因

  • 记忆赛道此前多是"给某个 harness 加插件"（如 10-20 期推的 ai-memory）；这次是模型厂把记忆做成独立产品 + 独立模型，并且直接对上"编码轨迹"这个最脏的数据形态——用 diff-chain 记录代码怎么一步步演化，而不是把聊天记录塞进向量库。
  • MemHub 的定位很关键：它不绑定单一 IDE，而是做跨 harness 的记忆中间层。这意味着"记忆"可能像当年的 LSP 一样，从各家自建变成一层公共基础设施。
  • 对医学/健康类业务尤其相关：病历、随访、饮食记录的"长期演化"本质上也是 diff-chain 问题（指标怎么变的、方案为什么改），这套建模思路可直接迁移。

3. HasteHealth：给"AI 原生健康应用"的开源 FHIR 服务器，MCP 与 SMART on FHIR 是内置件

地址：https://github.com/HasteHealth/HasteHealth ｜ ★84 ｜ Rust ｜ Apache-2.0

事件内容
定位一句话：Epic / Oracle Health / HL7v2 进，FHIR R4、SQL-on-FHIR、MCP 出。临床数据以 FHIR R4 存储，通过单一 API 同时服务前端应用、分析任务和 AI agent；OAuth2、SMART on FHIR、MCP 全部内建，Rust 编写，可自托管，也提供带 BAA 的托管版。单二进制同时跑 server / worker / CLI，docker compose up 即可起全栈（Postgres + server + worker + admin 前端）。

当日提交集中在 FHIR 查询语义的补全：ne/eq 对 quantity 的支持、lt/gt/le/ge 前缀、Number 的 eq 前缀、Token/Date/Reference/Quantity 的 :missing 修饰符，以及 FHIRPath 的 toQuantity / convertsToQuantity。

值得关注的原因

  • 之前几期推的医疗项目多停在"技能库/护栏/影像 agent"层，这次动的是最底下的数据底座：让 agent 直接用 MCP 说 FHIR，而不是先写一层 REST 胶水。MCP 内建意味着 Claude/Cursor 这类客户端可以零适配接入院内数据。
  • 它的工程取舍值得抄：Rust + 单二进制 + 静态链接，明确针对"医院内网不能随便装 Node/Python"的现实；同时把合规（BAA、SMART 授权）当产品功能而非文档附录。
  • 反过来说，今天补的全是 FHIR Search 的边角语义——说明它离"能替代成熟 FHIR 服务器"还有一段路，评估时要盯 _include、_revinclude、版本化与批量导出这几项。

4. ai-mammogram-triage：把乳腺钼靶分诊做成 MCP 服务，并且老老实实公布了校准数字

地址：https://github.com/avalderrama/ai-mammogram-triage ｜ ★1（新库，创建于 10-20）｜ Python ｜ Apache-2.0

事件内容
一个 MCP server，输入 CC/MLO 视图的钼靶图像，把每一侧乳腺分到 BI-RADS 1-2 / 3 / 4-5 三组并给出优先级（high_priority / review / no_suspicious_findings）。流程是：先用 OCR 遮掉图像上的个人信息（读到的文本不返回也不记录）→ 校验这确实是钼靶而非超声/MRI/随手拍 → 用 512/1024 双分辨率全局模型分类，图像高度 ≥1500px 时追加 2048 patch 模型（对钙化更敏感）并输出热力图和最多 3 个可疑区域 → 仅在客户端显式给出 sides 时才合并同侧多视图 → 套用校准阈值。图像不落盘。

作者公布的是留出集（VinDr-Mammo 官方 test split 中未参与校准的那一半）按乳腺的指标：BI-RADS 4-5 有 87% 落入 high_priority 或 review，同时 BI-RADS 1-2 只有 6.5% 被误升到 high_priority，AUC 0.89；CPU 单图 1-3 秒。

当日提交：任意分辨率下的视图分隔检测、按需分两层下发热力图、通过 Cloudflare tunnel 自动部署 main。

值得关注的原因

  • 它示范了医学影像 agent 的"合规姿势"：先脱敏再推理、先验模态再分类、不存图、明示"研究工具、非医疗器械、未做临床验证"。这几条比模型精度更决定项目能不能进医院。
  • 指标口径值得学：报的是按乳腺而非按图像，且明确区分"校准集"与"留出半 B"，还直接写出 6.5% 的误报代价。医疗 AI 里"召回好看"很容易，把代价一起写出来才是可信。
  • 对我们的直接价值：这是"把专科判断封装成一个可被 agent 调用的工具"的完整样例——含输入校验、拒答路径、结构化输出与自然语言摘要分离（structuredContent 恒为英文）。

5. 营养赛道的两条新路线：数据厂商官方 Agent Skills vs 专科计量纵深

地址：https://github.com/edamam-llc/edamam-skills （★0，10-16 后有推送）｜ https://github.com/ksullivan86/kidney-health （★1，当日有提交）

事件内容

  • edamam-skills：营养/食品数据库厂商 Edamam 把能力封装成可移植 Agent Skills（遵循 agentskills.io 开放标准），同一份 skills/ 目录同时是 Claude Code 的 plugin marketplace 和 Gemini CLI 的 extension，数据通过其托管 MCP（mcp.edamam.com/mcp/food）取。首个技能是条码查询：输入或拍摄 UPC/EAN，返回热量、宏量营养素与完整营养表。凭据一次性写进本地环境，不进对话。
  • kidney-health：自托管的饮食记录 + 患者手册，专攻慢性肾病合并 1 型糖尿病：按钾、磷、钠、蛋白质、液体、碳水六个维度计量，含膳食计划、条码扫描、离线 PWA。当日仍在提交。

值得关注的原因

  • 这两条路线正好对应营养类产品的分岔口：一条是"数据供应商把自己 skill 化"——不写 App，直接住进用户的 agent，按 API 调用计费；另一条是"在通用营养素之外做专科计量"——钾、磷、液体这些指标，通用卡路里类 App 基本是盲区，而这恰恰是 CKD 患者每天真正在算的东西。
  • 值得警惕的是第一条路线的信号强度被高估：edamam-skills 星标为 0、main 分支近期无实质提交（最近一次是 10-16 的隐私政策），目前更像"占位式上架"而非被验证的分发渠道。判断这类"厂商官方 skill"要区分"已上架"和"有真实装机"。
  • 对我们的业务含义：做营养/健康管理，通用营养素表已成红海，专科计量（肾病、糖尿病、孕产、肿瘤营养）才是护城河；而分发侧要考虑"被 agent 调用"这个新入口，别只想着做 App。

三、今日趋势观察

  1. 瓶颈从"模型"移到"协作协议"。今天最热的三个 AI Coding 项目——git-ai（源码管理）、reason-network（agent 之间通信）、kandev/harp（几十个会话的可观测与调度）——没有一个是模型，全是在解决"多个 agent 同时干活时，人怎么不被淹没、代码怎么不打架"。这是从"更强的单体 agent"转向"agent 团队的操作系统"的明确信号。
  2. 记忆开始分层：引擎 / 模型 / 中间件三件事被拆开。Hy-Memory 同时给了引擎（SDK）、模型（30B-A3B FP8/GGUF）和中间件（MemHub 跨 5 类编码工具），MemT-1.0 则直接把记忆做进基座（省 66 倍 KV 存储）。上一期还是"给 harness 加插件"，这一期已经是"记忆作为独立基础设施"。
  3. 医疗 AI 的竞争点下沉到数据语义层。HasteHealth 今天补的全是 FHIR Search 的 quantity 前缀、:missing 修饰符、FHIRPath 函数——这些枯燥的边角语义，恰恰决定 agent 能不能真的查对一条检验值。相比之下，"再做一个医疗问答 bot"的边际价值在快速下降。
  4. 合规不是文档，是代码路径。ai-mammogram-triage 把"先脱敏、先验模态、不存图、拒答路径"写进了处理管线，Medical-Harness 则规定"检索失败就不许编来源"。这类硬编码的自我约束正在成为医疗健康类项目的入场券，比在 README 里写免责声明有效得多。
  5. "厂商官方 skill"要分清真上架与真装机。Edamam 把营养数据做成 Agent Skills 并双端上架，方向对，但 0 星、main 分支无近期实质提交——这类仓库更像"占位"。选型时应看装机量、issue 活跃度与提交历史，而不是看"是否支持 Claude Code"。
  6. 国产算力进入开源推理栈的默认清单。DeepInfer 把华为昇腾 950 与 NVIDIA SM100 并列写在支持硬件里，这在半年前还是少见表述。
