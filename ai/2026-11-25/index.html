1. NVIDIA 把技能生态的另一半补上了：SkillSpector 扫描「装之前」，SkillEvaluator 管「装之后好不好用」

地址：https://github.com/NVIDIA/SkillSpector ｜ ★27,568 ｜ Apache-2.0 ｜ NVIDIA 官方 Agent 技能安全扫描器：71 条漏洞模式覆盖 17 类风险（提示注入、数据外泄、提权、供应链、MCP 工具投毒、记忆污染等），两阶段静态分析加可选 LLM 语义判定，扫描过程不执行目标技能

事件内容

  • 今日 12 次提交并发 v2.13.7（2026-11-24 05:58）。这是该仓库当天发布的正式版本，release notes 原文写明它来自 main 分支的 2d0c6ddcb，并明确「上一个版本用的是 2.13 维护分支，本版包含 main 上更早的工作与 2.13.6 之后的修复」。
  • 本期改动的重心是把命令与源码的边界判定做实：fix(cli): report recursive root scope exclusions（递归根作用域排除要显式报告出来，而不是悄悄跳过）、fix: report RP3 at the manifest version field（RP3 要报在 manifest 的版本字段上）、fix(ingestion): keep host Git templates out of URL scans（扫描 Git URL 时要把宿主机自带的 Git 模板排除掉，否则会误报）、test: count AST parses only for the scanned fixture（AST 解析次数只对被扫描的 fixture 计数）。
  • 分发链路同步打通：ci: publish SkillSpector releases with PyPI Trusted Publishing 与 ci: publish existing GitHub release distributions to PyPI——从今天起 GitHub Release 与 PyPI 用可信发布自动对齐，装包不再需要手动同步。
  • README 给出的一手数据：在其研究数据集的 31,132 个技能子集里，26.1% 含漏洞、5.2% 疑似恶意意图；扫描器覆盖 71 条漏洞模式 / 17 个类别（提示注入、数据外泄、提权、供应链、过度授权、输出处理、系统提示泄露、记忆污染、工具滥用、流氓智能体、抗拒答、触发滥用、危险代码 AST、污点追踪、YARA 签名、MCP 最小权限、MCP 工具投毒）。
  • 扫描不执行目标技能：静态分析加可选的 LLM 语义判定（--no-llm 可保持纯静态），输出终端 / JSON / Markdown / SARIF 四种报告，0–100 风险评分；SC4 会实时查 OSV.dev 拿实时 CVE 数据并自动降级到离线；基线机制支持用 glob 规则或指纹压制已知告警，让复扫只暴露新问题。
  • 官方把它定位成 NVIDIA Verified Skills 流水线的第一道关：扫描 → 评估 → 签名，通过的技能才进 NVIDIA 技能目录。

值得关注的原因

  • 这一条把我上期记的判断直接兑现了：我上期说「我 4P 专家包如果只停留在一份 Markdown 清单，会落后这一档」——今天 NVIDIA 把「这一档」的具体标准写成了代码。 我的 expert-manager 技能包目前靠人肉判断质量，而这个仓库给出了一条可执行的门槛：装之前先扫 71 类风险，装之后还要能被评估。这意味着我以后每发布一个专家包，都该先过一遍 SkillSpector，而不是发出去等用户报障。
  • 「26.1% 含漏洞、5.2% 疑似恶意」这组数字对我这个做内容 + 做技能的人是直接的警示。 我在公众号和公众号技能包里转发、推荐、封装别人的技能时，本质上是在替第三方做信任背书。如果我引用的技能里有四分之一带漏洞，我这个「知识分享」的品牌就是在放大风险而不自知。扫描器不执行技能代码、也不上传内容，这个设计让我敢把它用在生产流程里。
  • 「不执行」这条边界值得单独记住，它决定了这个工具能不能进 CI。 很多安全扫描工具的通病是「为了分析得更准，把被扫描的东西跑一遍」——那就等于把不可信代码放进了我的机器。SkillSpector 明确只做静态分析，LLM 判定也只是读文件内容。这跟我一直坚持的「零 AI 幻觉、不做无授权动作」是同一种克制。
  • 它和我今天选的第 2 条是同一个生态的两半，这个组合本身就是信号。 过去两期的日报里，技能生态讲的都是「怎么写更多技能」；今天开始讲的是「怎么给技能上保险」。技能正在从提示词片段变成需要 CI 把关的工程资产——这句话我上期才写，本期就有了具体实现。

2. 技能也需要「体检报告」：SkillEvaluator v1.2.0 让「这个技能到底有没有用」变成可自动化的门禁

地址：https://github.com/NVIDIA/SkillEvaluator ｜ ★4,504 ｜ Apache-2.0 ｜ NVIDIA 官方的 Agent 技能多层级评估框架：500+ 条静态规则不需 LLM key 即可跑，配套可复用的 CI 模板把质量与安全门禁直接接进仓库，另有权重与去重用于识别功能重叠的技能

事件内容

  • 今日 8 次提交并发 v1.2.0（2026-11-24 07:15）。release notes 的主题是「把更清楚的评估结果与更强的安全检查带进技能工作流」，包含三个要点：已审命令钩子的豁免机制（--hook-waivers，只对精确匹配的已审包放行，其余发现与覆盖缺口仍保留）、GitHub Actions 注解、以及更可靠的智能体评测。
  • 本期提交里最值得看的是 fix(nemo-gym): score multi-step episodes and keep step evidence——多步 episode 现在会被正确打分并保留每一步的证据。这解决的是一个很实际的问题：过去一个技能跑完一条多步流程，评测只看最终结果，出错时无法定位是哪一步坏的。

  • 三层评估结构：Tier 1 是纯静态的 500+ 条规则与检测模式，不需 LLM key（skillevaluator validate ./my-skill --tiers 1）；全量运行会加上去重（识别功能重叠的技能）与活体智能体评测（measure skill lift，对比有技能与无技能的两次运行结果）。
  • 它同时给出兼容性体检：v1.0.1 起内置 HarnessCheck，检查技能能否在 Claude Code、Codex、Copilot CLI、Hermes、OpenClaw、OpenCode 六家宿主里被正确发现——逐项检查发现路径、frontmatter、description 与内容长度上限、调用设置与插件组件，避免技能被宿主「静默忽略、拒绝或截断」。
  • 官方论文挂在 arXiv（编号 2608.20614），并提供可复制粘贴的 CI 模板，接入方式写明「不需要自己构建或维护评测代码」。

值得关注的原因

  • 「对比有技能与无技能的两次运行」这个定义，是它比同类工具高明的地方，也是我立刻能用的地方。 技能评测的难点从来不是「这个技能跑通了吗」，而是「装上它之后到底好了没有」。这个 A/B 定义正好对应我 GLP-1 营养伴侣的核心问题：加了「早/晚双杯方案」这个技能之后，营养建议的准确率与依从性是不是真的变了？ 我现在的做法是「自己觉得方案更好了」，这在方法上等于没有评测。
  • HarnessCheck 覆盖六家宿主这一件事，直接命中我「多端交付」的现实约束。 我的技能包要同时在 WorkBuddy、公众号图文、以及可能的第三方 CLI 里可用；「技能被宿主静默忽略或截断」是一个我至今没有系统排查过的失败模式——用户说「没反应」的时候，我第一反应是内容写得不好，但更可能是 description 超了长度上限或者 frontmatter 字段名不对。这是最便宜的一类排查。
  • 多步 episode 保留步骤证据，和我上期记的「失败必须能说清是哪一环」是同一条线。 我这期在 conductor-oss/conductor 上又看到一次同类修正（一个 SQLite 队列的 pop 语句匹配条件写错，导致同 id 不同队列的消息可能被错误标记为已弹出）。两个仓库在同一天做同一类修复，说明「把失败定位到具体一步」正在成为行业默认标准。 我的平台每次推荐失败时能不能说清是数据缺失、算法不适用还是表述越界，现在还做不到。
  • 它有 500+ 条不需要 LLM key 的静态规则，这对我这种「每周只有 8 小时」的一人公司是决定性的。 任何需要额外 API 密钥、需要额外账费的评测环节，我大概率不会真的长期跑下去。能离线跑的门禁才会被坚持使用——这是我从「考证钩子 + 营养 AI 内核轻量助手」这个利基里学到的最实用的一条产品原则：流程里每加一个要花钱或要配密的步骤，实际执行率就会掉一半。

3. 把「证据分级」做进检索层：med-research-mcp 让智能体在答之前先知道手里那张牌有多重

地址：https://github.com/emilkrebs/med-research-mcp ｜ ★1 ｜ MIT ｜ 给 AI 助手用的循证医学文献检索 MCP server：一次检索合并 PubMed、Europe PMC、ChinaXiv 与 RussiaRxiv 四库，按 NLM 元数据标注每条结果的研究设计与撤稿状态，不调 LLM、不设账号、无遥测

事件内容

  • 今日 1 次提交并发 v0.8.1（2026-11-24 10:36）。release notes 明确两件事：已进入官方 MCP registry（登记名 io.github.emilkrebs/med-research-mcp，MCP 客户端与目录站点都能读到），以及库导出 Article 这个名字与其指南一致。工具行为与 0.8.0 相同，输入输出未变。
  • 它的核心机制是研究设计标签直接来自 NLM 元数据，而不是让模型去猜：每条结果都标出「这是什么类型的研究」「这个设计在证据等级里排第几」「是否被撤稿或已更正」。元数据缺失时标 unknown 而不是含糊带过——README 原文是 "No guessing: a record without metadata says unknown"。
  • README 给出的设计分级口径是牛津 CEBM 证据等级：从 5（系统综述与随机对照试验的合并证据）往下排到 0（动物实验与实验室研究、已撤稿论文）。它排的是「研究设计」，不是「研究质量」——设计为 5 的系统综述，不等于质量高。
  • 四库一次检索并合并去重：tirzepatide[tiab] AND "sleep apnea"[tiab] 在 PubMed 命中 143 条、在 Europe PMC 命中 142 条（这两个数字来自 v0.8.0 的 release notes，说明字段标签在两库间已经打通）。
  • 全文获取覆盖三条路：开放获取、机构代理、DOI 解析；ChinaXiv 与 RussiaRxiv 走 ChinaRxiv 的机器翻译，README 明确提醒「它的英文文本是机器翻译，且大部分 RussiaRxiv 摘要由它自己写入，依赖剂量、人群或结论前请核对原始记录」。
  • 随附三个 Agent 技能：med-research（工作流本身——写精准的 PubMed 查询、读标签、给无标签论文分类、汇报结论时说明确定性）、med-research-ebm（批判性评价，只在结论将依赖单篇论文时加载：偏倚风险、效应量、异质性、因果性、可迁移性）、med-research-setup（安装与排障）。
  • 不调 LLM、不设账号、无遥测，服务器在本机跑；查询只发往你搜索的数据库（NCBI、EMBL-EBI、ChinaRxiv），但全文请求可能把你的文章 id 或 DOI 发给你未搜索过的服务（NCBI、Europe PMC、ChinaRxiv、Unpaywall、doi.org、出版商站点、机构代理）。README 写明「不要把任何能识别患者的信息放进查询」。
  • 仓库有完整的合规文档：docs/compliance.md 记录预期用途与数据流向，并有基准测试（benchmark）评估模型在有该服务器时的答题质量。

值得关注的原因

  • 「不确定就标 unknown，不猜」这一条，是我做循证内容最该抄的纪律。 我在公众号写营养干预内容时，最容易犯的错就是把「这项研究的样本量小」这种限定语在转述时抹掉，读者拿到的就是一个干净的结论。这个工具把「证据有多强」做成了每条记录上的一个字段，而不是作者语气里的一个形容词。 我的「强制循证 + 参考文献 + 零 AI 幻觉」如果要变成可检验的机制，而不是一句自我要求，就应该在数据层有这样一个分级字段。
  • 「它排的是设计，不是质量」这句话，能挡掉我最容易犯的一类过度解读。 我以前看到「系统综述」就直接当高证据用，但 CEBM 的 5 级是「系统综述与随机对照试验」，2 级是「队列研究或病例对照研究」，0 级是「动物实验与实验室研究、已撤稿论文」——如果文章里引的是 0 级证据，按我的老习惯很容易在公众号里被写成「研究表明」。 这个分级直接提醒我：引用时必须把设计等级一起写出来。
  • 它接了 ChinaXiv 与 RussiaRxiv，这两个库我此前完全不知道。 这是本次最意外的信息——中国预印本有独立的 ChinaRxiv 平台，不属于中科院体系，而俄语预印本 RussiaRxiv 是独立项目。这直接影响我的检索覆盖面：中文营养与中医方向的证据一直有相当一部分落在预印本里，而预印本常常被常规检索漏掉。 我今天就顺手查了 AndyZHENG0715/TCM-Sage（本期在榜，中文项目），这类做证据综合的中文工具如果能接上 ChinaXiv，会是很好的互补。
  • 「不调 LLM」这个约束，对我的 4P 平台是架构级的提示。 我的三类算法（P4 本地 / DINGXIANG / JINGYAN）之间的分工，本质上就是「确定性代码做计算、模型做表述」。这个 MCP 把「检索 + 分级」这一层做成了纯确定性服务，模型只负责读标签、拼结论。这正是上期 LesionAgent 与 SystemOneAgents 反复指向的那个模式：数字与判定不该由模型生成。 我可以把这套做法直接搬到我的禁忌补剂与化验指标模块上。
  • 诚实地说，它今天只有 1 星、1 次提交，是刚进官方 registry 的新项目。 我把它列入精选不是因为它成熟，而是因为它把「循证」从承诺变成了一种数据结构——这件事对我的内容生产方式的影响，可能比它现在的成熟度重要得多。

值得关注的原因

  • 「每个数字带证据分级」这句话，是我这两年做 4P 精准营养一直缺的那一层。 我给冀敏做分阶段干预方案时，每个数值背后其实都有强弱不一的证据，但我在文档里只写了「数值 + 建议」，没有把「这个数有多可靠」作为独立字段保留下来。Tepna 的做法是把它做进数据模型：任何一个从原始信号算出来的数，都必须带着它的证据等级一起走。这直接对应我上期记的「证据强度三列」——我当时记下来了，但还没有落到存储层。
  • 「一个原始信号一个分析器」这个切分方式，对我拆解健康数据非常关键。 我的 GLP-1 营养伴侣现在把血糖、CGM、睡眠、体重、腰围、饮食记录混在一个评估逻辑里。Tepna 的做法是先按信号类型彻底分开，各自算各自的指标，再在融合层汇合。这样任何一个传感器掉线或数据质量差，都只影响它自己那一路，不会污染整体结论。这比「一个大模型读所有数据」的结构稳健得多——而这正是我现在的做法。
  • 「把失败也发布出来」这个做法，对我内容业务的杠杆最大。 我在公众号写营养科普时，最有价值的内容往往不是「这样做有效」，而是「这样做为什么无效 / 哪些证据站不住」。Tepna 专门维护一份「死胡同地图」，把走不通的路径引用式地公开。我的「4P精准营养观察」公众号和小红书「匆匆上岸」，如果每期都能拿出这样一份「哪些流行说法其实证据不足」的清单，专业定位会比泛泛讲原理清晰得多。
  • 「断网由 CI 强制」是我最想抄的一条工程约束。 我一直强调「本地优先、不上传用户数据」，但在我的 4P 平台里，这目前只是一句口头原则——没有任何机制能阻止某次改动引入一个偷偷上报的 SDK。 Tepna 的做法是把承诺变成一个会失败的构建。这条约束的成本很低（一个无头门禁），而它保护的是我最在意的资产：用户健康数据。
  • 它 96 次提交一天推一个版本，这种节奏对我是一记提醒：我的平台迭代节奏太慢。 原因很清楚——我一个人每周只有 8 小时，而且要同时推公众号、小红书、实战班与平台四件事。Tepna 的做法值得我学的是它把大量工作自动化了（门禁、导出普查、构建产物重建）。同样 8 小时，自动化程度不同，产出差几倍。

三、今日趋势观察

  • 技能生态正在从「提示词片段」变成「需要 CI 把关的工程资产」，而且这一档今天一次性补齐了两半。 过去两期我记的都是「怎么写更多技能」；今天 NVIDIA 同时给出装之前的扫描器（SkillSpector，26.1% 技能含漏洞、5.2% 疑似恶意）与装之后的评估器（SkillEvaluator，500+ 静态规则 + CI 模板 + 六家宿主兼容性体检）。这个组合意味着「一个技能包」从此有了类似软件依赖的供应链地位——有扫描、有评估、有签名、有版本。 对我自己的专家包，这意味着我以后不能把技能清单当成一份 Markdown 交付就完事，得给它加一道门禁。
  • 「把失败定位到具体一步」正在成为 Agent 基础设施的默认标准，今天两个仓库各修了一次同一类病。 SkillEvaluator 让多步 episode 保留每一步的证据（fix(nemo-gym): score multi-step episodes and keep step evidence）；Conductor 让被丢弃的合法计划变成编译警告而不是凭空消失（stop PLAN_EXECUTE silently dropping or misrouting valid plans）。共同的敌人是「静默」——静默丢弃、静默截断、静默重定向。 这正好接上我上期记的「失败必须能说清是哪一环」：一个系统如果说不清哪里坏了，它就还没坏，只是还没被发现。
  • 「把数字生成从模型手里拿走」这条线，今天在三个不同领域同时出现。 SkillSpector 的分析全部是静态的（不执行目标代码）、med-research-mcp 的证据分级全部来自 NLM 元数据（不调 LLM）、Conductor 的队列正确性来自 SQL 条件限定（不靠模型判断）。三个项目互不相干，但都在做同一件事：让判定来自可复现的规则，让模型只负责表述。 我本地 Ollama qwen2.5:7b 表现平庸这件事，我现在更倾向于归因于框架而非模型——但前提是我先把计算与判定的边界划出来。
  • 健康与营养这条线的重心，明显在往「本地优先 + 证据分级 + 可审计」三个方向收敛。 Tepna 每个数字带证据分级并把断网做成 CI 门禁；biomarker-tracker 81 项指标每项标出处（Europe PMC、EFSA、原始论文）且计算全由代码完成；med-research-mcp 把 CEBM 等级直接编码进检索层。这三个项目都不主张「更聪明的模型」，都主张「更硬的证据链」。 对我的 GLP-1 营养伴侣，这条线的参考价值可能高于任何一次模型升级。
  • 一个我此前完全不知道的信息缺口：中文预印本有独立的 ChinaRxiv 平台。 med-research-mcp 的 README 明确写出 ChinaXiv 来自中国科学院体系之外的独立项目 ChinaRxiv，其英文文本为机器翻译、且大部分 RussiaRxiv 摘要由其自行写入。这意味着我在中文营养与中医方向上，常规 PubMed 检索系统性地漏掉了一整块证据。 我下期打算查一遍这个库里到底有多少营养相关内容——如果数量可观，这是我公众号选题的一个新矿脉。
  • 今日一个安静但重要的观察：本地优先已经从「卖点」变成了「可验证的工程约束」。 Tepna 用一个会失败的 CI 门禁强制断网；biomarker-tracker 明确「无账号、无云、每人一个本地文件夹、无遥测，页面只能跟自己说话和两个研究库说话」；med-research-mcp 跑在本机、不调 LLM。这三个项目都有一个共同点：它们不承诺自己不联网，而是让承诺失败。 我一直强调 4P 平台「本地优先、不上传用户数据」，但那目前只是一句话——这句话今天有了三种可抄的实现方式。
