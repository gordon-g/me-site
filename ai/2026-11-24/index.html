1. 医学智能体开始把「算数字」这件事彻底交给确定性引擎：LesionAgent 让 LLM 一次数字都不许算

地址：https://github.com/MIC-DKFZ/LesionAgent ｜ ★13 ｜ Apache-2.0 ｜ 德国癌症研究中心（MIC-DKFZ）的免训练肿瘤追踪智能体：把冻结的 3D 基础模型当工具用，LLM 只负责判断，RECIST 1.1 的每一个测量值和分类都由确定性指南引擎算出

事件内容

  • 今日 1 次提交（link to paper），但动作本身是实质性的：论文《LesionAgent: Training-Free Agentic Tumor Tracking and Response Assessment in Longitudinal CT》于 2026-11-20 挂上 arXiv（编号 2611.27876），仓库当天补上链接。作者来自 Maximilian Rokuss、Jeya Maria Jose Valanarasu、Alejandro Lozano、Benjamin Hamm、Yannick Kirchhoff、Fabian Isensee、Klaus Maier-Hein。
  • 架构是按「决策类型」拆开的：3D 基础模型负责感知（VoxTell 检测、nnInteractive 分割、uniGradICON 配准、LongiTrack 跟踪、TotalSegmentator 分配器官），LLM 负责判断模型判断不了的事（这是不是病灶、下次访视是不是同一病灶、新出现的点是不是真的进展、哪些该随访），而确定性指南引擎负责在掩膜上量尺寸并套用 RECIST 1.1。README 原话是 the LLM never computes a number or a response category。
  • 智能体只通过 18 个有类型的工具行动，分四组：感知（detect/segment/track_all/refine_lesion/edit_mask/totalsegmentator）、检视（study_info/view/view_pair/inspect）、登记（review_candidates/update_lesion/set_visit_judgement）、决策（score_lesions/propose_targets/set_targets/recist_report），外加一个人类通道 ask_clinician。
  • 论文摘要给出的关键数字：同样的 3D 模型用固定规则串联，在 56 次随访里误判进展 33 次，LesionAgent 只误判 2 次；在临床随访 CT 上与放射科医生对疗效判断一致 20/23 次，且包含每一次变化；不经过 DeepLesion 训练的情况下，病灶召回 89.0%，高于所有在 DeepLesion 上训练过的跟踪器（87.4%）。
  • 论文里最狠的一句是：决定差距的是框架不是模型——同一个 LLM 加同样的 3D 模型，Claude Code 的检出 F1 只有 41%，LesionAgent 是 78%；而一个能跑在医院内网的开源权重模型从 6% 提到 73%。
  • README 明示当前状态是「Coming soon」，路线图列出论文、代码、CLI / Python API 与 napari 读片应用四步；napari 应用支持任何 LLM，临床医生可实时旁观、回答智能体提问（比如两套有效靶病灶集给出不同疗效时该用哪套）、纠正任意决策，RECIST 报告随后从登记库重新生成。

值得关注的原因

  • 这条给我这一行提供的是一个可以直接抄走的架构范式，不是一个工具推荐。 我一直卡的那个问题——干预报告里的数字到底该由谁算——这里给出了明确答案：LLM 一个数都不许算，数字由确定性引擎从原始掩膜上算，LLM 只做它擅长的判断。 我的 GLP-1 营养伴侣目前是「模型读指标 → 模型给建议 → 模型写结论」，链条上没有一个环节是确定性的；如果指标读数不可信它仍然会给出一个数，那么「零 AI 幻觉」在我这里只是一句口号，而 LesionAgent 给出的做法是把数字生成这一步从模型手里彻底拿走。
  • 「决定差距的是框架不是模型」这句话，对我的一人公司是一记警钟。 Claude Code 41% vs LesionAgent 78%、开源权重模型 6% → 73%，说明同一堆模型换个框架，能力可以差十几倍。这意味着我本地 Ollama qwen2.5:7b 的效果差，未必是模型不行，可能是我没给它正确的框架（工具类型化、引擎分工、登记状态）。这比「换个更强的模型」便宜得多，也快得多。
  • 病灶登记库（lesions × visits 的矩阵，每个访视保留掩膜）是我「家庭健康档案」最该借鉴的一处。 我的伴侣里有「多成员 + 时间轴 + 指标趋势」，但每一次指标读数目前是孤立的一条记录，没有「同一件事在不同时间点的同一份原始证据」这个结构。登记库的设计保证了任何一次结论都能回溯到具体哪次访视的哪张掩膜——这就是我上期记的「证据强度三列」在存储层的落地方式。
  • 「18 个有类型的工具」这个数量级值得我记住。 它既不是「给 agent 一个万能 shell」，也不是「把几十个 API 都塞进去」，而是刚好覆盖这条读片流程所必需的判断面。工具类型化 + 引擎分工 + 人类通道这三件套，是我 4P 平台做「算法模块 + LLM 编排」时可以直接复用的接口设计。
  • 诚实地说，这条今天只有 1 次提交、13 星、代码未发布，论文数据来自 arXiv 而非仓库实测。 但它是我这周看到的唯一一条把「循证」从承诺变成代码结构的项目：每一个数字都能追溯到掩膜，每一个分类都能追溯到规则表。这种项目对我的价值不在于能立刻用，而在于它指明了我该往哪个方向改。

2. 不生成文本的智能体：SystemOneAgents 把「模型只判断、代码负责组装」做成 97.0% 的可复现流程

地址：https://github.com/eltzanis/SystemOneAgents ｜ ★15 ｜ Apache-2.0 ｜ 「System 1 agents: a method for local, reliable and fast agentic AI」的官方实现：确定性编译器把工具 schema 与请求转成有限选项的判断题，一次前向的决策模型只回答选项，代码负责组装调用

事件内容

  • 今日 1 次提交（Update README），仓库本身是 2026-11-16 挂上 arXiv（编号 2611.21053，18 页、5 图、9 表）的论文配套开源软件，作者 Eleftherios Tzanis 与 Michail E. Klontzas。
  • 核心机制：确定性编译器把每个工具的 JSON schema 与用户请求转成有类型的多选题，选项只来自请求与 schema；决策模型对每个选项给概率，一次前向作答；代码掌握控制流并组装调用。README 的原话是 the model judges; code assembles——所有工具名、参数名与参数值都来自目录、schema 或请求本身。
  • 论文摘要给出的数字：在 1,952 次请求 / 157 个生物医学工具上，最好的 System 1 智能体 97.0% 的请求要么选对工具、要么正确拒答，显著高于全部 18 组本地 LLM-agent 配置中的最好成绩（95.2%）；填参正确率 97.0%（共 6,056 个声明参数值）；编造内容 0 次，而 LLM 调用中编造率是 5.5–19.7%。
  • 三类情况被明确区分：枚举型参数问「枚举值」、布尔型问「on / off / not mentioned」、路径 / 数字 / 名称 / 自由文本则从请求、schema 或先前步骤里抽候选并附「not specified」。可选参数仅在概率 ≥ 0.7 时才填；必填参数若没有受支持的值，就报告缺失并向用户提问，而不是编一个。
  • 智能体明确会拒绝：没有任何工具能做某件事时直接拒绝，而不是硬凑一个工具调用。每一个问答对都可存储，因此一次运行可以逐个决策回放与审计。
  • 工程上它是本地运行的：决策模型通过 llama.cpp 跑，无微调；代码在 code/ 目录，pip install -e . 安装。

值得关注的原因

  • 「模型判断、代码组装」这八个字，直接对应我平台里的一个具体缺陷。 我的 4P 精准营养算法有三类（P4 本地 / DINGXIANG / JINGYAN），现在都是模型在自由文本里决定调哪个、带什么参数。这带来两个后果：一是参数值可能被「润色」成一个看起来合理但没依据的东西（编造率 5.5–19.7% 就是这个量级），二是整个决策过程无法逐条回放审计。改成「schema 限定选项 + 代码组装」之后，我的每个推荐都能回放成一道道有答案的判断题——这是「零 AI 幻觉」从态度变成接口契约的路径。
  • 「参数缺失就问，不要编」这一条，是我 GLP-1 伴侣最该照抄的。 我的客户端会同时用血糖、CGM、饮食记录、化验单、用药记录多源数据。当某次指标读数缺失时，我的系统目前是给一个估计值还是停下来问？ 按今天的判据，正确答案是「必填值缺失就报缺失并追问」。我的「指标改善 / 不变 / 恶化」判定逻辑，本质上正是一个分类问题，而它的输入（读数、用药依从性、运动量）恰恰大部分是可以枚举或抽取的——这个方法论几乎是为我的场景设计的。
  • 97.0% 对 95.2% 这个对比说明了一件容易被误读的事。 换成 System 1 之后，正确工具选择率只提升了约 2 个百分点，看起来「没什么用」。但真正的收益在另一栏——编造从 5.5–19.7% 降到 0。这跟我在 11-22 期记的 verifylens 那条判据是同一件事的两种表述：一个看起来合理的错误参数，比选错工具更贵，因为它会沿着后面的每一步传播下去。
  • 「本地跑、无微调、llama.cpp」这条对一人公司的现实约束是决定性的。 我一周只有 8 小时、约 1 个月的现金跑道，任何需要 GPU 微调、需要云端账号、需要付费 API 的方案都不该进我的路线图。这个方案不花钱、不训练、跑在本地，而且它论文里的场景（生物医学工具、本地敏感数据）正是我的业务场景——这是本期最应该认真读 README 的一个仓库。
  • 它还提醒我一件事：不要为了「更智能」而引入自由文本生成。 我一直在想给 4P 平台加一个「自然语言问诊式」的入口，让用户用口语描述饮食然后模型给建议。按今天的判据，这条路的第一步就该是受限的——先把结构化参数定死，把自由文本放在最后一层做润色，而不是让它承载决策。

地址：https://github.com/letta-ai/letta-code ｜ ★3,902 ｜ Apache-2.0 ｜ 有状态智能体框架（MemGPT / sleep-time compute 团队出品）：智能体有记忆、身份与长期经验，会主动改写自己的记忆、技能、提示词乃至框架本身

值得关注的原因

  • MemFS 用 git 跟踪全部上下文这一条，是我这期读到最「工程」的一个决定。 它意味着智能体的记忆不是数据库里的一个 blob，而是可以 diff、可以提交、可以回滚、可以 review 的一组文件。我在 GL-1 营养伴侣 V2 里做的「每次交互数据持久化以支持自我进化学习」，目前是往 SQLite 里写记录——能存，但没法看、没法版本对比、没法回滚。改成 git 之后，「智能体学到了什么」变成一份可以人眼审阅的 diff。这件事对我的意义比任何新功能都大：一个一人公司的自我进化系统，必须能被自己检查，否则它就是在偷偷漂移。
  • 「记忆是文件」还顺手解决了可解释性问题。 我的干预报告要回答「为什么给出这个建议」，如果记忆和技能都是文件，那么答案可以直接引用某个记忆块的某一行。这比「让模型解释自己」可靠得多——模型解释也是生成的，而 git diff 不是。
  • 今天的三条提交恰好都在给「自改进」装护栏。 子智能体按任务描述限定作用域、任务描述被记进轨迹、云端选项必须与实际解析到的计算机匹配——这三件事合起来是同一个问题的三种形态：智能体改自己的时候，改到哪儿去了、跟谁有关、跟哪台机器有关，必须全部记下来。 我上一期记过「自评闭环必须有外部钉子」，今天这一条补上另一半：自改进闭环必须有外部痕迹。
  • 对「每周 8 小时 + 1 个月现金跑道」的现实意义：这个项目有 3,902 星、有正式发版节奏、npm / uv / pipx 三种装法、且免费。 它不是又一个需要我评估半天的新框架，而是今天就能装、装完就有 /palace 和 /doctor 两个命令可以试。相比本地模型换新，把记忆变成可审阅的文件是我这个月更值得做的一步。
  • 它的 sleep-time compute 路线与我记过的「预热/反思」思路同源。 但我要提醒自己一点：它同时是一个商业产品（Letta Cloud 默认后端），本地模式虽然存在（--backend local），但云端默认意味着记忆默认出本机——对我这种做健康数据的人，落地时第一件事就是强制本地后端。 这条纪律我在 11-23 期记过（OpenScientist 的气隙模式），今天又遇到一次同样的选择。

  • 占位数据被明写为「不是真证据」，这条自我纪律比它的功能更有价值。 我的 GL-1 伴侣里有 153 个食材模板、15 个功能靶点，这些模板是我写的、不是临床验证的。我在产品里从来没有对用户说过这一点。 这个项目只用一行 README 就把这件事讲清楚了——「模板 vs 证据」的边界必须写在产物里，不能只存在于我的脑子里。
  • 服务端 fail-closed 的免责门禁，是给健康内容的一个可复用范式。 我的站（54hrm.com）页脚写着「本站内容不含医疗诊断，方案仅供研究参考」——但那是一句任何人都能忽略的文字。这个项目把它做成没设密钥就整个站点不可用。强制比声明有效，这一条对 GLP-1 营养伴侣的交付形态同样成立：不做医疗建议，就应该在产品结构上让它做不成，而不是在文案上保证不做。**
  • 它还示范了「声明矩阵作为流水线与前端之间的契约」这个结构。 我的干预报告有 9 章结构 + 24 个风险维度 + 6 个风险级别——这些其实就是一个 claim matrix，前端展示什么、后端算什么，两者靠一份 JSON 契约对齐。我的现状是后端算完直接吐 HTML，没有中间契约层，所以每加一个风险维度都要同时改前后端。这一层值得单独抽出来。

三、今日趋势观察

  • ⭐⭐⭐ 「数字不该由模型算」今天在两个互不相识的团队同时落地，凑成一条我可以直接抄的主线。 LesionAgent 把测量与 RECIST 分类交给确定性指南引擎，README 明说 the LLM never computes a number or a response category；SystemOneAgents 把整个工具调用编译成有限选项的判断题，README 明说 the model judges; code assembles。两个团队、一个共同结论：模型的职责是判断，计算的职责是代码。 我这两天的观察串起来正好是同一件事的两面——上期记的「拒绝比猜测好」，今天升级成「先划清模型能碰什么、不能碰什么」。
  • ⭐⭐⭐ 「证据本身也带偏见评级」是我这期最想抄的一条落点。 Concordance 用 brand-blind + 用户自定权重 + bias-rated cited evidence 三步做 GLP-1 对比，并把占位数据明写为 not real evidence；我的干预报告现在只有「有引用」这一列，没有「引用有多可信」这一列。一个 2019 年小样本 RCT 和一个 2026 年 III 期 RCT，在我的报告里现在长得一样——这跟「没写引用」是同一类问题。 加上「证据强度」这一列这件事，本周就能做。
  • ⭐⭐ 「记忆要能被自己检查」今天有了一个具体实现。 Letta Code 用 git 跟踪全部上下文（含记忆块），可同步到自定义 GitHub 仓库；smolvm 提供可 checkpoint、可分支、可回溯的微虚拟机；Concordance 用一份 claim matrix JSON 作为流水线与前端的契约。三条都在做同一件事：把智能体内部状态从「不可见的黑箱」变成「可 diff 的产物」。 我 4P 平台的干预报告现在是后端算完直接吐 HTML，中间没有契约层——这层该抽出来。
  • ⭐⭐ 「失败必须能说清是哪一环」今天在高提交量项目里成了主线。 AutoClip 的 12 次提交几乎全在这一类：Gemini 的网络失败仍归属到模型、单次 LLM 失败要分类、闭环试跑的失败原因要在 8 种语言界面都露出来；cli-agent-orchestrator 把「投递失败」和「回复已发送」拆开，并且要求 flaky 窗口的断言和它守护的属性一样严格；sglang_ling_v3 修 PP 预填充的释放时机。这类故障不报错、最贵—— 我 OCR→AI→App 链路现在的错误提示还停在「未识别到该指标」这一级。
  • ⭐ 「同一堆模型，换框架差十几倍」这条要写进我的技术选型逻辑。 LesionAgent 论文给的对照：同一个 LLM 加同样的 3D 模型，Claude Code 的检出 F1 是 41%，LesionAgent 是 78%；能跑在医院内网的开源权重模型从 6% 提到 73%。这说明我本地 qwen2.5:7b 表现平庸，未必是模型不行，可能是我给的框架不对。 对一周只有 8 小时的一人公司，这条比「换个更强的模型」便宜得多。
  • ⭐ ③ 健康/营养线今天终于有一个「口径清晰」的项目，但仍是低星。 16 个仓库里只有 TandoorRecipes/recipes（★8,745）上过三位数，其余全是 0–6 星的小项目——这与 11-18 至 11-23 连续六期一致。但本期有两个值得看的：Concordance 的品牌盲 + 偏见评级 + 引用证据（见精选第 5 条），以及 strimma 的餐后分析（餐窗、恢复、餐时 IOB）与 leave a meal out of meal stats until its window has ended（窗口没结束就不计入餐后统计）——这条判断规则和我 GLP-1 伴侣里「指标按改善/不变/恶化触发重新优化」是同一类逻辑，值得对照。
