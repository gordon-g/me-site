2. MarissaFamularo/Calibrate：把"医生该不该信 AI"做成可测量的 2×2 矩阵——过度依赖与反射性否定这两个词，精准命中了我做补剂方案时的真实风险

地址：https://github.com/MarissaFamularo/Calibrate ｜ ★0 ｜ 未声明 ｜ Python ｜ 外科住院医 AI 依赖度模拟器（Meta Global AI Developer Hackathon，2026-10-27 ~ 11-04，血管外科住院医项目总监个人作品）

事件内容

窗口内 10 次提交（11-01 19:28Z ~ 11-02 02:14Z），主线是"让这个模拟器经得起真人试玩"。

  • 核心是一张 2×2 依赖度矩阵，把每一次 AI 辅助决策都归类：AI 对且医生跟随 = 恰当依赖；AI 错而医生跟随 = 过度依赖；AI 对而医生否决 = 反射性否定；AI 错而医生否决 = 恰当否决。报告里还单独统计"AI 给了但医生根本没看过的输出"、"开了但没看的提醒"、"看了但价值很低的提醒"。
  • AI 助手是故意被设计成"大部分时候对、但在特定点错"的——有些错得很有信心，有些会把真实文献引到错误语境里。关键设计意图是：住院医不是在找 AI 的错，AI 是一个要好好共事的同事，最终决定责任在医生。
  • 今天推的是"仿真化"和"细节对齐"：把练习脚本改成无脚本版本、让既往病历里的检查医嘱能带到检查步骤、把 ABI 提醒的评分限定在第 1 次就诊、修掉"给了 PVR 波形"这类与病例设定矛盾的输出。
  • 报告口径也做了收紧：复盘总评只给计数与具体产出名目，不再对"为什么这么做"做推测；demo 脚本与直播彩排脚本成对提交；主诊医生全程不显示内部 ID、也不提示哪些是"埋好的"。

值得关注的原因

  • "过度依赖"和"反射性否定"这两个词精准命中了我这个站的真实风险。 我做 4P 补剂平台的 AI 助手，本质上就是在用 LLM 替代一部分营养师判断。Calibrate 的整套评测框架可以直接搬过去：当 AI 给的补剂方案和化验指标冲突时，系统应该把这次决策归到哪一格？ 现在我的平台只记录"AI 说了什么"，没有"人信了 AI 还是推翻了 AI"这个维度——而这恰恰是决定方案是否安全的核心变量。
  • "把提醒按价值分级"是 4P 平台该抄的一条。 报告里统计"开了但没看的提醒"和"看了但价值很低的提醒"——我的干预报告里也有这个问题：24 个风险维度如果全都以同样的权重、同样的视觉优先级呈现，医生用户会全部忽略，而这和"没有风险提示"在效果上没有区别。把低价值提醒显式统计出来，是让提醒体系真正可用的前提。
  • "AI 是同事不是权威，责任在人"这个定位，比"AI 给建议"更接近医疗场景的实际。 对我做的补剂内容与课程，这个框架可以直接变成教学语言。
  • 一个诚实的提醒：仓库没有 LICENSE 文件，且是个人作品。但它的评测设计方法论（2×2 矩阵 + 逐项对账）本身不受版权限制，可以放心借鉴思路。

4. yantrikos/yantrikdb：记忆引擎开始管"矛盾"而不只是管"存储"——而且它把 SQLite 那个会静默损坏数据的坑写在了 README 第一屏

地址：https://github.com/yantrikos/yantrikdb ｜ ★71 ｜ Apache-2.0 ｜ Rust（带 Python 绑定）｜ AI agent 的认知记忆引擎：时间衰减 + 自主整合 + 矛盾检测 + 知识图谱

事件内容

窗口内 18 次提交（11-01 21:xx ~ 11-02 01:51Z），今天的主线是 CI、跨平台与可配置性。

  • 今天的实际动作集中在工程侧：ci: apply the CPU-only torch install to the lint and Linux test jobs、ci(benchmark): install CPU-only torch to stop filling the runner disk、ci: move macOS jobs from macos-14 to macos-15；同时把 redundancy_sim_threshold 从 Python 侧可达并默认在反序列化时开启，贡献者与 reviewer 也按规矩署名。
  • 产品边界写得非常清楚：README 开头就是"你的 agent 每次会话都从陌生开始。给 agent 挂个向量库并不能解决这个问题——什么都没被遗忘，近乎重复的记忆不断堆积，两个互相矛盾的事实并列返回且没有任何提示说它们冲突"。它要做的是管理记忆，而不只是存储记忆。
  • 能力清单：时间衰减、自主整合（consolidation）、矛盾检测、知识图谱，嵌在可嵌入的 Rust 库里并提供 Python 绑定。
  • 部署形态两个：作为库 pip install yantrikdb 直接调 record_text() / recall_text()（不需要装 sentence-transformers、不需要 ONNX runtime），或作为服务 pip install yantrikdb-mcp 挂进 Claude / Cursor / Windsurf / Copilot 的 MCP 配置，agent 自动召回、自动记忆、自动检测矛盾，不用写 prompt。
  • README 第一屏就写着一个会静默损坏数据的坑：同一进程里绝不能用第二个 SQLite 库打开同一个文件——POSIX 锁是按进程的，两边交错写 WAL 会无声地损坏存储；Linux 上引擎会检测到第二个实例并拒绝写入（ForeignSqliteInstance），每个平台上未走引擎的提交会排队触发完整性检查，检查失败则以 IntegrityCheckFailed 拒绝写入。

值得关注的原因

  • "矛盾检测"这个能力，对我的 4P 平台是刚需而不是锦上添花。 4P 补剂平台里，同一个客户的时间序列数据天然会冲突：3 月的 LDL 和 9 月的 LDL 不是一个值；用户补了三个月镁，血清镁没动；上一轮建议的剂量和这一轮的不一样。现在这些冲突是"取最新一条"糊过去的——但取最新一条不等于取最合理的那个。 一个能明确告诉我"这两条记录矛盾"的记忆层，直接决定干预报告要不要停下来问一句。
  • "什么都不被遗忘"是我一直在踩的坑。 我给客户改方案、每轮都加新信息，从不清理旧信息——近重复的方案越堆越多，最后没人说得清当前生效的是哪一版。 "时间衰减 + 自主整合"正对着这个病：旧信息自动淡出，同时被合并成更高层的结论。
  • 那个 SQLite 坑，是对我现有架构的直接警告。 我的 4P 精准营养平台就是 Flask + SQLite。README 描述的失效模式——同一进程内第二个 SQLite 连接交错写 WAL，导致数据静默损坏——在 Flask 应用里非常容易发生（一个请求线程直连、另一个走 ORM，典型的双写场景）。它给出的防护模式（引擎自带锁 + 完整性检查 + 失败拒绝写入）值得我回头审一遍自己的落库代码。
  • Apache-2.0 + 不依赖 sentence-transformers / ONNX，意味着装它不需要拖一整套模型运行时。对一个"每周 8 小时"的一人公司，这个依赖账算得很清。

  • 作者在 README 里先立了一条死规矩：Every claim, backed by evidence。仓库带 SPDX 头、OpenSSF Scorecard 徽章与 REUSE 状态徽章。

值得关注的原因

  • "先证明打分器是好的，再让它的分数算数"——这一句就值回我一期日报。 我正在做的两件事都踩在这个坑上：一是 GLPL 营养伴侣的化验指标趋势判断，二是 AI 病人补剂模拟 Agent 的题库引擎。我现在的评估方式是"看 agent 输出的报告对不对"，这跟"只看模型输出的评估会系统性高估可靠性"是同一个错误——如果打分的人（我）自己就是那个会犯错的人，那分数就没有意义。Aureproof 的做法是给打分器也做四组控制测试（参考正例 / 修复负例 / 空操作 / 反作弊），打分器先过体检，再去给别人打分。
  • "哈希链式日志 + 可离线重算"这套，正好对着我 4P 平台落库那件事。 我上一期记下的工程结论是"干预报告落库 checklist"，需要的是"数字按精确值比较、None 匹配存储空值、拒绝字面量占位符"。Aureproof 补上的是更外面一层：证据包要能被第三方离线重算。 我做"AI 助手 + 循证报告"的可信度，缺的正是这一层——报告存下来之后，别人能不能自己验一遍。
  • 预注册闸门返回三态（pass / fail / inconclusive）这个设计，比二元通过 / 失败诚实得多。 对我的场景直接可用：干预方案生成的评测里，"证据不足无法判定"必须是一个独立结论，而不是被塞进"通过"。 报告里混进"其实是 inconclusive"的项，比明确标注它更危险。
  • Apache-2.0 可商用，且它明确标注自己处于 pre-release、尚未断言基准结果——这种"不吹"的状态声明，本身就是我选型时愿意信任的信号，比很多 README 上写满 benchmark 数字的项目更靠谱。

三、今日趋势观察

今天的 102 个条目里，主线只有一条：agent 生态开始出现"分层的自我怀疑"——不是让模型更聪明，而是给模型配套的评测、记忆与安装链路补上验证层。这在四个方向上是同步发生的。

  • 评测层在补"打分器也需要被验证"这一层。 bhargavchintam/aureproof 要求打分器先过四组控制测试才允许给别的任务计分，cmisaico/healoi-ai-clinical-simulator 做双评分离散（差异 ≥ 2 分进人工复核）、引用逐条核验（没有可核验引用的分数直接作废）、并用加权 kappa 对齐人类评分，MarissaFamularo/Calibrate 把医生信不信 AI 拆成 2×2 矩阵。三个项目、不同语言、不同领域，指向同一件事：模型输出的可信度不能靠"看起来对"来保证。
  • 记忆层从"存"转向"管"。 yantrikos/yantrikdb 明确把问题定义成"什么都没被遗忘、近乎重复的记忆不断堆积、两个矛盾事实并列返回且没有提示"，Pseudogiant-xr/Pseudolife-MCP 强调 canonical fact 皮层与"诚实的遗忘"，fjwood69/mori 直接把矛盾来源定义为"策展决定留什么，provenance 决定它在哪儿有效"。这三家都不再把记忆当检索问题，而是当治理问题。
  • 技能分发开始出现"安装即攻击面"这个话题。 hussi9/skill-router 今天的三次提交全在加固：把 skills.sh 注册表字符串当作不可信输入（在校验之前不许它们到达命令或模型）、按 origin 文件与锚点标识符做 fullmatch 校验、审计看板不可用时选择 fail closed 而不是放行。一个技能生态一旦有了中心化注册表，"从注册表装东西"就等价于"执行第三方代码"——这个仓库是本窗口内唯一正面处理这件事的项目。
  • 健康与营养线的项目普遍在做"覆盖不到的部分也写出来"这件事。 richmondgoh8/macro-longevity 记录覆盖缺口与剩余复核范围，iashahussain/rounds-dashboard 承诺 100% 客户端、患者数据不出设备且仓库里不含任何患者数据，Razzleberrytt/hippie-scientist-site 用 Excel 主表作为唯一权威源、公开数据目录只当发布目标。这与我上一期记下的"把 116 条规则的覆盖率检查做出来"是同一个诉求。
  • 医学线出现了一个新的形态：把不确定性做成可执行的分支，而不是一个分数。 MarissaFamularo/Calibrate 的助手"大部分时候对，但在特定预设点错"；cmisaico/healoi-ai-clinical-simulator 的测试里明确有一个"评分器 A 被注入后会编造引用"的攻击用例，用来演示代码层控制能抓住它；bhargavchintam/aureproof 让闸门能返回 inconclusive。三者都拒绝把"不确定"压缩成一个数字。
