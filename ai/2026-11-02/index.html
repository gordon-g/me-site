3. ilodezis/vitals：103 个 MCP 工具、15 个健康领域——把 Garmin、Hevy、GLP-1、化验单和 VCF 基因文件接进同一个自托管健康数据湖，还带一份能冻结的"医生报告"

地址：https://github.com/ilodezis/vitals ｜ ★12 ｜ PolyForm Noncommercial 1.0.0（README 徽章，GitHub API 字段为 NOASSERTION）｜ Python 3.14 / FastAPI / PostgreSQL 18 / Redis 7 / React 19 PWA ｜ 单用户自托管的个人健康数据湖与仪表盘，通过 MCP 向 Claude.ai 暴露读写能力

事件内容

今天窗口内只有 2 次提交（11-01 17:45 与 19:29 北京时间），但这个项目的架构密度值得逐项看：它是目前见到的、把"个人健康数据 → MCP → AI"这条链路做得最完整的开源实现。

  • 103 个 MCP 工具（46 个读 + 55 个写），覆盖 15 个领域：体重与身体组成、InBody BIA、HRT/TRT、GLP-1、Garmin 活动睡眠恢复、Hevy 力量训练、营养与热量、补剂、护肤、化验、遗传学、自定义图表、时间线、目标里程碑、Signals/Telegram 通知。工具按启用模块动态过滤，关掉某领域就从 tools/list 里消失。

  • 遗传学支持导入 VCF（单次上限 5 万行），解析 SNP 并关联易感性目录，已列出 HFE、MTHFR、G6PD、CYP1A2、COMT 等基因；遗传信息会进入 Conflict Engine（116 条带证据等级与来源的规则），例如血色素沉着症相关规则会阻止或警告补铁。
  • GLP-1 模块有平台期检测：剂量超过 14 天且体重趋势低于每周 100 克时告警。补剂目录约 90 条，含中英文别名、剂量、服用时间与证据等级。
  • "医生报告"是今天最值得抄的一个设计：选定时间范围后系统冻结该时点的数据、生成不可变快照，返回带密码的分享链接，可配置到期时间、可一键撤销、记录访问次数；快照不进数据库备份；可下载为无脚本、无外部网络请求、可离线打开并打印的自包含 HTML。且"数据变化时必须新建报告，不能替换医生已经拿到的旧报告"。
  • 不可逆写入统一走 confirm=True：delete_record、resolve_all_alerts、create_shared_report 在未确认时返回 dry-run 预览而非直接执行。
  • 今天的两次提交：迁移到 PostgreSQL 18；以及一次依赖安全更新（glob 升到 v14、minimatch 覆盖到 11，标记 [security]）。

值得关注的原因

  • 它的领域切分几乎就是我 GLP-1 营养伴侣 V2 的领域切分。 我那个 V2 已经覆盖早/晚双杯、化验指标趋势追踪（血糖/HbA1c、血脂、肝功、维 D、铁/铁蛋白、尿酸、体重/腰围）、以及"依据改善/不变/恶化触发重新优化"这条主线。vitals 在同样的领域上已经跑出了可用的实现——尤其是 GLP-1 平台期检测（剂量天数 + 体重趋势阈值）这个具体规则，和我"停药 cascade / 用药周期"的设计是同一类问题。
  • "原始输入保留在 raw_payloads、解析器可重跑"这条，是我做"化验报告照片 OCR→AI→App 导入"时最该抄的一条。 我的路径设计里，OCR 结果一旦入库就当成事实了；但只要保留原始照片与原始 payload，未来的解析器升级就能对全部历史数据重跑一遍——这对我补齐"零 AI 幻觉"的证据链尤其重要：我可以证明"这次结论是从原始报告重算出来的，不是当时模型随口说的"。
  • Conflict Engine 的 116 条带证据等级规则 + 遗传信息参与冲突判定，和我的补剂禁忌逻辑是同一个问题的两种解法。 我现在的"禁用补剂"文档是人工维护的清单；它这里是规则引擎，且血色素沉着症 → 阻止补铁这类规则直接用了基因信息。"禁忌清单"升级成"带证据等级、可自动判定的规则集"，是我 4P 平台下一步最该做的升级。
  • "医生报告 = 冻结快照 + 不可变 + 可撤销 + 不进备份 + 自包含离线 HTML"，是我目前完全没有的能力。 4P 补剂平台的干预报告现在还是"生成即发送"，没有冻结与撤销。一旦用户拿着报告去看专科医生，报告必须是一份可追溯、不可篡改、能证明"这是 11 月 2 日的状态"的东西——这套设计比我现有的方案严谨一个量级。
  • ⚠️ 许可证是必须先解决的问题：PolyForm Noncommercial 1.0.0 允许个人使用、修改、分发，但不允许商业使用。 我的一人公司是要把这类能力卖出去的，这个仓库可以读、可以借鉴架构、可以抄思路，但代码本身不能进商业产品。要么谈商业授权，要么只把它当"参考实现"来看。这个判断必须在动手之前做，不是等到要上线时才发现。

  • 它还直接暴露了一个 WorkBuddy 用户会踩的坑：README 专门提醒 clawhub install 装到 <workdir>/skills/<slug>，而 WorkBuddy 只读 ~/.workbuddy/skills，必须指定 workdir。这种"某个客户端的技能目录约定不一样"的细节，正是我给学员做《精准营养干预实战班》SOP 时该写进手册的细节。

地址：https://github.com/claimseed/claimseed ｜ ★0 ｜ Apache-2.0 ｜ Node.js 22.13+ / Chrome-Chromium 渲染 / MCP server ｜ 完全合成的美国医疗账单样张（Medicare Summary Notice、住院逐项账单、Medicare Advantage EOB），每份都附 ground-truth JSON 说明埋了哪些账单错误

事件内容

今天窗口内 1 次提交（11-01 12:51 北京时间，合入 release-0.4.0 分支的合并提交），另有 0.3.0（10-29）与 0.1.0（10-28）两个已发布版本。

  • 合成数据的三条硬规矩：所有姓名、标识、地址、电话与金额均由种子生成，仓库内没有任何内容源自真实文档；每一页渲染出来都自带"这是样张"的标记——页脚文字带 + 以图形绘制的水印（不污染文字抽取层）+ 写入 PDF 元数据，由渲染器强制盖上，没有任何 CLI 参数、库调用或数据对象能把它关掉。
  • 同种子可复现：同一 Chrome 构建（CI 用 Linux）两次渲染字节完全一致，其他平台内容相同但字节可能随 Chrome 版本变化。
  • verify 命令给抽取器打分：比对抽取结果与答案键，输出字段准确率（含读错路径与漏读路径）、错误召回率与精确率、误报数；金额、日期与文本按文档上实际印出来的样子比对，而不是按解析后的值。
  • batch 命令渲染整套测试集：PDF、答案键，外加一份带每个文件 SHA-256 的 manifest.jsonl，verify --manifest 一次给整集合打分。
  • 以 MCP server 形式提供（@claimseed/mcp，stdio）：渲染出来的文档以页面图片形式回到聊天客户端里，可以直接在 MCP Apps 视图里把注入的错误和页面并排看；也提供带 Chromium 的容器镜像，docker run --network none 断网运行。

值得关注的原因

  • 它精确命中了我当前最想做但没有方法的一步：给"化验报告 OCR → AI → App 导入"这条链路做一套可复现的评测集。 我一直缺的不是解析器，是"我怎么证明这次抽取比上次准"。claimseed 的做法是现成的答案：生成带已知答案的样张 + 一个把抽取结果与答案键逐字段比对的评分命令 + 记录每份文件 SHA-256 的 manifest。这三件套加上，我就能对 4P 平台的抽取管线做回归测试——改了 OCR 模型或提示词之后，跑一遍就知道有没有变差。
  • "误报数"这个指标是我以前没想到要单独盯的。 我关心的是"漏掉了异常指标"，但如果抽取器把正常指标也报成异常，医生看到一堆假警报就再也不信这个系统了。漏报伤专业性，误报伤信任度，两个都要单列——这与我做 4P 干预报告"24 个风险维度、6 个风险级别"时的直觉是一致的，但现在有了更精确的度量方式。
  • "按文档上实际印出来的样子比对，而不是按解析后的值"，是一条容易被忽略但极关键的评测口径。 化验单上的日期格式、单位、区间符号、参考范围写法千奇百怪，用归一化后的值比对会掩盖真实的抽取错误。这条对我写评测用例是直接可用的原则。
  • "水印用图形绘制，所以不污染文字抽取层"这个细节，是对抗"评测集本身教出了错误行为"的漂亮解法。 合成数据最大的风险是它长得不像真数据，导致模型在真数据上失手。用图形水印而不是文字水印，保证了抽取器看到的文本层和真实文档一样干净，同时真文档上又确实有这个标记。这个"既要真实又要可识别"的平衡，比单纯加个 SYNTHETIC 字样讲究得多。
  • Apache-2.0 许可，可商用。★0、四个场景、17 个场景变体，规模不大，但它示范的是方法而不是产品——这个方法我可以整套搬到我自己的化验报告评测集上。

三、今日趋势观察

今天最值得记的信号，是"技能生态"这一层正在从"写一堆提示词"往"可校验、可治理、可部署"的方向硬化——而这个转向在三份完全不同的代码里同时发生。

第一，技能开始有了自己的 lint 与打包约定。Forge 的 forge skills validate 专门捕捉"只在运行时才暴露的静默工具注册失败"，并给出 default-deny 的工具治理指引；dsh 插件把 27 个技能装进侧边栏并给出六步初始化流程；claimseed 则用一份 ground-truth 答案键去校验抽取器输出。三件事指向同一个判断：一份技能的质量，正越来越由"它被机器检查过多少"决定，而不是由"它被读过多少遍"决定。 对我做专家包质检清单来说，这直接意味着清单要分成两栏——人读的语义标准，和机器跑的校验项。

第二，"缺失"与"零"必须被当成两回事。dsh 插件今天修的几个缺陷（评论总数缺失被当成已知、列表截断补回时快照归属核对不足、总数缺失时拿已取条数冒充总数），本质都是同一个错误：系统在数据不完整时给出了确定性的答案。这跟 10-31 我记的 OpenAdapt"agent 对 30 次坏保存全部宣称成功"是同一条线索的两端——一个在写入端谎报成功，一个在读取端把缺失当零。对一个要把"24 个风险维度、6 个风险级别"写进干预报告的系统来说，"我这份报告的某一项数据没取到"必须能原样传下去，而不是变成 0 或者一个看起来正常的值。

第三，健康类 AI 正在从"记数据"转向"管冲突 + 出可冻结的结论"。vitals 的 116 条带证据等级的冲突规则（并让基因信息参与判定）、GLP-1 平台期检测、以及那份"冻结快照 + 可撤销 + 不进备份 + 自包含离线 HTML"的医生报告，共同指向一件事：单用户健康 AI 的价值不在图表，而在于它敢不敢给出一个带时间戳、不可篡改、可以被医生审阅的结论。 对 4P 补剂平台的干预报告，这是同一条工程要求。

第四，合规边界正在被写进代码，而不只是写进文档。datalife-clinical-agents 这个研究脚手架，README 里专门列了一节"明确不做的事"：不做自主诊断、不做风险分级、不开处方、不摄入姓名与身份证号、不开无限网页浏览与 shell、不在临床系统里静默行动；claimseed 强制给每一页盖上合成标记且没有开关能关掉；haola-checkup-mcp 把凭据绑定到官方 origin、只跟随同源跳转。"显式列出非目标"正在成为 AI 项目的基本素养——对做健康内容的人尤其重要，因为合规负担不是靠声明免除的，是靠架构约束掉的。

第五，许可证在选型阶段就该分清，而且这一期的分化格外明显。本期新增的仓库里，MIT（dsh 插件、forge、claimseed、haola）、Apache-2.0（forge、claimseed、paxovela、gateway）适合当底座；AGPL-3.0（orbi、papez、marotte、flotta、cupful）只能读不能抄；PolyForm Noncommercial（vitals）连"个人用"和"能卖"之间那道墙都插在中间。一个每周只有 8 小时的一人公司，最贵的错误就是在动手前没看这一行、等到产品要上线才发现底座不能商用。
