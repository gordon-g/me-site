1. Google Gemini 团队把整套深度研究方法压进 16 行文本文件：盲测里裁判偏好它的输出超过 90%

地址：https://github.com/google-gemini/demolab ｜ ★1,096 ｜ Apache-2.0 ｜ Gemini 团队的实验性技能库，用纯文本技能文件规定智能体做深度研究时的范围、委派、核验与兜底边界

事件内容

  • 11 月 27 日 Google AI Studio 的 Philipp Schmid 宣布，Gemini 团队在 google-gemini/demolab 仓库公开了一份实验性 deep-research 技能，仓库当日有 2 次提交（feat: add deep-research skill 与对应的合并提交）。
  • 这个技能文件只有 16 行。 它不是模型、不是插件二进制，而是一份纯文本指令文件，智能体只在任务与其描述匹配时才加载它——目的是不把专门指导塞进每一个无关提示里。仓库 README 列出两个技能：deep-research 与 gemini-frontend-design。
  • 它真正起作用的地方是五个控制点：Scope（简单问题一次答完，宽问题拆成 3 到 5 个角度）→ Delegate（并行开搜索或浏览子智能体，每个封顶 8–12 步）→ Verify（必须用原始文件、论文、报告与 PDF，搜索结果摘要永远不能当作可引用来源）→ Recover（取消卡住的子智能体，最多允许一轮追问）→ Report（两句话总结加内联链接，来源冲突要标出来）。
  • README 给了自己一组对比数字：deep-research 技能「在用 Gemini 4 模型的数百次盲测中，裁判偏好带该技能的输出超过 90% 的时间」；gemini-frontend-design 则是「用户偏好带该技能的前端设计 67% 的时间，对比热门第三方前端设计技能时为 75%」。
  • 它的分发方式比内容本身更值得注意：README 一次性写清六条安装路径，覆盖 Vercel skills CLI、Context7 skills CLI、Antigravity、Claude Code、Cursor 与 OpenAI Codex。仓库同时带 .agents/plugins、.claude-plugin、.codex-plugin、.cursor-plugin 四套插件目录。许可证是 Apache-2.0，README 明确声明「不是 Google 官方支持的产品」。

值得关注的原因

  • 这是今天最直接命中我工作方式的一条。 我做的是「一人公司 + 每周 8 小时 + 约 1 个月现金跑道」，所有产出都要靠 AI 工具放大。但我一直在犯一个错：把研究方法写进提示词，等于每句话都在为此付 token；写进技能文件，则只在真正需要时才加载。 demolab 的 README 第一句话就把这件事说透了——「不给每个提示词都塞满」。我可以把这套「按需加载专门工艺」的做法，直接搬到我的专家包与技能包设计上：一个技能文件 = 一个明确的任务类型 + 一份边界说明。
  • 「16 行」这个数字对我有强烈的警示意义。 我做技能包的老毛病是写得很全——一份 SKILL.md 塞进几十条规则、十几个注意事项。结果是指令越长，智能体执行得越像在读说明书。 demolab 证明了一件事：约束不需要长，需要的是「在什么情况下该做什么、在什么情况下该停」。 它那个「每个子智能体封顶 8–12 步」和「最多允许一轮追问」，比我写十条「请注意……」有用得多。这直接可以抄进我的技能验收标准：写不出一页纸的技能，多半是没想清楚。
  • 「搜索结果摘要永远不能当作可引用来源」这一条，正是我公众号内容生产里最该硬编码的一条。 我一直要求自己「只引用能追溯到原文的一手结论」，但这条规则更多靠的是我自己的自觉。demolab 把它变成了智能体执行流程里的一道关卡——Verify 是四个控制点之一，不是备注。 这个位置差异很重要：当约束写成了流程步骤而不是注意事项，被遵守的概率完全不同。
  • 「最多允许一轮追问」这条限制，我准备原样抄进我的内容生产纪律。 我做深度选题时最常见的失败不是搜得不够，而是无限追问：一个问题引出三个问题，三个问题引出九个，最后两周过去一个可发布的结论都没有。一轮追问封顶，等于强迫自己在信息收敛的那一刻就动手写。
  • 「来源冲突要标出来」也是我一直在找但没找到的表述。 我给公众号写的循证内容，经常遇到文献之间结论不一致——多数工具的处理方式是二选一，挑一个看起来对的写。demolab 的做法是「把冲突标出来」：这既是诚实，也把判断的责任还给了读者。 对健康内容来说尤其重要，因为两个来源冲突的时候，正确答案往往是「现有证据不一致」，而不是硬选一边。
  • 诚实地说，它有两个我要提醒自己的地方。 其一，「90%」是团队自测的盲评数字，不是独立复现，我不该把它当成「用了就提升 90%」来引用；其二，它的定位是实验性的、明确声明非 Google 官方支持产品。所以我的结论是：我把它当一份「写法范本」来抄，不把它当一个「效果承诺」来相信。

2. 本地深度研究智能体把「引用审计」做成流水线最后一道工序——它的范例报告里就有一份 GLP-1 司美格鲁肽心血管试验

地址：https://github.com/jolovicdev/shandu ｜ ★16 ｜ MIT ｜ 跑在本地终端与浏览器的深度研究智能体：拆题、并行检索、逐句核对引用，产出按证据量决定长度的报告

事件内容

  • 11 月 27 日发 v4.0.0，当日 12 次提交，主线是 Gradio 图形界面重做（Redesign the Gradio web GUI with live activity, run options, and linked reports）与发布打包收紧。
  • 它把研究流程拆成六个显式阶段，每一阶段背后都有确定性的 Python 检查（完整流程图见仓库 ARCH.md）：研究简报（把问题拆成 3 到 8 个具体子问题并选定交付形态）→ 并行研究（子智能体跨网页检索与 arXiv、OpenAlex、PubMed 交叉查证，整页与整份 PDF 读完，而不是读搜索摘要）→ 引文与可信度检查（每个页面按同行评审／官方／新闻／厂商／博客分类打分，主张必须带原文逐字引用，任何页面上找不到的引用在代码里被丢弃）→ 覆盖度驱动循环（按「多少个独立可信站点支持这个子问题」打分，覆盖足够、迭代无新增或预算耗尽即停）→ 动态报告（长度随问题与证据量走，每个引用来源低于 300 字，全文下限 400 字）→ 写后引用审计（审计员逐句、逐要点、逐表格行核对每个 [n] 标记背后的实际证据，剥掉来源不支持的引用）。
  • README 里直接给了三份范例报告的引用审计计数，这组数字比任何形容词都有说服力：推测解码报告 36 个来源，112 条 supported、19 条 partial、1 条 removed；HTTP/3 对比报告 25 个来源，101 / 20 / 0；SELECT 与 SOUL 司美格鲁肽心血管试验报告 12 个来源，78 / 6 / 0。成本分别标为 1.22 / 0.55 / 0.41 美元，默认模型是 deepseek/deepseek-flash，也可换成任意 LiteLLM 支持的模型。
  • 界面是一套完整产品：终端 UI 显示当前迭代、阶段追踪、活跃子智能体、已读页面数与模型调用数；网页 GUI 支持覆盖深度、研究者模式、报告长度、美元上限、站点白名单黑名单、发表起始日期与是否开启引用审计；还能 --share --auth user:pass 生成带密码的临时公开链接。

值得关注的原因

  • 这一条几乎是为我量身定做的，因为它的范例报告里就有我正在做的 GLP-1 项目。 我在做的 GLP-1 营养伴侣 V2 要处理司美格鲁肽的用药、停药与化验指标趋势，shandu 恰好把「SELECT 与 SOUL 司美格鲁肽心血管试验」做成了一份带完整引用审计的范例报告，12 个来源、78 条 supported、6 条 partial、0 条 removed。 我可以直接拿它对照自己的写法：它的 partial 是怎么标的、removed 那一类长什么样——这些是我目前只能凭感觉处理的东西。
  • 「主张必须带原文逐字引用，任何页面上找不到的引用在代码里被丢弃」——这一条把「零 AI 幻觉」从态度变成了代码路径。 我在公众号和课程里一直讲循证，但我的做法本质是「写完之后自己再核一遍」，这是人肉执行、且不稳定。shandu 的做法是让代码去丢弃找不到的引用：这不是「提示模型别编」，而是「编了就拦下来」。 我做 GLP-1 营养伴侣的参考文献模块时，这正是我想要的机制——校验应该是一个独立于生成的环节，而不是同一环节里的一句叮嘱。
  • 「partial」这个第三档，是我在这期里看到的最有价值的一个设计。 我做内容时的习惯是二分法：这条有引用 / 这条没引用。shandu 是三档——supported（来源完全支持）、partial（来源只支持一部分）、removed（完全不支持，剥掉）。 现实里绝大多数结论都落在 partial：论文说的是一个亚组，我的标题写的是全部人群。「partial 也要标出来」这个纪律，能治我内容里最常见的一类硬伤——把有限证据说成普遍结论。
  • 「报告长度随证据量走，每个引用来源低于 300 字」这个约束，对我「每周 8 小时」的时间预算来说是刚需。 shandu 明确写「一个狭窄的事实性问题就该保持简短，而不是被填满空章节；一个密集的技术或临床综述才扩展成对比表格与注意事项」。我上一期就记过「无限追问」是内容生产的头号杀手，这里它给的是同一件事的另一面：不要为了显得完整而注水。
  • 「美元上限」和「站点白名单黑名单」这两个开关，也是我该抄的。 我一个「一人公司」跑 AI 的真实成本必须可预期、且能设硬顶。shandu 把成本上限做成了单次运行的运行参数，而不是让我事后看账单。 这正好对上我记过的另一条：per-pass 的限额不是会话级的花费上限——预算必须是会话级、运行级的硬约束。
  • 诚实地说，它只有 16 星，是个小项目。 但它的价值不在规模，在于它把「引用审计」这个概念从「提示词里的一句叮嘱」做成了「流水线里的第六道工序 + 一份带计数的公开报告」。 我会拿它当方法论参照，不会当依赖库。

3. 写下「7 毫米的不对称病灶」这种话，99% 的隐私规则都拦不住——有人用 1024 个权重把这件事解决了

地址：https://github.com/YauhenBichel/privacy-gate-llm ｜ ★2 ｜ Apache-2.0 ｜ 提示词 PHI/PII 检测闸门：在文本离开本机送往云端模型之前，判断「这段话该不该留在这里」

事件内容

  • 本期 4 次提交，主线是压力测试后的加固：fix(guard): stress-test findings: linear time, NaN fails closed, split and hidden values，同时发布 v1.1.0。
  • 它解决的问题写得很具体：正则规则擅长识别带标记形状的东西（sk-ant-…、AKIA…、patient_id: 40219、base64 图片），但对用日常英语写成的同一类信息完全失明。 README 举了一句例子——「The woman from Tuesday's clinic, 34, has a 7mm asymmetric lesion on her left shoulder and a biopsy booked for the 20th.」——这句话能通过今天规则集里的每一条隐私规则。
  • 差距被量化了：在 206 条样本的黄金集上，纯正则规则的集捕获率只有 9.0%（111 条敏感样本里只拦住 10 条），误拦率 1.1%——也就是说 101 条敏感样本直接放行。
  • 它的解法不是微调对话模型，而是一个双向编码器加线性头：BAAI/bge-m3 把文本变成 1024 个数字，一个 1024 权重的线性头再转成一个分数，对比阈值 0.1209。README 明确说只有头被训练，编码器按原样使用——这正是它能在 CPU 上跑、每次调用只要几十毫秒的原因，代价是换嵌入模型就会失效（头的权重数恰好等于 bge-m3 的维度数）。
  • README 给了一组四行对比表，这是本期最有说服力的一组数字：纯正则规则（AUC 无、捕获 9.0%、误拦 1.1%）→ hashed 词 unigram（AUC 0.7818、捕获 98%、误拦 83.2%）→ Qwen3.5-0.8B 提示式（AUC 0.4609，等于随机猜测）→ bge-m3 + 逻辑回归头 v1（AUC 0.9927、捕获 99.1%、误拦 5.3%）。五折交叉验证，每个分数都来自没见过该样本的头。在训练之后新写的 20 条句子上，11 条敏感全部抓住、9 条无害留住 1 条。延迟是 p50 34–43 ms、p95 不到 50 ms（在一台负载较高的共享机器上实测），批处理时每条 18 ms。
  • 项目明确声明 「不是医疗器械」——它只决定文本该不该离开机器，不对任何病灶下判断。原名 molecare-privacy-gate（1.0.0 / 1.0.1），改名后旧包不再更新。

值得关注的原因

  • 这是我今天读到的最扎心的一条，因为那个「7 毫米不对称病灶」的例子，写的正是一个正在做临床咨询的人。 如果我把这样的对话发给云端大模型，传统的脱敏清单一个都拦不住。 我做 4P 精准营养与功能医学相关的内容与咨询，客户的情况描述天然就是「用日常英语写成的健康信息」——没有 patient_id，没有证件号，就是「34 岁、7 毫米不对称病灶、20 号预约活检」。
  • 「Qwen3.5-0.8B 提示式的 AUC 是 0.4609，等于随机猜测」这一行，是我今天最想抄进自己笔记的一张表。 我一直默认「用小模型做敏感信息判断，加一句提示词就行」。它给出的证据是：提示一个小模型去推理出那个词，0.8B 做不到；而嵌入模型做一次前向、线性头做判定就可以。 这跟我在 11-27 期记的「self-assessed / observed / grounded 三向量对齐确定性检查」是同一个方向——把判断交给确定性机制，不要交给另一个模型的主观输出。
  • 「1024 个权重 + 一个偏置，34–43 毫秒」这个工程事实，决定了我能不能真的用它。 我一个每周 8 小时、现金跑道约 1 个月的一人公司，不可能为了一次调用去部署一套重型服务。 一个能跑在我本机 Ollama 上的 bge-m3、毫秒级、不需要 GPU 的检查器，这才是我能在真实工作流里长期用下去的东西。
  • 它的架构位置也抄了：它是第二道闸门，排在正则规则之后，而且「只会加 hold，永远不会放行」。 这意味着它不替代我现有的脱敏规则，只做它们的补充。这个设计比「换个更聪明的检测器」要稳得多——任何一次误拦都比一次漏放更可接受，因为它只是让人工确认一下，不会改变数据流向。
  • README 里那句自我限定我特别想记下来：「Not a medical device. This is a privacy tool. It decides whether text should leave a machine and says nothing about what a lesion is.」一个工具主动划清自己「不做什么」的边界，这在我看过的项目里不多见。 我做内容时最看重的就是这个——说清楚边界，比宣称能力更可信。
  • 诚实地说，它只有 2 星，是本周刚起步的新项目，且 README 明确说明「头是在 Ollama 的输出上拟合的，换另两个后端是否给出相同判决是实测出来的，不是假定的」。 所以我的结论是：架构思路和数字都值得我照做，但我不会在真实客户数据上直接依赖它——我会先用它自己的黄金集跑一遍我的中文语料，看漏放率，再决定是否上生产。

4. 营养管理开始有了「确定性规则引擎」这一层：NutriVision 把糖尿病、PCOS、高血压、CKD 与孕期各自写成可解释的规则，而不是交给模型自由发挥

地址：https://github.com/drmedhealth/nutrivision ｜ ★0 ｜ MIT ｜ 拍照即得按病情定制的营养评分的开源本地优先应用：自带密钥、无后端、无账号，支持 2 型糖尿病 / PCOS / 高血压 / 慢性肾病 / 高胆固醇 / 孕期六类状况的确定性评分与替换建议

事件内容

  • 今日 29 次提交并发 1 个版本，是 ③ 线本期动作量最大的仓库。它的核心不是「让 AI 看图说营养」，而是把评分拆成两层：图像识别出食物与克数是一层，打分是另一层，由确定性规则引擎完成。
  • 规则引擎覆盖的具体项目都写明了对应病症：糖尿病与 PCOS 看血糖负荷（glycemic load），高血压看钠，CKD 看钾、磷与蛋白质，高胆固醇看饱和脂肪，孕期给食安警告，再加过敏原与饮食风格冲突（素食、生酮、清真等）。每条结果都给出理由与具体的替换建议，不是只丢一个分数。
  • 它对「零」的处理暴露了设计者的用心：零卡食物（水、黑咖啡）标为 n/a 而不是误导性的 0 分；用户手动把某项改成 0 克的东西，不计入、不评分、不保存。这两个细节正好是我在自己引擎里最容易做错的地方。
  • 完全本地优先：图片在你的设备上解码、缩放、JPEG 压缩，并剥掉 EXIF/GPS 数据后才发出去；食物数据存在 IndexedDB；密钥存在 Keystore（AES-GCM + IndexedDB 设备密钥）；没有后端、没有账号、没有追踪。
  • 模型侧支持 Ollama：ollama pull llama3.2-vision，用 OLLAMA_ORIGINS 放行来源即可本地跑。这是我本地 Ollama 那套环境能直接用的形态。
  • README 里的边界写得很克制：「只给估算，不是医疗或饮食建议」，并点名 CKD、孕期、糖尿病用药与进食障碍史这四种情况必须咨询注册营养师或临床医生；功能说明写明没有 FDA 认证，不诊断、不治疗、不替代专业照护。

值得关注的原因

  • 这是今天 ③ 线里唯一把「AI 识别」与「规则判定」显式分开成两个层次的项目，而这正是我自己的营养引擎最该抄的结构。 我这一两年一直在处理同一个难题：模型给的结果一旦直接进方案，就没有第二道关。 它把「模型看图」限制在它擅长的那一层（这是什么、大概多少克），把「该不该吃、吃了对你有什么影响」交给可审计的规则。这个分层的逻辑可以直接搬进我的 GLP-1 营养伴侣与 4P 精准营养平台。
  • 「按病症分别写规则」这个做法，对我的精准营养业务是直接可用的。 它的六类状况里有四类（糖尿病、PCOS、高血压、CKD）正好落在我这半年反复处理的那几类人群上，而每一类的判断依据都是该病症真正关心的指标——CKD 看钾磷而不只是看总热量，这个分法比我之前的笼统打分精细得多。我的引擎下一步就该把「按病症分档」做成结构，而不是给所有人一套通用规则。
  • 「结果必须带理由与替换建议」这一条，正是我公众号内容最缺的那一档。 我写营养干预内容时最怕的是「建议吃这个」，但读者真正需要的是「为什么，以及换成什么」。规则引擎天然产出的是理由和替换项，而不是结论——这和我这半年反复强调的「附参考文献、附证据等级」是同一个方向，只是它在产品层做，我在内容层做。
  • 那两处关于「零」的处理，我会直接抄。 零卡食物标 n/a 而不是 0——在营养表格里，「没有」和「是零」是两个完全不同的意思，我在自己的模板里一直靠人眼分辨，这次可以固化成规则。手动改成 0 克的东西不计入不评分不保存——这一条堵住了「把不想吃的项删掉来抬高分数」这个漏洞，我的引擎同样面临这个问题。
  • 它的隐私设计对我这种要处理客户体检数据的人有直接参考价值：EXIF/GPS 剥掉后再发送。 我做「百十工程」和 4P 精准营养千人先锋项目时，会经手客户上传的体检单照片，那些照片的 EXIF 里可能带着地理位置甚至设备信息。这条我之前完全没有在流程里写明，是真实的漏洞。
  • 诚实地说，它今天 0 星、刚起步，且它自己的免责声明写得比功能还长。 我不会因为架构漂亮就当它是成熟产品。但它把「规则层与模型层分开」这件事做成了可运行的代码，这比任何架构图都更值得我借。

5. 临床科研这条线上今天最扎实的一个动作：把论文 PDF 里的化学结构式变成「校验过、可直接入库」的数据

地址：https://github.com/Kohulan/MARCUS ｜ ★31 ｜ MIT ｜ 把化学论文 PDF 里的结构式转成经过校验的化学结构，产出可直接写入 COCONUT 天然产物数据库的数据

事件内容

  • 本期 23 次提交，是 ② 线里窗口内动作最密集的项目之一。提交主线不是加功能，而是修可靠性：fix(coconut): Send waits for a DOI; a 403 login says to verify the COCONUT email（等待 DOI 的行为要正确处理，403 登录态要提示去核实 COCONUT 邮箱）、fix(coconut): the form fills its organism, parts and place when the annotation ends after it opened（表单在标注之后才打开时的填写时序）。
  • 它的处理链路是完整的一栈：结构识别用 DECIMER、MolScribe、MolParser 三个模型，加上文字标注、R-group（Markush）表格处理、以及人工校对环节，最终产出直接落进 COCONUT 天然产物数据库。
  • 值得单独指出的是它把 COCONUT 的接口边界当成一等公民来处理：DOI 要等、403 要认、缺邮箱要去核实、标注与表单的先后顺序要对。这些全是「往一个真实存在的外部数据库写数据」时才会冒出来的边界情况。
  • 许可证是 MIT，仓库带 llama-cpp、docling、ketcher 等依赖，主题标签覆盖化学结构识别、化学信息学、COCONUT、数据校对、Markush。

值得关注的原因

  • MARCUS 让我看到一条和我完全不同的「证据生产线」长什么样——但底层逻辑和我做内容是同一件事。 它把论文里的原始素材，经过「识别 → 标注 → 校验 → 入库」变成可以被下游直接使用的可信数据。我做的事在结构上是同一个：把研究文献变成带出处的、别人能直接用的结论。 差别只在载体是结构式还是文字。
  • 「把 COCONUT 的接口边界当成一等公民」这一点，是我现在最该学的工程习惯。 我做循证内容时，引用核验这一环经常是「我手工打开原文看一眼」——没有系统性地处理「链接要等、403 要认、原文改了要认」这类现实情况。MARCUS 用了 23 次提交专门修这些。 这提醒我：任何自动化核验流程，都必须把上游接口的失败模式当成正式需求，而不是异常情况。
  • 「结构识别用三个模型 + 人工校对」这个组合，也回答了我一个悬着的问题。 我一直纠结：完全靠模型识别，还是完全靠人。MARCUS 的答案是「模型先跑，人工兜底」——这与我做内容时「AI 起草 + 我逐条核引用」的结构完全一致。它给了这个结构一个具体到模型名的实现范式。
  • 它还顺手解决了一个我一直没解决的现实问题：R-group（Markush 结构）。 天然产物数据库里大量条目是「一族化合物」而不是单一分子，用普通 SMILES 表达不了。我读营养与功能医学的综述时偶尔会碰到「某类多酚」这种表述，一直没找到好的结构化方式。 MARCUS 专门处理了这一类，这对我做成分层面的内容是实打实的工具。
  • 诚实地说，它只有 31 星，是一个具体到「给 COCONUT 灌数据」的项目，离我的业务很远。 我看它的方式是「看别人怎么把一件看似简单的自动化做到能写进真实数据库」——这对我做内容工厂、对我把 GRPM 营养基因组学的报告做成可复用数据，是同一类工程参照。

三、今日趋势观察

  • ① 线今天的主线是「把智能体的可信度做成有状态机的东西」。 signet 把技能版本做成 draft → validated → published → certified（外加 rejected / deprecated / revoked / archived）八态生命周期，每一次发布都要过 W3C SHACL 图形状校验 + 本体校验 + LLM 语义分析 + 人工复核四层，签名用 RFC 8785 JCS 与 RDFC-1.0 双向规范化后附分离签名。这正好对着我上期记的 dokimi 那条「指令存在 ≠ 指令被加载」——signet 解决的是下一层：「指令加载了，但它可信吗、还是最新版吗」。 我用 WorkBuddy expert-manager 建专家包时，从来没有「版本 / 有效期 / 撤回」这回事。
  • ② 线今天的主角仍然是「校验」，但校验的对象变了。 上一期是校验文献与结构式（linkml / MARCUS / GroundCheck），今天多了一层校验「机器能不能看」：privacy-gate-llm 拿 1024 个权重去判断一段文本该不该离开本机，med_fabric 明确写「提交即失败、不可回滚」，agentic-orchestration 干脆让 AI 只产出规格、由普通代码去校验执行、人来批准。三件事指向同一个判断：AI 的产出必须经过一层不是 AI 的检查。 这正是我给自己定的「零 AI 幻觉」应该长成的样子。
  • ③ 线今天出现了一个真正的结构变化：从「记录工具」转向「规则引擎」。 今天这一组里，NutriVision 把糖尿病、PCOS、高血压、CKD、孕期各自写成可解释的确定性规则并给出替换建议；nutrivision 的两处「零」处理（零卡标 n/a 而不是 0、手动改 0 克不计入不保存）暴露的是一个更根本的问题——营养评分的价值不在模型看得准不准，而在规则判得对不对。对我这一条线尤其重要：我一直在做「用模型估营养」，今天第一次看到一个把模型与规则显式分层的可运行实现。
  • ④ 线值得单独记的是「节流」这层开始独立成产品。 token-goat 做提示与成本优化，nexus-llm-router 做可替换的 LLM 路由，Xolotl 把 552B 模型跑成本地编码智能体，mnemo-cortex 用 SQLite FTS5 加语义做跨智能体记忆。对一个每周 8 小时、现金跑道约 1 个月的一人公司，「省 token」和「本地跑」不是锦上添花，是能不能活到下个月的变量。
  • 还有一个横向信号：本期 87 个仓库在窗口内累计 1,270 次提交，25 个发了正式 release。 「发了版本号」正在重新成为开源项目表达「这件事现在能用」的主要方式——这对本站内容也一样：一篇日报说「这个项目很活跃」不如说「今天发了 v4.0.0」。
