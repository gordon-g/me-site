3. craft-b/formula-forge：临床营养配方 agent 划出了一条硬边界——模型只许提结构，营养数字一律由确定性层重算

地址：https://github.com/craft-b/formula-forge ｜ ★0 ｜ MIT ｜ Python / FastAPI + LangGraph + Groq，面向临床与机构营养场景的食品配方设计系统（肾病人群、糖尿病、高蛋白、低脂、纯素）

事件内容

这是一个只有 0 星的新项目，但它把"AI 生成营养方案"这件事的工程边界划得比大多数商业产品都清楚。

  • 信任边界是单一函数：_resolve_formula() 是生成结果进入界面的唯一路径，系统只接收每个配方行的三个字段（ref、percentage、notes），模型输出的其他营养字段直接丢弃；CandidateFormula 类型本身就不含营养字段，也不含 overrun_pct。
  • 解析失败硬拒绝：食材引用解析不到受治理食材库就硬拒绝，绝不猜测替换成相近食材；配方总百分比偏离 100% 不超过 40 个百分点时做有界比例修复，超过即拒绝。
  • 一次受限修复：首次生成违规后最多重新生成一次，修复提示里写明每个违规项的实测值与限值；仍违规就明确标记为不合规返回，不伪装成已验证配方。_resolve_formula() 是直线代码没有循环，结构上不存在第三次生成。
  • 指标是硬数字：受治理食材库 34 种、数据集版本 2026.10.0（USDA FDC Foundation Foods）、后端与领域测试 420 项、golden compliance set 18 个用例、schema 有效率 100%、合规准确率 100%、路由评估 46 个已标注 brief、意图路由正确率 100%、规则集激活正确率 100%。
  • 10-28 当天三条提交在收拾"多嘴"问题：Stop the UI narrating a pipeline it cannot see, and the proxy failing silently（让界面停止叙述它看不见的流程，并修掉代理静默失败）、Merge b3-verified: close B3, and stop three surfaces asserting what they cannot see（关闭 B3，并让三个界面不再断言它们看不到的东西）、Explain the wait on the Idea Stream, where a first visitor actually lands。

值得关注的原因

  • "模型只提结构、数字由确定性层算"这句话，就是我一直在说的"强制循证 + 零 AI 幻觉"的工程版本。 我在 GLP-1 营养伴侣 V2 里靠"食材模板 + 规则引擎 + 禁用补剂清单"来实现，它靠"受治理食材库 + 领域层纯 Python 计算 + 声明式 JSON 规则集 + 一次性受限修复"。两条路殊途同归，而且它的可验证性做得更硬——合规准确率 100% 这种数字，是能直接写进我方报告的说服力资产。
  • "最多一次修复"这个上限设计，比"循环直到通过"高明得多。 我在做补剂配方冲突时的逻辑一直是"给一次带具体违规反馈的重来机会"，但我从来没把它写成硬约束。它用代码结构（直线函数、无循环）保证"不存在第三次生成"——把产品原则写进类型定义和函数形状，而不是写进文档里靠人记，这是我可以整体搬过去的一招。
  • 它最戳我的是最后那条提交：让界面停止叙述它看不见的流程。 这正是我反复警惕的"AI 说得好听但其实啥也没跑"。它把"界面不许宣称自己没验证过的东西"当成 bug 级别的问题来修。这条对 4P 补剂平台的干预报告是直接的：报告里任何一句"已优化""建议调整为"，背后都必须有真实的计算痕迹。
  • 它把"受限食材库 + 版本化数据集"当成核心资产，而不是附属数据。 我做 4P 精准营养的食材库时，一直把它当成"查表用的静态资源"；它把它当成需要版本号、需要定期 ETL、需要人工补充功能属性的一等公民（PAC/POD、过敏原、成本）。这个定位差别，会决定我后面数据维护的成本结构。

4. hashgraph-online/hol-guard：Agent 运行时终于有了自己的「杀毒软件」——危险工具、密钥外泄、提示注入、恶意包与 MCP 一并拦截

地址：https://github.com/hashgraph-online/hol-guard ｜ ★1,002 ｜ Apache-2.0 ｜ Rust + Python，AI Agent 运行时防护（阻断高风险工具调用、密钥访问、提示注入、恶意包、MCP 服务器、插件与 Skills）

事件内容

今天它的提交密度是全站 AI Coding 类里最高的一档，而且八条提交里有五条在做同一件事：把"谁批准的、批的是哪一层"固化成可验证的状态。

  • 10-28 当天：feat(guard): preview a redacted source export from the Workspaces tab（从工作区页预览脱敏后的来源导出）、refactor(approvals): settle an approval's scope and persistence in one resident ask（在一次驻留询问里同时确定审批的范围与持久化）、refactor(supply-chain): settle a package review from the resident's verdict（依据驻留判定结论确定一次包审查结果）、refactor(codex): walk a Codex hook source's inventory in the resident（在驻留态里遍历 Codex hook 来源的清单）、fix(runtime): watch mode keeps the known-vulnerable runtime finding over an earlier warning（watch 模式下保留"已知存在漏洞的运行时"这条发现，而不是被更早的警告覆盖）、feat(dashboard): load commands for command-line tools Guard has only seen in use、fix(command): read npm's report verbs as the reads they are（把 npm 的 report 动词按"读"来解析）、fix(command): create a branch at a start point without asking。
  • 防护面覆盖六类风险：危险工具与命令（含 shell、工作区沙箱、cd 路径、工具权限）；密钥与凭据访问（在持久化工具调用通知前遮蔽 Bearer token、API key、X-Api-Key、X-Auth-Token、--password、--api-key）；提示注入（prompt policy、approval context、提交 hook）；恶意包与供应链（manifest 依赖解析、lockfile 一致性、版本冲突、离线安装前校验 bundle 签名，拒绝签名无效/过期/回滚的 bundle）；MCP（provider catalog、工具权限、URL 安全、持久化子进程生命周期）；插件与 Skills（发布者信任绑定、命令描述符、审批规则）。
  • 核心工程原则是 fail closed：原生运行时无法完成可信决策时不会自动降级为放行；策略决策有作用域粒度（global / harness / artifact / family）；本地一次性审批使用完整性材料并原子消费，避免重复使用。
  • 多 harness 集成：Claude Code、Codex、Copilot、Grok、Oh My Pi、Pi、OMP；分发形式包括 CLI、GitHub Action、Claude Code plugin、devcontainer feature、dashboard，以及 Kubernetes（k0s / k0rdent）部署示例。

值得关注的原因

  • "fail closed"这一条是我做 AI 助手产品最该抄的默认值。 我在 4pwellness 的 MCP 连接器和营养 AI 助手上，默认应该是"检测不到风险就按通过处理"吗？不是。默认应该是"无法确认就阻断并提示人工"——这个默认值决定了我的产品在上线后的第一周会不会被用户投诉。
  • "审批的作用范围"这个概念，正是我在 4P 精准营养千人先锋项目里最缺的一块。 我一直担心的是"授权一次就被无限复用"。它把作用域拆成 global / harness / artifact / family 四层，再用完整性材料 + 原子消费实现"一次性授权只能用一次"——这正是我一直想要却没想清楚怎么表达的"授权边界"。
  • secret 遮蔽的具体字段清单可以直接复制。 我给 AI 助手接模型密钥时，token 会不会被打进日志、会不会出现在错误信息里被 agent 读走再回传给模型——这是真实风险。他们把这些字段名逐一列出来，我照抄即可。
  • 它同时说明了另一件事：agent 安全正在从"扫描仓库"转向"运行时拦截"。 NVIDIA 的 SkillSpector 扫的是安装前的技能包，hol-guard 管的是运行中的每一次工具调用。两道闸门不冲突，而且是标配。 我在做"考证钩子 + 营养 AI 内核"的一人公司产品时，这两样都不该省。

5. JuneYaooo/open-medical：给医生用的开源桌面 Agent——把"证据从哪来"做成三级分层，把"AI 改档案"做成待确认提案

地址：https://github.com/JuneYaooo/open-medical ｜ ★11 ｜ MIT ｜ TypeScript / Electron + Node.js + SQLite，面向医生的开源桌面 Agent（macOS / Windows）

事件内容

这是今天医学线里设计最完整的一个，它对"循证"和"人机分工"的处理方式值得逐条看。

  • 证据三级分层：治疗审查按 knowledge → literature → web evidence tiers 组织；知识库命中后可查看原文行号；资料保留作者或机构、年份、来源链接与版本；知识图谱、思维导图与流程图节点均可回溯原文；提取不到依据时不会自动补齐关系。文献检索支持 PubMed 与 Europe PMC，循证任务可准备 PICO 与检索式。
  • AI 改档案走提案制："AI 对档案的更新以待确认提案呈现，医生核对后才写入"；同日冲突的数据保留供核对，不把不同单位的数值混成同一条趋势；检验结果导入保留项目、日期、数值、单位与出处。
  • 14 个临床任务模板覆盖收治病例全流程、整理病历、摘录检验、核对用药资料、生成病历草稿、用药安全核查、患教大白话、检验报告解读、出院小结草稿、值班交班记录、诊疗决策流程图（Mermaid，保留节点出处）、不良反应筛查（辅助准备 Naranjo 评估）、个案报告写作（CARE 框架）、准备循证检索。其中用药安全核查依赖有限的内置规则，检验报告解读依据报告单打印的参考范围。
  • 随访走微信：支持企业微信或个人微信渠道，流程是"AI 起草 → 医生确认发送 → 回复按条目整理 → 确认归档"；知识库机器人只引用明确允许对外使用的资料。
  • 10-28 当天：Improve clinical evidence review and overview recovery（改进临床证据复核与概览恢复）；10-27 一天六条：Document evidence-based clinical interface development rules、Improve clinical overview hierarchy and reading contrast、Complete lab, source export and verifiable backup recovery workflows、Improve case context, follow-up linkage and source reading、Clarify task context, model connection status and patient intake、chore: release desktop 1.0.30。
  • 本地优先但坦白边界：患者与消息数据存本机 SQLite（~/.open-medical-workbench/medical.sqlite，数据库本身未加密），模型密钥走本地凭据保险库加密；明确承认"本地优先"不等于用云模型时材料不会离开本机；同时明确列出不支持项——多人权限体系、机构级审计、HIS/EMR/FHIR 对接、机构部署验收。

值得关注的原因

  • "AI 对档案的更新以待确认提案呈现，医生核对后才写入"这一句，是我全部健康内容生产原则的产品版。 我做 4P 补剂平台的干预报告时，一直坚持"用户确认后才落库"，但从来没用过"提案"这个载体——提案天然带 diff、带撤回、带审计痕迹，这是把"强制循证"从口号变成数据结构的正确方式。
  • 它把"证据从哪来"分成三级并要求可回溯到原文行号，这正好补上我 GRPM 系统一直缺的外部标尺。 我在评估自家生成的营养建议质量时，最大的痛点就是"我拿什么当标准答案"。当一个系统能把每条结论指回原文行号，我就可以拿它的结构去做我的回归测试基准——这比我自己写一套 rubric 靠谱得多。
  • 它的自我边界披露方式值得学。 明确写"数据库本身未加密""本地优先不等于数据不出本机""DRG 是演示规则不能用于实际医保结算""AI 临床有效性尚未验证不能替代医生判断"。这不是示弱，是把合规风险提前声明——对一个要面对真实用户健康数据的产品，这种坦白比多几个功能更能建立信任。
  • "医生确认 → 发送 → 按条目整理回复 → 归档"这条微信链路，和我 4pwellness 微信群客服 Bot 的设想几乎一模一样。 差别只在垂直方向——它是临床随访，我做的是营养与补剂指导。这是我第一次看到一个把"真人确认后再触达用户"写进产品流程的开源实现，值得逐行读一遍它的边界处理。

三、今日趋势观察

  • 今天最值得记的一条，是腾讯云把"云开发后端"正式做成了 Agent 生态位。 CloudBase-AI-Toolkit 38 个 MCP 工具、482 个测试用例、托管远程连接器走 Streamable HTTP + OAuth 并已提交审核、Cursor Plugin 0.2.1、.codebuddy/skills / .cursor/rules / .claude-plugin / dsh-plugin 五种分发格式同步刷新——这不是一个功能更新，是一个生态位的宣告：云后端不再是 agent 去"猜"着调 API，而是主动长出 Skill 和 MCP。 同一周里 HKUDS/AutoSwarm 把 Codex、Claude Code、DeepSeek Harness、Muse、Grok、WorkBuddy 统一编排，OrchestratorInc 在 30+ 编码 agent 之间做统一调度，三件事指向同一件事——"多 harness 统一"正在从个人技巧变成标准工程动作。
  • AI 生成健康方案的信任边界，今天被两个项目从两侧夹住了。 formula-forge 从模型侧收口：只接收三个字段、营养数字由确定性层重算、解析失败硬拒绝、最多一次修复、420 项测试与合规准确率 100%；open-medical 从医生侧收口：证据三级分层、AI 更新以待确认提案呈现、提取不到依据就不补齐关系、明确列出不支持项。两个项目星数分别是 0 和 11，但它们定义的东西——"模型负责提议，规则负责判定，人负责确认"——正是我在 4P 补剂平台干预报告里已经写死却还没找到参照实现的三段式。
  • Agent 运行时安全的重心，从"扫描安装包"移到了"每一次工具调用"。 NVIDIA/SkillSpector 扫的是装之前的技能包，hol-guard 管的是运行中的危险工具、密钥外泄、提示注入、恶意包与 MCP；今天的提交里"审批的作用范围"被固化成 global / harness / artifact / family 四层、一次性审批用完整性材料原子消费、fail closed 成为默认。这跟上一期日报里"agent 系统的下一个战场是状态与权限"完全接上了——只是这一期，权限开始有了具体的层级和默认拒绝语义。
  • 健康类项目开始集体学一件事：不把"我算出来的"说成"我验证过的"。 formula-forge 让界面停止叙述它看不见的流程；open-medical 承认本地优先不等于数据不出本机、承认数据库未加密、承认 DRG 只是演示规则；itsoso 的发布提交把"照片引用的安全评审"直接当阻塞项；BrooklynD23 在文档批次里专门处理"RAG-TIMEOUT-GROUNDED 已被回答""开放项保持开放"这类措辞。四个不同团队、同一天、在四个不同的项目里，做同一件容易被忽略的事：把"没做到"写进产品里，而不是藏起来。 对健康内容而言，这种"自我限制的可见性"比任何功能都更接近专业。
  • 三个零星项目提示了"营养 AI 内核"的另一种建法：不追求大模型能力，而追求确定性资产。 formula-forge 用 34 种食材的受治理库 + 版本化 USDA FDC ETL + 声明式 JSON 规则集，做出一个合规准确率 100% 的系统；forma 用训练师 + 营养师 + 厨房 + 医疗安全复核四个角色分工而不是一个全能 agent；itsoso 用规则 Agent 专门看药物与补剂相互作用、药物基因组和训练负荷。共同的思路是：让模型去处理"人写不清规则"的部分，把"必须算准"的部分交给代码。 这对每周只有 8 小时的一人公司路径是最现实的架构——先建小而硬的确定性资产库，再让模型去填剩下的。
