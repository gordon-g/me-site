地址：https://github.com/12burb/hermes-fledge ｜ ★0 ｜ MIT ｜ Python ｜ Hermes Agent 的插件，把"技能保存/改写"的评审权从模型手里收回到一套可审计的证据评分规则

事件内容

窗口内 27 次提交（11-05 02:12Z ~ 11-06 02:12Z），主线是给 Fledge 自己的判定逻辑补边界条件，并把验证过程写成可复核的文档。

  • ⭐ 核心命题来自一个具体的用户抱怨：README 直接引用 Kilo 对 1300+ 条 r/openclaw 评论的读法——用户最不喜欢 Hermes 的一点是"自我评价永远通过"（"It always thinks it did a good job. ALWAYS."）。从一次悄悄跑歪的运行里学出来的技能，会把错误带到下一次，而下一次"自我改进"还能覆盖掉你花一晚上调好的技能。 Fledge 的立场是：在 Hermes 保存或改写技能之前，去看它据以学习的那次运行里到底发生了什么——没有模型给模型打分。
  • 打分完全基于 Hermes 通过插件钩子报告的事实，每条都有明码分值：这轮以错误结束 3 分；被打断 2 分；你的下一条消息是在纠正它（"that's wrong" / "not what I asked" / "still broken"）3 分（"try again" / "not quite" / 光一个 "No." 只算 1 分）；紧接着跑了 /undo 或 /rollback 恢复 3 分（/retry 算 2 分）；结束时仍在失败的任务工具每个 2 分（terminal 工具按程序判定——后面一条 rm tmp.txt 不算前面的 ./fetch.sh 恢复成功了）；连着失败两次以上且未恢复再加 1 分；其他工具在结束时仍失败每个 1 分（工具失败总分上限 4）；在审批提示里拒绝了动作每个 1 分（上限 2）。总分 ≥3 判为 bad（strictness 可调：宽松 4 / 标准 3 / 严格 2）。一个干净结束的 0 分是 clean，中间地带是 unclear——既不加分也不减分。
  • 三个机制构成了完整的生命周期：保存闸（Save gate）——从跑歪的运行里学出来的技能被扣在 Hermes 自己的复核队列里而不是直接上线，你看到原因再决定留还是丢；试用期（Probation）——新技能和被改写的技能先当"雏鸟"，干净的真实运行让它毕业，持续跑歪就让它落地（归档，可恢复），一次运行后你立刻做了纠正的保存当场落地；手改保护（Hand-edit protection）——你手工改过的技能不再被覆盖，agent 的自主改写或删除降级成提案，等你批准或否决。
  • 本期窗口内的提交几乎全在补判定边界：engine: an agent write Fledge failed to record is not mistaken for a hand edit（agent 写的、但 Fledge 账本没记下来的写，不能被误判成手改）；engine: a write already staged in Hermes' queue stays held if Fledge's ledger fails（账本挂了就保持扣住，绝不放行）；engine: don't resurrect a skill that was deleted before its use was judged（用途判定之前就删掉的技能不许复活）。另有 docs: VALIDATION.md with live results; fail-open exception disclosed; 138 tests 与 VALIDATION.md: install from GitHub verified / VALIDATION.md: no local username in paths——它把自己的验证结果和唯一的 fail-open 例外都写进了文档。测试规模 138 个，且不需要装 Hermes（Hermes 表面全部被 fake）。
  • 披露写得极其克制：读——钩子载荷（工具名、状态、错误文本、轮次结果、你下一条消息的前 280 个字符用来识别纠正）与技能文件夹指纹；写——自己的 SQLite 文件（技能名、指纹、裁定理由、会话/轮次 id），裁定理由只引用短摘录（匹配到的纠正短语 ≤60 字符、失败工具的错误文本 ≤80 字符）；从不做——网络调用、模型调用、读取凭据、执行 shell 命令、起后台进程、上报遥测。它只增加摩擦，从不批准任何事，且无人应答时提问是排队而不是等待。

5. lud3nb3rg/DataNyx：让 AI agent 处理你的数据，但永远看不到数据——给你的是"无值 schema"和一份假数据，不是你的患者数据

事件内容

  • ⭐ 核心契约只有一张表，却非常干净：结构化数据（datanyx schema）给 agent 的是字段名、类型、格式、嵌套、主键与外键——绝不给出数值、样例、枚举标签、计数或统计量；自由文本（datanyx anonymize）给的是把姓名/邮箱等标识符替换成 <PERSON_1>、<EMAIL_1> 之后的文本——绝不给出标识符本身，且文档明说这是尽力而为、需要人工复核。

三、今日趋势观察

本期最明显的一条主线是："把承诺写进代码，而不是写进提示词"这一形态正在从医疗 AI 扩散到整个 agent 工程。AdelIA 把临床契约、红旗短路、逐字引文与拒答阈值做成带测试的代码；cf-skills 把证据采集做成不经过语言模型的 47 条命令；hermes-fledge 把"谁来评分"变成一张可审计的分值表；Gaskin 把危险信号做成 AI 改不动的锁定规则；DataNyx 把"数据不出本机"做成无值 schema。四条线互不相干，却都在回答同一个问题——在什么条件下，我应该拒绝输出，以及谁来证明我没有越线。 这与我前几期记下的 aureproof 三态闸门、Calibrate 的 2×2 依赖度矩阵是同一条线索的第三阶段：上一阶段是把不确定性做成可执行分支，这一阶段是把约束下沉到代码里，并让 CI 与测试替我盯着。

第二条："证据"正在从一种引用格式变成一种带固定字段的数据结构。 cf-skills 的证据记录有四个固定字段（来源 / 读取日期 / 实际依赖的字段 / 不许留空的局限说明），Gaskin 的每个计划条目带证据等级与来源，AdelIA 的每条临床陈述带 [ev_N]，hermes-fledge 的每条裁定理由带短摘录与字符数上限。共同点是：证据不再是一段散文，而是有 schema、可比对、可回归的字段。 这对内容生产链路的含义很直接——循证内容如果不能结构化，就只能靠人工复核；一旦结构化，回归测试就有了落点。

第三条：本周期的低星项目依然是信息密度最高的选题矿脉，但本期出现了两个新的形态——一个是"技能/规则的自我评分"（hermes-fledge、skill-studio 的盲评队列、skilltrim 的 token 评审），另一个是"健康数据出站边界"（DataNyx、Gaskin 的默认去标识化、cf-skills 的网络规则即代码）。89 个条目里 40 个星标 ≤100，其中信息密度最高的六个全部落在后两个形态上。星标数衡量的是关注度，不是可迁移性；对一人公司而言，"这个设计能不能直接搬进我的平台"的判断远比"有多少人在 star"重要。

第四条：模型路由与网关这一层的形态同质化继续加剧，但本期出现了两个值得注意的偏移。37 个基础设施条目里，ClawRouter / weave-os router / HiRoute / codex-router / dsh-model-router / brick-SR1 / NadirClaw 全都是"本地网关 + 多模型路由 + 成本优化"，形态几乎一致；真正的差异出现在细节里——Hermes-router 专门做"保住编码客户端给推理模型的输出预算"、Switchyard 强调"保留各供应商的原生响应格式"、dsh-model-router 直接接进本机 dsh 生态、speakeasy 的 gram 干脆把战场抬到"企业级 AI 控制平面"（权限、威胁检测、token 成本可见性）。这说明这一层的竞争点已经从"能不能接上"转向"接上之后会不会吃掉别的东西"——预算、格式、凭据归属，这三件事正在变成路由器的真正战场。

第五条：授权字段的误判率依然高得离谱，而且本期再次出现了"API 说一套、文件写另一套"的情况。89 个条目里，API 报 NOASSERTION 的有 8 个，逐个读 LICENSE 实文后才发现其中有 4 个实际是 MIT / MIT 含附加条款 / Apache-2.0 这类可商用条款，另有 2 个是 PolyForm Noncommercial、FSL-1.1-ALv2、BUSL-1.1 这类商用受限条款。外加 16 个仓库根本没有任何 LICENSE 文件（已用 core 端点逐一确认）。对一人公司来说这是生死线：MIT 与 Apache-2.0 占 60 个（67%），可放心选型；AGPL-3.0 有 5 个、PolyForm Noncommercial 有 1 个，只能读不能抄；剩下 16 个"未声明"在动手前必须先问一句作者。
