地址：https://github.com/nicobailon/skill-diet ｜ ★237 ｜ MIT ｜ Python ｜ 给其它 agent skill 做"减肥"的技能包 + 一个跨模型复检技能 skill-model-gap

事件内容

窗口内 3 次提交（11-06 04:31Z ~ 11-06 06:18Z），主线是发布 v0.2.0，把"技能瘦身"从一次性动作升级成可持续的维护契约。

  • ⭐ 核心命题是一句很硬的观察："agent 每次使用技能都会把整个 SKILL.md 读一遍。" 因此技能里多写的每一行，都是每次调用都要付的钱。README 直指四类冗余：只有部分任务用得上的细节、模型本来就知道的东西、写给人看而不是写给 agent 看的说明、以及一个概念就能替代的清单。更隐蔽的一类是：教工具的技能会把工具的参考手册抄一份进自己体内，而这份抄件会随工具演进而变成过期信息。
  • ⭐ 瘦身的结论是可复算的，不是感觉：README 明确写"在真实技能上，diet 砍掉了 70–80% 的 token 且测试结果没有下降，并且找出了技能里记录、但实际已经不能用的命令"。也就是说瘦身不只是省 token，它还兼职做技能与工具的漂移检测。
  • ⭐ "瘦身"有一套五层归位法，把每条事实放到"仍能到达 agent 的最低层"：① 技能 description（每个场景一个触发器，每次会话都读）② SKILL.md（每个任务都要的，用技能时读）③ 参考文件（只有部分任务要的，场景出现时才读）④ 工具自己的 help（flag、允许值、示例，agent 选命令时读）⑤ 工具自己的报错与检查器（正确名字、怎么修、下一步，agent 猜错时读）。越往下越省上下文——这一层级就是一条明确的"上下文成本账本"。
  • ⭐ v0.2.0 新增的 skill-model-gap 解决的是一个我几乎没意识到的问题：大多数技能只在最强的一个模型上写和测，但很多人跑在别的模型上，而它会"悄悄地"做得更差。 做法是在每个你选的模型上跑同一批任务，找出弱模型为什么失败，只保留"对弱模型有帮助且不伤害其他模型"的修法。首次试验的结果被写在发布说明里：改动技能 description 里的一行，把 Kimi 的通过率从 78% 提到 98%、Haiku 从 85% 提到 100%，同时 GPT 与 GLM 不降。
  • ⭐ 评分规则被收紧，防止"因为错误的原因而通过或失败"：v0.2.0 明确运行被禁命令现在直接判该次运行失败；存在缺失运行的对比现在判失败，而不是给出一个误导性的结论。这一条比前面的数字更重要——它堵的是"评测本身在说谎"这条路。
  • ⭐ 瘦身的判定门槛是"三版对照 + 盲评"：用旧技能、新技能、完全不给技能三种配置跑同一批任务，只要新版不更差就保留；且争议答案由一个没见过哪版写的全新会话来裁决；评分器如果发现新版比"随机水平"还差、或者新版从未通过旧版总能通过的任务，就判瘦身失败。任务集在动手删之前就先写好。
  • ⭐ 对"教工具的技能"还有额外三步：逐条证明技能与工具的不匹配（要么真跑一遍，要么指向源码行）；读会话日志找出 agent 最常调用的命令，只把那些展开写全；统计 agent 到底多常打开这个技能， seldom 打开的规则就搬进工具的报错与提示里。README 承认了一件反直觉的事——"请 agent 更新技能"通常会让技能更长，因为 agent 倾向于多加而不是少删。

值得关注的原因

  • ⭐ 这直接命中我最痛的一件事：我用 WorkBuddy 的 expert-manager skill 批量生产专家包，而每个专家包都是一份"每次都要全文读进上下文"的 SKILL.md。 截至本期，我已经有 19 期日报、几十个专家包、多个公众号内容模板，但我从来没有量过任何一个技能"每次调用到底烧掉多少 token"。skill-diet 给出的做法是先量、再归位、再用旧版/新版/无版三路对照——这条流程可以原样搬进我的专家包质检流程，作为第一条固定工序：专家包发布前必须报告"瘦身前 token 数 / 瘦身后 token 数 / 测试结果变化"三个数字。

  • ⭐ "读会话日志找出 agent 最常调用的命令，只把那些展开写全"是一条几乎零成本、立刻见效的优化。 我的专家包与公众号内容模板里，大量篇幅写的是"这个字段有哪几种取值"——但agent 实际每次只用得上一种。
  • MIT 授权，可读可改可商用，且它本身就是一份"如何写技能"的现成范本——我可以把它当成技能写作的 lint 工具来用。

三、今日趋势观察

本期最明显的一条主线是：约束正在从"提示词里的要求"变成"运行时里不可绕过的闸门"，而且闸门开始自带证据。 skill-diet 用"旧版/新版/无版三路对照 + 盲评 + 评分器自己也会失败"来保证瘦身不引入回归；navigator 让 stop_completion 在完成标记缺失时直接拒绝 agent 结束这一轮，并把每次拒绝写进日志；archestra 让 agent 运行时 pod 以非特权方式跑在可配置的 gVisor RuntimeClass 下，并把"工具以谁的身份运行"写进鉴权协议；myfitnesspal-mcp 的做法最朴素——写入后把日记读回来核对。这四条线互不相干，却都在回答同一个问题：不是"AI 该怎么做"，而是"AI 做不到的时候，系统会怎么拦它、拦下来之后有没有留下证据"。 这与我前几期记下的 aureproof 三态闸门、Calibrate 的 2×2 依赖度矩阵、AdelIA 的答案契约、Gaskin 的锁定项是同一条线索的第四阶段：上一阶段把约束下沉到代码，这一阶段把约束下沉到运行时，并让运行时留下可审计的痕迹。

第二条线是"成本的度量单位正在从 token 变成 token × 模型 × 场景"。 skill-diet 报出"砍掉 70–80% token 且测试结果没降"这组数字时，还报了一个更反直觉的：改一行 description 就让 Kimi 从 78% 提到 98%、Haiku 从 85% 提到 100%——同一个"瘦身"动作，在不同模型上的收益完全不同。navigator 报的是"加载 token 从 150,000 降到 12,000、结束上下文从 95% 降到 35%"，也是以可对比的量化指标说话，而不是"体验更好"。这两条合起来意味着：现在评估一个 AI 产物或技能的性价比，不能只看"它多聪明"，必须看"它在哪个模型上、烧多少 token、通过了多少任务"三元组。 我做专家包与一人公司产品时，这正是我一直缺的度量口径。

第三条线：健康与医学线的"本地优先 + 证据可追溯"正在成为默认假设，而不是个人偏好。 syntropy-health 跑在你自己的电脑上，它对健康数据的每一次操作都是只读且有日志的；medical-illustration 强制"每项用于医学讲解的解剖结构都要有匹配部位、视角与层次的可信依据"，并逐幅登记"这份依据只支持哪一部分"；myfitnesspal-mcp 反向工程 MyFitnessPal 的私有接口，但把"这是逆向工程、随时会坏、用你自己的账号"三句话写在最前面。三者共同点是：把"数据在我手上"与"结论有依据"这两件事同时做成可检查的事实。 这与前几期记下的 cairn（HTTP 只绑 127.0.0.1）、DataNyx（无值 schema + schema-diff 进 CI）是同一条趋势的延伸——本地优先已经是这类产品的默认架构假设，而"证据可追溯"正在补上第二块。

第四条线：授权形态正在从"一个 LICENSE 文件"升级为"分层 + 路由 + 三层分别声明"。 medical-illustration 把自有核心 Skill 与脚本定为 MIT、自有原创文档与漫画定为 CC BY 4.0、第三方素材保留原许可，并明说"使用 Skill 创作的新作品不自动继承上述许可"；archestra 用"默认 AGPL-3.0-only + 标 Enterprise 的区域走商业许可"的首条匹配即胜路由规则，把 SPDX 头、REUSE snippet、路径约定（*.ee.* / ee/）与 vendored 依赖逐层排好；ClawBio 上一期记的"三段式许可证"（代码 / 模型 / 数据取最严者）是同一族思路。对一人公司的直接含义是：选底座时不能只看仓库首页那个许可证徽章，必须把"我要用的是哪一部分"和"这一部分归谁"两件事问清楚。 本期实测仍有 5 个条目确认无 LICENSE 文件（dromlakhani/MD2SKILL、ImHangLi/maru、anbeime/skill、linhay/harmony-next.skills、anthropics/skills），其中 anthropics/skills 本期有一条 "Move Office skills to the Apache 2.0 license" 的提交——连最上游的官方技能仓库也在把授权切到更宽松的一侧，这本身是个信号。

第五条线，也是给 Gordon 的直接提醒：我这一期看到的三条"读回校验"，分属三条不同的技术栈，但都在解决同一个错误。 myfitnesspal-mcp 用一次日记读取解决"AI 写了不存在的食物"；navigator 用"完成标记 + 拒绝日志"解决"agent 交回了一个看起来合格的残次品"；medical-illustration 用"逐幅登记证据"解决"这张图其实不支持这句话"。我现在的三个项目——4P 平台、GRPM 报告、公众号内容——三处都在做"AI 生成结构化结论然后落库/发布"，但三处都没有读回校验。 这条几乎是零成本的改进：写入 → 按主键读回 → 比对 → 不一致就标红并阻断下游。相比之下，我更该警惕的是 skill-diet 那句提醒——"请 agent 更新技能通常会让技能变长"，意味着我若把专家包的迭代交给 agent 自动做，成本会单调上升。
