一、今日精选 5 条

1. Omnigent：11k★ 的"元 harness"，把 Claude Code / Codex / Cursor 收进同一层并开始管住它们

地址：https://github.com/omnigent-ai/omnigent ｜ ★11,013 ｜ Apache-2.0 ｜ Python，已发 PyPI 包 + macOS 桌面端

事件内容
Omnigent 自定位为 meta-harness：在 Claude Code、Codex、Cursor、OpenCode、Hermes、Pi 以及用户自己写的 agent 之上加一层统一编排，做到"换 harness 不用重写"。能力清单相当完整：会话跨设备接管（终端里开始，浏览器里继续，手机上接着看，消息/子代理/终端/文件同步）；一个会话里混跑多个 agent，可以让一个 agent 去审另一个 agent 的产出；模型侧同时支持自带 API key、Claude/ChatGPT 订阅与任意兼容网关；策略治理可按整个服务器、单个 agent 或单次会话设置——高风险动作先暂停等人工批准、封顶花费、限定 agent 能碰哪些工具；执行侧接了 12 种沙箱后端（Modal、Daytona、Blaxel、Islo、E2B、Gensee、CoreWeave、Kubernetes、OpenShell、Boxlite、microsandbox、Databricks），另有团队协作与 fork 会话。

当日 4 个提交全是主干稳定性修复，且修的都是"编排层才会遇到"的问题：#11469 处理"被挂起的一轮，宿主回来了但 runner 没回来"要说清楚状态；#11463 把 Claude 报错的失败边界留给 StopFailure 钩子；#11458 在 model_not_found 停止时正确显示"模型不可用"卡片；#11436 修画布上会话串号。

值得关注的原因

  • 昨天我们还在讨论"harness 竞争转向成本结构与生命周期"（hermes-agent、openhuman、deer-flow），今天出现的是再上一层：不造 harness，而是管 harness。对企业的直接含义是——不必在 Claude Code 和 Codex 之间二选一，先在编排层统一策略与审计，底层可换。
  • 它修 bug 的位置很说明问题："宿主回来了但 runner 没回来"、"错误边界归属哪个钩子"，这些是分布式会话的状态对账问题。这一层一旦成为入口，可靠性要求就等同于基础设施，而不是开发者工具。
  • 对医疗健康业务尤其对路：策略层能同时表达"PHI 不许外发""付费 API 日限额""某类工具仅限内网"，且作用于全部底层 harness——这正是合规审计想要的"一处声明、处处生效"，而不是每个 agent 各写一遍 prompt。

2. Last EHR：把"agent 写病历"做成一个可审批的协议，并公开自己的覆盖上限

地址：https://github.com/cbetz/last-ehr ｜ ★4 ｜ Apache-2.0 ｜ TypeScript，Web + MCP 双入口

事件内容
Last EHR 是无头 FHIR EHR 之上的 agent 层（不是 EHR 本身，不 fork 后端）。三件事做得非常具体：

读得宽，而且敢报数：按 US Core 9.0.0 的 27 个可读资源类型，覆盖 25 个，横跨 23 个患者维度分区，并顺着引用把作者、就诊、provenance 从"死指针"变成可取内容；覆盖率文档写明分母来源与生成日期（2026-05-31），并明确拒绝给一个"占 R4 的百分比"（附"为什么不给百分比"一节）。

不许编造"没有"：读操作会如实报告"窗口被截断""引用查询被拒""某分区的编码过滤没匹配到但该分区确有记录"；分区无法应用的过滤器会被拒绝并回传合法取值，而不是静默丢弃。README 把这称作安全边界测试而非 best-effort。

写一律是提案：开源了 Approval-Gated Agent Writes on FHIR v0.1 草案——Proposal → Decision → Commit → Audit，两个实现（Web 审批卡、MCP elicitation 门控写工具），外加一套用自身 FHIR 读来校验实现的 conformance 套件（npx @lastehr/agent-write-conformance）。MCP 侧默认只读，仅 4 个有界读工具，写必须逐次人工批准。后端一套接口下挂 5 个 FHIR 实现（Medplum、HAPI、Firely、Aidbox、Oystehr）。

当日提交（PR #200 "durable work lab"）把真实 Claude 助手接进"可审阅的持久 FHIR 工作流"，并留下真实助手验收与持久化的证据记录。

值得关注的原因

  • 医疗 agent 长期卡在"能读不能写"。这个项目给出的答案不是"让模型更可靠"，而是把写权限降级成提案 + 引入协议与一致性测试——这是把"人类在环"从产品文案变成可校验接口的少数实践。
  • "不能报告一个它没查过的缺失" 这句话值得所有做临床/健康 agent 的团队抄进设计规范：模型最危险的错误不是答错，而是把"没查到"说成"没有"。
  • 它主动标注 alpha、只许合成数据、把 HIPAA 部署前置条件单列文档，延续了我们这几期观察到的"主动划界即成熟度信号"。4 星不影响判断，协议本身比星标重要。

3. HL7 官方仓库一天之内把"分子肿瘤委员会"从患者横幅做到 AI 综合

地址：https://github.com/FHIR/genomics-operations ｜ ★34 ｜ Apache-2.0 ｜ HL7 FHIR Genomics Operations 公开参考实现

事件内容
FHIR/genomics-operations 是 HL7 FHIR Genomics Operations 的官方参考实现（配套 JAMIA 论文），提供 find-subject-variants、find-population-tx-implications 等基因组操作，用于把"患者有哪些变异、对应什么表型/用药含义"标准化成 FHIR 接口。过去两天它的提交记录很集中，全部围绕一个新加的 MTB（Molecular Tumor Board，分子肿瘤委员会）应用，且节奏是层层递进：

  • 10-23 18:41 用临床数据生成患者横幅（patient banner）
  • 10-23 20:59 用临床数据生成病历摘要（chart summary）
  • 10-23 23:47 构建治疗时间线（treatment timeline）
  • 10-24 00:51 加入 AI 综合（AI-based synthesis）

也就是说，一个由标准组织维护的"接口参考实现"，在 6 小时内长出了一个面向临床决策会议的 AI 应用雏形：横幅 → 摘要 → 时间线 → 综合判断。

值得关注的原因

  • 这是本期最值得记的一次方向信号：AI 应用层正在被直接写进"标准参考实现"里。以往标准仓库只管接口与测试，现在它同时示范"接口之上该怎么用 AI"。对做医疗信息化的团队，这意味着官方示例会逐渐成为产品形态的默认答案，选型与合规评审都会向它对齐。
  • MTB 场景选得很准：它是基因组数据真正落地的地方（体细胞变异→可及试验→用药），也是"多源证据 + 时间线 + 综合建议"最典型的形态——恰好是 agent 擅长的活儿。
  • 提醒一句：参考实现 ≠ 可上线的临床系统。它给的是数据形状与流程骨架，判断逻辑与责任边界仍需自己补；今天这条的价值在于"标准侧承认了 AI 综合这一段"，而不是"可以直接用于临床"。

4. 医药证据 agent 的 240 次消融实验：技能层是性价比拐点，Sonnet 贵 16 倍只多 2 个点

地址：https://github.com/Akhilesh-Vangala/healthcare-evidence-agent ｜ ★1 ｜ MIT ｜ Python 3.10+，Claude Code 作运行时

事件内容
这是一个受治理的医药证据 agent，回答生物医药商业化/医学事务/政府事务问题，数据面锁定三类公开源：FDA 标签、ClinicalTrials.gov、Medicare NCD。工程形态清晰：Claude Code 是运行时，工具是 6 个工具的 MCP server，流程封装为 4 个 Agent Skills，公开数据、无 PHI、明确声明非医疗建议。

最值得看的是它把消融做成了正文（240 次运行，含 95% 置信区间）：

配置通过率（95% CI）引用可核率单任务成本中位延迟
固定流水线（无 LLM）20%（7–37%）不适用$00.1 s
A. Haiku，闭卷23%（10–40%）0%$0.001410 s
B. Haiku + MCP 工具80%（63–93%）89%$0.002511 s
C. Haiku + 工具 + 技能95%（87–100%）94%$0.003314 s
D. C 换 Sonnet97%（90–100%）94%$0.053216 s

另一条硬约束是程序化校验器：一条论断只有在 source_id 于本次运行中被检索到、且引文是该来源的逐字子串时才被接受。当日提交把仓库拆成前端/后端/agent 三个 workspace，并清掉会泄露部署 token 的本地文件。

值得关注的原因

  • 这组数字对"要不要上技能层"给出了少见的定量答案：闭卷 23% → 加工具 80% → 加技能 95%；而换更强模型只从 95% 到 97%，成本却贵 16 倍。对预算敏感的业务（健康管理、营养咨询这类高频低单价场景）含义很直接：先补工具与技能，再谈换模型。
  • "逐字引用 + 本轮检索"这个校验口径，比"提示模型要引用"强一个量级——它把幻觉引用变成可执行断言，而不是事后抽查。这一点与昨日 Odyssey 的"每个 claim 配测试"同源。
  • 它把"治理"落在代码里：数据源白名单、无 PHI、pass rate 与失败样例（3 个失分全是"复核标记过度升级"）都写在报告里。这种"失败也要分类"的做法，比只报一个总分更可信。

5. 把营养做成硬约束求解：预算、蛋白下限、钠上限、过敏原同时约束，还要和官方计价对账

地址：https://github.com/harry1729/mcd-nutrition-planner ｜ ★1 ｜ MIT ｜ JavaScript，零依赖

事件内容
一个面向团餐/会议餐的决策助手：输入"20 人、人均 40 元、深圳科技园"，它去麦当劳 MCP 查门店真实菜单、用官方计价接口算钱，然后在四重约束下求解——人均预算硬上限、蛋白质下限、钠上限、过敏原规避，用二维 0/1 背包 DP 求最优券分配，输出可直接下单的清单（含每份数量、单价、合计、人均，以及每人热量/蛋白/钠估算），最后做一次MCP 官方计价 vs 本地估算的一致性复核（示例输出两者都是 ¥630.00）。

工程上：零依赖零构建，npm test 可离线验证全部求解逻辑（45 个测试通过），不需要 MCP Token 就能跑；README 明确写"门店菜单与价格按日轮换，复跑结果会不同——这属正常，不是模拟数据"。

当日提交为 README 首屏重构与公众号发布包（图片设计 + 合规检查 + 一键导出），求解器本身在 10-22 完成。它是麦当劳 1024 程序员节参赛作品，规模小、星标 1，请按"方法样本"而非"生产工具"看待。

值得关注的原因

  • 营养类产品长期停在"记录 + 建议"，这个项目换了个问法：不是"建议你吃什么"，而是"在这些硬约束下有没有解"。把营养从软性提示变成可行解问题，是能直接嵌进企业团餐、食堂配餐、慢病配餐的业务形态。
  • 价格对账这一步很关键：本地估算与官方计价必须一致才输出方案，本质上是把"数据可信"做成了运行时断言，而不是免责声明。
  • 连续性也值得注意：10-19 期我们推过 FoodGuard（离线国标配料评级）、10-22 期推过 Edamam 官方 skills 与 CKD 六维计量，今天这条是第三条路线——约束求解。三条路线合起来说明：营养 AI 的竞争点已经从"识别食物"移到"能不能给出可执行、可核对、有边界的最优解"。

三、今日趋势观察

  1. "写权限"成了医疗 agent 的分水岭。昨天的医疗 agent 还在比"答得准、说得清"，今天的 last-ehr 直接把问题改写成："谁批准了这次写入、批准的是不是提交的那一份、事后能不能追"。Proposal → Decision → Commit → Audit 这套四段协议 + 一致性测试，很可能成为下一批院内 agent 的默认骨架；不能留痕的写入，将来很难过评审。
  2. 评测的形态从"跑分榜"变成"消融表 + 引用可核"。healthcare-evidence-agent 的 240 次运行把增益拆得很干净：工具 +60 点、技能再 +15 点、换更强的模型只 +2 点但贵 16 倍。这给"该往哪儿投钱"提供了可复用的判断框架——先补工具与技能，再换模型；而"逐字引用 + 本轮检索"把幻觉从"抽查问题"变成"断言问题"。这与 Odyssey 的"每个 claim 配测试"是同一套纪律。
  3. 编排层之上又长出一层"管 harness 的 harness"。omnigent 11k★ 把 Claude Code、Codex、Cursor、Hermes、Pi 统一收口，再叠策略与沙箱；它今天修的全是"宿主与 runner 失联""错误归属哪个钩子"这类分布式状态问题。含义是：企业不再需要在多个 harness 之间押注，而是先在编排层统一治理与审计，底层保持可替换。
  4. 标准组织的仓库开始直接示范 AI 应用层。HL7 的 FHIR/genomics-operations 用一天时间把 MTB 应用从患者横幅做到 AI 综合。这比任何创业公司的 demo 都更能改变采购与评审的默认预期——"官方参考实现长什么样，产品就得长什么样"的压力会传导到医疗信息化厂商。
  5. 营养 AI 的第三条路线：把营养当硬约束求解。继"离线国标规则引擎"（FoodGuard）、"官方 skills + 专科计量"（Edamam / CKD 六维）之后，今天出现的是多约束最优解 + 与官方计价对账。三条路线的共同点是：都不再满足于"识别出食物"，而是要求可执行、可核对、有明确边界。做健康管理业务的团队，值得把"约束是否写死、数据是否对账"当作选型硬指标。
  6. 健康信息安全小专栏（第 2 期）：php2shell 的修复窗口正在关闭。PHP 8.5.12 / 8.4.27 / 8.3.36 已于 10-21 发布，今天 php-src 仍以 +716★ 冲上趋势榜第 2，说明大量团队还在"找版本"阶段。此前推送过的自托管健康/营养/MCP 项目（HealthLog、SparkyFitness、plate、medicationtrackerbot 等）若跑在 PHP 栈上，请今天就核对版本——这类预认证 RCE 不需要应用层漏洞，等不到"下周排期"。
