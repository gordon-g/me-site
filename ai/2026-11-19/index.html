2. 有人给「AI 写的界面」造了一把尺子：renderlint 今天发 v0.2.0，把移动端溢出、对比度、重叠变成构建失败

地址：https://github.com/ngocanhnckh/renderlint ｜ ★686 ｜ MIT ｜ 面向 AI 编程智能体的「渲染后 UI」检查器，用无头 Chromium 在手机/平板/桌面宽度下截图并报告文字溢出、低对比度、元素重叠、响应式断裂等缺陷

事件内容

  • 昨日 15:31 发布 v0.2.0，这是该项目的第一个打标签版本，也是第一次以 @yitec/renderlint 名义发到 npm。今日窗口内 14 次提交。
  • 检查原理是「渲染后」而非「源码」：README 明写「TypeScript and ESLint can't see any of this, because the code is fine. It's the pixels that are wrong.」工具在手机、平板、桌面三种宽度加上暗色模式下渲染每个页面，并在其间的宽度上扫一遍，再用更长的文案、更大的数字、更长的 API 数据复检一次；每个缺陷给出元素定位、源文件、带标注的截图和具体修复建议，用智能体能直接执行的纯文本表述。当前 58 条规则。
  • 今日的三个动作分别对应我关心的三件事：①「Phones: zoom-disabled, input-zoom, html-lang, safe-area」——手机专项检查；②「Fewer false positives from real sites: covers you can scroll clear of, negative margins, dev-server chunks」——用真实站点压误报，规则只有「可滚动让开的浮层」「小的负边距」「开发服务器分块」才不报；③「Audit cleanup: disclose network and processes, SECURITY.md, regex exec → match」——审计清理，把正则从 exec 改成 match、披露网络访问与子进程、加入 SECURITY.md。
  • 新规则 text-near-overlap（warn）：两段文字并排、间距小于 ¾ 字号且不在同一行、其中至少一段位于绝对或固定定位层内时告警。典型场景是居中的空状态文案压在标题被固定的面板上。
  • 还有一条相当诚实的工作流提交：「Baseline and progress: adopt renderlint on an app that already has findings」——在已经有问题存在的应用上启用它，而不是在一个干净样例上展示它。
  • 安装方式面向智能体：npx -y @yitec/renderlint init 会写入配置、构建闸门、AGENTS.md 指令与 Claude Code hook；之后 npx renderlint 一旦发现错误即以退出码 1 中断。

值得关注的原因

  • 「移动端文字可读性」是我反复提、反复不满意的一件事，这个工具直接对着这个洞。 我做的是单文件离线 HTML 应用（个人办公工作台、GLP-1 营养伴侣 V2、这个日报站本身），每次都要人工确认手机端字号、排版、按钮可点区域。这类检查本该是构建闸门，不该是我每发布一次就重看一遍眼睛。 把它接进我的构建流程，是我下周就能落地的三件事之一。
  • 「用已经有问题的应用验证工具」这个工作流，比任何 demo 都有说服力。 我做产品验证时的老毛病是想找一个干净的样例来证明方法有效 —— 这恰恰是我自己在营养内容里反复警惕的「挑数据」。先在有问题的存量应用上跑，把发现数记下来，再看修完剩多少，这才是可交付的验收方式。
  • 误报治理那段对我有直接价值。 它把「可滚动让开的浮层」「小的负边距」列为不报 —— 这些恰好是我这种单文件应用里最常见的合法写法。一个不懂你的技术栈的检查器必然误报，而误报率决定它能不能进 CI。 我若要给自己的内容站加检查，这套「先在真实站点上压误报」的流程照抄即可。
  • 安全侧同样干净：正则从 exec 改 match、披露网络与子进程、有 SECURITY.md。一个要驱动浏览器、要跑 dev server 的检查工具，它的攻击面比普通 linter 大得多。 我把它放进自己仓库之前一定会先读这三处。
  • 现实提醒：★686、第一个正式版本，规则还在快速迭代（今天一上午就调了手机规则和基线规则）。规则会变、误报会反弹，我如果接进 CI 要预留一条「临时豁免」的通道，否则我会被它逼着天天改 CSS。

4. 有人把「干预到底让生物年龄变年轻，还是只把时钟挪动了」做成了一个可打分的模拟环境：longevity-gym v0.1

地址：https://github.com/di-omics/longevity-gym ｜ ★0 ｜ 许可证未声明 ｜ 一个模拟强化学习环境，用八个模拟衰老时钟与隐藏真值回答同一个问题：干预是否真的让人变年轻，抑或只是移动了时钟读数

事件内容

  • 仓库今日创建（2026-11-18），当日 4 次提交（08:25 — 12:41 UTC，均在窗口内），首个版本 v0.1。这是一个从零起步、当天就搭出完整方法论骨架的项目。
  • 问题设定只有一句：「did this intervention make simulated people biologically younger, or did it only move the clocks?」
  • 项目把自己的边界写在最前面：「Status: v0.1, simulation only. Nothing here is trained on real data. The repo holds no real proteomic or methylation data, no published clock, no participant-level trial data and no stored model or agent.」只有两个东西是拟合出来的，且都在运行时、且只用模拟数据：八个充当时钟的小型岭回归，以及捷径检查里的两个小型学习策略。唯一真实的数字是从论文公开附表中算出的少量聚合统计量，只用在一节里校准模拟器的噪声并设定一个可选噪声档；其余每一个数字都是假定默认值，全部列在 docs/ASSUMPTIONS.md。
  • 模拟世界构造：每个模拟人有七个器官年龄、全身炎症、纤维化活性与血细胞混合；生物学年龄定义为器官年龄均值，炎症、纤维化与细胞构成会渗进组学数据，但按此定义它们不算衰老。组学为 240 个模拟蛋白特征与 200 个模拟甲基化特征，带板效应；其中四个肺富集蛋白被设定为健康人中最强且噪声最小的年龄标记、同时随纤维化活性升高。
  • 它引用的真实研究恰好是它要质疑的那类证据：2026 年 9 月 Insilico Medicine 与若干学术团队发表对 rentosertib 治疗特发性肺纤维化的 12 周 2a 期探索性分析，在 42 名受试者血清上跑了六个已发表的蛋白组衰老时钟；54 次比较（6 时钟 × 3 剂量组 × 3 访视）里 21 次显示预测年龄降幅大于安慰剂（单侧检验，FDR 0.10），其中 11 次出现在第 4 周。项目明写自己不使用该试验的任何数据、也不使用那些时钟，并引用论文自陈的局限：蛋白组时钟本身无法把「对衰老的作用」与「药物的抗纤维化作用」分开。
  • 今日四次提交的走向很清晰：longevity-gym v0.1: clock_trial environment, eight simulated aging clocks, QC card → Rebuild from the paper: verified clock recipes, shared fibrosis proteins, continuous truth, paired QC → Second review: make the reward pay for the cross-modality check, calibrate the reference → Check the simulator's clock noise against real clock readouts; add a calibrated noise option。姊妹项目 drugdev-gym 的定位是「hidden truth, named mistakes, and a QC card that says what the reward can and cannot see」。
  • 奖励函数要能被质询：README 与提交信息都强调「QC card」——奖励函数能看见什么、看不见什么，必须写成一张卡片；第二次评审甚至改成「让奖励为跨模态检查付费」。

值得关注的原因

  • 这几乎就是我「百十工程」观察指标分析里那个没解的问题的最小版本。 我分析参与者观察指标、调整干预方案、看配方效果时，真正的风险一直是：指标动了，是人真的改善了，还是只是把某个时钟读数挪动了？ 今天这个项目把这个问题变成了一个可以打分的模拟任务。它的做法是：先造一个有已知答案的世界，再看模型能不能读懂一组时钟。 我不必有真实数据也能照这个结构设计 —— 先用历史数据造一个「答案已知」的离线版本，验证我的评价逻辑会不会被表面指标骗过去。
  • 「把奖励函数能看见什么写成一张卡片」是我 4P 干预报告该加的一页。 我的风险评级算法目前对外就是一个分数。这个项目的要求是：明确写出我的评级依据看见了什么、没看见什么。 「炎症指标变了但未测肌酐」这种情形，我的分数到底是基于什么得出的？客户看不到这一层，就无法判断我的风险分级该不该信。这一页是我下一个版本可以立刻加的。
  • 「炎症、纤维化会渗进组学但按定义不算衰老」这种区分，是精准营养报告里最需要、也最容易含糊过去的判断。 我的干预报告里，「代谢炎症改善」和「生物学年龄改善」经常被混着说。这一条提醒我：指标归属必须显式声明定义，否则客户会自己脑补因果。
  • 整个仓库最值得我抄的是它对自己边界的那段声明。 没有真实蛋白组数据、没有真实时钟、没有真实试验数据、没有存下来的模型或智能体 —— 全部假定默认值集中在一个文件里。我做的每一份干预报告里引用的每一个数字，都该有同样的「这个数从哪来、有没有跑过」的交代。 这和我上几期记的「没跑就不报数字」是同一条，但这次它连「默认值都集中登记」都做了。
  • 现实提醒：★0、当天创建、纯模拟、无真实数据。这是方法论样板，不是产品，更不是疗效证据。 我借鉴它的思考结构，绝不引用它的任何数字。

5. 「不用向量库也能做 RAG」这条路今天往前走了一步：PageIndex v0.7.2 把抽取与计费绑到同一个作业里

地址：https://github.com/VectifyAI/PageIndex ｜ ★40,478 ｜ MIT ｜ 免向量的推理式 RAG 文档索引器，用目录树结构替代切块与向量检索，本地与云端同一套客户端

事件内容

  • 今日窗口内 2 次提交，但关键动作是发版：v0.7.2 于今日 12:44（北京时间）发布，距上一次 v0.7.1（11-17）仅两天。
  • README 的定位句是四段并列：「No Vector DB, No Chunking. Context-Aware Retrieval. Reads Like a Human.」发版说明同样四段式：比向量 RAG 更便宜（索引与查询两侧都算）、更快（树由版面统计量生成）、统一 SDK（本地或云端，索引与对话都用）、可直接跑在 Claude 订阅上。
  • 本地模式不需要服务器、不需要向量库、不需要 API key：client.submit_document("report.pdf") 后 client.chat("What does the report conclude?")；PageIndexLocalClient(storage_path=...) 与云端是同一个客户端，提交、取树、取页面内容、对话、agent 工具在两种模式下全部齐备，代码可平移。
  • Flash 引擎是本地默认（mode="standard" 保留经典 LLM 流水线）：嵌入式书签在被信任时才消费，树优化默认开启 —— optimize="merge" 走确定性、无 LLM 的那一遍，"full"（默认）额外加 LLM expand，且改为并发跑一波节点而非一次一个来回。
  • 今日那次提交是一处计费归属修正：feat: PageExtractClient.extract(file) uploads the file with its job, so the upload is not charged on its own (#690) —— 上传随作业一起提交，上传本身不再单独计费。另一处是 build: lift the litellm cap。
  • README 的更新记录写着 10 月的 Page Search API：「find the pages that answer each question in about a second, and send your LLM only those. Cut 97% token cost on document question answering」，并附了对比基准仓库。

值得关注的原因

  • 「索引与查询两侧都比向量 RAG 便宜」如果成立，直接打在我 4P 平台 AI 助手的成本结构上。 我的 GRPM 营养基因组学系统和 4P 精准营养平台都依赖 RAG 检索知识库。成本这件事我不是只在表格里看过 —— 我的报价模型里 LLM 成本是要算进去的。 一条不依赖向量库、本地能跑的路径，值得我实测一次再决定要不要动架构。
  • 「本地模式不需要向量库、不需要服务器」这条和我的部署现实完全吻合。 我的 Flask+SQLite 全在本地 8899 端口跑，本机还有 Ollama qwen2.5:7b。如果检索层能在本机跑完，客户的健康数据就完全不必出本机 —— 这条对我 4P 平台的隐私承诺是最直接的落地方式。
  • optimize="merge" 是确定性、无 LLM 的那一遍，这个设计我很喜欢。 我此前几期反复记的那条原则 —— 能确定性算的数值就别交给模型算 —— 在检索层也成立：目录树结构先由版面统计确定性地长出来，LLM 只在需要扩展时介入。 这和我 GLP-1 营养伴侣把数值计算搬进表里是同一个思路在不同层的落地。
  • 今天这次提交专门修「上传被单独计费」，这条值得我引申。 我的内容生产链路里有一个长期困惑：AI 辅助生成的量到底该算在谁头上。把上传与作业绑定、让上传不单独计费，是在给「一次任务」一个清晰的责任单位。 我的公众号内容流水线与这个日报的构建流水线同样需要这种责任单位划分。
  • 现实提醒：★40,478 但发版节奏极快（两天一版），README 的性能主张（97% token cost 削减、更准更快）附的是自家基准仓库，我若要引用必须自己去跑一遍对照，不能拿别人的基准当自己的结论 —— 这条我给自己的内容规范也这么写。

三、今日趋势观察

  • 「技能生态」今天正式从策展目录变成了依赖管理问题。 microsoft/apm 用一个 apm.yml 加一份 apm.lock.yaml 把技能、插件、MCP 与提示词纳入版本化解析，另有 whyihaveyou/dsh-suite 每小时刷新插件活目录、mattpocock/skills 与 obra/superpowers 稳居星标榜首 —— 过去两年「技能怎么装」是各家自己写 README，今天开始有了统一答案。 对我这类要交付他人使用的产品（4P 专家包、营养 AI 内核），交付形态必须从「拷贝目录」变成「一条安装命令」，这一条我下周就该动手。
  • 「AI 写的界面需要人写的检查器」这个缺口今天有人填上了。 renderlint 用无头 Chromium 在真实宽度下渲染并把像素级缺陷变成构建失败，还在新规则 text-near-overlap 里把「两段文字间距小于 ¾ 字号」判为告警。它同时踩中了我长期不满意的那块 —— 移动端文字可读性。我那几个单文件 HTML 应用（工作台、GLP-1 营养伴侣 V2、这个站）都能直接受益。
  • 「把奖励函数和评价依据能被质询」今天在三个互不相识的项目里同时成形。 longevity-gym 的 QC card 写明奖励能看见什么、看不见什么；oya-browser 用「一次任务录成确定性重放剧本」留下审计证据；APM 把策略检查从声明值改到实际生效值。三件事的本质相同：结论必须挂在一个可回溯、可被外部检查的环节上。 我 4P 干预报告的风险评级目前还是「一个分数」，缺的就是这一层。
  • 「没跑就不报数字」这条纪律今天再次被完整执行。 longevity-gym 明确列出「无真实蛋白组数据、无已发表时钟、无试验级数据、无存下来的模型」，只有从论文附表算出的少量聚合统计量用于校准噪声，其余全部是登记在案的假定默认值；营养线的 NutriTracker 今日发版、健身教练 ironm 写明「每次改动先问你」、PageIndex 今日把上传计费并入作业 —— 这四个项目分别在数据、流程、成本三个位置守住了同一条线。
  • 今日分类③ 依然偏薄，且这个厚度是真实的。 10 个仓库里星标最高的是 foldseek（★1,332）与 matchms（★278），其余多为 ★0 ~ ★81 的个人与实验室项目；营养与健康方向的高星项目今天没有动作。 我不硬凑 —— 健康线的高星空档，每个月都会出现一次，说明这个方向的开源投入仍以小团队为主。 我做 4P 健康与精准营养时，这条生态空档本身就是机会信息。
