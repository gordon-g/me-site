1. 浏览器厂商开始给「网页知识」配评测仪表盘：Google Chrome 把 203 条指南做成了需要持续回归的资产

地址：https://github.com/GoogleChrome/modern-web-guidance-src ｜ ★5154 ｜ Apache-2.0 ｜ 由 Chrome、Edge、Firefox、MDN 团队共同维护的技能源码库，把现代 Web 平台知识做成可检索、可安装、可评测的编码智能体技能

事件内容

  • 今日 17 次提交，集中在评测体系与分析器能力两条线：js: add discipline guide, expectations, daily-grind eval, and 11 analyzer rules (#3525)、evals: define benchmark lexicon and align ui, cli, and docs (#3562)、analyzing: 4.5x faster legacy-scan (#3565)。
  • 分析器新增三项能力并逐条公布：扫描 .scss 文件与预处理样式块里的空 // 注释、通过 TypeScript AST 提取 Lit 的 CSS 模板字符串、不把 <script-*> / <style-*> 这类自定义元素误判为脚本或样式块。
  • 项目自述的资产策略写得很直白：指南「designed to be token-efficient」，靠跑评测来「prune lowest-common-denominator content that models already know」，即模型已经会的低价值内容直接剪掉。
  • 交付方式是 CLI：npx modern-web-guidance@latest install 交互式安装，也可用 search / retrieve / legacy-scan 单独调用；仓库同时托管一个公开的 Eval Dashboard。
  • README 显示技能按学科分目录组织（用户体验、CSS 布局、可访问性、内置 AI、语言检测等），当前 README 列出 203 条指南条目。

值得关注的原因

  • 这正好接上我上期记下的主线（技能是工程资产、需要 CI 把关）。「靠评测剪掉模型已经会的低价值内容」这一条可以直接抄进我 4P 专家包的规范文档——我现在做的每一份干预报告模板里都有大量模型肯定已经会的通用营养学常识，真正该占 context 的是我自己的判定框架和阈值表。
  • 官方评测仪表盘（Eval Dashboard）这个形态对我意义很大：我的 4P 平台如果只输出报告而不输出「这份报告用了哪几段技能、哪几条规则」的可见面板，就等于把最重要的一层藏起来了。
  • 「11 条 analyzer 规则」「daily-grind eval」「benchmark lexicon」这些命名说明他们把评测当成持续跑的日常流水线，而不是一次性验收。这和我上期记的「失败的臂 ≠ 没跑的臂」是同一个纪律的两种说法。
  • 现实提醒：这一整套东西是浏览器厂商 + MDN 联合维护的，也就是「通用领域知识」这部分技能正在被巨头收编并标准化。我 4P 专家包真正不可替代的部分，是营养干预的判定逻辑和临床边界规则，不是通用医学常识。

2. 临床知识第一次有了「官方技能库」形态：CQF 把 CQL、FHIR、临床推理全部写成带评测的 Agent Skill

地址：https://github.com/cqframework/cqf-skills ｜ ★0 ｜ Apache-2.0 ｜ 由 Clinical Quality Framework 社区维护的开放 Agent Skills，用来编写、审查、测试并打包临床知识构件（CQL 库、measures、PlanDefinitions 与相关 IG）

事件内容

  • 今日 21 次提交，全部是「新增技能 + 配套 evals」成对合入：Add usqualitycore and cms-qmd skills, from usqualitycore*, with evals (#10)、Add uscore and us-cql-ig skills, split from uscore, with evals (#9)、Add cql-ig skill for Using CQL With FHIR 2.0.0, with evals (#8)、Add fsh skill (FSH 3.0.0, SUSHI 3.x) with evals (#7)、Add fhir-extensions skill for the R4 Extensions Pack, with evals (#6)。
  • 仓库当前含 12 个 SKILL.md、11 个具名技能（cql、cql-ig、us-cql-ig、cms-qmd、fhir、fhir-extensions、uscore、usqualitycore、crmi、cpg、fsh），按 cql / fhir / clinical-reasoning / fhir-ig 四个插件分组，同一插件内的技能可单独安装。
  • 仓库树里与评测相关的文件共 114 个，也就是说每个技能都自带一套 evals，不是只给一个总评测。
  • 技能内容写到了规范版本号的粒度：CQL 1.4 / 1.5.3 / 2.0.0、FHIR R4、US Core 6.1.0 与 9.0.0、US Quality Core 0.5.0、CRMI 2.0.0、FHIR Extensions Pack 5.4.0；README 明确标注仓库状态为 early development，技能是一个一个从其他仓库迁入的。
  • 技能格式遵循开放的 Agent Skills 规范，因此在 Claude Code、Claude.ai、Claude API 等支持 SKILL.md 的智能体里都能直接用。

值得关注的原因

  • 这是我一直在等的样本：临床领域终于出现了「社区公认、有版本号、有 evals」的技能库形态。 我上期记的作业是「4P 专家包该做一套 30~50 题的两两对比评测」，CQF 提供了可直接照抄的三件事：① 一技能一评测，不做总评测；② 技能按插件分组、可按需装；③ 知识版本号写进技能名与内容（US Core 6.1.0 / 9.0.0 并列）。
  • 「技能从一个仓库迁入另一个仓库、一个一个来」这个迁移路径对我特别有参考价值——我 4P 专家包的内容来源恰好是分散的（功能医学框架、循证文献、我的判定规则），逐个技能建目录、逐个配评测，比一次性堆一个大 Markdown 文件更容易维护，也更容易说清哪条结论来自哪里。
  • 它没有解决「谁来判断临床正确性」的问题。FHIR 与 CQL 有公开规范可依，临床营养干预没有——这正是我 4P 包必须自己写评测集、而不能指望上游给现成方案的原因。这条判断今天得到了实证支持。
  • 一个诚实的细节值得记：仓库自己标注 early development。「官方」不等于「成熟」，这一点我写进我自己的规范文档时也要照做。

4. 医学影像模型开始长出自己的 MCP 面：MedMLX 把 CT / MRI 分割搬到 Apple Silicon 本地

地址：https://github.com/MedMLX/medmlx ｜ ★29 ｜ Apache-2.0 ｜ 面向 Apple Silicon 的医学影像原生推理层，一套 Python API、CLI 与 MCP 服务跑 TotalSegmentator、nnU-Net、MedSAM2、SynthSeg 等模型

事件内容

  • 今日 6 次提交，并发布 v0.9.1 与 medmlx-core v0.2.7 两个版本（发版时间 2026-11-13 23:00 UTC）。
  • 今日提交集中在接口收敛与错误分类：Return a typed RunResult from run and wait、Key run outputs by role and keep provider error categories、Use MedSAM2's pixel-named prompt arguments。
  • 模型清单覆盖真实临床任务：musclemap（113 块肌肉与骨骼结构）、totalsegmentator（全身 CT 分割）、nnunet 系列（肝 / 胰 / 自定义 PET / BraTS2021）、mrsegmentator、siam（全头分割）、synthseg（脑分割与分区）、medsam2（框 / 点 / 掩膜提示）、sam3、biomedparse-v2（文本提示分割）。
  • 三段式 CLI 值得注意：describe 列出参数、readiness 只检查 Metal 与输入路径不下载权重、run 实际执行；medmlx setup --all --progress 可预先下载全部权重供离线使用。

值得关注的原因

  • 这对我这个站的健康线读者是实打实的降本信息：把 CT 全身分割、器官与病灶分割这类模型跑在本机 Apple Silicon 上，意味着影像类辅助分析不必每次调用云 API。这与 4P 精准营养的长线方向（把多组学与影像指标接进干预方案）直接相关。
  • 「readiness 只检查不下载、权重可预先离线备齐」这个设计对我很有用——我本机 Ollama 那套本地推理的运维经验在这里被复现了：先做环境与路径体检，再决定是否拉大文件。
  • 今日提交里「按 role 归类输出、保留 provider 错误分类」是典型的工程纪律：把不同来源的错误分开归类，才能在上层给出可解释的失败原因。我 4P 平台在 OCR 导入化验单那条路径上，应该照这个做——区分「图像质量不足」「模型未安装」「字段解析失败」，而不是统一报「识别失败」。
  • 许可证 Apache-2.0、权重各自保留条款，这一点也值得提醒读者：代码开源不等于模型可商用，这正是我给内容加「循证 + 零幻觉」标签时需要区分的那一层。

地址：https://github.com/BotHarness/DeepSeekBot ｜ ★845 ｜ MIT ｜ 运行在 DeepSeek Harness 上的开源 GrokBot 平替，多个有身份、人格与长期记忆的 Bot 组成一个团队

值得关注的原因

  • 「成员只能创建一个空白 Bot」「私有 Bot 权限缺口被关闭」这些提交，比任何宣传语都更接近我要的东西：多 Agent 系统的真实风险不是模型不够强，而是权限边界含糊。D 今天一天把这条线收紧，是这个生态从玩具走向可用的标志。
  • DSH 生态今天在我这四期里第一次出现「三条并行」——应用层（Tobs）、协议层（ACP 接入编辑器）、方法论层（微生物组插件的技能包 + 证据链）。这条线应该正式升格为独立跟踪项，而不是当作「Agent 框架」的一个子类。
  • 微生物组插件里那句「外部工具是否由 Agent 直接执行，由『路径是否可访问 + 用户是否允许』决定」正是我 4P 平台该抄的边界设计：工具执行权不由模型决定，由用户授权 + 路径可达共同决定。 这比在提示词里写一句「请谨慎」强一个量级。
  • 现实提醒：这一轮我把 4P 平台最该落地的一件事定下来——凡是需要调用外部生信工具的环节，默认「只生成命令、不代跑」，除非用户显式打开开关。这条不需要等任何外部能力。

三、今日趋势观察

  • ⭐⭐⭐ 「技能」今天同时出现了三种制度化形态：厂商维护 + 社区维护 + 论文流水线。 Chrome/Edge/Firefox/MDN 维护 203 条带评测仪表盘的网页指南；CQF 社区维护 12 个每个都配 evals 的临床技能；ASB 从 477 篇方法学论文蒸馏出 11,830 条带逐字证据锚点的技能。三者的共同点不是内容而是机制：技能必须能被独立评测、必须有版本号、必须能被追溯到来源。 我 4P 专家包要做的正是这三件事，目前一个都还没落实 —— 这是本期对我最刺的一条。
  • ⭐⭐⭐ 「证据缺失」开始被当成一等状态显式建模，而不是默默忽略。 ASB 今日 11 次提交全在补 PII 门禁的边界漏洞（连字符后的邮箱域名、加号后的空格、35 个根域之外的任意根域）；ontology-atlas 明确写「missing evidence shows as unknown, never as safe」，并规定 Markdown 示例、隐藏注释、引用块不能用来支撑能力主张；cqframework 的每个技能都写明依据的规范版本号（US Core 6.1.0 / 9.0.0 并存）。三家的做法殊途同归：不把「没查证过」写成「没问题」。这条应直接进我的规范文档模板。
  • ⭐⭐⭐ 权限边界今天在多智能体生态同时收紧。 Tobs 今日提交全是收紧方向：关闭私有 Bot 权限缺口、成员只能创建空白 Bot、Owner 桥接组合被保留。多 Agent 系统真正的风险不是模型不够强，而是权限边界含糊 —— 这与我上期记的 clinmesh「最终 Actor 始终是点击审阅框的登录人类」是同一条规律的不同实现位置。
  • ⭐⭐ 「AI 只挑不算」的分工今天又多了两个可抄的实现。 meal-manager 把 LLM 限定为「semantic translator」，明确写「The LLM is a Translator, Not a Judge」，评分、库存、会话状态全部是确定性 Python，歧义只在意图解析处解决一次；kawsay（昨日入榜）同样是 AI 只选目录项和份量、数字全部由表算。连续两期看到同一原则在不同生态独立收敛，说明这不是某个团队的偏好，而是这类产品的最优解。
  • ⭐⭐ 本地推理正在从「文本模型」扩展到「专业模型」。 MedMLX 把 CT / MRI 分割、MedSAM2、SynthSeg 搬上 Apple Silicon，并提供 MCP 面与离线权重预置；上一期 ddalcu/mlx-serve 也指向同一方向。对我这个站的意义是：4P 平台若要接影像类指标，本地跑正在从「不现实」变成「有现成路径」。
  • ⭐⭐ 上一期的观察名单今天有了结果，但都不进表格。 NVIDIA/SkillEvaluator 今日 8 次提交，其中 feat(harness): flag a harness release the profiles were not verified on (#545) 与 fix(scanners): enforce pinned SkillSpector during automatic selection (#550) 延续了「未验证的组合要明确标注」这条线；addyosmani/agent-skills 今日 18 次提交（版本清单升到 0.6.16）；但 anthropics/skills、mattpocock/skills、cloudflare/security-audit-skill 今日默认分支仍无任何提交。三者此前已在历史期次入榜，按跨期去重规则不重复计入表格。
  • ⭐ DSH 生态今天三线并行，是本期最值得单独追踪的动向。 应用层（Tobs，95 次提交）、协议层（deepseek-acp 经 ACP 接入编辑器）、方法论层（dsh-bio-human-microbiome-function-mining 用 9 个 skill + 25 个脚本产出证据链与可证伪实验方案）。加上 11-13 的 dsh-context / dsh-multitask / dsh-as-mcp，DSH 已从「个人插件」走到「行业场景适配」再到「企业交付边界」，正式升格为独立跟踪项。
  • ⭐ 一人公司的现实提醒：本期 155 个条目里，真正能在下周就动手的仍然只有 3 个（CQF 的「一技能一 evals」组织方式、OpenNutri 的「每个数值都标注来源与可信度」字段设计、meal-manager 的「LLM 只做翻译」边界）。其余大多是长线观察，不要为凑条目把自己拖进「每周读完 155 个仓库」的陷阱 —— 每周挑一个落地即可。
