值得关注的原因

  • 这是我 4P 专家包「30~50 题两两对比评测」那件拖了多期的作业，最现成的执行模板。 前几期我记下的一直是原则（NVIDIA/SkillEvaluator 要区分「没跑的评测臂」和「失败的评测臂」、cqframework 要一技能一 evals、ASB 要锚定逐字证据），今天第一次看到有人把整套流程做成一条命令链：读失败 → 转评测 → 验评测公平 → 配对统计出结论。我那 30~50 题的作业，第一步不是「写题」，而是「把我这几个月专家包里跑砸的会话捡出来」。
  • 「评测的参考补丁改写了验证器要跑的测试，评测自动作废」这条，正是我这类「用 AI 生成干预报告再用 AI 打分」的方案最危险的漏洞。 我的评测题如果是 LLM 生成的、答案也是 LLM 写的，那评测分数可能只是在给自己盖章。coding.sh 把这个漏洞做成了自动检查项——我可以直接把这条抄进 4P 评测规范：任何自动生成的评测，必须先通过「参考答案不得改写验证器测试文件」这一关。

  • 配对统计（paired statistics）这条比「跑 3 次取平均」严谨得多。 我的评测对象是提示词、模型、报告模板这类强相关的变体，独立样本 t 检验在这里是错的，配对检验才是对的。这一条我直接写进评测方法学。

地址：https://github.com/ybkim95/health-cua ｜ ★1 ｜ Apache-2.0 ｜ 医疗电子病历中临床计算机使用智能体的评测基准，让同一批智能体分别通过 API 和图形界面两种入口完成同一临床任务

  • 今日 23:52 一次提交即完成一次大版本：Revised grader v4 as the leaderboard grader, Gemini 4 Carbon on the leaderboard (17 models), release 1.1.0。仓库创建于 2026-11-08，仅 10 天。
  • 评测设计是全文最硬的部分：任务、病历、评分器三者全部固定，唯一变量是接口——通过 API 时智能体用 PhysicianBench 放出的工具调 FHIR 服务器，通过 GUI 时用鼠标键盘操作网页版 EHR。两种界面读写同一份 HAPI FHIR R4 记录，每个 episode 前恢复到已验证的快照，由同一个确定性评分器检查最终记录里留下的医嘱与病历。

  • 另有一条独立轨道：150 道留出的合成任务，Claude Opus 5.5 API 78.0 / GUI 88.0，合成任务评分器为 synth_reasoning_v9。
  • 评分器版本纪律写得很完整：原始评分器是论文预注册的primary outcome（S2 的前身 P1），改写版接受临床等价的医嘱与剂量区间、拒绝禁忌与过量医嘱，因此没有任何排序脚本能刷过它；--grader v3 / --grader original 仍可选，论文表格与排行榜表格数字不同这件事被明写并给出复算命令。
  • 局限也照实写出来了：改写评分器在自带的对照组上，43 个临床等价医嘱里仍误拒 3 个，12 个十倍剂量里仍误收 2 个；合成任务集里带 Synthea 生成的病历痕迹；任务集的医师复核字段仍标为 pending。

值得关注的原因

  • 「固定任务、固定病历、固定评分器，只换接口」这个实验设计，对我 4P 精准营养平台的报告质量归因是现成方法论。 我的客户说「报告不好用」，我现在的排查方式是凭直觉猜：是干预方案本身不对？是化验指标解读错了？还是报告太长、重点没突出、格式不适合医生看？这三个归因如果混在一起，我的迭代就是盲改。 Health-CUA 给了标准做法：把变量一个一个固定住，只动一个再测。我可以把 4P 干预报告的质量评测拆成三条平行轨道——判断层（方案正确性）、数据层（指标解读准确性）、呈现层（格式与可读性）——各自独立打分。
  • API 分数普遍低于 GUI 分数，这个反直觉结果对我很有用。 排行前列的模型 GUI 臂几乎都高于 API 臂（Opus 5.5 差 13.7 分、Sonnet 5.5 差 7.7 分、Gemini 4 Carbon 差 20.5 分）。README 解释了原因之一：GUI 消息表单只能发给患者，而 API 消息工具可以发给任何人——发给非任务患者就算伤害，所以这种伤害只可能通过 API 发生。换句话说，API 之所以更难，不是因为它信息更少，而是因为它能干更多危险的事。 这个洞察可以直接迁移到我的 AI 助手：能力越大不等于体验越好，能力越大意味着工具边界必须更严。
  • 「没有任何排序脚本能刷过它」是评分器的硬指标，我的报告质量评分器目前没有这一关。 我该给自己定一条：我的评测里如果存在一条「只要按某个固定格式输出就能拿高分」的捷径，那它测的就不是模型能力。Health-CUA 的做法是把这条捷径直接设计成评分器要拒绝的对象。
  • 照实写出评分器自身的误判率（误拒 3/43、误收 2/12），是我前几期记的「证据缺失建模」在评分器层的对应物。 不是「我的评分器很准」，而是「我的评分器在哪些地方不准，准确到什么程度」。我的 4P 报告如果给客户一个风险评级，同样必须交代这个评级器本身的误差边界。
  • 现实提醒：★1、创建仅 10 天、零 issue，这是研究代码不是产品，且排行榜上的模型代号（Claude Fable 5.2、GPT-6.1 Sol、Gemini 4 Carbon）说明其评测对象是远超我本机 Ollama qwen2.5:7b 能力边界的模型。我可以借它的实验设计与失败归因方法，不能直接拿它的分数做任何推断。

值得关注的原因

  • 「付费跑分没跑，所以一个数字都不报」——这一句话是我做循证内容最该抄的自律模板。 我在公众号写功能医学与精准营养内容时，最大的诱惑就是在没有实测数据时给出一个「大概有效」的百分比。这条原则用工程语言写死了：没有跑的评测不产出数字，而不是产出「参考值」。 我的 GLP-1 营养伴侣第 61 版反复迭代至今，缺的正是这条——我一直在改提示词，却没有把「评测跑没跑」变成一个必须回答的字段。这条直接进我的内容与产品规范。
  • 「每个段落都不跨页，所以每条引用都精确指向一页」是引用可核验性的物理保证。 我前几期记的「每个数值标来源与可信度」，一直停留在口号层面。今天这个项目给出了可执行版本：切分粒度必须与引用粒度对齐，否则「标了出处」也验不了。这条我要写进 4P 补剂平台的知识库规范：营养建议的每个数字，要么能落到具体某一页/某一条标准，要么就不写。

  • 现实提醒：★0、今天刚建、许可证未声明（README 里也没有 LICENSE 文件），可以学设计，不能直接抄代码进商业项目。但方法论层面今天它是全网最对味的一个。

值得关注的原因

  • 「召回噪声占 top30 的 76.2%」这个数字，是我今天读到的最刺眼的一条。 它意味着一个记忆层哪怕召回 30 条，其中 23 条是污染的——而记忆层的价值恰恰建立在召回质量上。我 GLP-1 营养伴侣第 61 版的核心卖点就是「每次交互数据持久化以支持自我进化学习」，如果我那些历史交互数据里混进了大量低质量或过期的记录，我所谓的自我进化就是在往系统里灌噪声。 今天这条给我的行动项很明确：在做任何记忆增强之前，先量化我自己的召回噪声率。
  • 「distill freeze 被证伪」——以为堵住入口就能挡住污染，实际旧数据回填会绕过它。 这个教训我在 4P 平台上有对应场景：如果我只是给知识库加一个「冻结」开关或时间过滤，历史脏数据依然会通过别的路径进上下文。 防御必须是结构性的（写入时就校验、来源可追溯），不能靠一层运行时开关。
  • 「十天内第二次同型复发」这个写法，比「我们修复了这个问题」诚实得多。 我自己的规范文档模板里，一直缺一条：故障要按「复发次数」记录，而不是按「已修复」记录。 一个修了两次的问题和一个一次都没出过的问题，成熟度完全不同。这条我直接进 4P 平台的运维记录规范。
  • 部署精度纪律（int8 判失败、int4 判禁止）是一条我完全没意识过的硬约束。 它的逻辑是：量化到 int8 时标签一致率掉到 98.28%，就意味着有 1.72% 的案例会被判错，在风险分级这种场景里不可接受，所以宁可拒绝部署也不降级使用。我的 4P 风险评级如果将来要跑在量化模型上，这条判据直接可用：不是「精度损失在可接受范围」，而是「超过某个阈值就禁用」。
  • 「同一个模型、两个 harness」的对照排行榜（v5-harness 26.7% vs mini-swe-agent 16.7%，+10.0 个百分点）说明：智能体的能力上限很大程度由 harness 决定，而不是由模型决定。 我一直把「我的 AI 助手不够好」归因到「本地模型不够强」，这条数据提醒我先查 harness，再查模型。
  • 现实提醒：★1,258 但许可证是 Modified MIT 变体（非标准 SPDX），且今天的四条提交全是值班日志而非功能，商业使用前必须逐条读 LICENSE 原文。这条我照例进开源依赖清单。

5. 「先按权限过滤，再按相关性检索」被做成了产品：schemagate 让无权访问的表根本不出现在提示词里

地址：https://github.com/ashishsinha1602/schemagate ｜ ★137 ｜ Apache-2.0 ｜ 面向 Text-to-SQL 的访问控制层，按调用者权限先裁剪 schema，只把该读的表交给模型

事件内容

  • 今日 6 次提交，02:06 发布 v1.18.2（v1.18.1 为 11-11、v1.18.0 为 11-09，本周已三版）。提交包括 release: 1.18.2 - case-sensitive Oracle names reach the model in quotes、fix(oracle): show case-sensitive names in the quotes SQL needs、以及 Docker 基础镜像从 3.14-slim 升到 3.15-slim。
  • 核心机制一句话说清：它先按调用者的授权过滤表，再按相关性选表，因此受限的表是「不在提示词里」，而不是「排在后面」。 README 原话：「restricted tables are absent from the prompt rather than ranked low」。
  • 效果是量化的：50 张表以上的数据库，schema token 中位数减少 91.1%（24 个数据库实测）。README 给了一个可复现的极端例子：1,201 个对象的 schema，全量是 146,695 个提示词 token，schemagate 只送 12 张表（包含查询真正需要的全部 3 张），共 1,348 token——而且注明这是脚本从种子 fixture 重建、用 tiktoken cl100k_base 数的，不是画出来的图。
  • 精度不打折：BIRD Mini-Dev 榜单三种方言全部第一（SQLite 81.0、PostgreSQL 72.6、MySQL 72.4 执行准确率，Claude Opus 5.5、每题一次模型调用）；UniQL Oracle 首次尝试 63.7%。
  • 检索质量对比：在数仓上，schemagate 选中的表集包含金标查询所需全部表的比例为 86.7%；同表数、零模型调用的条件下，对比 BM25 的 78.7% 与向量检索的 78.2%，schemagate 为 85.3%，BIRD 上为 98.7%（对比 81.0% / 89.4%）。
  • 它把行级安全失效的后果写得很具体：「模型对调用者无权读取的表写出合法 SQL，RLS 剥掉每一行，用户看到的是『没有记录』——与『这个数据不存在』无法区分。」
  • 支持 LangChain、LlamaIndex、MCP 与任意 SQL agent，覆盖 Postgres、Oracle、MySQL、SQL Server、SQLite；带 OpenSSF Best Practices 徽章，专利申请号 US 64/183,987。

值得关注的原因

  • 「无权访问的表不在提示词里」和「无权访问的行查询后显示『没有记录』」，是同一个漏洞的两种失败形态，而后者严重得多。 我的 4P 精准营养平台是 Flask + SQLite + admin 后台，客户数据在同一库里。今天这条等于给我做了一次安全审计：我的 AI 助手如果开放自然语言查库，客户 A 的化验数据会不会被客户 B 的查询命中，然后用一句『没有数据』掩盖过去？ 这不是假设风险，是我该在本周就自查的点。
  • 「先授权后检索」这个顺序，和我前几期记的「AI 只挑不算」是同一类原则的另一个面：不是先算再判断权限，而是先框定边界再做任何计算。 我 4P 平台的 AI 助手如果要做「按客户查最近三个月 HbA1c 趋势」，正确顺序应该是：先按客户 ID 圈定可访问的行级范围，再在这个范围内检索指标——而不是先检索全库再过滤结果。 前者泄露风险为零，后者永远存在竞态窗口。这条我要写进我的助手指令模板。
  • 91.1% 的 token 节省与精度不降，对我一周 8 小时的约束是直接的现金收益。 我的 4P 平台每次调用都要把大量客户资料塞进提示词上下文，如果其中九成是无关表，那既烧钱又稀释注意力。这类「既省钱又不损质量」的优化，应该优先于任何模型升级。
  • 它的证据呈现方式值得整体照抄：写清楚「Measured, not drawn」（实测而非绘制），并给出重建脚本。 这和我前几期反复记的「不硬凑数量」是同一个精神——数字要么是实测的，要么就不写。 我 4P 平台的每个技术选型文档都应该附一条「怎么自己复现这个数字」。
  • 现实提醒：★137、仓库创建于 2026-09-06（两个半月），专利申请中（尚未授权），MIT/Apache 之外的许可状态需要注意。核心思路可以自建，不建议直接依赖一个专利pending的组件。

三、今日趋势观察

  • ⭐⭐⭐ 「评测本身要能被质疑」这条主线今天在三个生态同时落地，而且互不相识。 coding.sh 有 eval validate 专门检查评测的裁判是否公平（今天刚修的漏洞是「参考补丁改写了验证器要跑的测试」）；nautilus-compass 有 caliber-bench 给基准本身打分，测标准漂移、污染与裁判稳定性；Health-CUA 直接把「没有任何排序脚本能刷过它」写进评分器设计，并公开自己的误判率（43 个临床等价医嘱误拒 3 个、12 个十倍剂量误收 2 个）。三个方向合起来是完整的一套：评测要公平、基准要可信、评分器要自曝误差。 我 4P 专家包那套「30~50 题两两对比评测」，这三个维度一个都还没落实。
  • ⭐⭐⭐ 「没跑就不报数字」今天成了硬规矩，而不是个人风格。 nutrition-rag 明写评测框架已建好但付费跑分未发布，因此一个答案质量数字都不报；schemagate 明写「Measured, not drawn」并给出重建脚本；cal-dining-macros 明写「某个营养素在官方文件里是空的，就显示 - 并且不计入合计，而不是编一个数字」。这三个项目在三个不同领域做了同一件事：不拿估算冒充实测。 这正是我公众号内容与产品文档最需要的纪律——我 4P 平台至今没有一条「这个数字跑没跑」的字段。
  • ⭐⭐⭐ 「把失败归因到正确的层」今天有一个可直接迁移的实验设计。 Health-CUA 固定任务、病历、评分器，只换 API 与 GUI 两种接口，从而分离出「临床判断错」与「界面难用」。我的 4P 干预报告质量归因正是这个难题。而且它给出一个反直觉的发现：API 分数普遍低于 GUI 分数，原因不是 API 信息更少，而是 API 能干更多危险的事（GUI 只能发给患者，API 可以发给任何人）。能力越大不等于体验越好，能力越大意味着工具边界必须更严——这一条我直接抄进 AI 助手指令模板。
  • ⭐⭐ 记忆层开始公开自曝故障，并且把失败量化成比例。 nautilus-compass 今日三条提交分别给出：召回噪声首次量化（占 top30 的 76.2%）、冻结蒸馏的方案被证伪（旧会话回填绕过冻结灌入正式库）、以及十天内第二次同型活锁复发。「修了两次」和「没出过」是两种完全不同的成熟度，我给自己的规范文档模板补一条：故障按复发次数记录，不按「已修复」记录。
  • ⭐⭐ 权限边界要嵌进数据通路，而不是加在出口。 schemagate 的机制是先按授权裁剪 schema，无权访问的表根本不出现在提示词里；medical-privacy-guard 是本地 fail-closed 护栏，四态裁决（放行/改写/等人工/拦截）加哈希链审计日志；compactbench 则把提交、联系方式与 MCP 限制收敛到一步数据库操作。三者都在说同一件事：边界要在数据流动的路径上强制，不能指望出口处的一道判断。 我 4P 平台的客户数据隔离该按这个思路重做一遍。
  • ⭐ DSH 生态连续第四期有动作，且今天落在「分发与打包」这一层。 runzhliu/deepseek-harness-docker 今日发 image-v0.2.2-rc.4-r1（加固镜像 + Compose + Helm + Web UI + 无头 CLI），adsorgcn/DeepSeekHarness 发 v1.1.32（持久本地记忆 + 一键安装 + 技能库 + Gitee 国内镜像）。前几期记的是应用、协议、方法论三层，今天补上的是「让别人好装」这一层——这恰好是我一人公司最缺的能力：不是造东西，是让东西能被装上。
  • ⭐ 工具链正在把「上下文压缩」变成一个独立的、有基准的工程对象。 compactbench 明确说它「测的是压缩层，不是模型」，并给出八类压缩失败模式（被埋的约束、决策被推翻、实体混淆、指代解析、数字精度、条件作用域、任务连续性、来源权威），配套 oracle / null / truncate-last-n 三个对照与每轮重新采样的隐藏排名集。上下文压缩过去是各家 Agent 框架的私有实现，今天开始有了公共基准——这和上一期我记的「评测器本身要被评测」是同一条曲线的下一步。
