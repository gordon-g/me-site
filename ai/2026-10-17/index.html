五、今日精选：5 条最值得关注

① CLI-Anything：MCP 之外的另一条路——把"命令行"翻译成 Agent 接口

  • 事件：HKUDS/CLI-Anything 今日 +323★ 冲上 Trending（累计 53.5k★，Apache-2.0）。它不去说服软件厂商自建 MCP Server，而是直接包装已经存在的 CLI：编程助手按 7 步流水线扫描源码、把 GUI 动作映射到 API、产出带 REPL / --json / undo-redo 的 Click CLI，再附一份 SKILL.md 让 Agent 自己发现它；配 CLI-Hub 注册表，形态接近"Agent 工具界的 npm"。
  • 为何值得关注：MCP Server 全球也就几千个，而 CLI 有几十万个——这是现存最大的"工具接口面"。CLI-Anything 等于把长尾任务的接入成本一次性打平。但要清醒看待风险：把任意 CLI 交给 Agent，等于把 rm -rf、DROP TABLE 和所有破坏性 flag 一并交出去，README 里的沙箱与权限模型是否经得起审计，决定了它最终是基础设施还是事故源头。对内部有大量自研 CLI 工具的团队，这是让老系统"零重写"获得 Agent 能力的最快路径。

② 医学证据合成开始"可审计"：ReviewPilot 把 PRISMA 流程做成带来源的多智能体

  • 事件：ZhaoqianXue/ReviewPilot（arXiv:2610.21042，10-15）用对话式多智能体自动跑完 PRISMA 全流程。关键差异不在准确率，而在可追溯性：每一条筛选决策都记录排除理由，每一个抽取出的数值都锚定到原文位置，配置与修订由项目记忆保存。在流行病学专家综述上筛选 macro F1 达 0.776、抽取 F1 达 0.788，三个 LLM 上均胜过单提示基线与 AgentSLR，医学与 HCI 案例与人工标注高度一致。
  • 为何值得关注：LLM "深度研究"工具的通病是——它能总结，但说不清排除了哪些研究、数据从哪来。而在临床指南制定、药企真实世界研究、营养与流行病学证据综述里，"说不清来源"等于不可用。ReviewPilot 的价值在于把"可审计性"当成第一性设计目标，而不是事后加班补的引用。对做循证营养、慢病干预证据库、CRO 数据服务的团队，这是可直接借鉴的工程范式。

③ 一个人 + 一个编程 Agent，开源了一整套 MRI 分析工具包

  • 事件：Liohtml/MedCheck 把"自己读 MRI"做成了可复用产品：本地 ResNet18 对每层切片做异常打分（不需要 API Key），把最可疑的若干层交给视觉 LLM 按解剖结构逐项（ACL/MCL/半月板/骨挫伤/积液…）结构化解读，最后生成带箭头标注的 PDF、可交互 HTML 与 API 用 JSON。支持本地 DICOM、ZIP、直接对接放射科门户，Docker 一行启动，65 个测试全绿，9 个 good-first-issue 开放。
  • 为何值得关注：这是"个人医学工具门槛崩塌"的一个清晰切片——过去需要 Windows 商业软件 + 放射科医生的事，现在一个人加一个编程 Agent 就能开源出来（对比 Shopify CEO Tobi Lutke 用 Claude 现场写 MRI 阅读器）。同时它也划出了边界：作者明确声明 MedCheck 不是医疗器械、所有结论必须由合格放射科医生复核。对医疗软件团队的启示是双重的——编排范式值得抄，但"研究工具"与"医疗设备"之间的合规鸿沟并没有因为 AI 而变窄。

④ 健康数据正在被"协议化"接入 Agent：一批医疗健康 MCP 集中出现

  • 事件：同一时间窗口内出现了一整批面向个人健康的 MCP 服务器：nutrients-mcp（食物照片→热量/维生素/矿物质/过敏原）、wellness-cgm-mcp（Dexcom 与 FreeStyle Libre 血糖）、google-health-mcp、garmin_mcp（110+ 工具含营养与女性健康）、lecka-mcp（比赛营养规划）、vitamind-mcp（日照维D合成）、evipedia-mcp（带 PMID 的循证干预）。临床侧则有 HealthChain（类型化 FHIR）与 carejobs-mcp。
  • 为何值得关注：过去一年 Agent 接入健康数据的做法是"每个团队自己写一遍胶水代码"，现在开始出现标准化的工具层。这意味着"营养摄入 + 血糖 + 睡眠 + 运动 + 循证证据"这五路数据可以在同一个 Agent 会话里被同时读取与推理——慢病干预、体重管理、运动营养这三个业务的可行性因此显著上升。但要提前想清楚两件事：一是这些 server 的质量与维护度高度不均（多为个人项目、无版本承诺）；二是它们大多"本地优先 + 自带凭证"，把个人健康数据的访问权集中到了一个 Agent 进程里，权限边界需要自己划。

⑤ ⚠️ 反面教材来了：自托管健康应用 SparkyFitness 一天内曝出两个 CVE

  • 事件：10-16 同日披露两个漏洞，均位于自托管健康/营养追踪平台 CodeWithCJ/SparkyFitness（6.4k★，MIT）的 1.6.0 之前版本：
    • CVE-2026-92263（High，CVSS 7.2）：POST /api/admin/backup/restore 把上传文件名直接插进 shell 命令，管理员上传一个文件名含 shell 元字符的恢复包即可以服务进程权限执行任意系统命令（宿主机 RCE）。commit 修复
    • CVE-2026-102923（Medium，CVSS 5.4）：chatService.ts / labelScanService.ts 未校验自定义 AI 服务 URL，任意已认证用户可保存恶意 URL 触发服务端请求，用于内网探测并以受控 Bearer 值发起 POST，同时泄露 AI 系统提示词（SSRF）。
    • 两个漏洞均在 v1.6.0 修复。
  • 为何值得关注：这是一个高度典型的"AI 功能与运维接口挤在同一个进程里"的架构风险样本。健康类应用的三个特性叠加——① 必然要处理敏感个人数据、② 为了省钱/隐私要支持 BYOK 自定义模型端点（于是有了 SSRF 入口）、③ 为了可运维必须有备份恢复（于是有了命令注入入口）——恰好把攻击面从"数据泄露"扩展到了"宿主机接管"。给做健康管理 / 营养 / 慢病 SaaS 团队的三条直接动作：自定义 LLM 端点必须做白名单与出网限制；把文件名等用户输入永远当代码对待；把备份恢复这类高权限操作拆到独立低权进程。另外值得注意，这类项目往往 star 不俗却由个人主导（该项目属社区维护），选型时把"安全公告响应速度"当硬指标比看功能清单更重要。

六、趋势小结

  1. "Agent 该用什么接口"出现路线分化：MCP 派（标准化协议，但需人建人维护）与 CLI 包装派（CLI-Anything 式翻译层，复用几十万存量工具）正面相遇。真正的胜负手不是协议本身，而是沙箱与权限模型做得够不够硬。同日的 NVIDIA/OpenShell、smolvm、microsoft/mxc 都在抢这个位置。
  2. 医疗健康赛道进入"数据层标准化"阶段：上期是"技能库规模化"（医学 Skill 上千项），本期是"数据源 MCP 化"——血糖、营养、可穿戴、FHIR、医疗招聘各自有了标准工具接口。技能层与数据层同时标准化，垂直 Agent 的搭建成品期正在快速缩短。
  3. 医学 AI 的竞争焦点从"答得对"转向"说得清"：ReviewPilot 要求每条决策附理由、每个数值附来源；MedAgent-Pro 对每个推理步骤做验证；RRI 专门解决"开放式临床任务没有标准答案"的评价难题。可审计性正在成为医疗 AI 的准入条件，而不是加分项。
  4. 自托管健康应用的安全账单开始到付：SparkyFitness 一天两个 CVE（含宿主机 RCE）不是孤例性事故，而是"AI 功能 + 运维接口 + 个人敏感数据"三合一的必然代价。这个赛道的团队接下来会同时被功能需求和合规审计两头夹击。
  5. Agent 自进化的"进化可靠性"被打上问号：本期两篇工作从不同角度指向同一结论——HarnessMDP 主张控制策略应当可学习，RRI 则揭示了自改进会被奖励黑客污染。前一日业界更在讨论"外壳自进化换一批新题就崩"的泛化问题。"能自进化"和"进化了真有用"是两件事，对准备上自动优化流水线的团队，保留独立留出集验证是底线。
